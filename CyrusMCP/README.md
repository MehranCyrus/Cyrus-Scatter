## Install a matching offline package

Use the separately generated MCP folder under `dist/`; source alone is not an offline installer. The package contains pinned wheels/checksums, source host and installer. External runtime is **64-bit CPython 3.11**, MCP Python SDK **2.3.0**; Max uses its bundled Python.

```powershell
.\Install_Cyrus_MCP.ps1 -PythonExe 'C:\path\to\python.exe' -RegisterCodex
```

Registration is optional. The installer creates an isolated environment/build, verifies payloads and refuses an existing build/connection overwrite. It prints the exact `host/Start_Cyrus_Automation.ms` path. It does not copy DLLs/scripts into Max's startup/profile or modify scenes. The matching Scatter plugin must already be installed and Max restarted. This implementation campaign creates packages, not an installation into the artist profile or Codex configuration.

## Enroll, review and apply

For an unprepared scene, select 1–32 objects and choose **Inspect selected scene objects (read-only)**. Describe the result and assign/correct receiver, boundary, source, exclusion, preserve or context roles; objects may have several roles. **Task details…** reopens the task; **Share selected context objects** adds references without losing the brief/roles or resetting the read budget. Measurements report world bounds, source-local geometry and separately qualified receiver eligibility; asset dependencies remain unchecked.

**Enable design proposals…** is a separate local scope review, defaulting to Cancel. It retains the same task while issuing new design input IDs; assigning roles alone never grants authoring. One verified horizontal convex receiver and 1–3 static supported mesh prototypes are required. Boundaries/exclusions retain convex-spline rules; with no boundary, the whole verified receiver is used without creating an input spline. Handoff creates no scene nodes; every actual write still requires exact proposal approval. Design bindings are locked, while brief edits revoke outstanding proposals and keep native output/own Undo. See [handoff evidence and limits](M02_HANDOFF.md). Disconnect, scene open/reset, unrelated enrollment and successful local Undo currently clear transient task memory; durable/returning-task behavior remains unfinished.

1. Run the printed host startup script through **Scripting > Run Script** in Max 2027.
2. Choose a static horizontal convex site and one to three allowed mesh assets. Optional straight closed convex planting splines constrain the area; none uses the whole verified site. Add supported excluded/protected regions as needed.
3. Enable viewport sharing only if images should be available to the client; it can include other visible objects. Connect the selected design scope.
4. Read context/capabilities/schema, propose Plan 0.73 and validate. Inspect the normalized settings/counts/assets in Max and **Approve displayed proposal** locally.
5. Apply that exact digest once; query the operation and actual result. One separately approved refinement may replace only its owned layers/masks.
6. Cancel queued work, Undo/reject the next own result, disconnect or take over manually. Local Undo has its own queryable operation receipt; uncertain completion requires review before another mutation. Save/reopen preserves supported authored state and requires fresh enrollment. Cold reopen can reconstruct a pending Manual publication from saved settings; retention of its earlier warm result is unqualified (see [process-loss evidence](M01_PROCESS_LOSS.md)).

Select an existing Cyrus controller and use **Inspect selected Cyrus scatter (read-only)** for bounded cached inspection. This grants no authority to edit it. Current recipe can be pending while publication describes the previous complete epoch. Refresh manually if desired and re-enroll; readers do not solve/reconcile to answer a question.

Example: “Read the connected scope. Propose two layers using its assets/regions, 600 aggregate candidates and deterministic seeds. Validate and show source radius, self gap and layer-pair gap in metres. Wait for local approval; apply once and report actual emitted count/shortfall and matching publication.”

[Installed source preparation](M03_INSTALLED_SOURCES.md) connects a bounded derivative index to the installed catalog. Sharing metadata alone grants no preparation authority. **Enable installed source proposals** locally permits up to eight selected-source preparations per task; each contains at most three models. The assistant uses opaque catalog refs, observes native readiness, then proposes hidden source copies through the existing exact approval/apply/status/Undo path. This requires retained native package API 1; older single-package builds cannot enable this installed workflow. `.max` files are prepared only in owned content-build scenes, never merged into the artist document. Missing derivatives and budget/adapter limitations remain explicit; preset and complete recipe application remain unfinished.

## Bounds and supported semantics

The MCP budget belongs to one enrolled scope. Its source, layer and candidate limits are independent of the local Scatter controller's larger work limit:

| MCP enrollment budget | Maximum |
| --- | ---: |
| Mesh source count | 3 |
| Region / layer count | 3 |
| Aggregate requested candidate count | 2,000 |
| Successful applications | 2 |
| Viewport captures | 2 |

Plans cap 32 KiB; context 64 KiB; images 1,536-pixel long edge/2 MiB base64. There are 24 ordinary calls with defined outcome/idempotent-retry recovery exceptions. Publication pages cap 500 rows; five-minute handles expire when replaced; 2,048 attempts per enrollment include failed/stale attempts.

Design geometry is baked Editable Mesh/Poly or supported primitives, without modifier stacks, keyed/constraint/procedural controllers or renderer proxies. Receiver geometry plus fallback sources retain the aggregate 10,000-triangle / 12,000-vertex budget. In the internal source prototype, native source API 1 separately admits up to three baked Editable Mesh sources with an aggregate 2,000,000-triangle / 1,000,000-vertex limit. Explicit `scene_measure_objects` purpose `source` uses that scalar native path; its default `receiver_and_bounds` purpose retains the smaller budget. Source-only bounds/radii are not receiver area, canopy clearance, asset-unit provenance or material/dependency readiness. [Contracts and scoped Max/SDK evidence](M03_SOURCE_METADATA.md) distinguish this prototype from the packaged baseline. Read-only inspection may report cached existing inputs outside design admission without certifying them for generation.

Lengths are metres, rotations degrees, multiplicative scales unitless. Plan 0.73 normalizes the supported uniform/XYZ scale, yaw/XY tilt/projected movement, source scale/lift/radius/follow-scale, self rule, layer pairs, cleanup, enable/visibility and display/update subset. Layer order is explicit; old priority/blocker fields do not exist. Count is a candidate budget; each layer chooses underfill `allow` or `reject`. Missing/unsupported fields are errors, not silent fallback.

Existing artist objects remain read-only. The adapter creates its own controller and bounded masks and may refine only those objects. Relevant external edits revoke freshness. It keeps local exact-digest approval, ownership, scene revisions, idempotency, queued main-thread dispatch, journal and verified rollback. Rendering, playback, modal state and an active Undo transaction block admission.

## Configure and Update development contract

`scatter_validate_change` accepts `change_schema: "cyrus.owned-change/1.0"`, the current context/controller/generation/configuration IDs, a mode, and explicit count/seed patches by stable owned layer ID. Read `cyrus://capabilities` and the tool schema. Validate, review and approve locally, then use the same `scatter_apply_plan` and original-key status/retry workflow. [Transaction contracts and evidence](M01_CHANGES.md) track qualification; this is not a new installed release.

`configure` requires Manual on root and children. It changes only named settings, keeps the previous publication/generation/export and returns a newer `configuration_id` with `publication_pending: true`. `update` has no patches: it calculates the current owned settings. `configure_and_update` patches then calculates within the same Undo hold. Neither operation replaces layers/masks nor changes the update mode. Update verifies every final native row against the approved constraints; accepted output can be lower than the candidate count. The previous complete result survives a verified failed transaction.

While pending, exported plan/layout describe the previous publication; `current_configuration_id` identifies the newer authored settings. A successful Update creates a new generation, clears pending and supplies a matching new record. Changes to unsupported fields or to artist-owned/inspection setups are rejected. This increment does not expose general property mutation or qualify every native editing feature.

The current scope retains two publication applications (including creation), eight configure-only commits and its other declared budgets. Status polling and exact-key apply retries do not consume normal calls; a new apply is charged once. A newer configuration invalidates old proposals even when the published generation stays unchanged.

## Diagnostics and recovery

**Scatter > Modify > Statistics & diagnostics > Advanced** records without MCP. Defaults are off; recording caps 4,096 events/4 MiB/ten minutes. Container movement/ownership adds action summaries. No telemetry/cloud endpoint or inferred training labels are introduced. Automation's independent sharing checkbox grants reading of that exact process trace, including other controllers' recorded events; revoke it or change scope/session to remove permission. Recording does not imply sharing.

An unknown apply outcome requires query/reconciliation of the existing key; do not assume nothing happened or generate a new retry key. Incomplete journal entries after process loss become `outcome_unknown`; corrupt journal/failed rollback blocks further work. Own Undo checks the exact next label/fingerprint and does not undo unrelated artist actions. Synchronous admitted generation is bounded but not cancellable mid-native-call; completed work must be undone.

Operation `state` and `effects` are independent. Effects are `none`, `committed`, `verified_rollback` or `unknown`. `POST_COMMIT_FAILED` retains the native result and identifies committed changes despite failed completion checks. `JOURNAL_FAILED` reports a durability failure; in-memory outcome queries remain available. Recovery-required operations block new mutations across scope reset/re-enrollment. A restarted unfinished record retains any persisted commit witness. **Review unresolved operation…** is a local artist action: inspect the scene/evidence, then explicitly retire the operation without replay. The exact review must remain current and be saved durably. Unknown effects remain unknown; retirement preserves the scene, discards previous authority and requires fresh enrollment/approval. The AI cannot confirm this action through MCP. A `failed` state alone never proves no scene changes.

On restart the panel immediately disables design enrollment/approval when unresolved work exists. Owned-change receipts distinguish the approved `target_identity` before execution from a recorded `commit_identity`; neither recreates scene authority. Query the original epoch/key after reconnect. [Actual process-loss tests](M01_PROCESS_LOSS.md) cover queued, unacknowledged-native and journalled-commit boundaries. Cold reopen may reconstruct the native publication from pending saved settings; do not claim the previous warm Manual result survived or silently resume from an old publication handle. Returning-task/adoption support remains goal work.

Current development publication pages use **`cyrus.procedural-publication-page/2.0`**, advertised by the manifest. Each row reports separate **`effective_radii_m.xy`** and **`.xyz`** values. Do not collapse them into an unspecified radius. Native generation readback uses token-checked pages of at most 500 rows within the existing design budget; counts alone are not evidence that every row was inspected. The [M01 report](M01_OPERATIONS.md) records scoped native/client evidence and remaining qualification.

Owned replacement now records native publication Undo alongside authored settings, initializes the root identity before publication, and verifies the old immutable publication/generation during failed-operation recovery. Native tests cover full cached Undo/Redo and three failed-successor checkpoints. Complete Plan 0.73 refinement still replaces owned layer identities. The development owned-change contract above preserves them for its qualified patch subset; broader targeted settings remain goal work.

Default connection directory is `%USERPROFILE%\.cyrus-scatter\automation`; installed isolated builds live under `%USERPROFILE%\.cyrus-scatter\mcp`. The Windows-user-restricted directory contains credentials and a bounded 128-record journal. Never share `connection.json`. Multiple Max sessions require distinct directories/client configurations. Client command is the installed environment's Python with `-m cyrus_mcp.server` and optional `--connection-dir`.

Current-generation execution export caps exactly **1,500,000 bytes**. Cached publication rows/opaque input signatures are not a complete portable recipe/source-assets package. Operational records have training eligibility false. The separate offline Design Lab remains experimental with no Max render/training endpoint or reference-image model.

It does not add remote render or Brush authoring. Max 2026 MCP authoring is not qualified by Scatter's separate Max 2026 host checks.
