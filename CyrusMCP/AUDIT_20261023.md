# MCP capability and readiness audit — 23 October 2026

## Assessment and scope

Cyrus MCP has a useful bounded transaction/inspection foundation. It does not yet
provide full artist-workflow control of current Scatter. The immediate operational
problem is that the configured client runs an older package than the repository,
and its saved host endpoint is no longer alive. Expanding tool declarations alone
would not address either problem.

This is an audit and implementation recommendation, not a new delivery or a claim
of current Max runtime qualification. No product code, installed client settings,
artist profile, scene, release version or installer was changed. No Max process
was launched or restarted. Arrange, Physics Lab and licensing administration are
separate products/workstreams, not automatically part of Scatter MCP parity.

## Current authoring envelope

The source supports one locally enrolled static horizontal convex site, one to
three mesh assets, one to three planting regions/layers, up to three protected
regions, 2,000 aggregate requested candidates, two successful applications and two
captures. Aggregate design geometry is capped at 10,000 evaluated triangles and
12,000 vertices. Plans cap 32 KiB; context caps 64 KiB. Ordinary calls have a
24-call budget with recovery/paging exceptions. Publication pages cap 500 rows
and use separate attempt/expiry limits. Native Scatter's larger capacities do not
extend these MCP limits.

Supported writes include owned layer count/seed/weights; uniform/XYZ scale,
yaw/XY tilt/projected XY movement; source scale/lift/Manual radius/follow-scale;
convex exclusions; self and layer-pair spacing; cleanup; visibility/enable; and a
display/update subset. Count is a candidate budget with explicit underfill policy.

Existing artist controllers have read-only enrollment. A design scope creates one
owned controller and can refine that controller; it does not edit arbitrary
existing setups. Save/reopen keeps scene results but requires fresh enrollment.
Approval, enrollment, cancel/revoke, own-top-Undo and recording/share grants are
local panel actions, not public AI tools. Native generation is synchronous; local
cancel can stop queued work, not interrupt an admitted native call.

## Readiness issues to resolve before expansion

1. **Align deployed client and host contracts.** Build and test a matched source
   package and host adapter, then update the client deliberately. Add a preflight
   response that binds package/build, plan/config/publication/recipe versions,
   current native/script identities, Max version and supported feature versions.
   Reporting hashes is useful but is not admission against a matched compatibility
   manifest. Report a dead endpoint distinctly from an uncertain mutation outcome.
2. **Repair contradictory help and qualification entrypoints.** MCP README still
   opens with CyrusUnified1/UI 0.79; the capability matrix header names
   CyrusUnified1/schema 58; catalog C30 still says schema 58. Current source and
   delivery use CyrusUnified2/schema 59. The historical
   `unified_073_mcp_host.py` fixture asserts CyrusUnified1, and
   `mcp_acceptance.py` imports the retired `require_legacy_mutation`. Preserve old
   receipts, but create a current successor campaign rather than treating them as
   current acceptance. The draft compiler in `procedural_plan.py` is explicitly
   offline-only and includes retired model-owning sets/background semantics; do
   not promote that draft into the current authoring schema unchanged.
3. **Make discovery executable and concise.** Feature cards currently contain
   prose rather than independently typed read/write/qualification flags. Add
   task-specific capability/feature queries usable by clients that do not surface
   resources conveniently. Validate help, schemas, adapter mappings and loaded
   capabilities together. Give every unavailable feature a reason.
4. **Strengthen response contracts.** Discovery confirms each tool's output schema
   currently requires only `ok` and permits arbitrary other fields. Add typed
   context, validation, operation, configuration/publication and error envelopes,
   including explicit pending/published identities and machine-readable recovery.
   Audit tool annotations for refinement, which can replace existing owned data.
5. **Qualify passive reads on the current host.** Publication/event paths avoid
   geometry fingerprinting by design. Configuration/context call `fresh()`, whose
   design-scope fingerprint can snapshot evaluated geometry; all such reads are
   not equally cheap. Measure cost and counters rather than promising universal
   zero evaluation. Current recipes have evolved far beyond the original adapter;
   current property bindings, shared ownership and exact publication reads need
   fresh Max 2027 tests.

The MCP specification supports structured tool outputs and optional output
schemas, and URI-addressed contextual resources. The narrower Cyrus response and
discovery improvements above are product recommendations, not a claim that the
current server must implement every optional protocol feature. See the official
[tools specification](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
and [resources specification](https://modelcontextprotocol.io/specification/2026-07-28/server/resources).

## Recommended implementation sequence

1. **Restore a trustworthy current connection.** Resolve the package/plan mismatch,
   preflight, contradictory guidance and current host fixtures. Verify all twelve
   tools/seven resources through the intended client and a matched owned Max 2027
   profile. Exercise inspect → validate → local approve → apply → status → actual
   publication → explicitly shared capture; cover stale approval, exact retry,
   failure retention, own-Undo and reconnect. Do this before expanding writes.
2. **Deliver complete everyday tasks.** Add bounded library search/inspect and
   approved recipe instantiation first; then typed editing of explicitly enrolled
   existing setups: layers, receivers, sources, amount/density, transforms, current
   clearance, eligibility, layout and Relax. A small recipe-oriented command can
   reuse substantially more of the current plugin than hundreds of UI setters.
3. **Add spatial authoring and precise edits.** Paint Areas/vector/spline transfer,
   Paths/Bands, maps/Analyzer bindings, source pools/containers and snapshot-bound
   per-instance operations. Qualify each family independently with its ownership,
   units/topology, cost, Undo and failure behavior.
4. **Add bounded job workflows when needed.** Expose authorized queued-operation
   cancel/own-result rollback and progress, with honest non-interruptible phases.
   Later add camera/profile-enrolled render jobs and small design comparisons with
   verified images/manifests and persistent time/storage/attempt budgets. Broader
   automatic session authority requires a separately defined local bounded grant.

Use domain operations, not a generic MAXScript evaluator or arbitrary property
setter. A patch should name an immutable base revision, preserve untouched owners
and persistent IDs, and normalize to a complete effective transaction before
approval. Make create/copy/remove/reset/inherit/preserve meanings explicit. Pending
Manual values and the prior published result stay separate. Failure retains the
previous complete result. Large calculations/storage remain in existing C++;
MCP and MAXScript coordinate bounded authored operations on the host thread.

The local Automation panel currently has a 490×650 initial size, separate scope
selection, inspection, viewport sharing, a proposal selector/text review, approval,
cancel, own-Undo, disconnect and diagnostics. Source inspection suggests a useful
developer panel, with raw JSON settings in the review text. For broader editing,
replace that review with readable before/after owner/setting differences, affected
layers, estimated work and explicit Update effects, keeping details expandable.
This is a source-based UX assessment; no current panel screenshot or physical UI
test was performed.

Completion should mean that every maintained feature family has a truthful
read/write/unavailable state, and supported natural-language tasks produce the
correct final recipe/publication/artifacts through tested clients. Include
underfill, preserved paths, source-versus-receiver distinction, Manual pending
state, stable IDs, unsupported requests, stale contexts, retry/restart, budgets,
failure retention and misleading scene labels in agent-level acceptance. Raising
the 2,000-candidate/two-application limits needs measured host cost and locally
bounded policy; increasing constants alone is not qualification.

The next recommended scope is connection/contract alignment plus one current
Max 2027 end-to-end acceptance campaign. Product implementation, installation and
client reconfiguration remain future actions beyond this audit.
