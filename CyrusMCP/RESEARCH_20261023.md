# MCP design, performance and agent understanding — research, 23 October 2026

Research only. The user's active fixes and optimizations continue separately.
No plugin/server implementation, dependency installation, client configuration,
scene operation or host launch was performed for this research. The companion
[repository audit](AUDIT_20261023.md) records the earlier inspected implementation;
active development means its source identities are not a frozen future baseline.

The sources below were checked on 23 October 2026. Official specifications define
protocol behavior; vendor engineering articles describe their experience; papers
report results on particular models, datasets and harnesses. None measures Cyrus
Scatter performance or proves a particular design will outperform alternatives
in Max. Proposed names and interfaces below are recommendations, not new tools.

## Assessment

MCP standardizes access to context and operations. Useful agent understanding also
depends on the model, the client runtime, clear domain semantics, current scene
state, useful feedback and examples. Merely exposing every property does not
establish that an assistant can complete a planting task correctly. The official
[Python SDK overview](https://py.sdk.modelcontextprotocol.io/) describes MCP as
separating provision of context from the LLM interaction; the practical tool-design
guidance below explains the additional design work.

For Cyrus, optimize three separate things: the AI's decisions/context, transport
and orchestration overhead, and the actual Max/native work. Success must include
the resulting scene and truthful reporting, not just valid JSON or a returned
success flag. These are engineering recommendations informed by the sources,
not published performance claims about this plugin.

## Prioritized reading

1. **Current MCP specification and July release explanation.** The `latest`
   specification resolved to **2026-07-28** when checked. Read the official
   [tools contract](https://modelcontextprotocol.io/specification/2026-07-28/server/tools),
   [resources contract](https://modelcontextprotocol.io/specification/2026-07-28/server/resources),
   [transport overview](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports)
   and [release explanation](https://blog.modelcontextprotocol.io/posts/2026-07-28/).
   Structured results can have output schemas; tools should have deterministic
   listing order. Modern stateful applications use explicit handles rather than
   implicit protocol session state. The July revision differs substantially from
   older tutorials, including moving Tasks into an extension. Pin a supported
   protocol/client combination rather than copying an old server example or
   upgrading dependencies without interoperability tests.

2. **Anthropic: Writing effective tools for agents**, 11 September 2025.
   [Engineering article](https://www.anthropic.com/research/writing-tools-for-agents).
   Prioritizes distinct useful workflows, meaningful results, context efficiency,
   clear names/descriptions and agent evaluations. Its advice is practical
   experience rather than a universal optimum. Cyrus application: test operations
   such as applying a library recipe or editing one layer's clearance instead of
   mechanically exposing every UI control.

3. **OpenAI: Define tools.** [Current plugin design guidance](https://developers.openai.com/plugins/plan/tools).
   Starts from the user's expected outcome, groups coherent operations, separates
   actions with different authority, and asks descriptions to explain purpose,
   prerequisites and differences from related tools. Cyrus application: keep
   inspection, proposal validation, approved mutation and renderer jobs distinct;
   reuse coherent transactions inside each family.

4. **Which Metadata Matters for LLM Tool Selection in MCP?**, 9 October 2026.
   [Paper and source links](https://arxiv.org/abs/2610.14334).
   Controlled interventions across five models/five tasks found parameter-schema
   changes had the largest, most consistent selection effects among the tested
   changes. Descriptions explaining parameters also helped selection; tested
   models often favored separate top-level fields. Important limit: single-turn
   generated English requests, small candidate sets, and no tool execution.
   Cyrus application: compare schema alternatives empirically, especially units,
   owner IDs and operation intent. It does not justify flattening every complex
   recipe or replacing explicit persistent IDs with ambiguous natural-language
   labels merely to influence selection.

5. **MCP Tool Descriptions Are Smelly!**, revised 31 May 2026.
   [Paper and source links](https://arxiv.org/abs/2602.14878).
   Examines 856 tools from 103 servers. Its fully augmented descriptions improved
   median task success by 5.85 percentage points in the reported evaluation, but
   increased steps by 67.46% and regressed in 16.67% of cases. Compact component
   combinations could retain useful behavior at lower cost. Cyrus application:
   evaluate description quality and cost together; neither maximum verbosity nor
   minimum word count is a sound universal rule. Verify statements against code.

6. **Effective context engineering for AI agents**, 29 September 2025.
   [Anthropic article](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).
   Explains selective, just-in-time context retrieval and the tradeoff between
   initial context loading and runtime exploration. Cyrus application: small
   capability/scene summaries first; fetch the relevant feature, layer, source or
   publication page only when needed. Historical knowledge is separate from live
   scene state and write authority.

7. **Tool search and programmatic orchestration.** Read
   [OpenAI Tool search](https://developers.openai.com/api/docs/guides/tools-tool-search),
   [Anthropic advanced tool use](https://www.anthropic.com/research/advanced-tool-use),
   [Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp)
   and [Cloudflare's MCP Code Mode documentation](https://developers.cloudflare.com/agents/tools/codemode/mcp/).
   These describe loading relevant definitions on demand and processing/filtering
   intermediate results outside model context. Availability and orchestration
   mechanisms belong partly to the client/provider, not just a server. Cyrus
   application: prefer small server-side summaries and bounded batches first.
   Optional sandboxed orchestration may call approved typed tools; it need not
   grant arbitrary Python/MAXScript execution inside Max. Published token savings
   from unrelated examples are not predicted Cyrus speedups.

8. **MCP-Universe**, August 2025, with a maintained research repository.
   [Paper](https://arxiv.org/abs/2508.14704) and
   [Salesforce research code](https://github.com/SalesforceAIResearch/MCP-Universe).
   Evaluates real servers and multi-step work, including Blender-based 3D design.
   Useful for task/evaluator construction and examining tool-use traces. Its
   original model scores are historical; updated repository features and separate
   token-saving claims do not automatically inherit the paper's qualification.

9. **MCP-Atlas**, revised 19 May 2026.
   [Paper](https://arxiv.org/abs/2602.00933) and
   [research code](https://github.com/scaleapi/mcp-atlas).
   Covers 1,000 tasks, 36 servers and 220 tools; distinguishes call failures from
   failures to understand, synthesize or finish after successful calls. Scoring
   is based on factual claims and allows alternative valid trajectories. Limits
   include judge-model uncertainty and a snapshot of changing live servers.
   Cyrus application: separately score correct calls, actual scene changes and
   the assistant's final account. Use deterministic native/scene assertions where
   possible instead of relying solely on a language-model judge.

10. **MCPMark.** [Maintained benchmark repository](https://github.com/eval-sys/mcpmark).
    Provides stateful tasks, isolated environments and strict automated outcome
    checks; its Verified set pins environment versions and distinguishes old
    results. Cyrus application: owned disposable Max profiles, frozen assets and
    exact loaded builds. Borrow the reproducibility discipline; this benchmark
    does not directly test Scatter or qualify Windows/Max behavior.

11. **Official implementation/testing tools.**
    [Python SDK](https://github.com/modelcontextprotocol/python-sdk),
    [Inspector](https://github.com/modelcontextprotocol/inspector) and
    [Conformance framework](https://github.com/modelcontextprotocol/conformance).
    Use the SDK's matching-version documentation, Inspector for discovery/call
    inspection, and relevant conformance scenarios for the actual supported wire
    version/transport. The documented conformance server runner targets HTTP;
    choose an applicable harness for Cyrus's stdio surface rather than pretending
    an HTTP-only run covers it. Protocol conformance is separate from agent
    usefulness and Max correctness. No tool was installed or executed here.

12. **Long-running work and cancellation.**
    [Official Tasks extension](https://tasks.extensions.modelcontextprotocol.io/specification/2026-07-28/tasks).
    Supports asynchronous handles and polling when both peers declare support.
    Cancellation is cooperative; acknowledgement does not guarantee work stopped.
    Cyrus application: retain explicit operation IDs and unknown-outcome recovery;
    consider the extension only after intended clients are tested. Existing typed
    operation/status tools remain a practical application-level pattern. An async
    MCP response does not make a synchronous native solve interruptible.

13. **3ds Max host constraints.**
    [Autodesk's Max 2027 Python threading guidance](https://help.autodesk.com/cloudhelp/2027/ENU/MAXDEV-Python/files/MAXDEV_Python_threading_html.html)
    says Python worker threads must not use `pymxs` or its objects. Concurrent IO
    and native parallel computation have different boundaries. Cyrus application:
    network work and copied data can run outside host dispatch, while scene reads,
    mutations and publication remain on the Max thread. More concurrent incoming
    requests must not become simultaneous scene mutations.

14. **A relevant DCC integration example.**
    [MCP for Blender](https://github.com/ahujasid/mcp-for-blender) is a community
    project, formerly `blender-mcp`, not a Blender Foundation product. Its own
    README documents scene/material operations, visual verification and direct
    Blender Python execution. Useful for studying inspect → act → see-result UX.
    Its broad execution mechanism is not evidence for importing that authority
    model into Cyrus's bounded transaction contract. Repository descriptions and
    demonstrations are not measured comparative benchmarks.

Additional useful research: [MCP-Bench](https://arxiv.org/abs/2508.20453), with
[Accenture's code](https://github.com/Accenture/mcp-bench), separates tool-level
usage, trajectory planning and task completion. [Semantic Tool Discovery](https://arxiv.org/abs/2603.20313)
studies retrieval on 140 queries/121 tools/five servers; useful as a design option,
but that small evaluation is not a reason to add a vector database to today's
twelve-tool Cyrus server.

## Proposed Cyrus architecture

This is our engineering synthesis, not an implementation claimed by a paper.

| Layer | Responsibility | Agent-visible result |
| --- | --- | --- |
| Versioned domain knowledge | Feature purpose, owner, units, inheritance, prerequisites, supported combinations, examples and unavailable reasons | A concise feature card relevant to the task |
| Live scene context | Explicit enrolled scope, stable owners/references, units, current authored revision, pending state and completed publication | Small typed snapshot with freshness and provenance |
| Planning and validation | Convert typed intent/patches to complete effective transactions; check authority, base revision, dependencies and bounds | Readable difference, warnings, normalized digest and approval requirements |
| Execution | Existing native calculation and bounded host-thread commands; journal admission and publish atomically | Operation ID, truthful state, actual counts/publication or retained prior result |
| Verification | Compare requested effects and unaffected owners; optionally inspect a matching viewport | Technical assertions plus generation/camera-linked visual evidence |

Feature knowledge should say, for example, which owner stores source clearance,
how each scope inherits, whether a radius is world distance or a multiplier, and
whether changing it in Manual mode changes pending values or published plants.
Live context supplies the actual current IDs/values. Neither a generic manual nor
an image alone supplies both pieces reliably.

For each callable operation define: when to use it; when to use another operation;
required scope/owner/base revision; named units and ranges; absence/reset/inherit
semantics; side effects and evaluation cost; normalized result; publication state;
error code/recovery; identity lifetime; and one or two examples for ambiguous use.
Keep common fields shallow and consistent where sensible, while preserving typed
objects for coherent recipes. Avoid one catch-all string payload/property setter.

Use one authored model and native evaluator shared with the UI. No second AI
placement engine is needed. Independent metadata/IO may overlap, but host reads
and writes must respect dispatch and revision ordering. Preserve the existing
split between approval to share/inspect and approval to mutate.

## Proposed user interaction

Example task: “Use the meadow recipe on this terrain, keep this path empty, make
the grass denser, and leave the trees where they are.”

1. Discover actual supported capabilities and the explicitly enrolled setup,
   receiver, library entry and protected path IDs.
2. Read just the relevant recipe, grass/tree owners, pending/publication state and
   feature rules. Unsupported requested behavior is reported before mutation.
3. Normalize a scoped patch, preserve unaffected tree/source identities and
   validate against the exact current base revision. Distinguish estimates from
   actual evaluated counts; validation alone must not invent accepted output.
4. Show a readable review. The user's approved authority must cover the concrete
   operation; any future batch/session grant needs its own bounded local contract.
5. Queue the approved digest with a stable idempotency key. Report queued/running,
   then completed, failed or unknown honestly. Reconcile an uncertain operation
   before considering another mutation.
6. Verify the actual publication, path exclusion and unchanged tree results.
   Capture a matching viewport only when shared. Report shortfall, pending edits
   and technical/visual limits explicitly.

This is a future acceptance example: it includes capabilities absent from the
audited public MCP authoring subset. It must not be advertised as working today.

## Performance and reliability measurements

| Concern | Measure separately |
| --- | --- |
| Agent usefulness | Fully correct final task, correct owner/units, preserved constraints, truthful unsupported/failure reporting |
| Discovery | Relevant feature/tool found, wrong-tool rate, time/calls before a useful operation, missed capabilities |
| Schema usability | Invalid arguments, wrong enum/unit/owner, ambiguous inheritance/reset, error-recovery success |
| Model context | Tool-definition tokens, response tokens, repeated metadata, irrelevant records and visual input cost |
| Orchestration | End-to-end time, model turns, avoidable round trips, polling frequency, retries and duplicate applications |
| IPC and host | Serialization bytes/time, network dispatch, queue delay, fingerprint/snapshot cost, scene reads/mutations |
| Native work | Solve, preparation, source upload, draw, peak/retained memory and responsiveness independently |
| Recovery | Stale approval rejection, unknown-outcome reconciliation, rollback retention, Undo/reopen/reconnect and bounded cancel behavior |

Compare median/tail latency and cold/warm cases on frozen matched builds/assets.
Use the same prompts, model/client versions, fixtures and authorization policy
when comparing two tool designs. Report both task success and cost; shorter
responses or fewer calls can be worse if they hide missing work. There is no
evidence here for a universal best tool count, response size or latency threshold.

Practical first optimizations to test: return cached scoped summaries, add filters
and stable paging, reuse unchanged metadata, combine coherent independent reads,
apply one approved multi-setting transaction with one intended evaluation, return
artifact handles for large data, and avoid unrelated recomputation. Polling and
captures should be deliberate, not a substitute for correct result state.

## Work to resume after the current fixes

1. Freeze source/package/loaded identities and resolve the installed-versus-source
   contract gap identified in the audit. Choose intended clients and supported
   protocol revisions explicitly; test optional features rather than assuming
   presence from the latest spec.
2. Define a small representative task suite before adding tools: passive
   inspection, preset instantiation, independent layer edits, source/receiver
   distinction, exclusions, Manual/Live, underfill, stale approval, exact retry,
   failure retention, Undo and generation-linked visual verification.
3. Design a small coherent tool surface and machine-readable feature cards around
   those tasks. Reuse validated recipe functionality first; add typed editing of
   explicitly enrolled existing setups next. Full coverage means each feature has
   a truthful supported/read-only/unavailable state, not a tool for every spinner.
4. Compare descriptions/schema variants with agents, using deterministic scene
   and publication checks plus visual review where appropriate. Run protocol,
   domain, host and agent-level tests as distinct layers.
5. Expand Paint/Paths/Bands/source containers/Edit and then renderer jobs in
   measured slices. Adopt deferred discovery, custom semantic retrieval or Code
   Mode only when an observed bottleneck and client compatibility justify them.

Do not copy cloud-scale transport infrastructure, autonomous learning, a generic
Max script executor or model-training pipelines merely because a demonstration
uses them. The evidence supports better contracts, selective context and measured
task completion; additional infrastructure must earn its place in Cyrus.
