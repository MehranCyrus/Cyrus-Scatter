# Knowledge harness audit and prioritized worklist

27 October 2026, Asia/Tehran. Read-only system inspection and bounded live-tool
probes; recommendations are not implementation or activation. Plugin sources,
the other AI's interaction work, index selection and refresh authorization were
not changed. Local measurements are under
`build/knowledge-harness-audit-20261027-01/`.

## Assessment

Keep the existing foundation. It has exact citations, source fingerprints,
explicit enrollment, historical qualifiers, complete-contract retrieval, bounded
workers and substantial retrieval evaluations. These are useful safeguards.

The largest immediate gains are current coverage, smaller evidence delivery,
selective startup context and evaluation of actual task cost. A vector database
or model fine-tuning would not directly fix the measured duplication, missing
enrollment, stale sources or conflicting current-version statements.

This system is an evidence-retrieval component of an agent harness. It is not a
trained representation of every plugin subsystem. Its generation contains 64
explicitly selected parents and 1,091 search fragments; only 21 parents have the
Scatter component label, and selected ranges do not cover every line or module.
Disk storage is not automatically model context: material consumes context when
the agent loads it or the client forwards tool output.

## What was inspected

- Current skills/startup instructions and knowledge source routing.
- Corpus v43, active binding, published artifacts and refresh-policy references.
- Search/ranking, source validation, result construction and MCP transport.
- Chunk/contract boundaries, current enrollment and provenance labels.
- Existing evaluation implementation and exact selected candidate evidence.
- Three live searches and one full-source status request, with full raw results
  saved locally and compact measurements returned during the audit.

This does not certify every source claim, rerun the full retrieval suite, test a
new model harness, or measure billed model tokens. The live probes are a small
warm-session sample with uncontrolled background activity.

## Prioritized worklist

### K01 — Reconcile current facts and publish useful current coverage

**Priority:** first. **Benefit:** reliable grounding and fewer failed searches.

- Resolve contradictory current schema/version statements before reindexing.
- Replace fragile release extraction from historical prose with explicit,
  validated facts distinguishing delivered package, live development and saved
  formats. Preserve independently versioned products.
- Review source applicability/authority labels and selected spans. There are
  35 `unknown` labels; these are preserved provenance, not proof of wrong data,
  and should not be mechanically promoted to current.
- Deliberately admit the Scene preset owners/guides and relevant completed editor
  contracts. Review the full source-cap/memory/read budget before expanding it.
- Coordinate one stable reviewed successor. Keep ongoing interaction changes
  visibly separate and retain the prior generation for recovery.

**Acceptance:** current-topic questions retrieve the correct owner and limits;
changed sources still reject; actual consumer status verifies the published
scope. A new feature absent from enrollment is reported as a coverage gap, not
as proof that it does not exist.

### K02 — Reduce routine evidence and status output

**Priority:** first. **Benefit:** direct reduction in context material.

- Add a compact normal view and an explicit detailed audit view. Agent-side
  orchestration can first avoid printing both MCP copies without changing the
  server contract.
- Deliver original evidence once. Omit normalized indexing text and duplicated
  excerpts from the normal model-facing view.
- Carry generation, exact citation/hash, evidence role, applicability, historical
  qualifications, failure state and verification scope. Put repeated build/runtime
  inventories behind an inspectable receipt reference.
- Verify how each actual consumer exposes text and structured content before
  changing compatibility transport. Preserve existing clients and full evidence.

**Acceptance:** identical required evidence/qualifiers and stale/corrupt refusal,
smaller measured model-facing payloads, actual-client checks. Report character
counts separately from observed or estimated token counts.

### K03 — Make startup small and task-directed

**Priority:** first. **Benefit:** less repeated reading before useful work.

- Keep a short foundation with current scope, critical ownership constraints,
  delivered/development distinction, protected work and routing to exact owners.
- Move accumulated release narration out of the startup path while retaining its
  links and immutable receipts.
- Select the required workflow/contract sections by task type. Preserve explicit
  user scope and all applicable safety/engineering requirements.
- Reuse valid information already read in a task; reread on relevant changes.

**Acceptance:** routine documentation and small fixes avoid a broad startup dump;
publication/units/ownership questions still obtain their full relevant contracts.
No task loses a required constraint merely to meet a target size.

### K04 — Create a small subsystem and ownership map

**Priority:** next. **Benefit:** structural understanding and faster source routing.

Use a simple reviewed manifest, not a new graph service by default. For each
subsystem record its artist feature, setting owner, data flow, dependencies,
Manual/Live behavior, persistence/identity rules, failure behavior, source
entrypoints, relevant contracts, tests and qualified evidence.

Start with Library/save-load, placement, Paint, Edit, display/render and source
preparation. Add the live interaction work only through its owning delivery.
Canonical-source links already exist and should be reused.

**Acceptance:** a question such as “saving edited plants fails” routes to the
save selector, serializer, Edit transfer and asset store with their real limits;
it does not begin by loading every plugin document. Knowledge coverage is not
presented as remote mutation authority through MCP.

### K05 — Separate discovery from exact evidence reading

**Priority:** next. **Benefit:** controllable context growth.

- Offer a small topic/result discovery response, followed by exact section or
  evidence-ID reads bound to the generation and source identity.
- Start narrowly and expand with an explicit rationale. Use an aggregate context
  target rather than only `top_k`; permit necessary complete-contract expansion.
- Merge redundant overlapping windows and diversify by relevant section/owner
  without hiding qualifiers or weakening protected evidence tests.
- Retain keyword/path/identifier lookup and existing bilingual terminology.

**Acceptance:** the model can request the missing section directly, knows when
more evidence is available and sees no silent clipping. Exact lookups and source
validation remain reproducible.

### K06 — Add real task-cost and answer-quality evaluation

**Priority:** establish a baseline early; use for every optimization decision.
**Benefit:** verifies whether the system actually helps.

- Keep existing frozen retrieval tests intact. Add representative explanations,
  bug investigations and bounded fixes across subsystems, with reviewed expected
  evidence, outcomes and required limits.
- Compare direct inspection, current retrieval and the proposed compact/routed
  workflow under matched model/settings and frozen source snapshots.
- Measure correctness, successful completion, stale/historical mistakes, tool
  calls, total task tokens where available, wall time and rework. Label token
  estimates when actual usage is unavailable.
- Evaluate representative runs through the real client/harness, not only direct
  tool calls. Keep genuinely unseen tasks separate from repeatedly tuned cases.

**Acceptance:** lower median total cost at equal or better task correctness and
no increased critical constraint failures. A reduced prompt that causes more
debugging is not an efficiency win.

### K07 — Make freshness and maintenance more local

**Priority:** after the compact baseline. **Benefit:** keeps useful knowledge
available while another component changes.

- Explore shared core plus explicit component/topic scopes, with coordinated
  cross-component evidence and version boundaries.
- Refresh/review affected owners with deterministic change reports and bounded
  scheduling. Run the broader protected suite when shared contracts change.
- Review and deliberately rebase the standing refresh policy before resuming it.
  Keep mechanical freshness separate from semantic approval.
- Provide one active configuration manifest; retain old corpus/review/evaluation
  definitions as historical evidence rather than forcing routine discovery across
  all 43 corpus, 53 review and 138 evaluation definition files.

**Acceptance:** changes in one topic do not cause unrelated material to be
represented as globally fresh or globally unavailable. Required cross-component
constraints remain retrievable. Existing source integrity is not bypassed.

### K08 — Turn verified fixes into reusable lessons and task state

**Priority:** after routing exists. **Benefit:** fewer repeated investigations.

- Use the existing lesson format: trigger, cause, correction, scope, evidence,
  uncertainty and invalidation condition. Link the reproduction/regression case.
- Store short task state for completed reads, decisions, current source identities
  and unresolved questions; invalidate it when the owning input changes.
- Reuse reviewed lessons across sessions. Keep hypotheses, chat instructions,
  user authorization and proven facts distinct. Do not ingest conversations or
  agent guesses as established knowledge.

**Acceptance:** a repeated known failure reaches the correct cause faster, while
a changed source/version prevents blind reuse of an obsolete fix.

### K09 — Optimize integrity-work reuse only if it remains material

**Priority:** later; preserve the existing isolation and correctness guarantees.

The current fresh-worker design repeatedly verifies generation artifacts. If
end-to-end measurements show this is costly, evaluate a verified immutable
generation cache or a read-only service lifetime. Preserve tamper detection,
root/binding checks, cancellation, resource bounds and returned-source freshness.
A stat-only shortcut or stale fallback is not a valid optimization.

**Acceptance:** matched warm/cold latency and memory evidence, corrupt/stale and
lifecycle checks, with no reduction in required integrity guarantees.

### K10 — Trial semantic retrieval only for demonstrated language misses

**Priority:** optional experiment after K01–K06.

If current natural-language questions still miss the right concepts, compare
hybrid semantic retrieval with the existing exact/lexical system. Preserve exact
symbol/path lookup and filter evidence by source role and applicability.
Include embedding/index maintenance cost and actual task outcomes in the test.

**Acceptance:** better relevant-owner discovery or lower total task cost on the
identified failures, without more misleading historical evidence. No full
vector rewrite or model fine-tuning is justified by this audit alone.

## Recommended delivery sequence

1. Agree the benchmark/acceptance cases; correct current facts and coverage (K01,
   baseline part of K06).
2. Implement compact consumption/status and selective startup (K02–K03). These are
   the most direct context-cost opportunities found here.
3. Add the subsystem map and exact evidence expansion (K04–K05); compare against
   the baseline through the real harness (K06).
4. Improve scoped upkeep and reusable lessons (K07–K08).
5. Attempt caching or semantic search only when measured failures/cost justify
   K09 or K10.

Do not begin a new native plugin build, fine-tuning run, graph database, global
watcher restart or index activation as a side effect of this audit.
