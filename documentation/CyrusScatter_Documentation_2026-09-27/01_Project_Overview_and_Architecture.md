## Scatter core

**VERIFIED CURRENT SYSTEM:** `AminScatter/CMakeLists.txt` builds `amin_scatter` as a static C++17 library from `src/scatter.cpp`. The public header uses its own geometry/data types rather than Autodesk types.

The public API includes `Settings`, `Instance`, `Area`, `LineBand`, `BoundaryFalloff`, `FinalSettings`, and operations including `scatter`, `finalize`, `boundaryFalloff`, `orientBoundary`, `edgeBorderPoints`, `sampleSource` and `pointCloud`.

This separation is strategically valuable: the mathematical engine can remain license-agnostic and unit-testable.

## Max bridge

**VERIFIED CURRENT SYSTEM:** `max_bridge.cpp` converts Max nodes/meshes and MAXScript arguments into native structures, calls the core, and converts results back to transforms/source rows. It exposes high-value visible primitives including `aminScatterAdvanced` and related operations.

It is therefore a natural native licensing boundary.

## Preview

**VERIFIED CURRENT SYSTEM:** `preview.cpp` implements native preview/cache behavior. Future license checks should occur before authoring work, not inside drawing loops.

## CS Edit

**VERIFIED CURRENT SYSTEM:** CS Edit is a native Max modifier with storage/stack support. Project guides and source show persistent editing behavior rather than a disposable scripted effect.

Commercial policy should gate **mutation** while allowing saved state to evaluate for scene fidelity and rendering.

## Generated MAXScript

**VERIFIED CURRENT SYSTEM:** `AminScatterObject.ms` is roughly 964 KB and generated by `tools/ui/generate.cjs`. Generator stages cover spacing, centers, weights, overlaps, edit, orientation, edge-border, display modes, boundary falloff, analyzer-area, street layout, performance, responsiveness and more.

Do not hand-edit generated output for commercial licensing. Add licensing UI through generator stages/templates. The existing `activation.cjs` is a feature-enable stage, not commercial activation; rename it before adding a licensing module.

## Render path

**VERIFIED CURRENT SYSTEM:** `templates/pflow.ms` orchestrates transient Particle Flow structures and render callbacks. Existing project documentation describes automatic final rendering and cleanup.

This means render workers may need to recompute placements from an existing scene. Licensing must distinguish render evaluation from authoring.

## Surface Analyzer

**VERIFIED CURRENT SYSTEM:** Analyzer is a separate static C++17 engine plus `CyrusSurfaceAnalyzer.dlx`. `analyzer.h` exposes `analyze(const Mesh&, const Settings&)`; `bridge.cpp` converts Max geometry and exposes `cyrusAnalyzeSurface`.

Result data includes boundaries, paths, points, area, region area, path length and per-element metadata.

## Runtime flow

```text
3ds Max startup
 -> native modules + startup/macro scripts
 -> Cyrus controller/UI
 -> scene parameters
 -> native bridge
 -> scatter core
 -> native edit/final processing
 -> placement rows
 -> native preview OR PFlow final-render orchestration
```

Analyzer runs in parallel:
```text
Analyzer MAXScript -> cyrusAnalyzeSurface -> native bridge -> analyzer core
 -> boundaries/paths/points -> MAXScript cache/display -> optional Scatter consumption
```

## Build

AminScatter CMake registers six CTest executables and can build the core without Max via `AMIN_BUILD_MAX=OFF`. Native Max modules link against the 2026 SDK.

Surface Analyzer has a separate static library, CTest executable and 2026 Max module.

## Versioning

Version notions are currently fragmented across CMake, native descriptions, README/feature guides and internal generated data. Before commercial release, create one product/release version source of truth while keeping scene-format migration IDs independent.

## Trust boundary

MAXScript is customer-editable and cannot be authoritative DRM. Native code is harder to patch but still reversible. The durable security property must be cryptographic authenticity plus multiple native authorization boundaries.
