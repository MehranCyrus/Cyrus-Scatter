# 10: Editing, Scripting, and Effects

## 1. Purpose and scope

This specification defines Stage S10, the editing model, manual creation tools, undo behavior, persistence, Effects, and the MAXScript interface for Cyrus Scatter. It extends `00_ARCHITECTURE.md` sections 4, 5, 6, 7, 11, 12, and 13. It does not redefine `StableKey`, `KeyParts`, `Population`, `ItemFlags`, `ViewMask`, `StageContext`, `IStage`, `DirtyBits`, or `SharedCacheRegistry`. It adds authored records that make edits durable while preserving the recomputable population contract.

The implementation goal is feature parity where Forest behavior is documented, while deliberately fixing the parts that make procedural edits fragile. The central distinction is between an item generated by the pipeline and an item authored by a person. A generated item has a `StableKey`; a manually created item has an immutable `entryId`. A user's edit is therefore data, not a mutation of an ephemeral output array.

S10 reads the output of S9 and writes user edits and effect mutations into the working Population. It runs before S11 shading and S12 compaction, exactly as 00 defines. Effects see the result of user overrides. Effects do not silently trigger collision or boundary re-evaluation in v1. If a user changes a parameter that invalidates an earlier stage, the pipeline restarts from its dirty checkpoint and S10 reapplies the authored records.

### Why two edit mechanisms

ForestPack's Custom Edit is a useful interaction model but an unsafe persistence model for a procedural engine. Its documented behavior is that switching Generate to Custom Edit preserves the distribution and excludes collision rejects, while returning from Custom Edit to Generate loses Custom Edit changes. Forest also warns that Generate indices are not fixed and may change. Areas do not apply in Custom Edit. These are [FP-OBS] or [FP-DOC] behaviors, not claims about Forest's private storage. See the [Custom Edit tutorial](https://www.itoosoft.com/es/tutorials/how-to-use-forest-packs-custom-edit-mode), [Items Editor reference](https://docs.itoosoft.com/forestpack/forest-plugin/item-editor), [official forum explanation](https://forum.itoosoft.com/forest-pro-(*)/custom-editfreeze-mode/), and [area reference](https://docs.itoosoft.com/forestpack/forest-plugin/areas).

Cyrus keeps the familiar editing workflow but has two coexisting mechanisms:

1. `OverrideRecord` modifies a procedural candidate without turning the whole population into a frozen array.
2. `ManualItem` creates an authored item that exists independently of procedural generation.

This makes edits survive density, seed, area, geometry list, and map changes when the candidate identity still exists, and makes a missing candidate visible instead of silently applying an edit to a different item. A command called **Freeze to manual** provides the explicit one-way conversion when a user wants a fully fixed result.

## 4. Data structures

All types in this section are core types unless explicitly marked Max layer. They use plain C++20 data and no Max headers.

### 4.1 Override records

```cpp
struct TransformDelta {
  Vec3f translation{0,0,0};
  Quatf rotation{1,0,0,0};
  Vec3f scale{1,1,1};
  bool hasTranslation=false;
  bool hasRotation=false;
  bool hasScale=false;
};

enum class OverrideTransformMode : u8 { Delta, Absolute };

enum OverrideField : u32 {
  O_Position=1u<<0, O_Rotation=1u<<1, O_Scale=1u<<2,
  O_Geometry=1u<<3, O_Visible=1u<<4, O_Tint=1u<<5,
  O_UserID=1u<<6, O_Seed=1u<<7
};

struct OverrideRecord {
  StableKey key;
  u32 recordVersion=1;
  u32 generatorAlgoVersion=0;
  u32 fields=0;
  OverrideTransformMode transformMode=OverrideTransformMode::Delta;
  TransformDelta delta;
  Transform absolute;
  u32 geometryEntryId=0;
  bool hasGeometry=false;
  bool hidden=false;
  bool hasVisibility=false;
  u32 tintRGBA8=0xffffffffu;
  bool hasTint=false;
  i32 userID=0;
  bool hasUserID=false;
  u64 randomSeed=0;
  bool hasSeed=false;
  u64 lastSeenPopulationVersion=0;
  bool orphan=false;
};
```

The map is `std::unordered_map<u64, OverrideRecord>` keyed by `StableKey.v`, but all serialized output is sorted by key. StableKey is generated by the upstream stage from `KeyParts`; it is not an array position, geometry list index, or UI selection index. Geometry swaps store immutable geometry `entryId`, as required by 00 section 6. A missing entryId is reported and does not silently fall back to display index.

Delta mode means the user's move, rotate, or scale is applied on top of the regenerated base transform. Absolute mode stores the final transform in Forest-local coordinates and is useful for scripted placement. Rotation deltas are composed as `delta.rotation * base.rotation`, scale is componentwise multiplication, and translation is added in the selected transform frame after conversion to FL. Absolute scale may be negative only when mirror is explicitly enabled.

Manual items append to the Population with a deterministic synthetic `StableKey` derived from `GenKind::Manual`, the owning Cyrus object ID, and the low 32 bits of `ManualId`. The manual ID itself remains the authoritative persistence key. `F_MANUAL` is set. A deleted manual item is retained as a tombstone until save compaction so undo and references remain valid.

### 4.5 Max layer types

`CyrusScatterObject` owns the ParamBlock2 parameters and Max node references, while a private Max-layer `CyrusEditState` owns the selection cache, pending gesture, and display handles. `CyrusEditRestore : RestoreObj` stores a core `EditDelta`, never a raw Max mesh or pointer. A `CyrusEffectParamAccessor` converts controller, texture, and curve references into immutable snapshot values in S0. The Max layer may include `IParamBlock2`, `INode`, `RestoreObj`, `IObjParam`, `SubSelectionPolyMod`, and `FPInterface`, but these types must not leak into core headers.

## 5. Algorithms

### 5.1 Applying procedural overrides

S10 receives a Population whose entries have passed S9. For each live item, look up `key.v`. Apply only records whose fields are present. Then mark `F_OVERRIDDEN`. Do not erase rows. If an override record is not observed in the current generated population, retain it as an orphan.

```cpp
void applyOverrides(Population& p, OverrideStore& store, u64 version) {
  std::vector<u64> seen;
  seen.reserve(p.size());
  for (u32 i=0; i<p.size(); ++i) {
    if (!(p.flags[i] & F_ALIVE)) continue;
    const u64 k = p.key[i].v;
    seen.push_back(k);
    auto it = store.find(k);
    if (it == store.end()) continue;
    OverrideRecord& r = it->second;
    r.orphan = false;
    r.lastSeenPopulationVersion = version;
    if (r.transformMode == OverrideTransformMode::Delta) {
      if (r.delta.hasTranslation) p.pos[i] += r.delta.translation;
      if (r.delta.hasRotation) p.rot[i] = normalize(r.delta.rotation * p.rot[i]);
      if (r.delta.hasScale) p.scale[i] = p.scale[i] * r.delta.scale;
    } else {
      if (r.fields & O_Position) p.pos[i] = r.absolute.position;
      if (r.fields & O_Rotation) p.rot[i] = normalize(r.absolute.rotation);
      if (r.fields & O_Scale) p.scale[i] = r.absolute.scale;
    }
    if (r.hasGeometry) p.geomId[i] = resolveGeometryIndex(r.geometryEntryId);
    if (r.hasVisibility && !r.hidden) p.flags[i] &= ~F_HIDDEN_USER;
    if (r.hasVisibility && r.hidden) p.flags[i] |= F_HIDDEN_USER;
    if (r.hasTint) p.tintRGBA8[i] = r.tintRGBA8;
    p.flags[i] |= F_OVERRIDDEN;
  }
  for (auto& [key, record] : store) record.orphan = true;
  for (u64 key : seen) store[key].orphan = false;
}
```

The pseudocode's final loop must be implemented with a temporary observed set, not by setting every record orphan and then relying on map insertion. It should be linear in live population plus record count. Orphan state is diagnostic state and is serialized only when the user has chosen to retain an orphan explicitly. The record itself remains serialized by default.

An override survives a density change if its StableKey is still generated. Lowering density must never reshuffle survivors: S5 uses StableRNG keyed by candidate key and a density threshold, so an edited survivor remains the same candidate. A seed change usually changes keys or the random decisions. The orphan UI lists records no longer present and explains the cause only when known: changed seed, area removed, map tile changed, surface miss, collision, or geometry source deleted. The UI must not claim a cause if only the key comparison is available.

If an area moves or its order changes, a procedural key may disappear. The override remains orphaned. If the same key returns later, it is reapplied. If density increases, newly appearing candidates have no override. If a geometry list entry is renamed, its entryId remains valid; if deleted, the override shows a missing geometry source and preserves its last requested ID. A migration command can remap missing entry IDs explicitly.

### 5.2 Freeze to manual

Freeze is explicit, undoable, and has two scopes: selected items or all current survivors. For each selected live procedural item, copy final S10 transform, source entryId, tint, userID, visibility, and link state into a new ManualItem. Then add a tombstone or remove the override only if the user selected **replace with manual**. The default command keeps the procedural record hidden to prevent duplicate display and stores a source link in the manual record. A second confirmation is required for replacing the procedural source.

```cpp
ManualItem freezeItem(const Population& p, u32 row, ManualId id) {
  ManualItem m;
  m.id = id;
  m.geometryEntryId = geometryEntryIdFromIndex(p.geomId[row]);
  m.transformFL = {p.pos[row], p.rot[row], p.scale[row]};
  m.tintRGBA8 = p.tintRGBA8[row];
  m.userID = readUserID(p, row);
  m.visible = !(p.flags[row] & (F_HIDDEN_USER|F_HIDDEN_EFFECT));
  m.sourceTool = 1;
  return m;
}
```

Why not automatically freeze on entering Edit mode? Automatic materialization makes the result hard to inspect, produces large save files, and makes later parameter edits surprising. Cyrus's Generate mode remains procedural, while Freeze to manual states exactly what is being traded away.

### 5.3 Manual creation

The create tool resolves geometry according to Add mode. Selection uses the geometry selected in the Properties combo. Random selects a geometry entry using StableRNG with purpose `ManualCreateRandom` and the new manual ID. Sequence uses a per-object creation counter modulo enabled entries, in UI order, while retaining entryId. Disabled entries produce a deliberate gap only if the user selected them explicitly.

Creation tools produce a local transform:

* Single: viewport ray hit on the Cyrus construction plane or active surface, otherwise FL Z=0.
* Along path: build or read an arc-length table, sample spacing and optional endpoint policy, create one manual record per sample with tangent orientation.
* On pivots: snapshot reference node pivots and use each pivot's world transform converted to FL.
* On faces: viewport ray or reference face hit, barycentric point and normal, converted to FL.

`Link to Surface` records the source surface entryId and UVW or surface-local hit. It recomputes the linked position and normal when the surface changes and prevents free Z movement while linked. `Place Items` performs a one-time hit and sets `SurfacePlaced`; later surface changes do not move the item. With no surface and no hit, Z is exactly 0 in FL, matching [FP-DOC] behavior.

### 5.4 Selection and viewport hit testing

Use a two-level query. First, query the per-tile spatial index with the screen ray's world-space segment and an expanded item bound. Second, perform exact proxy hit testing against the selected source's bounds or a point billboard. The default is nearest depth, with Ctrl adding, Alt removing, and Shift toggling. Region selection projects item bounds to screen and uses center-in-region or bounds-overlap according to the standard Max sub-object selection mode.

The spatial index is read-only and can be rebuilt from PublishedPopulation. It stores stable key, manual ID, bounding sphere, tile ID, and row index for the current population version. If a result is returned after a rebuild, reject it unless the version matches. Point cloud display uses a coarse proxy and then exact item center tests. A selected hidden item remains selectable through the item list but is not selectable by viewport hit unless **show hidden** is enabled.

### 5.5 Transform gestures

The Max adapter must expose a sub-object level whose selected handles use standard Move, Rotate, and Scale tools. The exact SDK class names and override signatures must be verified against the installed 3ds Max SDK headers. The intended SDK path is `IObjParam` and sub-object selection support, with `XFormModes` or the current equivalent to supply Move, Rotate, and Scale overrides. Verify the signatures for `GetSubObjectCenters`, `GetSubObjectTMs`, and the relevant `Move`, `Rotate`, and `Scale` virtuals before implementation. Do not infer these signatures from forum snippets.

At gesture begin, resolve selected handles to keys and capture their before values. During mouse moves, update a preview copy without creating undo records. At gesture end, convert the final Max transform into a delta in the selected frame. For a pivoted multi-selection, apply the same group matrix to each original transform, then factor the result into per-item delta or absolute values. A linked ManualItem converts world motion back to surface coordinates and rejects a Z component that violates the link policy.

Numerical details:

* Normalize quaternions after each multiplication and reject norms below `1e-10`.
* Use double for the group pivot and matrix multiplication, then store float transforms as 00 requires.
* Preserve negative scale as mirror plus positive scale where possible; do not encode a reflection in a quaternion.
* Quantize neither edits nor preview. Save full float values and let export select precision.
* When the Max gizmo supplies Euler angles, convert once to a quaternion in a documented order and never repeatedly accumulate Euler values.

### 5.6 Commands

Delete sets `hasVisibility` and `hidden` for procedural items, or sets `deleted` for ManualItems. It does not erase a procedural row from the Population. Change Model stores the selected geometry `entryId`. Select By Type queries all live rows with the same entryId. Randomize model chooses a new source using the edit seed and records it. Reset Size clears scale delta for an override or restores ManualItem scale to one relative to its stored source size. Re-Seed stores a new per-item random seed and recomputes only the random transform inputs for that row. Store Transform captures the visible final transform as absolute, or computes an equivalent delta against the current base, and clears the randomization contribution so a future upstream rebuild preserves the displayed result.

### 5.7 Attach, detach, and consolidate

Detach selected items creates a new Cyrus object with copied geometry references, surfaces only when explicitly requested, and ManualItems in the new object's FL. The source object's selected items become hidden tombstones, not silently deleted. Attach reads one or more Cyrus objects' published items or manual records and creates ManualItems in the destination. With Consolidate Geometry List enabled, match entries by normalized display name and geometry type, then verify source signature where available. A match is accepted only when name and type agree. If two entries collide on the same name and type, require a deterministic tie break based on source object ID and report it. Unmatched sources are appended with fresh entryIds. `entryId` values are never copied across objects.

### 5.8 Effects language

The language matches Forest's documented expression model while adding a safer compiler and deterministic random functions. Identifiers and keywords are case-insensitive. Statements end with semicolons. `#` comments continue to end of line. `print(expr);` evaluates only for the first item in a batch and writes to the diagnostics panel, never to standard output on worker threads.

#### Tokens

Tokens are whitespace, comments, identifiers, integer literals, real literals, strings for parameter names, punctuation `(){}[],.;`, member dot `.`, assignment `=`, arithmetic `+ - * / ^`, comparison `== < > <= >= !=`, logical `& | !`, and end of file. A number may use decimal or scientific notation. Units are not part of expressions in v1; user parameters perform unit conversion in the Max adapter.

#### EBNF

```text
program       = { statement } ;
statement     = assignment ";" | expression ";" | print_stmt ";" ;
assignment    = lvalue "=" expression ;
print_stmt    = "print" "(" expression ")" ;
lvalue        = identifier [ "." identifier ] ;
expression    = conditional ;
conditional   = logical_or [ "?" expression ":" expression ] ;
logical_or    = logical_and { "|" logical_and } ;
logical_and   = equality { "&" equality } ;
equality      = relation { ("==" | "!=") relation } ;
relation      = additive { ("<" | ">" | "<=" | ">=") additive } ;
additive      = multiplicative { ("+" | "-") multiplicative } ;
multiplicative= power { ("*" | "/") power } ;
power         = unary [ "^" unary ] ;
unary         = [ ("+" | "-" | "!") ] primary ;
primary       = literal | identifier [ "." identifier ] | call | "(" expression ")" ;
call          = identifier "(" [ expression { "," expression } ] ")" ;
literal       = real | integer | vector ;
vector        = "(" expression "," expression "," expression ")" ;
identifier    = letter { letter | digit | "_" } ;
```

The parser distinguishes vector cross product from scalar power by types. `*` is scalar multiply, vector dot product, or componentwise vector multiply only where the type rules make it unambiguous. `^` is scalar power or vector cross product. Ambiguous vector operations are compile errors rather than implicit conversions. `if(p,q,r)` is a built-in expression function and evaluates only the selected branch for scalar and vector values, so expensive map and spline functions can be avoided.

Types are `real`, `int`, `vector`, `bool`, and internal `void`. Implicit conversion from int to real is allowed. Real to int requires `int(x)` and uses truncation toward zero. Scalar to vector broadcasts only through `vector(x)` or explicit component construction. Vector components are `.x`, `.y`, `.z`. Boolean comparisons return bool, and `if` accepts numeric predicates with zero false and nonzero true for compatibility.

The compiled program records that it used a compatibility alias, allowing diagnostics to warn about list reorder sensitivity. Effects writing geometry, scale, or position do not rerun S8 or S9 in v1. The Stats panel reports this explicitly.

### 5.10 Built-in functions

The compiler exposes categories:

* Math: `abs`, `min`, `max`, `clamp`, `lerp`, `floor`, `ceil`, `round`, `mod`, `sqrt`, `pow`, `exp`, `log`.
* Trigonometry: `sin`, `cos`, `tan`, `asin`, `acos`, `atan`, `atan2`, `degToRad`, `radToDeg`.
* Vector: `dot`, `cross`, `length`, `normalize`, `distance`, `lerp`, `component`, `setX`, `setY`, `setZ`.
* Easing: `smoothstep`, `smootherstep`, `easeIn`, `easeOut`, `easeInOut`, `bias`, `gain`.
* Surface: `surfaceHit(origin, direction)`, `surfaceNormal`, `surfaceHeight`, `surfaceUVW`, `surfaceMaterialID`. These read immutable S0 snapshot services and return a documented miss value.
* Geometry: `randomGeom`, `geomCount`, `geomBounds`, `geomRadius`.
* Maps and curves: `evaluateTexture(parameter, uvw)`, `evaluateCurve(parameter, x)`, `insideSpline(object, point)`, `distanceSpline(object, point)`, `nearestPosSpline(object, point)`, `nearestTangSpline(object, point)`.
* Random: `randomReal(a,b,purpose)`, `randomInt(a,b,purpose)`.

`randomReal` and `randomInt` are pure functions of object seed, StableKey, effect program ID, call-site ID, and the caller's purpose token. The VM does not maintain mutable random state. Repeating an instruction gives the same value; changing thread count cannot change results. A call-site ID is emitted by the compiler so adding an unrelated random call does not shift all later values. If a user wants a new random field, they should name a purpose such as `"leafTilt"`; the compiler hashes the string into the purpose namespace.

Surface and spline functions never call Max on worker threads. S0 supplies acceleration handles or baked samplers. A missing object parameter returns a typed invalid result, sets the item diagnostic bit, and follows the configured error policy.

### 5.11 Compiler and VM

Compilation proceeds through lexing, parsing, name resolution, type checking, constant folding, attribute binding, register allocation, and bytecode emission. Registers are typed and allocated per basic block. The compiler stores source spans on instructions so an execution error can identify the exact expression. Bytecode is immutable after publication.

Execution batches rows in SoA chunks, ideally 4K to 32K items. Each instruction operates on register arrays, with masks for inactive or hidden rows. Vector built-ins use SIMD where available, while scalar fallback is required for unsupported types. The batch evaluator does not branch on individual item errors unless a safe mask can be formed. Division by zero yields a diagnostic and a policy-defined zero or previous value.

```cpp
void runEffect(const RegisterBytecode& bc, PopulationChunk chunk, VMContext& ctx) {
  Registers r(bc.registerCount, chunk.count);
  ExecMask active = chunk.aliveMask();
  for (const Instruction& ins : bc.code) {
    if (active.none()) break;
    executeSIMD(ins, r, active, ctx); // no Max calls, deterministic lanes
    if (ins.op == OpCode::Print && ctx.firstChunk) ctx.diag.printFirst(r[ins.a]);
  }
  commitWritableBindings(bc.bindings, r, chunk, active);
}
```

To preserve stacked-effect semantics, commit each effect's writes before executing the next effect. A later effect reads the prior effect's writes. The order is list order, top to bottom in the UI, and is recorded in the snapshot. Errors are per program with line, column, expected type, actual type, and a short source excerpt. A program with compile errors is disabled and cannot partially mutate the Population.

Sandboxing means no file IO, no network, no Max API, no dynamic code generation, no unbounded loops, no recursion, no allocation in the hot loop, and a configurable instruction budget. Loops are not in v1 grammar. A future bounded `repeat` must be statically bounded. Parameter objects expose values only, not node pointers. Texture and curve samplers are immutable handles.

### 5.12 Effects library and browser

An effect library file is versioned JSON or XML with `libraryVersion`, `pluginMinVersion`, `name`, `description`, `tags`, `source`, parameter declarations, and optional preview metadata. It must not embed absolute scene node paths as executable references. Object, controller, texture, and curve parameters are declared by name and bound on import. Imports are validated, compiled in a temporary sandbox, and only then added to the list. The browser shows compile status, required parameters, and compatibility warnings. Export can include source and compiled bytecode, but source remains the canonical representation and bytecode is invalidated on VM version changes.

## 6. Pipeline integration

S10 consumes Population fields from S1 through S9, all authored override and manual records, and compiled effects. It writes `pos`, `rot`, `scale`, `geomId`, `tintRGBA8`, `animSample`, and status flags. It uses no global mutable cache. Effect surface and map calls use `SharedCacheRegistry` handles created by S0. `D_OVERRIDES` restarts at S10. `D_MANUAL` restarts at S1 only when manual placement depends on a changed surface snapshot; otherwise it can restart at S10. `D_EFFECTS` restarts at S10. Geometry entry changes restart at S6 when source dimensions or collision radius changed, but an explicit model swap through an override can remain at S10 if the target source is already in the geometry table.

The stage is chunked and deterministic. Overrides are map lookups by key. Manual records are merged by ManualId order, and the final published order remains the canonical tile then key order from 00. Effects execute in chunks but have no cross-item state. `print` uses the first canonical item, not the first completed worker chunk. S10 sets `F_HIDDEN_USER` for user hides and `F_HIDDEN_EFFECT` for Effects visibility zero. It never clears `F_CULL_COLLISION` or other upstream cull flags.

Incremental re-evaluation must preserve the old published population until the new S12 result is complete. A transform gesture can publish an edit preview using a temporary population, but the committed state is the only state persisted or exposed to render. If an edit arrives during a background procedural build, queue it against the authored state, cancel stale preview, and rebuild from the latest snapshot.

### 7.3 FPInterface and MAXScript proposal

Cyrus publishes a versioned `FPInterface` with stable names, while also exposing a small set of MAXScript-friendly wrappers. The public API has two identity domains. A procedural snapshot item is addressed by `StableKey` plus `populationVersion`; a ManualItem is addressed by its persistent `ManualId`. An index is accepted only as a convenience for the current snapshot and is never serialized or silently resolved after a rebuild.

Proposed methods are:

Names are illustrative until verified against the SDK's function publishing conventions. Implement a strongly typed internal dispatch first, then publish it through `FPInterfaceDesc` and the appropriate `FUNCTION_MAP` or current SDK equivalent. Verify the exact declarations, parameter type descriptors, return-value conventions, interface IDs, and lifetime rules in the installed 3ds Max SDK headers. Do not invent a class name such as `FPInterfaceDesc` usage or assume a macro signature from a different Max release. The adapter must compile with warnings enabled and have a small `showinterfaces` smoke test that checks every published method by name.

Every mutating method accepts an optional batch token. If no token is open, the method creates one transaction and one `RestoreObj`. `beginBatch` records the current authored state and suppresses intermediate notifications. `endBatch(true)` computes one compact EditDelta, calls `theHold.Accept`, sends one dependency notification, and requests one rebuild. `endBatch(false)` restores the before state. A script exception or invalid item causes the batch to abort unless the caller explicitly requests best-effort mode. Best-effort mode returns per-item errors and still commits valid changes as one transaction.

`getItemSnapshot` returns a struct with `id`, `kind`, `populationVersion`, `position`, `rotationRadians`, `scale`, `geometryEntryId`, `geometryIndex`, `flags`, `tintRGBA8`, `userID`, surface provenance, area distances, and optional channel values. The output includes `space` and `rotationUnits` metadata. `getItemId(index)` returns a key only for the exact current population version; scripts should prefer IDs. `getItems` accepts IDs and returns results in caller order, with an error record for missing or stale IDs rather than shifting results.

`exportSnapshot` supports a channel array such as `#(key, position, rotation, scale, geomEntryId, geomID, normal, uvw, areaIncDistance, areaExcDistance, tintRGBA8, flags)`. It writes CSV, JSON, or a compact binary chosen by extension, plus a metadata object containing algorithm version, population version, seed, coordinate space, units, and channel types. The export is intentionally analogous to `ForestPack.exportData`, but stable IDs and explicit units are mandatory. Compatibility aliases include `trees.getPosition`, `trees.setPosition`, `trees.setRotation`, `trees.getSelected`, and `ForestPack.exportData` only when a user enables the compatibility interface. Aliases convert degrees to radians where needed, map old numeric geometry indices to current entryIds, and warn that index access is snapshot-scoped.

List management always uses `entryId` in the primary API. `getGeometryEntries` returns entryId, order, name, type, enabled state, color ID, probability, and source signature. `moveGeometryEntry` changes only UI order. `removeGeometryEntry` does not reuse the ID and reports affected overrides and ManualItems. Area APIs likewise distinguish immutable identity from ordered program position. Compatibility list properties may expose parallel arrays for legacy scripts, but writes are collected and validated as one transaction before applying to entry records. This avoids reproducing Forest's parallel-array corruption risk while still allowing migration scripts.

The interface is not allowed to call Max scene methods on worker threads. Scripting calls execute on the main thread, update authored state, and schedule asynchronous evaluation. Snapshot getters read the latest published immutable population. A script can request `waitForPopulation(version, timeoutMS)` on the main thread only when the caller explicitly accepts blocking; render callbacks must not block waiting for a script request. API errors use a stable code, message, item ID, and optional source span, so tools can handle them without parsing UI text.

### 7.4 Undo and restore

A gesture begins with `theHold.Begin()`. The Max-layer restore object captures an immutable before and after `EditDelta`, then `theHold.Accept("Cyrus Move Items")` commits. Cancel discards the preview. The exact use of `theHold` and restore callbacks must follow the target SDK's thread and notification rules.

```cpp
class CyrusEditRestore final : public RestoreObj {
public:
  EditDelta before, after;
  void Restore(int isUndo) override { owner->apply(isUndo ? before : after); }
  void Redo() override { owner->apply(after); }
  int Size() override { return sizeof(*this) + before.bytes() + after.bytes(); }
  TSTR Description() override { return TSTR(_T("Cyrus item edit")); }
};
```

`Size()` must report the actual owned vectors, strings, and record payload, not just `sizeof`. A gesture records one delta, even if the mouse generated hundreds of intermediate previews. A script batch records one restore object. A delete records hidden state or manual tombstone transitions. A Freeze command records created ManualItems and source visibility changes. A generator change and its resulting orphan transitions are one coherent transaction when initiated by one UI action.

When Restore or Redo changes authored records, mark the appropriate DirtyBits, publish no partial population, and send one `NotifyDependents` after state is coherent. Test nested holds and canceled transactions. The historical Forest bug where items disappeared during Custom Edit Undo/Redo is a direct reason for these tests [FP-DOC](https://forum.itoosoft.com/announcements/forest-pack-pro-6-0-1-beta/).

## 8. Persistence

Extend 00 section 11 with three versioned chunks:

```text
CYRS_OVERRIDES chunkVersion u32
  objectStableId u64
  recordCount u32
  sorted OverrideRecord records
CYRS_MANUAL chunkVersion u32
  nextManualId u64
  recordCount u32
  ManualItem records, including tombstones until compaction
CYRS_EFFECTS chunkVersion u32
  effectCount u32
  source and parameter declarations for each program
```

Records are length-prefixed and little endian with explicit field widths. Unknown fields are skipped by length. Save records sorted by key or ManualId for reproducible files. On load, validate finite numeric values, quaternion norms, entryId references, and chunk bounds. Invalid records become diagnostics and are not allowed to crash the object. Migrations must preserve old behavior where possible, but no old Forest Custom Edit file format is read in v1.

Override records may include the generator algorithm version that last observed them. This is diagnostic, not a reason to reject a record. If `algoVersion` changes and a key is absent, retain the record as an orphan. Do not attempt fuzzy spatial remapping automatically. A user can use an explicit **Remap orphan by nearest position** tool in a future version, which must create a new override and preserve the old one for undo.

Effect source is canonical. Compiled bytecode is a cache and may be discarded. Effect parameter object references are saved as Max references in the adapter plus stable parameter names in the chunk. Missing references produce a disabled parameter, not a null dereference.

## 9. Edge cases and failure modes

* A density or seed change can orphan many overrides. Show a count and preserve all records unless the user purges.
* A deleted geometry source makes a model override unresolved. Keep the item visible with its prior source only if that source snapshot is still available; otherwise hide it and show a missing-source badge. Never substitute silently.
* An effect writes a geometry index outside the list. Clamp is not acceptable. Report an error and retain the prior geometry.
* A manual item linked to a deleted surface becomes `SurfacePlaced` at its last valid FL transform and reports a broken link.
* A surface hit miss on a linked item does not move it to the origin. Keep its last valid position and mark link stale.
* A viewport selection from an old population version is discarded and must be retried.
* A zero scale from an effect is valid for hiding geometry but may invalidate bounds. Mark invisible if all components are zero and skip collision re-evaluation.
* NaN or infinity from an effect is rejected per field and retains the previous value.
* A user deletes the item selected by a pending drag. Cancel the drag and discard its restore object.
* Two attached objects contain the same name and type but different meshes. Use source signature to warn; never assume geometry equality.
* Reordering the geometry list does not change stored entryId references. Sequence mode intentionally changes future creation order because UI order is its definition.
* Effects `print` on a distributed batch reports the canonical first item once per program, not once per worker.
* An effect with expensive spline queries is bounded by the instruction budget and sampler cache.
* A script attempts to edit a generated item by index after a rebuild. Return a stale snapshot error and require a StableKey.

## 10. Performance targets

Targets are [DESIGN] and measured on the recorded-snapshot harness from 11. S10 override application should process 10M rows in under 250 ms on 16 cores when the override map is sparse. Manual merge should add under 50 ms per 100K records. Selection hit testing should return within 4 ms for a viewport query over 10M items when the spatial index is warm. A transform preview should update under 33 ms for 100K selected proxies; larger selections use point proxies until commit.

The Effects VM target is 10M rows with a simple three-instruction program in under 500 ms on 16 cores, with SIMD enabled. A map or spline lookup target is under 1 microsecond per item when the sampler cache is warm, but this depends on map complexity. Avoid per-item heap allocation, virtual dispatch, string lookup, or Max calls. Pre-resolve attributes to column IDs and cache parameter values in the snapshot.

Memory targets are under 32 bytes of override metadata before optional fields, under 96 bytes per manual item, and less than 2x the Population working set for a full Effects pass. Store orphan records compactly and avoid copying the entire Population for each effect. Checkpoint sharing from 00 remains the source of truth.
