## 2. Findings

| Priority | Finding | Location | Evidence |
| --- | --- | --- | --- |
| P1 | F1: A displaced previous-round blocker can keep a valid candidate rejected, even with unused retry allowance | `AminScatter/src/source_clearance.cpp:192`, `:250` | Fresh native probe; same missing placement with 2 and 16 allowed rounds; solver stops after 2 with no limit flag |
| P1 | F2: Preference on a source with no candidates can change another layer's output by selecting a different settlement schedule | `AminScatter/src/source_clearance.cpp:129` | Fresh native probe; later layer changes from one accepted placement to zero; only the unused source's preference flag changes |
| P2 | F3: Source-pair compilation is quadratic in source metadata and repeated for ranked solves | `AminScatter/src/source_clearance.cpp:125`, `:163` | Empty ten-layer probe: about 0.9 ms at 32 sources/layer, 12.5 ms at 128, 199 ms at 512; illustrative single-run timings |

The two P1 findings are separate: F1 incorrectly retains an old rejection within the ranked schedule; F2 unnecessarily changes schedules because an unused source influences schedule classification. Correcting only one does not establish the other case.

### F1 — Retest candidates whose remembered blocker is displaced

At line 192, admission defers a candidate whenever its stored blocker was kept in the previous round. That decision is made before this round's priority resolution. The stored blocker can then lose to a newly consumed preferred candidate, but the deferred candidate is not reconsidered. The late replay trigger at lines 250–254 handles disappearing blockers only after cleanup removal and under the dependent layer's retry permissions. It does not handle the displacement demonstrated here.

**Minimal native setup:** all placements have radius 1, factor 1, gap 0, so the pair threshold is 2. All lie on the X axis.

| Layer | Placement | Position | Relevant settings |
| --- | --- | --- | --- |
| A | A0 | 0 | Normal; candidate-budget population; same-layer spacing enabled |
| A | A1 | 1.5 | Normal; same source as A0 |
| P | P0 | 100 | Preferred source; accepted target 1; initially consumed candidate |
| P | P1 | -1.5 | Same preferred source; refill candidate |
| PIN | PIN0 | 100 | Protected Edit placement |

P requests clearance against all other layers. Layer P has an attempt limit of 2. The probe runs with a round allowance of 2 and then 16.

Round 1: protected PIN0 blocks P0; A0 is accepted; A0 blocks A1. Layer P extends its consumed prefix to include P1.

Round 2: admission skips A1 because A0 was previously kept. P1 is accepted and displaces A0. The final accepted set contains P1 and PIN0, but neither A0 nor A1.

**Expected:** A1 survives. It is distance 3 from accepted P1, above the threshold 2, and far from PIN0. Its old blocker A0 is no longer accepted. This is not a request for maximal packing of arbitrary holes: A1 is already a consumed, eligible candidate whose recorded rejection points to a rejected placement.

**Observed:** Layer A has no accepted rows. A1 still reports SelfSpacing. With 16 permitted rounds, the solver still stops at round 2 and `limitReached` is false. Increasing the artist's round limit therefore does not resolve this witness.

**Impact:** interacting layers can retain avoidable holes after preferred refill, and rejection reasons can refer to plants absent from the final result. This contradicts the intended accepted-blockers-only behavior.

**Suggested correction:** treat previous-round blockers as scheduling hints, not final occupancy. Before publication, resolve candidates deferred by a blocker that did not survive the current priority pass. Preserve Count admission, protected precedence, deterministic order and bounded work. Do not make this dependency correction depend solely on cleanup-removal flags or on enabling cleanup repair. Add this exact regression, including the 16-round case and reason/blocker validity checks, before changing the algorithm.

### F2 — Ignore absent sources when determining whether priority changes settlement

Lines 129–131 classify every pair of source policies, including rows with no placement candidates. The classifier marks a component changed when an effective rule is enabled and either source is preferred. That can route otherwise unchanged active placements through ranked acceptance, with cleanup timing different from inherited owner settlement.

**Minimal native setup:**

- Layer A contains one ordinary placement at X=0, radius 1. A also has an enrolled second source with no candidates.
- A's cleanup removes isolated placements: neighbor radius 1, minimum neighbors 1, minimum island 0.
- Layer B contains one ordinary placement at X=0, radius 1, without cleanup.
- The inherited A–B spacing rule is enabled with factor 1, gap 0, 3D metric.
- Both layers use candidate-budget mode with no cleanup repair.

With the unused source Normal, inherited settlement cleans A before processing B. A is empty and B contains its expected one placement.

Change **only** that unused source to Prefer. No candidate, transform, radius, target, quota or effective rule between actual placements changes. The classifier selects ranked settlement; A provisionally blocks B and is then cleaned. The published result has zero placements in B.

This is relevant to the host path: `validSources` in `unified-core.ms:1589` includes usable registered rows without filtering on weight, and `procClearanceSpecs` captures them. A zero-weight registered model can therefore have a policy but no generated rows. Protected rows must still count as participation if present.

**Impact:** editing a model that contributes no placements can change visible plants in another layer. It weakens the claim that preference acts only on actual clearance conflicts and makes zero-weight/inactive configuration hard to reason about.

**Suggested correction:** determine effective scheduling changes from sources represented in the admitted prepared candidate pool, including valid protected rows and authorized refill suffixes. Do not look only at the currently published subset or the initial consumed prefix, because future refill candidates still matter. A source absent from the entire prepared pool must not change priority scheduling. Preserve ordinary inherited settlement where the active rules and precedence are equivalent. Add both pure-native and zero-weight host witnesses with cleanup enabled.

### F3 — Bound or reuse metadata compilation

`clearanceComponents` loops over source pairs for every layer pair. Ten populations with 512 sources each cause approximately 14.4 million source-pair comparisons even when there are no placements. A ranked evaluation constructs another Context and performs another effective-source-pair traversal to size its grids.

The isolated probe with empty populations measured:

| Sources per layer | Ten-layer evaluation |
| --- | --- |
| 1 | 0.035 ms |
| 32 | 0.883 ms |
| 128 | 12.510 ms |
| 512 | 199.463 ms |

These are one-run native measurements on this machine, not host frame rates or release performance distributions. They establish the metadata scaling pattern; normal three-model scenes do not incur the maximum case.

**Suggested improvement:** compile and retain the validated rule snapshot once per policy/source-cohort revision, reuse it for component classification and broad-phase bounds, and avoid traversing absent sources when deriving effective runtime interactions. Track compilation time/work separately from neighbor visits. Use actual participating source/layer groups or equivalent bounded summaries before considering a more complex spatial structure.

## 5. Architecture and calculation quality

### Ownership and native boundary

The implementation correctly keeps layer population ownership. A source policy changes relationships and conflict precedence without creating a separate source population or Paint quota. Source-row IDs are distinct from native correspondence. The bridge checks the prepared cohort's population, source count and correspondence entries before constructing policy-aware samples. This is much better than interpreting current list positions as persisted identities.

The source ordinal is added to the acceptance Sample; the underlying 96-byte placement Record remains unchanged. Native transforms, radii and accepted views are retained rather than round-tripped into placement-sized MAXScript arrays. Policy metadata is bounded to 512 active sources per population, with authored sparse storage. Workers do not acquire live Max object pointers through the new solver.

These are appropriate extensions of the existing native foundation. A wholesale rewrite or generic graph framework is not justified by the defects found here.

### Rule semantics

Independent scope inheritance implements the earlier review correction. If both endpoints inherit the applicable scope, the existing layer/default pair rule applies. An explicit endpoint can request clearance, and another endpoint's Off is not a veto over that request.

The two-constraint representation supports both endpoint declarations. Same-metric constraints are merged only when one dominates the other in both factor and gap; crossing factor/gap constraints remain separate. This preserves the maximum evaluated threshold and avoids incorrectly adding gaps or independently maximizing factor/gap. XY and 3D predicates use their own radius metrics. Tangency remains permitted by strict-less-than comparison.

Protected edits reserve space first, and both protected conflicts can survive with conflict reporting. Ordinary candidates use explicit preference, then layer/set/candidate order. This matches the intended core hierarchy. The issues are in settlement/admission state, not the basic radius formula.

### Count and preference

The implementation chooses candidate-ordered admission before sorting admitted rows by preference. This directly prevents a distant preferred row from taking an already allocated Count slot. It also means Prefer is not an instruction to guarantee a particular source count or admit every future preferred candidate. Source lottery, candidate prefixes, coverage and attempt limits still matter.

The previous-blocker mechanism tries to avoid repeatedly admitting candidates already known to collide and to allow a later candidate to fill a shortfall. That optimization is where F1 occurs. The repair should preserve the useful separation between Count admission and clearance winners while validating current occupancy; simply returning to global priority-first Count allocation would reintroduce the earlier product problem.

### Bounds and recovery

Candidate/round/neighbor bounds remain, and native admission adds a conservative allowance for new coexistence/scratch. The report correctly distinguishes that allowance from actual measured allocation. Component acceptance is bounded and synchronous; no unsupported asynchronous-cancellation guarantee was introduced.

Current code still settles acceptance conservatively after a changed setup input key. Candidate preparation can be reused, but independent component results are not separately cached. That is a defensible first-delivery tradeoff if its Update cost is measured and described honestly. F3 identifies an avoidable metadata cost within that design.

The existing staged publication path remains in use, with prior complete results retained after a rejected successor. The new lifecycle host witness demonstrates invalid-input retention. Existing native publication suites provide additional coverage. This review did not inject a new install-tail failure into a live Max process; it does not upgrade those records into exhaustive new host fault acceptance.

## 6. UI quality and how it looks

**UI organization assessment: 8/10.** This is an assessment of the current layout specification/templates and existing recorded control/bounds tests, not a fresh visual screenshot rating.

The source panel now groups Radius mode, Radius, Follow Scale, Show Radius, three independent scopes, target layers and Conflict priority under **Radius and clearance**. That fits the artist action better than making the user interpret a layer-wide selector as a model-local control. Distance factor/gap/metric are kept behind **Clearance distance**. The target list appears only for Selected layers, and the default rule editor is labeled **Edit default rule / Other layer**.

Mixed selections explicitly display Mixed instead of pretending the first selected row represents all models. Edits write only the selected field. Binding guards suppress programmatic-control notifications while controls are filled, and the edit function captures the target/controller before rebinding. The recorded actual control-notification and Undo/Redo tests cover that behavior.

The Between layers repair replaces the nested lazy-rollout collect expression with bounded explicit peer/name loops. The baseline reproduction and final `CBN_SELENDOK` notifications are materially stronger evidence than a direct native call alone. The main-panel upgrade button/height is included in 100%/150% bounds evidence.

The remaining usability weakness is explainability. `clearanceSummary` mostly reports generic defaults/custom/missing-target text. It does not identify incoming requests that can still affect a source set to Off, or explain a concrete rejected plant. A lightweight cached effective-summary/witness would help artists understand why a source still avoids another model. This is a useful next improvement after correctness, not a reason to add a large relationship matrix.

Physical mixed-monitor behavior, actual spinner feel in heavy scenes and a fresh visual inspection were not performed in this review. Existing recorded layout tests cannot certify those interactions.

## 8. Test quality and remaining gaps

The existing native source-clearance test executable contains focused functions for scopes/protection, Count admission, effective-rule equivalence, cross-layer cleanup, invalid input, dormant distances/sparse stress and a 240-scene independent oracle. It is useful coverage, and it passed independently again.

The oracle is independently structured and enumerates blockers rather than reusing the production grid/compiler. However, its randomized scenes use candidate-budget, one-pass inputs. It does not set acceptedTarget/round/retry/cleanup state, and its comparison checks kept IDs rather than every rejection/conflict/replay transition. Thus it cannot catch F1. Its sources are ordinarily represented among the generated rows, and it has no cleanup schedule-transition witness for an absent preferred source, so it cannot catch F2.

The report's 100,000-row stress is a sparse two-source case. It does not qualify high source-count metadata compilation, dense mixed radii, million-row Max timings or all memory-history combinations. The delivery already discloses much of this limitation.

Required additions for the corrective change:

1. F1 with both 2 and 16 allowed rounds, checking the final surviving ID and that every stored rejection blocker still exists or is explicitly invalidated.
2. F2 with an absent source, plus a Max zero-weight source witness; include protected-only source participation and a source used only in an authorized refill suffix.
3. Stateful exhaustive cases with Count caps, prefix growth, preference changes between consumed rounds, cleanup removal, per-layer retry permissions and protected rows.
4. Full comparisons of kept IDs, conflicts, rejection reasons, attempts/shortfall, rounds and limit flags for those cases.
5. Equivalent effective-rule cases including no-op preference on unused sources and cross-layer cleanup.
6. Metadata compilation measurements at realistic and admitted extreme source counts, separately from placement/neighbor work.

Adding more randomized cases to the existing one-pass test alone will not cover the missing state dimensions. Extend the oracle's model rather than mirroring the current previous-blocker optimization.

## 11. Recommendation and next acceptance

Retain the overall design and source-local UI. Make one focused corrective change for F1/F2, led by the failing native probes. Preserve independent scope inheritance, candidate-ordered Count admission and explicit protected/source/layer precedence. Broaden the stateful oracle, then rerun the existing native/Python/generated checks.

Before a corrected user-testing delivery, exercise the two cases through the matched native/script path in an owned Max 2027 profile, recheck Manual/Live, cleanup/refill, zero-weight/protected sources, Undo/load and unrelated-layer behavior, then rebuild and reseal the exact installer pair. Choose any successor/correction label under the maintained version policy; this review does not assign or change a version.

The original scoped successes remain valid for their tested inputs. F1 and F2 remain open and no product fix is included in this review. No claim of complete artist/renderer/performance certification is made.
