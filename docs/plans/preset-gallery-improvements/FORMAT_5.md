# Revisioned recipe publication — format 5 contract

Implementation contract for PG03/PG04 in 0.85.1. Executed scope and limitations are recorded in [the progress ledger](PROGRESS_0851.md); this contract alone is not qualification. Complete recipe format/capability advances from 4 to 5. Scene schema 58, 242 authored setting fields and numeric-settings format 3 stay unchanged. Formats 1–4 retain strict read conversion; reading never rewrites a file. Original six example files remain frozen.

Format 5 adds `revision` (positive bounded integer) and nullable `presentation` to the existing complete recipe document. Presentation contains bounded category/tags/description, a hash/size-bound PNG attachment and optional capture provenance. The native catalog reads this embedded presentation without hydrating Paint. Earlier optional `.library.json` sidecars remain read-only input for older documents. A format-5 embedded record takes precedence; stale old metadata cannot label a new revision.

Save Copy creates a new logical recipe ID and revision 1. Update Existing preserves logical ID and increments revision; it takes the exact expected old manifest SHA-256 captured when the entry was reviewed. Rename/tags-only maintenance reads the stored document and immutable attachment descriptors without recapturing scene Paint or evaluating geometry. Bundled entries are read-only in the UI; copying goes to the writable user library.

The initial update contract is a local NTFS directory. It does not claim SMB/network or arbitrary filesystem atomicity. Cooperating Cyrus writers acquire an exclusive per-entry file lock, compare the expected hash, stage and verify all new Paint/image bytes under a uniquely owned directory, then replace the manifest once. Immutable payloads publish before the manifest switch. The previous complete manifest is retained as `.cyrus-previous-<manifest-sha256>.json` beside the public entry, so long artist filenames do not inflate its recovery name; its attachments remain intact. A failure before the switch retains the old entry; failure in optional cleanup after publication cannot roll back or delete the committed entry. Unexpected external edits found at the final comparison reject. This is not an OS-level compare-and-swap against unrelated applications that ignore the lock and write during the final replacement window.

All cleanup is limited to paths created by the current transaction. Stale lock handles close on process exit; immutable abandoned revision directories may be retained for explicit recovery. Never recursively clean a user folder or delete a PNG chosen as input. No scene Undo is created for file maintenance. Admission retains the existing manifest/Paint/image limits; staging storage and revision retention are reported separately from decoded gallery memory.

Explicit viewport capture uses the selected setup's existing publication. Save must verify the authored-content fingerprint still matches the captured state, with pending-state policy made visible. Capture records method, view and publication provenance and does not change the camera, selection, renderer or materials. Imported PNGs are marked as external images, not verified result captures. No ordinary browsing operation captures, renders or updates scatter.

Required witnesses: legacy strictness and format rejection; complete Paint round trips; Save Copy/Update/rename handlers; one atomic manifest switch; concurrent expected-hash rejection; staging and replacement failures; previous revision recovery; corrupt/stale preview handling; metadata-only zero scene work; capture ownership/pending edits; isolated Max 2027 lifecycle and exact-pair packaging. Consult the progress ledger for actual receipts and unresolved boundaries rather than inferring a pass from this list.

Library capability 3 extends entry summaries with verified thumbnail descriptors and logical revision. Catalog pages append a bounded collection page, total collection pages and collection count. Collection thumbnails refer to a representative existing recipe PNG; they do not render or hydrate Paint. The gallery and collection page are capped at 128 tiles; the tree exposes the first 128 collection names per library, while collection paging and All recipes retain access to the remainder.
