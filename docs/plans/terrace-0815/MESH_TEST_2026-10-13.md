# Mesh viewport investigation — 13 October 2026

**Result: cache reuse passes at an admitted load, but the full terrace Mesh
preview fails native memory admission and takes the CPU fallback. This scene
does not receive a clean Mesh performance pass.** No plugin implementation,
installation, source scene or artist profile was changed during this investigation.

The tested artist action was switching the nine-layer final terrace scene from
Point Cloud to Mesh, then navigating and selecting source rectangles. Expected:
the display representation changes while published placements remain stable;
warm navigation reuses source geometry, instance transforms and GPU buffers.
Relevant contracts: F04, F05, F06 and F08.

## Confirmed findings

The saved limits are 3,000 displayed instances and 2,000,000 faces **per layer**.
They produce 16,441,761 cached preview triangles across nine layers. These are
preview triangle counts; they are not a measurement of the user's reported
scene-wide edge count. All 245,664 accepted placements remain published.

Native publication reports:

> Retained preview unavailable; using the CPU preview. Refresh preview to retry.

The native generation has a fixed **512 MiB owner allowance** and the process
has a **1 GiB Mesh allowance**. Admission accounts for CPU snapshots, GPU buffers,
SDK system copies and upload scratch space. This is separate from the RTX 3090's
24 GiB physical VRAM. The successful individual-layer reservations alone total
937,988,472 bytes (894.5 MiB), excluding CPU snapshots and the woodland layer,
which was also rejected in this test process. Thus even this partial sum exceeds
the combined owner's allowance. Publishing all nine caches together is rejected.
The per-layer probe does not establish the woodland layer's isolated failure
cause because other reservations were still present.

The fallback loops over every displayed instance and every source triangle on
the CPU, computes shading and submits triangles through GraphicsWindow on each
redraw. Placement caching still works, but this path loses retained GPU
instancing. That is a concrete performance problem in the tested scene, beyond
the ordinary cost of drawing dense geometry.

| Face budget per layer | Cached preview triangles | Native admission |
| --- | ---: | --- |
| 2,000,000 — saved setting | 16,441,761 | Rejected; fallback reported |
| 1,000,000 | 7,500,025 | Rejected; fallback reported |
| 500,000 | 2,655,152 | Accepted; subsequently realized and drawn on GPU |
| 200,000 | 590,246 | Accepted at publication; no separate navigation qualification |

**Lowering the face budget is not a full-quality solution.** The code skips a
source when its whole mesh exceeds that layer's budget; it does not simplify it.
At 500,000, lavender, palms and framing-tree layers have zero preview triangles,
and other populations are sampled heavily. The accepted 2.66M-triangle preview
contains 133 instances. The rendered/published population is unaffected.

## Warm navigation and interaction results

The accepted run used a verified camera transform, a 1302 x 750 viewport,
Standard shading with Edged Faces enabled, and geometry degradation disabled.
Each arm ran 20 camera steps twice, reversing arm order on the second pass.
Representation changes, forced initial preparation and warmups were outside the
timed region. The captured Mesh image was inspected and contains visible plants.

| Display | Steps | Median step | 95th percentile |
| --- | ---: | ---: | ---: |
| Scatter preview off | 40 | 19.43 ms | 29.94 ms |
| Point Cloud | 40 | 20.29 ms | 40.97 ms |
| Proxy | 40 | 20.55 ms | 33.14 ms |
| Mesh, 500k faces per layer | 40 | 20.04 ms | 33.17 ms |

These are synchronous camera-change/redraw/message-processing times, **not
displayed FPS**. The host was private and hidden. PresentMon 2.6.0, scoped to its
PID, produced no presentation CSV. Other GPU applications were not controlled.
The small timing differences between these arms are not a reliable ranking.

All 48 navigation assertions passed: stable publication epochs, full placement
fingerprints, solver preparation counts, preview build counts, native generation
and preparation counters, uploaded buffers and failure counters. Native draw
counters advanced for every active display arm. There were zero additional CPU
fallback calls and zero Mesh reservation growth during the measured windows.

Seven additional checks passed at the admitted Mesh load: every current Mesh
group realized; selecting four source rectangles preserved caches and uploads;
a Manual Amount edit remained unpublished; restoring that amount preserved all
placement identities/transforms and the Mesh cache.

The initial full-load attempt was stopped after its redraw failed to return for
more than three minutes. Its camera capture also failed visibility validation,
so it supplies **no accepted FPS result**. An early navigation attempt retained
redraw suppression and showed artificial CPU fallback. That attempt and a
follow-up without clearing the suppression are excluded. The accepted successor
asserts redraw is enabled and checks native drawing/fallback counters explicitly.
This does not establish a separate product mode-switching defect.

The next implementation investigation should address combined Mesh memory
accounting/storage and the expensive fallback policy. Simply raising the cap is
not yet a qualified fix. Acceptance should reproduce the full nine-layer case,
keep useful plants visible, avoid the CPU triangle fallback during navigation,
preserve bounded memory and Manual publication, and measure actual presentation
in a visible host. No implementation or release change was authorized here.
