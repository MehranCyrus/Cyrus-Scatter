Cyrus Scatter — Independent External Engineering Research

Research date: 1 October 2026
Scope: Windows / 3ds Max 2026 and 2027; CPU scattering, host interaction, viewport graphics, optional GPU computation and production qualification.
Decision: Improve and measure the existing CPU/host workflow first. Investigate retained viewport rendering selectively. Do not authorize a GPU-compute backend, persistent executor or asynchronous rewrite without the gates below.

1. Decision brief: the five most consequential findings

1. “Faster scatter” is at least five different outcomes. Navigation without edits, edit-to-visible-result latency, a full rebuild, animation throughput and render preparation need separate baselines. A faster numeric loop may leave navigation unchanged; a faster redraw may leave edits unchanged. The most broadly applicable action is to identify which work repeats without any relevant data changing, and then remove or coalesce that work without losing invalidation. This is an engineering recommendation, not a diagnosis of the supplied project.

2. Retained viewport geometry and GPU instancing are credible, documented options—not a reason to rewrite everything. Autodesk exposes viewport instancing in both target SDKs. That is separate from render-time instancing. Shared source geometry is attractive when many placements truly share it; prepared CPU batches can remain the better long-term choice for small proxies, small populations or highly heterogeneous geometry. Select through experiment E02, not comparison with another product’s advertised FPS. S07S11

3. Preserve the placement contract before parallelizing or changing mathematics. Same density distribution is not the same seeded point set; same point set is not the same ordered source assignment. Prepared geometry and exact broad-phase rejection can preserve behavior, whereas a different sampler, relaxation schedule or random-stream scheme generally needs a versioned behavior change. Parallelize owned numeric work only after identifying the host-only boundary. Autodesk’s node/reference restrictions and explicit callback exceptions require a narrower design than “run the plugin on workers.” S01S25S50

4. GPU calculation has not earned a place in the production architecture yet. The first gate is an end-to-end cost model; the second is an extraction/copy/publication experiment that can reject offload without writing a real kernel. A useful graphics-instancing implementation does not prove GPU placement computation is useful, and an interoperability extension does not establish access to Max-owned resources. Actual benefit is unknown until measured. S38

5. Qualification and dependency discipline can matter more than the next speedup. Max 2027’s final SDK is explicitly incompatible with Max 2026. A compiling 2026 binary is not a tested 2026 product. Autodesk’s public USD integration also illustrates why dependency versions and loader paths need deliberate control. Require real target-host runs, loaded-module identity and physical 32 GB testing before expanding support claims. S13

Largest unknowns: the actual critical path; existing cache/invalidation quality; precise seeded-output contract; the native/scripted ownership boundary; current renderer adapters and their lifetime rules; peak memory across overlapping generations; source repetition/material partitioning; and performance under renderer contention. None can be established from external documentation.

4. Measurement: find the work artists are actually waiting for

4.1 Define operations before collecting numbers

Use a request/generation identifier to connect an artist action to the output eventually published and displayed. The following is a proposed instrumentation contract, not a claim about current project structure.

Operation Start and finish What to keep separate
Navigation, no edits A recorded camera gesture or controlled camera sequence to its displayed frames No placement rebuild should be presumed necessary; record any evaluation that nevertheless occurs.
Edit latency A parameter/source/mask change to first visible valid result for that generation Also record final-quality completion when a preview is intentionally different.
Full rebuild Explicit refresh request to completed placement result and publication CPU result-ready, host commit and GPU/display completion are distinct timestamps.
Animation Time change to usable state; sustained sequence throughput Source deformation, topology changes, controller evaluation and per-frame cache reuse.
Render preparation Render request to renderer-ready geometry/instances and first useful output Final rendering time and interactive restart/update time are separate.

Mark CPU spans for event scheduling, host evaluation, script/native conversion, geometry preparation, candidate generation, predicates/queries, transform construction, result compaction, publication and draw submission. Add counters for calls, candidates, accepted placements, displayed instances, unique source geometries, material partitions, actual triangles/points, uploaded bytes, allocations, cache hits/misses and invalidation reasons.

Do not turn every point into a logging event. Coarse spans plus aggregate counters usually answer the first question with less disturbance. Measure instrumented versus uninstrumented runs, and retain that overhead estimate. Use a monotonic clock and record units and timer origin. Thread IDs and generation IDs are essential for distinguishing duplicated callbacks from one long operation.

4.2 Amdahl’s law: a useful rejection test

For a serial critical-path operation, let fraction f be the part a proposal accelerates, s its speedup, and o its added overhead as a fraction of the original whole operation:

whole-operation speedup = 1 / [(1 − f) + f/s + o].

For f < 1, even infinite kernel speed cannot exceed 1/(1−f) when overhead is zero. If a kernel occupies 10% of an edit, accelerating it tenfold gives only about 1.10× overall. If it occupies 80%, a fourfold kernel gain gives 2.5×, before overhead. These are arithmetic examples, not measurements. A proposal that cannot beat the practical target even under an optimistic bound should stop before implementation.

For concurrent pipelines, use the measured dependency graph instead. CPU and GPU spans can overlap; adding all worker CPU time to all GPU time invents elapsed latency. In a simple two-stage steady pipeline, the slower occupied stage bounds throughput; queues, synchronization and dependencies can make actual latency substantially longer. Moving work off the main thread can improve responsiveness without shortening completion, while a deeper queue can improve throughput and worsen edit-to-visible latency. These are model deductions to test against traces.

A lower median is not sufficient for “buttery smooth.” Report median, p95, p99 only when the sample supports estimating it, and the raw distribution of hitch durations. Do not derive a stable p99 from a handful of actions. Separate shader/resource creation and initial extraction from warm navigation. Repeated frames within one gesture are correlated; use the gesture or trial as the resampling unit for uncertainty, not every frame as an independent experiment.

5. Mathematics and CPU algorithms: choose by workload and contract

Engineering assessment. The cost comparisons below are deductions about candidate designs, supported by the cited algorithms. They are not findings about current Cyrus code. The selection rule is always build/update cost plus queries over the actual reuse interval, not query time alone.

5.1 Freeze the behavioral contract

Before optimizing, establish what must match: ordered placement count and positions; source identity; random draws; transforms; layer ordering; rejection rules; boundary inclusion; density/falloff; and preview versus render populations. Record whether floating fields require exact bits or an already-approved tolerance. Distinguish four possible contracts: exact implementation replay, identical discrete decisions with bounded numeric error, statistically equivalent sampling, and deliberately approximate preview. This research does not grant permission to move between them.

A useful serial oracle should emit stable IDs and canonical numeric fields, not merely an image or hash of object memory containing padding. Sorting output before comparison can hide an order regression. A histogram can validate a distribution change but cannot validate seeded replay. Keep both the existing serial result and small analytically checkable fixtures; the existing result may contain bugs, but bug fixes must be separately approved rather than concealed as optimizations.

5.2 Sampling and density

For uniform world-surface sampling, select a triangle in proportion to its world-space area, then sample uniformly within it. With linear transform M and triangle edges e1,e2, that area is 0.5 × |(M e1) × (M e2)|. Nonuniform scaling does not generally multiply every triangle area by one common scalar. Exclude or handle zero-area/nonfinite triangles according to the established contract. Prepared weights must be invalidated by changes that alter their measure. PBRT provides the CDF and triangle-sampling foundations. S22

A linear weighted scan is a reasonable baseline for a few source types. A prepared cumulative distribution has linear storage/build and logarithmic binary-search selection. An alias table offers constant-time selection after linear preparation, but the extra structure is justified only with enough reuse. Switching methods can map the same random variate to a different source; zero weights, cumulative rounding and tie rules matter. Rebuilding a table for every point is worse than retaining a short scan. Measure total table maintenance plus selections. S23

For rejection sampling with acceptance probability a, obtaining N accepted candidates takes N/a proposals in expectation under the stated independent-trial assumptions. Low-density masks can therefore make proposal generation the actual cost. Record proposal-to-acceptance ratio and expensive mask evaluations. A spatially prepared density envelope or cell-weighted sampler is worth considering only when it preserves the intended measure and amortizes preparation. A discretized texture, signed-distance field or changed proposal process can alter positions and count. Treat those as explicit approximation/new-sampler options, not equivalent acceleration.

Moving an early rejection ahead of another stage is safe only if it does not change subsequent RNG consumption, errors or side effects. Keep existing random draws in their established order until the contract is known. Counter-based generators can derive keyed random values from stable candidate/channel counters without one shared evolving state; Random123 demonstrates that mechanism. It is useful for a newly versioned sampler, not an automatic replacement for current seeds. S29

The grid rule deserves precision. For radius r and cell width h, enumerate every cell intersecting the query’s conservative radius box, then use the original exact distance test. Do not assume “27 neighboring cells” for arbitrary radii or widths. Hash buckets must retain their full cell key so hash collisions cannot create false identity. Store occupied cells rather than allocating a dense array across enormous empty extents. Preserve candidate acceptance order: concurrently accepting mutually close candidates changes the result even with a perfect index. These are implementation requirements derived from the geometry, not guarantees from an API.

A prepared predicate has a simple break-even rule: if setup costs B, the old query costs q0, the new costs q1, and Q queries occur before invalidation, it helps only when B < Q(q0−q1), ignoring secondary costs. Apply the same rule to a BVH or source table. A threshold in candidate count alone is unreliable when complexity per candidate varies dramatically.

Bridson’s method uses an active list and a background grid; its linear-time argument assumes fixed dimension and candidate budget. The grid cell bound is tied to minimum spacing. Surface constraints, holes, strongly variable radii, geodesic distance and prescribed counts require additional decisions. Its usual candidate budget is not a quality guarantee for this product. A safer first optimization for an existing ordered dart-rejection method is an exact neighborhood accelerator around that same method. S25

5.4 Geometry traps that can invalidate an apparent speedup

A tree whose broad phase misses even one possible conflict is incorrect. Bounds must be conservative after transforms, including source extents—not just placement centers. For proximity, spheres or boxes are broad-phase tests unless that is the artist’s actual collision contract. Mesh intersection, minimum distance and non-overlap of proxy bounds are different questions.

For boundary containment, explicitly record whether holes use even-odd or winding rules, whether boundary points count as inside, what happens with self-intersection/open loops, and how zero-length segments are treated. GEOS distinguishes contains and covers; borrowing an index does not decide which semantics are correct for Cyrus. Adaptive exact orientation predicates can resolve near-collinear sign decisions, but do not establish a user-facing distance tolerance or repair invalid contours. S28

Extreme coordinates can lose low-order detail, overflow squared distances or overflow integer grid coordinates. Consider computing owned geometry in a local frame and using wider intermediates where needed, while checking whether this changes the accepted numeric contract. Compare points exactly on an edge, just inside/outside, coincident points and nearly zero-length features. An arbitrary larger epsilon is not an optimization.

For closest-point queries, transforming the query into a nonuniformly scaled source and minimizing ordinary local Euclidean distance can select the wrong world-space nearest point. Either evaluate distances in world space or use the correctly transformed metric. Ray direction normalization similarly changes the parameter’s distance interpretation. Establish these conventions before sharing a query cache between differently transformed sources.

For a nonsingular linear transform and column-vector notation, a normal transforms by M⁻ᵀ, followed by normalization. A reflection reverses handedness; transformed edge cross-products additionally carry the determinant sign. Apply the host’s winding/front-face convention deliberately rather than blindly applying both flips. Singular transforms need an explicit error/fallback policy. Port the mathematics to Max’s actual matrix convention, not by copying this notation literally. S30

5.5 Layout, allocation, SIMD and floating-point behavior

First remove repeated conversion, unnecessary geometry copies and temporary allocation. Use owned contiguous numeric arrays for measured hot loops; reserve output capacity when a safe estimate exists; reuse scratch space within a bounded lifetime. Structure-of-arrays can help a loop reading only positions, but converting the whole pipeline to it may cost more than it saves when each placement needs all fields. Compare bytes moved and total conversion-plus-kernel time. Avoid a second permanent representation simply because it is vectorizable.

Keep compiler vectorization as the first SIMD candidate; inspect generated code or vectorization diagnostics for the measured loop. Explicit SIMD is justified only after demonstrating a remaining hot arithmetic path, and needs a supported instruction baseline or dispatch. No AVX2-only baseline is established by this report.

MSVC’s /fp:fast allows transformations that change rounding and special-value behavior; contraction defaults also depend on compiler/settings. Consequently, changing flags, reassociating reductions or introducing fused operations can flip decisions near spacing/mask thresholds. Keep stable reduction order and existing flags while validating a performance-only change. Cross-device bitwise equality for an entire geometry pipeline is not a credible default promise without narrowly controlled operations; it may require retaining a CPU authoritative path. An alternative contract—identical integer IDs and discrete decisions, explicitly bounded floating error, and serial rechecking of ambiguous decisions—requires owner approval and measurement of fallback frequency. S32

6. Safe concurrency and interaction

6.1 The boundary is more important than the scheduler

The safe default is permitted-thread host evaluation, owned immutable numeric computation, and permitted-thread publication. A lock around a node-evaluation call does not establish that the call may occur on that worker. A raw pointer to a mesh owned by a node or MAXScript object is not an owned snapshot. Node/reference operations, notifications, graphics resources, UI and renderer access must each have their own API/lifetime justification. S01S03

Do not overstate this as “Max has no threaded callbacks.” The 2027 Deformer::Map const and MapNormal const methods explicitly require thread safety. The general guide also identifies threaded rendering callbacks. These exceptions make the rule follow the specific interface contract, not “all Max APIs are forbidden” or “all geometry APIs are safe.” S50

6.2 Serial versus bounded synchronous ranges versus a persistent executor

Choice Simplest credible use Main loss conditions / adoption gate
Optimized serial Small inputs; host-dominated work; strict ordered stages Retain unless a measured independent numeric region dominates. No startup or inter-worker merge cost.
Bounded synchronous ranges A substantial owned array with independent outputs; join before returning Snapshot/start/join/merge costs, load imbalance, cache contention and renderer competition can exceed saved work. Sweep task size and participant count.
Persistent executor Repeated sufficiently expensive numeric tasks where startup is a measured cost Adds teardown, reentrancy and scheduling policy; persistent does not automatically mean asynchronous. Stop if startup is immaterial.
Asynchronous editing Long computations that remain long after coalescing/optimization and demonstrably block useful interaction Adds stale-result handling, multi-generation memory, cancellation and Undo/scene lifecycle complexity. Requires a separate acceptance case.

Use the calling thread as a participant when appropriate rather than leaving it blocked while creating another worker. Preallocate disjoint output slots and compact in original candidate order. Retain serial random generation or another verified replay mechanism. An order-dependent spacing pass should not be parallelized merely by locking its output vector; that can alter accepted order while serializing much of the cost anyway.

Choose grain size using total useful work per chunk, not a magical point count. Compare a small range of bounded participation levels, including one, on the target machine and under render load. Higher CPU utilization can accompany worse latency when additional threads contend for memory, oversubscribe the renderer or delay the UI. For heterogeneous cores and NUMA systems, first use reasonable OS scheduling and measure outliers/locality. oneTBB exposes arena concurrency/core/NUMA controls but explicitly warns about composability; such controls are options, not mandatory architecture. S43

Standard execution-policy algorithms are not a turnkey host-aware scheduler: the draft specifies termination when an element-access function escapes by exception under standard policies. Do not assume ordinary catch-and-report semantics around a parallel call. With explicit ranges, catch worker failures, request cancellation, join every worker, and publish nothing partial. oneTBB provides exception/cancellation propagation, but canceled work can still leave incomplete output. The application retains responsibility for the commit boundary. S45

6.3 Prefer coalescing before asynchronous publication

The simplest interaction change is often to retain all dirty flags while coalescing duplicate requests into one refresh at a known safe boundary. A camera movement should not invalidate source topology. Conversely, a held-input optimization must not forget an edit that needs a final refresh after release. Manual mode needs its own state transition: do not turn a deferred redraw into an unauthorized rebuild.

A proposed cache contract records the value’s inputs, invalidation events, owner, readers, memory cap and destruction thread. Useful separate generations might include source geometry, source transforms, masks, placement parameters, display representation and view state. These are conceptual domains, not a demand to create six caches. Keep a single simpler cache if profiling and invalidation requirements do not justify splitting it.

Only if asynchronous computation earns its complexity should the following model be tried. This is pseudocode, not an Autodesk API recipe:

on relevant change, on the permitted host thread:
    advance request generation; retain all dirty reasons
    invalidate any result that would no longer be valid
    coalesce pending requests; enforce bounded queue/memory
    copy a validated, owned snapshot with scene epoch and stable identities

in numeric computation:
    read only the snapshot; write only owned result memory
    periodically check cancellation; never publish partial arrays
    capture errors; complete or cancel through one completion path

on a verified permitted-thread completion path:
    reject if shutting down, canceled, or scene epoch/generation differs
    revalidate target existence, time and relevant identity/version tokens
    atomically replace the completed result; request appropriate display update
    release old resources only after every permitted reader has finished

A generation counter alone is insufficient if a scene reset reuses IDs, source data changes without invalidation or a completed result contains dangling resources. Undo/Redo must either restore a valid matching generation or request recomputation. Node deletion, scene load/reset/merge, clone and shutdown must cancel or invalidate pending work. Cancellation must be cooperative inside the numeric work, not an unsafe forced thread stop. Workers must not outlive plugin code during unload; do not detach them as a shutdown shortcut.

Budget active snapshot + pending snapshot + result + old visible result + temporary indices + GPU resources, including allocator high-water marks. A bounded “one active, one latest pending” policy is a possible first design, not a proven optimal queue. If snapshot extraction or publication remains the dominant main-thread stall, asynchronous kernels alone have failed the premise.

7. Viewport architecture: retain the right work, not the wrong representation

7.1 Three architectures worth distinguishing

Engineering model. Immediate submission, retained expanded geometry and retained instanced geometry answer different questions. A retained implementation can reduce repeated upload/submission preparation without using instancing. Instancing can additionally avoid expanding each copy’s vertices. Test those effects separately; otherwise a faster prototype does not tell you which mechanism paid for itself.

For N copies of a source containing V vertices, expanded geometry has storage/work terms proportional to N×V; shared-source instancing instead has terms proportional to source geometry plus N instance records. This does not eliminate GPU vertex/shading work for visible copies. With many unique sources, incompatible materials or instance-specific topology, sharing shrinks. Source extraction, grouping and additional draw partitions can dominate small populations.

An illustration: assume, purely for arithmetic, one source with 10,000 vertices, 10,000 copies, a 32-byte vertex payload and a 64-byte instance payload. Expanded vertex payload alone is 3.2 GB; source vertices plus instance records are 960,000 bytes. These omit indices, materials, textures, bounds, renderer data, staging and duplicate CPU/GPU copies. They are not Max allocation sizes or a prediction of total memory. At the opposite extreme, expanding a handful of tiny pyramid proxies may be acceptably small and simpler than a new renderer.

Default recommendation: preserve the current correct display path as a fallback. Investigate retained resources when traces show repeat geometry preparation/upload/submission. Investigate instancing when repetition makes expanded geometry expensive. Do not count a reduced displayed population, lower resolution or changed shading as a like-for-like architecture speedup.

7.2 Documented APIs and integration constraints

The relevant class is MaxSDK::Graphics::ViewportInstancing::InstanceDisplayGeometry. The namespace documentation requires creation before update; updates cannot change instance count, introduce absent instance-data fields or change source vertex count. Recreate the relevant representation when those constraints are crossed. High Quality mode requires the documented position/normal/map/tangent/bitangent streams, including four mapping-stream entries; the module links optimesh.lib. These statements were checked in both 2026 and 2027 documentation. S07

Use the matching installed SDK’s class and samples to establish exact ownership and lifetime; do not assume input arrays remain borrowed or become copied without checking. The instance-data structure distinguishes world-space transformations from node-relative interpretation. It also permits specific per-instance UVW values, but these are constant across source vertices for the given channel, not arbitrary per-vertex remapping. S09

For retained mesh display, the documented preparation/get-items order matters. Returned IMeshDisplay2 geometry handles may be cached and shared: modifying them directly can affect other nodes, so follow the documented clone/decorator approach. Custom render items must be self-contained because Nitrous may realize/display them separately from object evaluation; an item reaching back into a mutable script object is not an acceptable shortcut. IObjectDisplay2 has per-node and per-view paths; per-view work must not silently multiply expensive preparation across all viewports. S04S06

Whether the current hybrid plugin has an appropriate native object that can expose these interfaces is unknown. Do not assume the bridge can acquire retained rendering through a MAXScript switch. A minimal native display adapter may be enough; replacing UI, placement generation and scene persistence is not justified by display work alone.

7.4 Proxy, point, full-mesh and sprite tradeoffs

Tiny geometric proxies preserve approximate orientation and extent at low source complexity. Points minimize shape information and are useful for distribution editing, but they do not validate source overlap or silhouettes. Full meshes preserve more appearance but increase source processing and GPU work. Camera-facing sprites trade geometry for textured screen coverage and can suffer overdraw; they are not an equivalent substitute for tree silhouettes, occlusion or close inspection. tyFlow’s grain documentation describes sprites as a display alternative when large grain populations remain expensive. S20

A display budget should specify its unit: instance count, triangle count, screen coverage or another explicit measure. A stable ID-based subset is a proposed way to reduce popping compared with a new random subset every redraw. LOD transitions and culling are quality policies and need visual approval. Keep render population independent from viewport population. Camera-only clipping cannot be assumed safe for final reflections, shadows or indirect visibility. S21

CPU preparation/batching can remain the final solution when it meets the artist’s latency target, has bounded memory and behaves correctly under updates. Keeping it is not an interim failure. Conversely, an attractive static instancing demo is insufficient if count changes or deforming sources continually force expensive recreation.

8. Renderer interfaces and documented production case studies

8.1 Renderer integration is a separate contract

Autodesk’s render-time interface groups shared RenderInstanceSource data and per-instance RenderInstanceTarget data under RenderTimeInstancingInterface; the documentation names the RenderTimeInstancedObject sample. Its benefit explicitly depends on a renderer consuming the interface. Neither those names nor Nitrous support establish Corona/V-Ray compatibility for final rendering, interactive rendering, motion blur, proxies or every override. S11

For the actual renderer adapter, inspect whether it supplies shared geometry or an expanded mesh, when it evaluates sources, how it exposes transforms across shutter times, who owns returned data, and when it becomes safe to release that data. A render-start preparation timer must include any expansion, conversion and synchronization. Releasing resources immediately after requesting renderer stop is unsafe as a general assumption: the 2027 Renderer::StopRendering contract is main-thread, asynchronous and nonblocking. S49

Verification limit: this pass did not establish current, complete Corona/V-Ray third-party SDK contracts or a tested host/version/mode matrix. Some Chaos documentation pages returned no readable body. The local engineer must obtain the applicable installed SDK/vendor documentation and confirm actual interface consumption. Do not substitute V-Ray AppSDK documentation for the 3ds Max plugin adapter API.

8.2 Case study: tyCache separates representations—and exposes costs

The tyCache manual documents Nitrous GPU instancing without generating/combining per-particle display meshes. A consequence is that mesh modifiers on the tyCache object do not affect that instanced viewport representation. It also warns that particle UVW overrides can force an expanded mesh; ignoring them improves sharing but changes displayed mapping. Its render controls separately describe instances, an I_VRAYGEOMETRY option and pre/post-render refresh. These are documented product behaviors, not evidence of proprietary implementation details or a Cyrus performance multiplier. S19

Transfer: use a feature compatibility table rather than forcing every appearance through one path. A fallback that preserves mapping is more honest than silently ignoring it. The tyFlow Display operator’s warning is useful corroboration within the same vendor, not independent confirmation. Autodesk’s limited constant-per-instance UVW data means the broad statement “Nitrous supports no UVW overrides” should not be adopted as a universal SDK fact. S18

8.3 Case study: Chaos Scatter warns against simplistic memory assumptions

Chaos’s November 2025 troubleshooting guidance explains that instances still have overhead, that retaining LOD variants can increase memory, and that grass clumps reduce instance count compared with individual blades. Its camera-clipping warning includes missing reflections or shadows. Those are useful workload and correctness lessons. Its examples do not establish like-for-like performance because representations/populations change. S21

Transfer: log unique geometry, instance records and all resident variants separately. Asset-design changes may be worthwhile artist options, but must not be presented as an implementation speedup with unchanged content. A lower viewport triangle count can coexist with higher total RAM.

8.4 Case study: Autodesk’s USD plugin demonstrates dependency discipline

Autodesk’s public build document maps Max 2026 to USD 24.11 and Max 2027 to USD 25.11, with tbb2020.3 in both corresponding dependency columns. It warns about stale library locations in PATH/PYTHONPATH. The moving branch is not a pinned source snapshot, but the mechanism is clear: dependencies are selected deliberately for an integration, not casually replaced with the latest runtime. S17

Transfer: enumerate what Max and installed renderers actually load before adding a scheduler. This does not mean Cyrus should link the USD plugin’s TBB or copy its entire dependency stack. It means a new runtime needs a coexistence and packaging case.

9. GPU computation: conditional defer, with a cheap way to disprove it

9.1 Which kernels are plausible?

Engineering assessment. Independent transform construction and simple mask arithmetic are regular but may be too cheap per byte to justify offload. Large batches of read-only ray/closest-point queries may have more work per result, but traversal divergence, data layout and acceleration-structure updates matter. A dense sampled distance field can make queries regular but adds resolution error and memory. Order-dependent spacing, sequential acceptance and iterative relaxation are poor first candidates when exact replay is required. Host node evaluation and arbitrary material/controller sampling are not made GPU-ready merely by choosing a compute API.

Rank candidates by measured share of the full artist operation, input/output bytes, update rate, numerical requirements and how long prepared data can remain valid. A CPU bottleneck does not automatically imply a GPU-suitable bottleneck.

9.2 Transfer-inclusive model

For a one-off operation with no demonstrated overlap, model:

T_offload = extraction + marshalling + allocation + upload + dispatch + kernel + synchronization + readback + publication.

Compare that with the best verified CPU baseline for the same work, including its preparation and publication. Persistent device data can amortize allocation/upload across repeated operations only when it is valid across those operations. For repeated valid input, divide one-time costs over the measured reuse count; when masks/topology change, charge the rebuild again.

If the CPU costs A_cpu + N×c and the offload path costs A_gpu + N×g, a large-population GPU crossover from a CPU advantage requires c > g; then the simplified threshold is (A_gpu−A_cpu)/(c−g). If the fixed GPU cost is already lower, it may win from the start; if its per-item cost is higher, it can instead lose as population grows. Real geometry queries need not be linear, so fit only within a regime the observations support. Here A, c, g and the useful population range are unknown. There is no evidence-based universal “GPU wins above X points” number.

NVIDIA’s guide emphasizes minimizing host/device transfers, limited pinned-memory use and the conditions for overlap. Copy and compute times may overlap only when the actual dependencies, queues and memory support it; do not subtract both from a one-off latency total because the API is asynchronous. GPU event timing measures a device interval, not extraction or host publication. S38

A theoretical bus bandwidth is not achieved transfer bandwidth. Measure the actual payload, pinned/pageable choice, copy direction and contention on the qualification machine. Record CPU staging memory, device allocations and transient duplication. Shared integrated memory is not proof that synchronization or copies disappear.

9.3 Backend shortlist—not a multi-backend proposal

Backend When it deserves an experiment Main reason not to adopt now
CPU serial / bounded CPU Default for all qualified machines; minimal data movement Can still lose on a demonstrated large numeric workload; measure rather than assume.
CUDA Optional NVIDIA-specific experiment when the workload and user fleet justify it; Windows guide 13.4 lists supported MSVC families NVIDIA-only deployment, driver/runtime/compiler qualification, GPU contention and transfer costs. No reason to require it for a CPU fallback user. S39
DirectCompute / D3D11 compute A plausible Windows graphics-oriented experiment with suitable feature support and owned resources Double precision is capability-dependent; an available compute API does not expose Nitrous-owned buffers/device. S41
OpenCL A cross-vendor experiment only after enumerating actual target devices, drivers and needed features Optional features and implementation/compiler variability; a version string is insufficient. The retrieved unified spec is v3.1.2, not the old 3.0 URL label. S40
SYCL Reconsider only when a chosen, supported Windows toolchain/backend solves a concrete maintenance need Adds compiler/backend/deployment questions before a workload is proven; specification portability is not deployment qualification. S42

For AMD and Intel machines, the initial supported calculation path should remain CPU unless a specific compute implementation is qualified. AMD’s retrieved Windows HIP SDK page is explicitly marked legacy, despite its latest URL and July 2026 date, and distinguishes support by GPU. It is not evidence that every Radeon supports the desired OpenCL/HIP configuration. Current cross-vendor driver/runtime coverage remains a named verification gap. S48

Khronos documents Direct3D sharing mechanisms, but this establishes an API mechanism—not Max permission, compatible buffer ownership or lifetime. Zero-copy Nitrous/renderer interoperability remains unverified. A standalone compute device with ordinary copies is the honest initial cost baseline. S40

9.4 Explicit decision

Defer a production GPU-compute subsystem. Run E03 only after E01 identifies a sufficiently large eligible numeric component. First time extraction, allocation/reuse, transfers and publication with a copy-only payload of the real size. If unavoidable overhead already consumes the maximum allowable offload budget, reject that design before writing the kernel. This rejects the tested transfer/lifetime architecture, not every conceivable persistent-GPU redesign.

The recommendation reverses if a small prototype meets the full-operation threshold under real update rates, 32 GB constraints, numerical parity and viewport/renderer contention, while retaining a usable CPU path. A fast kernel that stalls navigation, changes placements or doubles peak memory without budget is a failed proposal.

10. Ranked shortlist and explicit stop conditions

These are proposed decision gates, not measured facts. The full decision fields—including use case, evidence, simplest alternative, failure modes, experiment, confidence and reversal—are in decision_experiment_ledger.csv.

Rank / ID Status Recommendation Main falsifier
1 / D01 Broadly applicable now Instrument whole operations; identify redundant work; coalesce requests while preserving dirty state and Manual semantics No meaningful repeated work, or any lost update/stale display. Keep measurement even if optimization is rejected.
2 / D02 Investigate after local profiling Prepare/reuse predicates or add a small exact spatial accelerator around the existing serial algorithm Setup/invalidation cost, memory or small-scene regressions exceed savings; ordered output differs.
3 / D03 Investigate after local profiling Use bounded, joined numeric ranges only where independence and workload size are established Snapshot/start/join/merge cost dominates; host access leaks into workers; contention worsens artist latency.
4 / D04 Investigate after local profiling Compare retained expanded geometry and retained instancing with the best current CPU display path No submission/upload bottleneck; sharing too low; update recreation or feature incompatibility defeats gains.
5 / D05 Defer Add a persistent executor or asynchronous editing only when startup or long blocking work remains measurable after simpler changes Coalescing/serial optimization meets the need; snapshot/publication still dominates; lifecycle complexity is disproportionate.
6 / D06 Defer GPU compute, one backend only, only after E03 clears transfer and whole-operation gates Transfer-inclusive benefit or fidelity fails; unsupported deployment or unacceptable contention.

Do not build yet: a generic game-engine job system; multiple GPU backends; a universal geometry cache; a wholesale MAXScript/native rewrite; a GPU distance-field approximation presented as exact queries; a new random generator presented as seeded parity; an always-all-cores policy; and a dependency bundle justified only by popularity.

Reject as engineering claims: arbitrary Max scene evaluation on workers; GPU kernel timing presented as edit latency; fewer displayed objects presented as an equal-workload speedup; one high-memory workstation presented as 32 GB qualification; and broad host/renderer support asserted from a compiling DLL.

Proposed performance gates

Choose product budgets with the owner before measuring. For an initial decision, the following explicit defaults make the experiments falsifiable:

  • For a low-complexity CPU change, seek at least 15% lower median complete-operation latency, with a paired uncertainty interval excluding no improvement. A navigation architecture should instead target at least 20% lower p95 frame interval, or meet an agreed absolute frame budget. The reciprocal 16.67 ms corresponds to 60 FPS, but this is an example target, not a universal requirement or a guarantee of responsiveness.
  • Flag any representative small-workload median or p95 regression exceeding the larger of 5% or 1 ms. Such a guard deliberately tolerates timer-scale changes but prevents large-case averages from hiding noticeable regressions. Tighten it for workflows already close to a strict budget.
  • For a new GPU subsystem, require at least 25% lower median end-to-end latency in the intended eligible workload and a paired uncertainty interval excluding no improvement, with no unacceptable tail/interaction regression. This higher gate reflects larger support cost, not a law of GPU performance.

Any correctness mismatch, unauthorized host-thread call, use-after-free, unbounded growth, corrupt scene or broken fallback is a stop condition regardless of speed. These gates do not mean a 14% simple win must always be discarded: a changed acceptance decision must be written down before selecting favorable measurements. If confidence intervals straddle the practical margin, report “inconclusive,” not “faster.”

11. The three most informative local experiments

E01 — Where is the real edit/rebuild cost, and does CPU parallelism deserve expansion?

Decision distinguished: redundant host work versus numeric algorithm waste versus genuinely parallel compute. This is the first experiment; it can reject both a thread-pool proposal and GPU work without implementing either.

Input. Use one representative artist scene plus controlled fixtures: few simple sources; many repeated detailed sources; many unique sources/controllers; a complex closed boundary with holes; and a sparse density mask. Sweep from small to the largest memory-safe case. Candidate counts such as 1k/10k/100k/1m are possible pilot points, not mandatory product limits; select counts that bracket the observed crossover and record both generated and displayed populations.

Baseline. A verified current production/candidate build with exact loaded DLL/script hashes. Capture no-edit navigation, a representative mask/source/parameter edit, explicit rebuild, a short time sequence and render preparation separately. Record the seed, scene hash, unit scale, time and camera. Preserve the actual legacy/random contract.

Arms. First instrumentation only. Then choose one dominant numeric stage and compare existing serial code with either prepared/indexed serial code or bounded synchronous ranges. When both are plausible, compare optimized serial against the parallel version of that same optimized work. Do not compare an optimized threaded algorithm against an unnecessarily wasteful serial straw man. A safe no-op event-coalescing experiment can instead be the chosen change if duplicate evaluation dominates.

Controls. Identical output populations/representation; cold and warm regimes; explicit participant count; renderer idle versus controlled contention; matching caches; fixed instrumentation; randomized or reversed paired order. Disable adaptive degradation for the controlled viewport comparison, then test the real artist setting separately. Do not clear every cache between “warm” trials.

Measurements. Full-operation wall time, stage spans, per-thread CPU time, ready/wait intervals, call counts, proposals/acceptances, queries/primitive tests, allocations/bytes and peak private commit. Separately record first visible generation and final completion. Test scene reset and an exception/cancellation injection before accepting any worker change.

Correctness oracle. Exact ordered IDs, source assignments, counts and flags; existing numeric equivalence contract; brute-force checks on small adversarial geometry; no stale generation publication. A mismatch emits the first divergent row and its inputs, not only “hash failed.”

Raw output. One manifest; event timeline; one trial summary row per operation; canonical baseline/candidate output dumps or hashes plus first-difference records; profiler trace filenames; memory snapshots. See trace_schema.json for proposed fields.

Gate / stop. Apply D01/D02/D03 thresholds to the whole operation. Stop expanding concurrency when additional participants fail to improve the paired result or worsen tail/renderer contention. If extraction/publication dominates, do not conclude that a faster numeric framework will fix the edit. A flat or tiny numeric share also stops E03.

E02 — Is the next viewport gain batching, retained resources, instancing—or simply less work?

Decision distinguished: keep the current CPU path versus retained expanded geometry versus shared-source instancing. This is a controlled display adapter experiment, not a production rewrite.

Input. Feed the same immutable placement/source dataset into every arm. Include tiny proxies, one heavily repeated detailed mesh, a many-unique-source case, and material/color/UVW variation. Include static navigation and separate update cases: transform-only changes; count changes; source deformation; source topology/mapping changes. Test one and four viewports and Standard/High Quality styles. Begin with modest scenes that make correctness inspectable, then scale to the measured stress range.

Baseline and arms. A: best existing correct path, including its existing preparation/batching. B: retained expanded geometry. C: retained instancing for compatible groups with an explicit fallback. If A lacks straightforward CPU batching and that dominates, try that simpler control before B/C. B versus C separates residency from source sharing. Do not silently drop unsupported overrides in C.

Controls. Identical placements, displayed count, source topology, shading/materials, colors, viewport resolution, camera path and adaptive-degradation state. Record actual draw groups and uploaded bytes rather than assuming one draw per source. Disable random automatic display-percentage changes. Use fixed renderer-idle conditions first, then controlled interactive-render contention.

Measurements. CPU callback/preparation/submission spans; GPU/present timing where tooling is valid; actual displayed-frame intervals; cold creation and warm navigation; transform-update/count-recreation cost; hit-test latency; CPU private commit and device/staging allocation peaks. A faster synchronous redraw return alone is not the success metric. Isolate unrelated UI/renderer swapchains in presentation traces.

Correctness oracle. Compare prepared geometry/transforms/IDs and required attributes, conservative bounds and picking results. Use fixed-view image differences plus visual review for normal/material/UV/color fidelity. Pixel differences can arise between legitimate raster paths; they require explanation, not automatic dismissal. A population or appearance change invalidates an equal-workload claim. Run allocation failure, scene reset, node deletion and device/resource re-creation tests while old data could still be in use.

Raw output. Manifest; per-arm source/instance/triangle/group counts; camera sequence; trace and presentation CSV; per-update spans; images/difference images; picking assertions; peak/live resource log and disposal events.

Gate / stop. Require the navigation target without unacceptable edit/recreation regressions. Reject C for incompatible groups rather than weakening appearance. If B performs essentially as well as C within uncertainty and is materially simpler, keep B. If A already meets the target or both alternatives lose in realistic updates, keep A. Instancing is not compulsory because the API exists.

E03 — Can transfer-inclusive GPU offload beat a good CPU implementation?

Entry gate. E01 must identify a large independent numeric workload and enough potential whole-operation benefit. No eligible workload is a valid outcome: close D06 as deferred and do not write GPU code.

Decision distinguished: CPU retention versus a narrowly scoped GPU kernel, and one-shot data movement versus justified persistent data. This is not a requirement to implement every backend.

Input. Export a real owned snapshot from that hot stage, including input/output bytes and update frequency. Include small/large sets and difficult geometry/branching, not only a regular synthetic grid. Preserve precise flags, seeds and tolerance rules. The copied payload must represent the result actually needed by Max or the renderer.

Baseline. Best verified serial CPU and, where it wins, bounded CPU. Include the same extraction/publication costs in each full-operation total. Use the same accepted/queried population.

Phase 1: copy-only rejector. For one justified backend, allocate or reuse buffers under the intended lifetime; upload actual input-size data; execute a minimal dispatch; transfer the expected result-size data back; perform the real publication scaffolding. Record extraction, staging, each transfer, synchronization and total wall time. This is a lower-bound screen, not a simulation of a production kernel. Use a disposable fixture and known-valid placeholder output; never publish uncomputed values into an artist scene. Model persistent input only when the measured edit pattern permits it.

Phase 2: kernel, only after Phase 1 passes. Implement the single eligible numeric operation. Measure both device interval and end-to-end operation, with actual acceleration-structure preparation. Validate the result before publication. No renderer/Nitrous zero-copy credit is permitted without a documented ownership-compatible integration and a measured working prototype.

Controls. Warm/cold resources; ordinary artist edit rates; GPU idle, viewport-active and renderer-contention states; actual 32 GB system; device memory pressure; supported and unsupported-device CPU fallback. For a CUDA proof, NVIDIA-only scope is explicit. Other vendors need a later separate qualification, not an untested promise.

Correctness oracle. Ordered discrete decisions, source identity and declared numeric parity. Include near-boundary/radius cases, mirrored/nonuniform transforms and degenerate geometry. Record ambiguous-case CPU rechecks separately; frequent rechecks can erase the benefit. Fault/cancellation tests must leave the prior valid result or a clear error, not partial output.

Raw output. CPU baseline samples, bytes per stage, device/driver/compiler identity, allocations, copy/kernel/sync/publication timestamps, result differences, fallback outcomes, visible-latency/presentation trace during contention, peak CPU/VRAM memory.

Gate / stop. With target speedup R, reject a one-shot design when unavoidable offload overhead already exceeds T_CPU/R for that same operation, even with an ideal zero-time kernel. The proposed 25% latency reduction corresponds to R = 4/3, so that budget is 0.75 × T_CPU, not T_CPU/1.25. After Phase 2, use the higher D06 whole-operation threshold. Stop at the first failed correctness/deployment/lifetime gate. A kernel-only speedup is insufficient. A copy-only failure does not authorize an unplanned multi-backend/persistent-data rewrite to rescue the proposal.

Shared trial protocol

Run a short pilot to estimate variability and timer overhead. Choose repetitions based on the practical effect and uncertainty required, not an arbitrary “100 runs.” Use paired, reversed or randomized order and retain every raw sample, including outliers, failures and canceled trials. Report cold and warm results separately. For long gesture traces, use block/trial-level intervals rather than treating correlated frames as independent. Publish per-scene results; a pooled average must not hide small-scene regressions. When instrumentation cannot reliably identify a completed frame, label the timing boundary honestly and narrow the claim.

32 GB qualification concerns the whole working process and OS pressure, not merely a plugin cache counter. Record physical RAM and pagefile policy, process private commit/working set, hard-fault or paging evidence, renderer consumption and available memory. A 96 GB machine with a nominal cache cap does not recreate all pressure effects of the target workstation. Do not force dangerous system-wide exhaustion; inject recoverable allocation failures and scale workloads within a predeclared safety budget.

Peak memory needs more than a final snapshot. Count old/new generations, scratch arrays, host meshes, GPU staging, source variants, render-time conversion and retained device buffers. Allocation fallback that draws the same population more slowly may be correct; it must be visible in diagnostics so its latency is not mistaken for an unexplained regression. A fallback that silently drops instances requires an explicit artist-facing quality policy.

Packaging and dependencies

Keep SDK-facing types and allocation ownership within a documented ABI boundary. Verify allocator/CRT pairings; do not free memory through a different module’s allocator unless that interface explicitly permits it. Record import dependencies and loaded paths. Never replace Max’s or a renderer’s runtime DLLs globally to satisfy the plugin.

Adding oneTBB is optional. Its opened license is Apache 2.0; the precise distribution still requires bundled license/notice and component review. The CUDA agreement limits redistribution to specified portions under its terms; it is not permission to ship the entire SDK. These checks belong to release engineering before dependency adoption, alongside driver and compiler support. S46

Prefer an existing safe small-range implementation when it meets the need. A persistent scheduler needs an identified maintainer and coexistence tests, not just a package-manager entry. A new geometry library needs the same evaluation; the GEOS/nanoflann examples here establish mechanisms, not a decision to bundle them.

What a beta can honestly claim

A beta may state the exact hosts, builds, renderer modes, hardware classes and workflows actually tested, together with known limitations. It may report a controlled per-scene measured improvement with its populations and timing boundaries. It may not claim universal real-time behavior, general cross-vendor GPU support, Max 2026 runtime compatibility from a 2027 run, renderer support from viewport images, bitwise cross-device determinism without tests, or crash-free production reliability from short synthetic demos.

13. Focused Codex handoff and unresolved questions

The separate Codex_Handoff.md is ready to bring into the local project. It instructs the engineer to find real structures rather than inventing project paths or assuming this report describes the implementation.

Inspect first: all event/callback entry points and their invalidation chains; script/native conversions; source/mesh ownership; prepared query structures and their keys; RNG/acceptance ordering; parallel regions and error paths; display preparation/submission; per-view caches and picking; renderer adapters; generation/GC/resource teardown; installer/build identities and existing test evidence.

Do not adopt without evidence: a thread-count threshold, a spatial-index crossover, the assumption that current display expands geometry, the assumption that a native display adapter is already available, a renderer-interface ownership rule, a zero-copy GPU integration, or a changed floating/RNG contract. Reconcile each conclusion against current code and measured runs. Agreement between external and local reports is not proof.

14. Final recommendation and audit

The best next action is E01, followed by one small implementation selected by its result. E02 is the next architectural discriminator when viewport preparation/submission or expanded geometry is actually expensive. E03 remains gated; deciding not to add GPU computation is a successful outcome.

The second-pass audit narrowed several tempting conclusions: tyFlow’s UVW limitation is not a universal ban on all SDK per-instance UV data; instancing does not establish final-render compatibility; a new IDE does not settle the SDK toolchain; an OpenCL URL labelled 3.0 did not contain the retrieved spec version; an AMD URL labelled latest was marked legacy; and a copy-only model receives no unverified zero-copy credit. The audit also retained CPU batching as a legitimate endpoint and kept every numerical/quality change separate from strict-equivalence optimization.

This was a researcher’s self-audit, not independent verification. The deliverable is a decision and validation package—not a finding that the current plugin has any particular bottleneck, and not a certificate of production readiness.
