# 07 — Max 2027 interoperability: a concrete gate

[Contents](00_README.md) · [Deformation contract](06_GPU_DEFORMATION_AND_INSTANCING.md) · [Lifetime design](08_ASYNC_PUBLICATION_AND_LIFETIMES.md) · [Local probes](16_OPEN_QUESTIONS_FOR_LOCAL_CODEX.md)

**Decision — proposal.** Prototype CPU-produced compact guide poses consumed by a supported Nitrous HLSL vertex shader first. In parallel, probe the **documented Max 2027 native Direct3D 11 interface**. Direct CUDA/OpenCL sharing is a credible candidate, but neither the supplied project baseline nor this research qualifies a complete compute-to-retained-draw ownership path. Do not commission the full GPU contact solver on the assumption that such sharing already works.

**Evidence status.** Public 2027 API declarations and vendor interoperability rules were inspected on 27 October 2026. No installed Max SDK, Max host, Windows graphics device, CUDA execution or renderer test was available. All proofs below are **not executed**. Supplied descriptions of Cyrus's retained draw path are project facts, not observations made here.

Autodesk's 13 April 2026 release note describes removal of DX9 support and migration to DX11 equivalents. Old `ID3D9GraphicsWindow` recipes and Maya's `MRenderer::GPUDeviceHandle` examples are therefore not evidence for a Max 2027 solution. [M12](https://blog.autodesk.io/whats-new-in-3ds-max-2027/)

For capability discovery, the current public route includes `IDisplayManager::GetDeviceCaps(DeviceCaps&)`, with `DeviceCaps::FeatureLevel` (`Graphics/IDisplayManager.h`, `Graphics/DeviceCaps.h`). The older overview's `IVirtualDevice::FeatureLevel()` should not be assumed present in the current declaration. [M30](https://help.autodesk.com/cloudhelp/2027/ENU/MAXDEV-CPP-API-REF/class_max_s_d_k_1_1_graphics_1_1_i_display_manager.html), [M31](https://help.autodesk.com/cloudhelp/2027/ENU/MAXDEV-CPP-API-REF/struct_max_s_d_k_1_1_graphics_1_1_device_caps.html)

**Proposed read-binding order:** test a `VertexBufferHandle` initialized with documented buffer flags/data type, populated through `Lock/Unlock` or staging copy, then assigned by `SetBufferParameter`. If rejected, test a non-mipmapped float texture through `TextureHandle::Initialize`, rectangle upload and `SetTextureParameter`; use integer texel loads in the shader. For a tiny control only, use `SetFloat4ArrayParameter` or `SetMatrixArrayParameter`. D3D11 feature-level11 defines 4,096 16-byte constant-buffer elements (64 KiB), not an unlimited pose array. The hypothetical 451-guide × 8-sample × 32-byte pose already exceeds one such buffer before other uniforms. Batch or use buffer/texture lookup; do not promise a million-instance constant palette. HLSL effect packing and host-reserved bindings still require local inspection. [M06](https://help.autodesk.com/cloudhelp/2027/ENU/MAXDEV-CPP-API-REF/class_max_s_d_k_1_1_graphics_1_1_h_l_s_l_material_handle.html), [M32](https://learn.microsoft.com/en-us/windows/win32/direct3d11/overviews-direct3d-11-resources-limits)

## 2. The native-device probe: promising, not complete

The published interface macro is `D3D11_GRAPHICS_WINDOW_INTERFACE_ID`, `Interface_ID(0x155a3968, 0x14fa1b03)`. `ViewExp::getGW()` returns `GraphicsWindow*`, which inherits `InterfaceServer::GetInterface`. [M13](https://help.autodesk.com/cloudhelp/2027/ENU/MAXDEV-CPP-API-REF/id3d11graphicswindow_8h.html), [M14](https://help.autodesk.com/cloudhelp/2027/ENU/MAXDEV-CPP-API-REF/class_view_exp.html), [M15](https://help.autodesk.com/cloudhelp/2027/ENU/MAXDEV-CPP-API-REF/class_graphics_window.html)

**Proposed local probe, not compiled code:** in a documented current-viewport/callback scope, obtain that `GraphicsWindow`, query its public interface ID, record null/non-null, then read `GetDevice()` without changing state. Separately inspect the installed SDK's DX11 shader samples: the documented `IDX11VertexShader::ConfirmDevice/SetVertexShader` callbacks receive an `ID3D11GraphicsWindow*` directly. This is a typed acquisition route to investigate, not proof that Cyrus's custom render item gets the same device/context. [M16](https://help.autodesk.com/cloudhelp/2027/ENU/MAXDEV-CPP-API-REF/class_i_d_x11_vertex_shader.html)

The probe must answer four different questions:

1. **Device:** Is the returned device the adapter/device actually consuming this render item's resources across all viewports and graphics-device recreation?
2. **Resource:** Can Cyrus create and consume its own native buffer through a documented draw path, or publicly obtain/import an existing retained handle's native resource? `GetVertexBuffer(length,FVF)` has no retained-handle argument. Its existence does not establish an unwrapping operation. Do not register a borrowed engine buffer until ownership, reuse and destruction rules are resolved.
3. **Context:** Which callback permits command submission, and what state must be restored? D3D11 immediate-context access is not made safe merely by obtaining its pointer. Microsoft requires synchronization for shared context use. `GetImmediateContext` adds a COM reference that the caller releases; that rule does not establish the ownership of Max's `GetDevice` return. [M17](https://learn.microsoft.com/en-us/windows/win32/direct3d11/overviews-direct3d-11-render-multi-thread-intro), [M18](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11device-getimmediatecontext)
4. **Completion:** How can a successor become drawable only after compute writes finish, while the preceding generation remains readable? A native pointer alone supplies no retirement protocol.

**Stop criterion:** if these questions require private interfaces, unsupported downcasts, internal object layouts, taking over Max's immediate context, or unverifiable resource ownership, reject that direct-sharing path and use public uploads. A null query on one device is evidence about that configuration, not a universal assertion that the SDK lacks the interface.

## 3. Three interoperability mechanisms have different contracts

### Direct CUDA graphics registration

`cudaGraphicsD3D11RegisterResource` accepts supported native resources and increases their internal reference count until unregister. Registration can be expensive, so it belongs to allocation lifetime, not every drag event. Buffers and selected texture formats are accepted; the primary render target and depth/stencil surfaces are excluded. `cudaD3D11GetDevice(s)` identifies CUDA devices compatible with a D3D adapter/device. [M19](https://docs.nvidia.com/cuda/cuda-runtime-api/cuda_runtime_api/group__CUDART__D3D11.html)

The access protocol is register → map → obtain mapped pointer/array → bounded kernels → unmap → graphics consume → eventually unregister. No graphics or other-context access is allowed while mapped. Do not assume the mapped pointer survives the next mapping. This is **not** the same requirement as creating an OS-shared handle; direct registration does not universally require an external-memory sharing flag. [M20](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/graphics-interop.html)

### CUDA external memory and synchronization

A resource must be created as exportable, exported with the correct Windows handle type, then imported with matching allocation size/layout/type. Importing memory alone does not synchronize use. Explicit semaphore/fence or keyed-mutex handoff is separate. Imported mappings must be freed and outstanding waits/signals retired before their owners are destroyed. [M21](https://docs.nvidia.com/cuda/cuda-runtime-api/cuda_runtime_api/group__CUDART__EXTRES__INTEROP.html)

The current programming guide explicitly redirects D3D11 external-resource details to its archived **12.9** guide. That guide requires matching device LUIDs, `cudaExternalMemoryDedicated` for D3D11 resource imports, appropriate NT/KMT handle type and explicit Windows-handle ownership. It documents D3D11 fence and keyed-mutex synchronization. Treat this as a historical detailed recipe still referenced by current documentation, subject to the chosen toolkit's headers and runtime checks. [M22](https://docs.nvidia.com/cuda/archive/12.9.1/cuda-c-programming-guide/index.html#direct3d-11-interoperability)

Microsoft documents `D3D11_RESOURCE_MISC_SHARED_NTHANDLE` and `...SHARED_KEYEDMUTEX`, resource-format restrictions and mutually exclusive flag combinations. A generic “set SHARED” instruction is insufficient. [M23](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/ne-d3d11-d3d11_resource_misc_flag) Start with a plugin-owned test resource, never the host's swapchain. Choose **one** ownership mechanism per resource; do not mix registration and external-memory models casually. Bound waits and fail the job on timeout; an infinite sample wait is unsuitable inside an interactive host.

### OpenCL D3D11 sharing

`cl_khr_d3d11_sharing` defines device matching, buffer/texture creation from D3D11 resources, and acquire/release commands. Extension availability must be queried on the selected implementation. With `CL_CONTEXT_INTEROP_USER_SYNC` false, acquire/release provide specified cross-API ordering; with true, the caller supplies synchronization. Graphics access during OpenCL ownership is invalid. OpenCL does not avoid the missing Max resource/ownership bridge merely because sharing is standardized. [M24](https://registry.khronos.org/OpenCL/specs/unified/html/OpenCL_API.html#cl_khr_d3d11_sharing)

## 4. Adapter identity and multithreaded drawing

**Proposal.** Record display-device DXGI `AdapterLuid`, vendor/device IDs, CUDA UUID/LUID and ordinal, OpenCL platform/device identity and driver, and a **graphics-device epoch**. `DXGI_ADAPTER_DESC` provides the LUID and memory identity; matching names or assuming CUDA ordinal zero is insufficient. [M25](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/ns-dxgi-dxgi_adapter_desc)

| Configuration | Required decision |
|---|---|
| One NVIDIA GPU performs display/compute | Validate same device plus complete ownership protocol; this is the best direct-sharing candidate. |
| Two NVIDIA GPUs | Match the actual display device; do not select the faster GPU by ordinal and assume its allocation is drawable. Benchmark optional staged transfer separately. |
| Intel/AMD display, NVIDIA compute | Use compact CPU-mediated pose delivery unless a separately qualified cross-adapter route exists. Budget both readback and display upload. |
| Optimus/laptop or moved monitor | Re-check actual rendering device after configuration changes. The monitor's physical connector alone is insufficient evidence of render-device identity. |
| Remote/headless/software path | Discover capabilities at startup/activation and preserve CPU operation; no supported interop result is claimed here. |

Do not store `IVirtualDevice` across callbacks. Shared pose buffers may be immutable per generation, but command contexts remain callback-specific. `QueryHandle::GetData` reports readiness and optionally flushes commands; it is a documented graphics query API, **not** an external CUDA semaphore or a guaranteed portable asynchronous-publication mechanism. [M26](https://help.autodesk.com/cloudhelp/2027/ENU/MAXDEV-CPP-API-REF/class_max_s_d_k_1_1_graphics_1_1_query_handle.html)

## 5. Supported fallback and its actual cost

**Proposal.** CPU fitting → compact pose pack → public buffer/texture upload → HLSL shared-source deformation. This requires no CUDA/OpenCL runtime and no raw-resource access. It still needs the narrow shader/normal/bounds/picking proof. If GPU solving later wins, keep the same display path by reading compact poses to owned CPU staging memory, validating, then uploading through Max's handles. The CUDA device need not be the viewport adapter for that fallback.

**Analytical example, not timing:** assume eight pose samples per guide, 32 bytes/sample (position plus frame representation), 16 bytes guide-directory entry, and full changed-guide storage. The supplied 451-guide plant then costs `451 × (8×32+16) = 122,672 bytes` per unique fully changed pose, excluding visibility/status/alignment. Its 22,032 source vertices would need `22,032 × 40 = 881,280 bytes` for unique position/normal/tangent output alone. Sparse six-guide payload is `6×272 = 1,632 bytes` before packet overhead. The actual source sample counts are unknown; eight is an explicit design assumption.

| Workload | Compact pose one-way | Full vertex output one-way | Same payload readback then upload |
|---|---:|---:|---:|
| 100 fully changed supplied-size plants | 12.27 MB | 88.13 MB | 24.53 MB versus 176.26 MB |
| 1,000 fully changed supplied-size plants | 122.67 MB | 881.28 MB | 245.34 MB versus 1.76 GB |

The lower bound is `T ≥ bytes / achieved_bandwidth`; dispatch, packing, pinning, copies, validation and publication are additional. For a **hypothetical** effective 16 GB/s in each direction, 1,000 full poses consume about 15.3 ms of serial transfer alone, versus about 110.2 ms for full vertex output. These are illustrative arithmetic, not GPU predictions, and already show why compact readback is not universally cheap. Incremental changed guides and retained prior poses are crucial.

## 6. Four separate proofs before investment

Each gate must emit logs with toolkit/driver/build/device identity, source and result hashes, completed timings, byte counters and failures. They are separate; passing one is not passing the next.

| Gate — all not executed | Small reproducible input/output | Pass criteria | Reject/fallback |
|---|---|---|---|
| I0: standalone compute | Deterministic 256-guide packet with 8 samples, fixed anchors and analytic sphere; produce poses/status on CPU and candidate compute API | No NaNs/overflow; declared tolerances and work caps; accurate completed timing; clean shutdown with/without device | Stay CPU if correctness, distribution or crossover fails. |
| I1: standalone graphics sharing | Plugin-owned D3D11 device/resource; deterministic 256-ribbon pose or vertex pattern, double buffering; one registration model at a time | Exact expected integer IDs/status; numeric tolerance; no simultaneous compute/draw ownership; 10,000 update/retire cycles; loss/timeout handling | Use staged transfer if sharing itself fails. This does not qualify Max. |
| I2a: public in-Max shader path | One shared ribbon with two deliberately different CPU poses; then 100 plants; typed buffer and texture alternatives | Conservative same-generation item-local bounds; numeric roots/normals within declared tolerance; exact material/visibility identities and stable per-instance picking after sorting/compaction; mixed shaded/Wireframe viewports; selection/camera/F3 do not recook or reupload unchanged poses | Retain CPU deformation if HLSL parameter access or performance fails. |
| I2b: public in-Max native bridge | First read-only device identity probe; then one owned compute-written resource through verified public consumption path | Written SDK/sample ownership basis; exact device match; no host-state corruption; documented retirement; graphics recreation, Undo and deletion survive | Mark direct interop unavailable for that profile; use compact readback/I2a. Stop before private-pointer extraction. |
| I3: renderer/Bake/export | Same published source/pose IDs, one seam-split broad leaf, branched attachment and hidden root group | CPU final mesh matches evaluator within tolerance; material/UV/normal channels intact; correct instance transforms; cancellation and reload; selected renderer/version verified | Keep canonical CPU materialization; do not promise universal renderer support. |

The proposed 10,000-cycle count is a stress specification, not a completed test or a reliability probability. Per-dispatch time limits and acceptance tolerances are defined in [benchmark plan](10_BENCHMARK_AND_VALIDATION_PLAN.md).

## 7. Final geometry is a separate host contract

`GeomObject::GetRenderMesh(t,inode,view,needDelete)` supplies a renderer mesh and explicitly communicates whether it may be deleted. The multiple-mesh alternatives include `NumberOfRenderMeshes`, `GetMultipleRenderMesh`, and `GetMultipleRenderMeshTM`; long calls should handle renderer aborts. These are geometry-delivery contracts, not a promise that every renderer consumes a Nitrous custom shader. [M27](https://help.autodesk.com/cloudhelp/2027/ENU/MAXDEV-CPP-API-REF/class_geom_object.html)

**Proposed implementation boundary:** retain validated CPU source/binding/pose data. Materialize final meshes with the same mathematical guide evaluator used by the shader, preserving split UV/normal corners, material IDs, group visibility and attachment frames. Bake creates explicit owned scene geometry at a requested time/revision; export receives a suitable mesh or separately qualified procedural adapter. Do not read whatever viewport buffer happens to exist, nor silently export rest geometry because an instance is off-screen.

Arnold, V-Ray, Corona and other renderer versions need separate local tests. This report does not know the production renderer. A renderer requesting geometry while a preview job is incomplete must receive a valid matching final snapshot, invoke the admitted final CPU path, or report the operation as incomplete according to host policy. It cannot reinterpret an approximate viewport preview as final contact proof. GPU rendering may compete for the same VRAM/queue and changes the relevant latency budget.

## 8. Compiler and integration record

The 2027 SDK requirements specify VS2022 IDE **17.14.13**, v143, **C++20**, Windows SDK **10.0.19041.0**, .NET10 and Qt6.8.3. [M28](https://help.autodesk.com/cloudhelp/2027/ENU/MAXDEV-Developer/files/about_the_3ds_max_sdk/sdk_requirements.html) Autodesk's 31 July 2026 setup article further specifies **v14.38 (17.8)** build tools, even with a newer IDE. That agrees with the supplied local 14.38.33130 observation but does not establish a CUDA build. [M29](https://blog.autodesk.io/setting-up-3ds-max-2027-sdk-development-with-visual-studio-2026/)

Local engineers should record SDK build, `cl /Bv`, NVCC host compiler selection, runtime-library/iterator/debug flags from the installed SDK sample/property sheets, plugin configuration, and final imported DLL list. CRT compatibility was not independently established here. Keep CUDA/OpenCL implementation behind a versioned C ABI with caller-owned buffers or matching explicit release functions; do not pass STL containers or memory ownership casually across toolchain/DLL boundaries. The existing CPU plugin must load with the optional backend absent. The exact startup/redistribution policy is in [distribution](15_DISTRIBUTION_FALLBACK_AND_ARTIST_WORKFLOW.md).

**Gate conclusion — proposal.** The evidence supports a low-risk *attempt* at public shader deformation and a concrete native-device probe. It does not yet justify either “Max cannot expose Direct3D” or “CUDA zero-copy inside Max is solved.” The missing proof is supported resource consumption and synchronization over the real host lifetime, not the mere existence of a native device getter.
