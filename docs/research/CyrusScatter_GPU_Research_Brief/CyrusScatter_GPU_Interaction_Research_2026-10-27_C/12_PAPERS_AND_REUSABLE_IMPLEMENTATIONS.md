# 12 — Papers and reusable implementations

[Contents](00_README.md) · [Collision design](05_COLLISION_AND_GUIDE_SOLVING.md) · [Compute APIs](04_CUDA_OPENCL_AND_GRAPHICS_COMPUTE.md) · [Source ledger](17_SOURCE_LEDGER.md)

**Evidence scope.** Original papers, official release metadata, selected public source files and license files were inspected for this assignment. No library was built, no GPU kernel was executed, and no Max integration was tested. Repository inspection means the listed paths, not an audit of the complete dependency tree. Historical performance below is labelled as the authors' result and is never a Cyrus estimate.

## 1. Algorithm evidence and limits

| Primary work | Transfer to this workload | Limit and adoption decision |
|---|---|---|
| Müller et al., *Position Based Dynamics*, original VRIPHYS 2006 paper (later journal work is often cited as 2007), §3 [A01](https://matthias-research.github.io/pages/publications/posBasedDyn.pdf) | Constraint projection, anchors, inequality contact, iterative ordering | Original algorithm includes integration/velocity update. Reimplement only the required static constraints after defining the objective |
| Macklin et al., *XPBD*, MiG 10–12 Oct 2016, Eq. 18 and limitations [A02](https://mmacklin.com/xpbd.pdf) | Compliance/multiplier formulation, meaningful elastic parameters | Not finite-iteration exactness. A physical time step belongs to dynamics; static adaptation must be specified and tested |
| Bergou et al., *Discrete Elastic Rods*, SIGGRAPH 2008, §§4–8 [A03](https://www.cs.columbia.edu/cg/pdfs/143-rods.pdf) | Rest curvature, anisotropy, parallel transport, twist, inextensibility | Centerline remains dynamic in the original method; geometry binding and robust contact remain application work |
| Kugelstadt–Schömer, *Position and Orientation Based Cosserat Rods*, SCA 2016, §§5–6 [A04](https://animation.rwth-aachen.de/media/papers/2016-SCA-Cosserat-Rods.pdf) | Stretch/shear and bend/twist with quaternion degrees of freedom | Useful constraint reference; not a GPU implementation or commercial plant preparation system |
| Deul et al., *Direct Position-Based Solver for Stiff Rods*, CGF 37(6), 2018 [A05](https://animation.rwth-aachen.de/publication/0557/) | Direct coupled solve on an acyclic rod graph; addresses slow local error propagation | Arbitrary active contacts are not automatically an acyclic tree. Prototype only if long/stiff guide convergence is the measured bottleneck |
| Bouaziz et al., *Projective Dynamics*, SIGGRAPH 2014, §§3,8,9 [A06](https://users.cs.utah.edu/~ladislav/bouaziz14projective/bouaziz14projective.pdf) | Independent local projections and reusable global structure | Original implementation is C++/OpenMP, not a demonstrated GPU result. Dynamic constraints use matrix updates; hard boundaries approximated with weights can degrade conditioning |
| Macklin et al., *Unified Particle Physics*, SIGGRAPH 2014, §4 [A07](https://mmacklin.com/uppfrta_preprint.pdf) | Parallel constraint averaging/relaxation and batched contacts | Fixed particle-radius representation and visual-effect compromises differ from rooted broad-leaf geometry. Reuse scheduling ideas, not quality claims |
| Müller et al., *Fast Simulation of Inextensible Hair and Fur*, VRIPHYS 2012, §3.1 and §4 [A08](https://matthias-research.github.io/pages/publications/FTLHairFur.pdf) | Static root-to-tip follow-the-leader as an initializer; parallel independent strands | Sequential dependence within a strand; dynamic extension adds history/damping. Interpolated/follower hairs do not guarantee contact correctness |
| Macklin et al., *Local Optimization for Robust SDF Collision*, PACMCGIT 2020, §§3–9 [A09](https://mmacklin.com/sdfcontact.pdf) | Search a whole triangle/edge for contact instead of point-only sampling | Local minima and one-contact-per-element can miss simultaneous features; requires subdivision/multiple contacts and validation |
| Barill et al., *Fast Winding Numbers for Soups and Clouds*, SIGGRAPH 2018 [A10](https://www.dgp.toronto.edu/projects/fast-winding-numbers/) | Accelerated inside/outside signals for imperfect geometry | Thresholded open-mesh occupancy is a policy. Prefer a qualified closed proxy for authoritative exclusion |
| Karras, *Maximizing Parallelism in BVH Construction*, HPG June 2012, §§3–4 [A11](https://research.nvidia.com/publication/2012-06_maximizing-parallelism-construction-bvhs-octrees-and-k-d-trees) | Morton sorting and parallel radix-tree construction | A building block for bulk index builds; the scene's sparse edit pattern favors reuse/refit before rebuild |
| Zioma, *GPU-Generated Procedural Wind Animations for Trees*, GPU Gems 3, 2007, §§6.2–6.4 [A12](https://developer.nvidia.com/gpugems/gpugems3/part-i-geometry/chapter-6-gpu-generated-procedural-wind-animations-trees) | Hierarchical vertex-shader deformation and instancing | Phenomenological wind, not collision solving or strict physical coupling. It proves the conceptual separation between deformation and contact |
| Macklin et al., *Small Steps in Physics Simulation*, SCA July 2019 [A28](https://matthias-research.github.io/pages/publications/smallsteps.pdf) | Important later dynamics baseline for substeps versus iteration counts | Smaller physical substeps do not make the current editing operation a static solver. Do not adopt its time/history semantics implicitly |

**Historical measurement example.** The 2012 hair paper reports 47,000 short hairs / 776,000 particles at 25 fps, including rendering and collision against eight ellipsoids, using CUDA on a GeForce GTX 480. Its 1.9-million-particle long-hair example is 8 fps. These show why particle count, collision quality and rendering scope must accompany a performance claim. They establish neither current hardware speed nor million-clump feasibility. [A08](https://matthias-research.github.io/pages/publications/FTLHairFur.pdf)

No speedup from these papers is used in the decision matrix. Where the full original file could not be retrieved, the ledger identifies the accessible original sections or author/publisher metadata instead of claiming full-paper inspection. Mathematical ideas may be reimplemented, but paper access is not a software, asset or patent license.

## 2. NVIDIA Warp: useful prototype platform, conditional native reuse

**Verified release.** The official release list identifies **v1.18.0, 5 October 2026**, commit `f2eaed82d8d03b37bf1014cc975954067fefcf16`. Unversioned documentation currently exposes later development APIs; release source was used for implementation claims. The release's Windows/Linux default wheels use CUDA 13.4, R580-or-newer drivers and Turing-or-newer GPUs, with separate CUDA 12 compatibility wheels. These are that package's requirements, not the minimum feature set for a hand-written Cyrus fitter. [A13](https://github.com/NVIDIA/warp/releases/tag/v1.18.0)

| Inspected source at the pin | Useful operation | Integration obligation |
|---|---|---|
| `warp/native/mesh.h`: `mesh_query_point`, `mesh_query_point_sign_winding_number`, `mesh_query_inside_ray_tracing` [A14](https://github.com/NVIDIA/warp/blob/f2eaed82d8d03b37bf1014cc975954067fefcf16/warp/native/mesh.h) | Mesh closest-point barycentrics and sign routines | FP32 geometric implementation; failed nearest-face search is not outside; winding support must actually be built; sliver filtering must match admission |
| `warp/native/bvh.h`, `bvh.cu`: `BVH_QUERY_STACK_SIZE`, `bvh_refit_kernel`, `bvh_refit_device` [A15](https://github.com/NVIDIA/warp/blob/f2eaed82d8d03b37bf1014cc975954067fefcf16/warp/native/bvh.cu) | Packed traversal, GPU building/refit | Query stack size is 32; keep compatible builder depth invariants. Add application work/cancellation/overflow instrumentation rather than assuming it exists |
| `warp/native/volume.h`: `volume_sample`, `volume_sample_grad`, `volume_sample_f` [A16](https://github.com/NVIDIA/warp/blob/f2eaed82d8d03b37bf1014cc975954067fefcf16/warp/native/volume.h) | Sparse volume lookup/interpolation and gradients | Grid values/background do not by themselves certify a signed distance or its error; explicit coverage/sign metadata required |
| `warp/examples/cpp/00_cubin_launch`, `01_source_include`, `02_apic_visualization`, `03_apic_visualization_cpu` [A17](https://github.com/NVIDIA/warp/blob/f2eaed82d8d03b37bf1014cc975954067fefcf16/warp/examples/cpp/README.md) | AOT CUBIN/generated-source loading and captured workload replay in C++ | Python can remain an authoring/build tool for a narrowed AOT route; runtime dependency reduction and feature coverage still need an actual build proof |

**Recommendation — proposal.** Warp is a strong isolated experiment vehicle for batched queries, data layout and kernel iteration. Do not first embed a Python environment inside Max. If an AOT path removes unnecessary runtime dependencies and passes numerical/lifetime checks, compare it with a small native CUDA implementation. The current C++ examples prevent a blanket assertion that deploying Warp always requires Python, but do not qualify Max interop or every Warp feature for standalone C++ use.

**License.** The pinned `LICENSE.md` is Apache-2.0. `licenses/` includes separate NVIDIA CUDA/NVRTC/libmathdx and third-party notices, including winding-number and cuBQL components. Audit the exact linked/generated distribution and retain applicable notices; the top-level license does not replace dependency terms. No Warp code, wheels or binaries are bundled with this report. [A18](https://github.com/NVIDIA/warp/blob/f2eaed82d8d03b37bf1014cc975954067fefcf16/LICENSE.md)

## 3. TressFX: inspect the actual version and contact model

The publicly inspectable repository head at the cutoff is **`ba0bdacdfb964e38522fda812bf23169bc5fa603`**, last commit **24 January 2020**. Its README describes **TressFX 4.1**, a Radeon Cauldron sample with DirectX 12/Vulkan. The vendor's **TressFX 5.0 UE 5.4 update**, dated **4 August 2025**, is a separate Unreal patch requiring access to Epic's repository. Do not label the public 4.1 shader code as inspected 5.0 code. [A21](https://github.com/GPUOpen-Effects/TressFX/tree/ba0bdacdfb964e38522fda812bf23169bc5fa603) [A22](https://gpuopen.com/learn/tressfx-5-0-unreal-engine-5-update/)

`src/Shaders/TressFXSimulation.hlsl` uses different work mappings: `IntegrationAndGlobalShapeConstraints` is vertex work, `LocalShapeConstraints` traverses a strand, and `LengthConstriantsWindAndCollision` uses even/odd distance passes with group barriers. Previous positions, integration and shock propagation establish dynamic/history semantics. This is inspectable evidence that thread-per-whole-plant is not the only—or a generally appropriate—mapping. It is not a proposed replacement for Cyrus's static fit. [A19](https://github.com/GPUOpen-Effects/TressFX/blob/ba0bdacdfb964e38522fda812bf23169bc5fa603/src/Shaders/TressFXSimulation.hlsl)

`src/Shaders/TressFXSDFCollision.hlsl` contains `ConstructSignedDistanceField` and `CollideHairVerticesWithSdf`. Collision is at hair vertices, with sampled/interpolated distances and approximate gradients; out-of-grid or uninitialized samples can return without a projection. The forward variant skips the first two strand vertices. These choices do not prove segment, rooted-solid or leaf-surface correctness. Reuse the staged buffer/barrier ideas; write the application's explicit coverage and error contract. [A20](https://github.com/GPUOpen-Effects/TressFX/blob/ba0bdacdfb964e38522fda812bf23169bc5fa603/src/Shaders/TressFXSDFCollision.hlsl)

The public repository's `license.txt` is MIT; its `.gitmodules` references Radeon Cauldron. A shader adaptation needs notices and dependency review, while the access-gated Unreal patch has its own host/legal context. Porting the complete rendering/sample stack would add a graphics abstraction and hair-specific asset pipeline with little value to the first Cyrus prototype. [A21](https://github.com/GPUOpen-Effects/TressFX/blob/ba0bdacdfb964e38522fda812bf23169bc5fa603/license.txt)

## 4. CPU rod and sparse field references

**PositionBasedDynamics.** Inspected commit **`10a70bc146a97873dc3c8fef372f5217e010542e`**, **1 September 2026**, MIT. `PositionBasedDynamics/PositionBasedElasticRods.cpp` implements `PositionBasedCosseratRods::solve_StretchShearConstraint` and `solve_BendTwistConstraint`; the same file includes the direct stiff-rod solver. `Simulation/TimeStepController.cpp` processes sequential constraint groups with OpenMP within each group. Use it as a CPU mathematical/reference implementation and fixture source; exporting that object model to GPU kernels is a separate design. Its dependencies and demos require their own audit. [A23](https://github.com/InteractiveComputerGraphics/PositionBasedDynamics/tree/10a70bc146a97873dc3c8fef372f5217e010542e)

**NanoVDB/OpenVDB.** Inspected snapshot **`2ad72431a9f96084910ea5d9a6bb6f46d9073e62`**, **24 October 2026**; this is a source pin, not an asserted released SDK version. `nanovdb/nanovdb/NanoVDB.h` describes a compact read-oriented GPU/CPU tree; it requires 32-byte aligned storage and a separate caching read accessor per thread, and warns against copying accessors between CPU and GPU. `tools/GridBuilder.h` and OpenVDB's `tools/MeshToVolume.h` are construction leads. Reusing storage does not certify occupancy, distance accuracy, gradients or missing-tile semantics. The current root license and header are Apache-2.0, with a relicense note; do not apply an older MPL label to this pin. [A24](https://github.com/AcademySoftwareFoundation/openvdb/tree/2ad72431a9f96084910ea5d9a6bb6f46d9073e62)

**Recommendation — proposal.** Start with compact analytic primitives and a qualified triangle BVH. Add a per-source SDF only when repeated expensive queries amortize construction and the explicit error/memory budget wins. A small field implementation may be cheaper than importing full OpenVDB, but sparse background/sign correctness is substantial engineering. Choose based on measured build, query, transfer and refinement costs; do not count field lookup alone.

## 5. Why an existing physics engine does not settle the decision

**Jolt comparator.** The specifically inspected historical pin **`1b2e77e3c6c09709e5edc79dc208459b8ff32051`** identifies **5.6.1** in `Jolt/Core/Core.h` and uses MIT. `SoftBodySharedSettings.h` has rod stretch/shear and bend/twist constraints, while `SoftBodyMotionProperties::DetermineCollisionPlanes` calls `CollideSoftBodyVertices`; this is not a whole-span proof. The separate `Physics/Hair/Hair.h` explicitly describes unfinished GPU hair work, with missing wind/LOD and collision support beyond convex hulls plus duplicated CPU/GPU memory. This research does not assert that the supplied Cyrus release currently uses this pin or path. [A25](https://github.com/jrouwe/JoltPhysics/tree/1b2e77e3c6c09709e5edc79dc208459b8ff32051)

**PhysX comparator.** The inspected current repository snapshot **`b97365c6ddb32fda8469bc788ec18024862b0368`**, **15 October 2026**, has a **5.12.0** version header and an **Apache-2.0** `physx/LICENSE.md`; its README notes separately downloaded GPU binary content. Public “latest” docs were built **18 May 2026** and still contain an older BSD3 statement. Treat the pinned source license as evidence for those files, and separately audit distributed binary terms; do not blend versioned documentation into one imaginary release. [A26](https://github.com/NVIDIA-Omniverse/PhysX/tree/b97365c6ddb32fda8469bc788ec18024862b0368)

The May 2026 GPU guide describes GPU rigid bodies, particles and FEM, but also CPU scene queries/custom-contact restrictions and preallocated buffers whose overflow may discard contacts. Such behavior cannot be accepted as a complete-clear result. Selecting PhysX would require a new contact/solver/output adapter and explicit overflow-to-failure handling, not merely compiling Cyrus CPU code with CUDA. Current 5.12 parity with every older documented restriction remains a local qualification question. [A27](https://nvidia-omniverse.github.io/PhysX/physx/latest/docs/GPURigidBodies.html)

## 6. Reuse shortlist and rejection criteria

| Candidate | Reuse now | Reimplement/adapt | Reject when |
|---|---|---|---|
| Existing Cyrus CPU reference | Supplied fixtures, semantics, preparation and final audit | New serialized numeric snapshots and sparse GPU input adapter | Reference quality/ownership cannot be specified reproducibly |
| CUDA/OpenCL primitive libraries | Scan/sort/reduction where deployment terms and API fit; see [04](04_CUDA_OPENCL_AND_GRAPHICS_COMPUTE.md) | Stable-ID keying, bounded pair builders, diagnostics | Library scratch/cold costs erase benefit for active workloads |
| Warp | Isolated kernel/query experiments; narrowed AOT proof | Complete query wrapper, static constraints, source binding and host scheduler | Required feature lacks deployable native path, precision or bounded failure behavior |
| TressFX | Scheduling/barrier examples and selected permissive shader ideas | Stateless semantics, full-span/surface contacts, renderer-independent evaluator | Adaptation imports unnecessary history, follower collision gaps or graphics ownership |
| PositionBasedDynamics | CPU rod reference and constraint mathematics | GPU layout, conflict management, persistent result contract | Solver complexity exceeds measured benefit over focused static fit |
| NanoVDB | Sparse immutable field storage if justified | Build/sign/error metadata, fallback, source-local cache policy | Resolution/refinement costs exceed BVH or proxy solution |
| Jolt/PhysX | External comparisons, potentially qualified collision support | Plant-specific binding, static solving, whole-surface validation, delivery | Engine adoption is being justified only by the phrase “GPU physics” |

No weights, trained models or external foliage assets are required by this shortlist. Do not infer that repository licensing grants redistribution rights to every sample mesh, texture, shader compiler or runtime binary. The report ZIP contains research and optional original harness material only, not these third-party source trees.
