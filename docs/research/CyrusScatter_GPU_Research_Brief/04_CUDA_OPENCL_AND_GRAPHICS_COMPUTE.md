# 04. Architecture Comparison & CUDA vs OpenCL vs Graphics Compute

## 1. Five-Architecture Evaluation (Before Choosing an API)

Per `RESEARCH_PROMPT.md` §5, we evaluate the five candidate system architectures independently of compute API brand.

| Dimension | Arch 1: Optimized CPU Fit + CPU Deformation (Baseline+) | Arch 2: CPU Fit + GPU Vertex-Shader Deformation (Track 1) | Arch 3: CPU Neighbourhood + GPU Fit & Deformation (Track 2) | Arch 4: Full GPU Resident Neighbourhood + Fit + Deformation | Arch 5: Hybrid GPU Proxy/SDF Interactive + CPU/Exact Final Refinement |
|---|---|---|---|---|---|
| **What stays on CPU** | Spatial index, root exclusion, guide fit, surface refine, vertex skinning | Spatial index, root exclusion, guide fit, surface refine | Horizontal spatial index ($B(T_{\text{old}}) \cup B(T_{\text{new}})$), $O(K)$ snapshot management | Host capture & epoch coordination only | Horizontal spatial index; exact triangle-mesh audit on mouse-release / Bake |
| **What runs on GPU** | Retained instanced / unique mesh draw only | **HLSL SM5 Vertex Shader** deforms shared source mesh using uploaded compact guide poses + visibility masks | **Compute kernels** solve root exclusion, guide fit, foliage envelopes; **SM5 VS** (or CS) deforms vertices | **Compute kernels** maintain GPU spatial hash/BVH over $N \le 10^6$ instances + solve + deform | **Compute kernels** solve against cached local narrow-band SDFs + capsule proxies during drag; exact mesh pass on release |
| **H2D / D2H Transfers per Drag** | **H2D:** $K \times V \times 32\text{ B}$ deformed vertices ($336\text{ MiB}$ at $K=500$). **D2H:** $0\text{ B}$ | **H2D:** $M \times Nn \times 16\text{ B}$ compact poses ($1.83\text{ MiB}$ at $M=15\text{k}$). **D2H:** $0\text{ B}$ | **H2D:** $K \times 36\text{ B}$ transforms ($18\text{ KiB}$). **D2H:** $1.83\text{ MiB}$ compact poses (if no zero-copy D3D11 interop) + **H2D:** $1.83\text{ MiB}$ to Max VB/Texture | **H2D:** $64\text{ B}$ collider delta. **D2H:** $1.83\text{ MiB}$ compact poses (unless zero-copy interop proven) | **H2D:** $K \times 36\text{ B}$. **D2H:** $1.83\text{ MiB}$ compact poses during drag |
| **Synchronization Points** | CPU worker barrier $\to$ `VertexBufferHandle::Lock/Unlock` on main thread | CPU worker barrier $\to$ `TextureHandle` / `VertexBufferHandle` `Lock/Unlock` on main thread | 1 async GPU stream fence (`cudaEventQuery` / `ID3D11Fence`) $\to$ host epoch commit $\to$ Max `Lock/Unlock` | 1 async GPU stream fence $\to$ host epoch commit | Interactive: 1 GPU fence. On release: async exact refinement completion |
| **Expected Quality** | Exact match to `0.87.4.3` reference | **Bitwise-identical guide poses** to `0.87.4.3`; float32 shader skinning ($\le 10^{-5}\text{ m}$ vs FP64) | Matches reference within FP32 local-frame tolerance ($\le 5 \times 10^{-5}\text{ m}$) when using exact local BVH | Same as Arch 3 | Interactive drag has bounded SDF interpolation error ($\le 0.5\text{ voxel}$); release/render is exact |
| **VRAM Growth** | $\mathcal{O}(K_{\text{retained}} \cdot V)$ (**High**: $1{,}000$ deformed plants $= 672\text{ MiB}$) | $\mathcal{O}(V_{\text{source}} + M_{\text{retained}} \cdot Nn)$ (**Very Low**: $< 45\text{ MiB}$ for $1{,}000$ deformed plants) | $\mathcal{O}(V_{\text{source}} + C_{\text{BVH}} + M_{\text{retained}} \cdot Nn)$ (**Low**: $\sim 80\text{--}180\text{ MiB}$) | Adds resident GPU spatial index over $N=10^6$ ($\sim 64\text{--}120\text{ MiB}$) | Adds narrow-band SDF cache per unique collider ($\sim 2\text{--}16\text{ MiB/collider}$) |
| **Implementation Effort** | **Low** (1–2 weeks: fix $O(N)$ map copy + SIMD) | **Low–Medium** (2–3 weeks: extend `mesh_display.inc` HLSL + pose texture packing) | **Medium–High** (6–8 weeks: GPU BVH/solver + async epoch manager + fallback) | **High** (10–12 weeks: duplicates horizontal footprint index on GPU for $<0.3\text{ ms}$ gain) | **High** (8–10 weeks: requires two contact representations + release transition UX) |
| **Max 2027 SDK Requirement** | Public SDK only | **Public SDK only** (`HLSLMaterialHandle`, `TextureHandle` / `VertexBufferHandle`) | **Public SDK works via compact pose readback**; native D3D11 interop is optional optimization | Same as Arch 3 | Same as Arch 3 |

> [!TIP]
> **Why Architecture 2 + Architecture 3 Is Superior to Architecture 4:**
> On the CPU, querying a horizontal-split BVH or 2D ground-plane grid over $N = 1{,}000{,}000$ instances for $B(T_{\text{old}}) \cup B(T_{\text{new}})$ takes **$< 0.15\text{ ms}$** once the $O(N)$ successor-map copy bottleneck noted in `CURRENT_SYSTEM_CONTEXT.md` is replaced by a generational sparse table or copy-on-write page table **[ANALYTICAL-ESTIMATE]**. Moving the 1M-instance broad-phase index onto the GPU (Architecture 4) adds $64\text{--}120\text{ MiB}$ of persistent VRAM and complex incremental GPU tree refitting to save $< 0.15\text{ ms}$. **Architecture 2 followed by Architecture 3** captures $>98\%$ of the speedup at half the engineering risk.

## 2. CUDA vs OpenCL vs D3D11 Compute (`cs_5_0`) on the Same NVIDIA GPU

We compare **NVIDIA CUDA (12.x / 13.x)**, **Khronos OpenCL 3.0**, and **Direct3D 11 Compute Shaders (`cs_5_0`)** running the **exact same algorithm** (local-frame collider transform, root exclusion, 1-thread-per-active-guide FTL/XPBD solver, and float32 precision) on the **same NVIDIA GPU** (e.g., GeForce RTX 3090, Ampere GA102, Compute Capability `8.6`, Windows 11 WDDM) **[VERIFIED-PUBLIC]**.

### 2.1 Toolchain, Compiler Matrix, and Deployment Compatibility

| Feature | NVIDIA CUDA (12.4 – 13.x) | Khronos OpenCL 3.0 (NVIDIA Driver ICD) | Direct3D 11 Compute (`cs_5_0`) |
|---|---|---|---|
| **Max 2027 Compiler (`MSVC 14.38.33130`, VS 2022 `17.14.x`, C++20)** | **Supported.** CUDA 12.4+ and CUDA 13.x natively support VS 2022 `v143` (`14.38`) and C++20 **[VERIFIED-PUBLIC]**. Older toolkits (11.8–12.3) require `-allow-unsupported-compiler` when paired with newer VS 2022 headers, or host `.cpp` files can be compiled directly by `cl.exe` while kernels are compiled to fatbin/PTX via NVRTC. | **Supported.** Host C++ code compiles with standard `cl.exe` (`14.38`) using header-only `CL/opencl.hpp` (Apache-2.0) and links against `OpenCL.lib` or dynamically loads `C:\Windows\System32\OpenCL.dll` **[VERIFIED-PUBLIC]**. | **Supported natively.** `d3d11.h` and `d3dcompiler.h` ship in Windows SDK `10.0.19041.0` (the exact Max 2027 SDK baseline) **[VERIFIED-PUBLIC]**. |
| **Kernel Language & Code Sharing with CPU Reference** | **C++20 device code.** The exact same `constexpr` / `inline` C++ template functions (`__host__ __device__`) can be compiled for both the CPU fallback and the CUDA kernel, guaranteeing single-source parity **[VERIFIED-PUBLIC]**. | **OpenCL C (`-cl-std=CL1.2` / `CL3.0`).** C99-based dialect; cannot share C++20 templates/classes directly without macro shims (`DEV`, `GLOBAL`) or offline C++-to-SPIR-V toolchains. | **Driver & Runtime Requirements** | CUDA 12.x requires driver $\ge 527.41$ (or $\ge 572.61$ for 12.8); CUDA 13.0 requires R580+ ($\ge 580.xx$) **[VERIFIED-PUBLIC]**. Linking `cudart_static.lib` embeds the runtime; `nvcuda.dll` is delay-loaded from `System32`. | `OpenCL.dll` (Khronos ICD Loader) is installed by NVIDIA, AMD, and Intel graphics drivers in `System32` **[VERIFIED-PUBLIC]**. Delay-load or `LoadLibraryA("OpenCL.dll")`. | `d3d11.dll` and `d3dcompiler_47.dll` are part of the Windows 10/11 OS installation **[VERIFIED-PUBLIC]**. |

### 2.2 Execution Model, Primitives, and Hardware Throughput on Same NVIDIA GPU

On an NVIDIA GPU (such as the local RTX 3090 with driver `617.42`), CUDA kernels, OpenCL kernels, and D3D11 compute shaders all compile down to **PTX $\to$ SASS machine code** executed by the **same hardware warp schedulers** **[VERIFIED-PUBLIC]**:

1. **Raw Kernel Execution Speed:**
   - For compute- and register-bound loops like `fitGuide` ($Nn = 8$, $I_{\text{iters}} = 8$), CUDA, OpenCL, and D3D11 `cs_5_0` generate virtually identical SASS instructions (`FFMA`, `FMUL`, `FRSQRT`, `FSINCOS`) when fast-math flags are matched (`--use_fast_math` vs `-cl-fast-relaxed-math`), yielding **$< 5\%$ difference in pure kernel execution time** **[VERIFIED-PUBLIC]**.
2. **Dispatch & WDDM Submission Overhead:**
   - Under Windows WDDM, kernel enqueue latency is $\sim 3\text{--}8\text{ }\mu\text{s}$ per asynchronous stream launch in CUDA (`cudaLaunchKernel`), $\sim 5\text{--}12\text{ }\mu\text{s}$ in OpenCL (`clEnqueueNDRangeKernel`), and $\sim 4\text{--}10\text{ }\mu\text{s}$ in D3D11 (`ID3D11DeviceContext::Dispatch`), batched by the WDDM user-mode driver until a flush/event query **[VERIFIED-PUBLIC]**.
   - **CUDA Graphs (`cudaGraphLaunch` / `cudaGraphExecUpdate`):** Captures the fixed 4-stage pipeline (Upload $\to$ Root Exclude $\to$ Broadphase $\to$ Guide Solve $\to$ Readback) into a single graph launch, reducing multi-kernel CPU submission overhead by **40–60%** **[VERIFIED-PUBLIC]**. OpenCL has `cl_khr_command_buffer` (provisional extension, limited vendor support), while D3D11 has **no command-graph or multi-queue compute submission** (`ID3D11DeviceContext` is single-threaded; deferred contexts do not reduce driver submission cost for compute) **[VERIFIED-PUBLIC]**.
3. **Warp / Subgroup Primitives & Compaction Libraries:**
   - **CUDA:** Native warp intrinsics (`__ballot_sync`, `__shfl_sync`, `__reduce_add_sync`) plus **NVIDIA CCCL (`CUB` / `Thrust`)** (`Apache-2.0 WITH LLVM-exception`), providing single-pass `cub::DeviceSelect::Flagged` and `cub::DeviceRadixSort` (Merrill & Garland decoupled look-back) and **`NVIDIA/cuBQL`** (`Apache-2.0`) for GPU BVH build/traversal **[VERIFIED-PUBLIC]**.
   - **OpenCL:** Supports `cl_khr_subgroups` (`sub_group_ballot`, `sub_group_scan_exclusive_add`) on NVIDIA OpenCL 3.0 drivers **[VERIFIED-PUBLIC]**, but lacks a drop-in, vendor-maintained equivalent to CCCL/cuBQL that compiles cleanly inside NVIDIA's OpenCL C compiler without external dependencies.
   - **D3D11 (`cs_5_0`):** **Critical Limitation:** Shader Model 5.0 (`cs_5_0`, `fxc.exe`) does **not** expose wave intrinsics (`WaveBallot`, `WavePrefixSum` require **Shader Model 6.0 / `dxc` / Direct3D 12**, which is unavailable in D3D11) **[VERIFIED-PUBLIC]**. Compaction in `cs_5_0` must fall back to `groupshared` memory prefix scans (`32 KB` limit per thread group) or global `InterlockedAdd` on `RWByteAddressBuffer`.
4. **Memory Allocation & Pooling:**
   - **CUDA:** Stream-ordered memory allocator (`cudaMallocAsync` / `cudaMemPool_t`, CUDA 11.2+) provides sub-microsecond pooled suballocation with configurable release thresholds **[VERIFIED-PUBLIC]**.
   - **OpenCL / D3D11:** No built-in stream-ordered pool allocator; plugin must preallocate ring/arena buffers up to the admission cap (`K_max`).

### 2.3 FP32 / FP64 Precision and Determinism

- **Consumer vs Workstation/Datacenter FP64 Ratio:** On consumer/workstation Ampere (GA102, RTX 3090) and Ada Lovelace (AD102, RTX 4090), the hardware **FP64:FP32 throughput ratio is 1:64** (e.g., $\approx 0.56\text{ TFLOPS}$ FP64 vs $35.58\text{ TFLOPS}$ FP32 on RTX 3090), whereas datacenter GPUs (A100, H100) have a 1:2 ratio **[VERIFIED-PUBLIC]** ([CUDA Programming Guide — Arithmetic Instruction Throughput](https://docs.nvidia.com/cuda/cuda-c-programming-guide/index.html#arithmetic-instructions)).
- Therefore, running the entire iterative solver and BVH traversal in `double` (`FP64`) on artist GPUs (RTX 3060–4090) sacrifices **8× to 32× of compute throughput** and doubles register/memory bandwidth pressure.
- As shown in [09_MEMORY_PRECISION_AND_HARDWARE.md](09_MEMORY_PRECISION_AND_HARDWARE.md), **rebasing colliders into each plant's local metre frame on the host (in FP64) before uploading FP32 local coordinates** eliminates large-world-coordinate catastrophic cancellation and keeps FP32 node positions within **$< 5 \times 10^{-5}\text{ m}$ ($0.05\text{ mm}$)** of the FP64 reference.
- **IEEE 754 Reproducibility:** In CUDA, compiling with `--fmad=true` (default) fuses `a * b + c` into `fmaf`, which has a single rounding step compared to separate `mul` + `add` on CPU if the CPU is compiled without `/arch:AVX2` FMA **[VERIFIED-PUBLIC]** ([NVIDIA Floating Point and IEEE 754](https://docs.nvidia.com/cuda/floating-point/index.html)). Bitwise determinism across runs on the same GPU is guaranteed when thread-to-guide assignment is deterministic (via prefix scan rather than `atomicAdd` ordering) and no non-associative parallel atomic float reductions are used.

### 2.4 Profiling, Debugging, and Correctness Tooling

This is one of the largest practical gaps between CUDA and OpenCL on NVIDIA hardware **[VERIFIED-PUBLIC]**:
- **CUDA:** Fully supported by **NVIDIA Nsight Compute** (warp stall reasons, roofline, shared/global memory coalescing, register spilling), **NVIDIA Nsight Systems** (CPU/GPU/WDDM timeline, stream concurrency, PCIe transfers), and **`compute-sanitizer`** (`memcheck` for out-of-bounds/misaligned accesses, `racecheck`, `initcheck`, `synccheck`) **[VERIFIED-PUBLIC]**.
- **OpenCL on NVIDIA:** **Nsight Compute does NOT support profiling OpenCL kernels** **[VERIFIED-PUBLIC]**. Engineers debugging register pressure, uncoalesced global memory transactions, or subtle race conditions in a complex hierarchical branch/contact solver on NVIDIA OpenCL are effectively flying blind compared to CUDA.
- **D3D11 Compute (`cs_5_0`):** Supported by **RenderDoc**, **NVIDIA Nsight Graphics**, and **Microsoft PIX** for buffer inspection and shader debugging **[VERIFIED-PUBLIC]**, though lacking `compute-sanitizer` race/init checking and Nsight Compute's compute-specific source-line stall counters.

## 3. Sensitivity Analysis: When Does the Recommendation Shift?

| Scenario / Finding | Impact on API Choice | Recommended Action |
|---|---|---|
| **Case 1 (Default Expected):** Max 2027 public SDK does **not** expose raw `ID3D11Device*` or `ID3D11Buffer*` with UAV/shared flags; active drag batches reach $K = 100\text{--}5{,}000$ complex plants. | Both CUDA and OpenCL must transfer compact active guide poses ($0.2\text{--}2.5\text{ MiB}$) via pinned host memory into `MaxSDK::Graphics` `Lock`/`Unlock` buffers, where the **HLSL SM5 Vertex Shader** deforms the mesh. | **Winner: HLSL SM5 Vertex Shader (Deformation) + NVIDIA CUDA (Solver) + CPU Fallback.** CUDA wins decisively over OpenCL on single-source C++20 code sharing with the CPU solver, CCCL/`cuBQL` libraries, and Nsight Compute/`compute-sanitizer`. |
| **Case 2:** Local Probe P1 ([16_OPEN_QUESTIONS_FOR_LOCAL_CODEX.md](16_OPEN_QUESTIONS_FOR_LOCAL_CODEX.md)) discovers that Max 2027 exposes the Nitrous `ID3D11Device*` and allows custom `ID3D11ShaderResourceView*` / `ID3D11UnorderedAccessView*` binding on `IVirtualDevice`. | **D3D11 Compute (`cs_5_0`)** can write compact guide poses directly into a D3D11 `RWStructuredBuffer` that the Nitrous Vertex Shader reads via `StructuredBuffer` (`t` register) with **zero PCIe copies and zero inter-API sync**, working on NVIDIA, AMD, and Intel GPUs alike. | **Evaluate D3D11 Compute (`cs_5_0`) vs CUDA D3D11 Interop in Gate 2.** If solver complexity fits within `cs_5_0` (no wave intrinsics needed), D3D11 Compute becomes a strong cross-vendor contender. |
| **Case 3:** Typical artist scenes have $N = 1{,}000{,}000$ total instances, but collider drags only ever affect $K \le 30$ plants at once. | Once the $O(N)$ host map copy is fixed and vertex skinning is moved to the HLSL SM5 Vertex Shader (Architecture 2), the 8-thread CPU solver takes **$< 0.8\text{ ms}$**. | **Stop after Gate 3 (Architecture 2).** Do not ship a CUDA or OpenCL solver until artist workloads demonstrate $K \ge 100$ active plants per drag. |
