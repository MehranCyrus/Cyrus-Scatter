01Recommendation and evidence

Keep Jolt for rigid settling. Reuse its collision assets and query infrastructure for a focused static guide fitter. Treat CPU rods as a genuine alternative that still needs a substantial contact extension. This recommendation follows the inspected source and small executed counterexamples; it is not a measured performance ranking between completed implementations.

The exact dependency contains CPU Cosserat rods, but their environment collision is sampled at particles. The native probe reproduced a segment passing through a sphere while every particle stayed outside. A capsule query over that segment found the overlap. This establishes a useful implementation boundary: Jolt can supply a whole-segment collision query without supplying the corresponding two-endpoint rod constraint response. R07R08X01

For A — stones/debris, the existing rigid-body approach already matches the requested degrees of freedom: a pose per stone, solid moving collision proxies, fixed terrain and time integration. For B — rooted guides, Cyrus needs fixed attachments, rest curvature, length and material-frame control, whole-segment and visible-blade contact, a policy for impossible inputs, and publication through the prepared-source evaluator. Those responsibilities remain explicit even when a physics engine supplies some constraints. C18R02R03R04R05R06R07R08R09R10R11R12R13

Decision in practical terms

  1. Share the scene-to-collision layer: immutable geometry, local solve frames, units, cooked shape references, obstacle selection and diagnostic witnesses.
  2. Keep separate solve policies: rigid time integration for debris; a bounded static constrained fit for the initial rooted-guide product.

Cache keys and invalidation

Use three explicit identities. A prepared-source key covers rest geometry/topology, guides, frames, width/offset binding and evaluator version. A collision-shape key covers collision-source geometry, representation/cooking parameters, baked units/basis/scale, rounding, material/face mapping and exact Jolt cook/build identity. A fit-result key adds placement transform, all relevant obstacle shape and transform revisions, root/contact policies, solver settings and algorithm version.

Pure obstacle translation/rotation usually reuses its cooked local shape and changes the instance transform. A changed obstacle mesh, collision representation or baked nonuniform scale recooks the proxy. A changed source rest curve or topology invalidates its preparation and dependent fits. An unchanged source repeated thousands of times can share its preparation and collision shape; different accepted bends do not thereby share final vertex positions.

Mesh cooking may reorder triangles. Keep per-triangle user data when required and store stable source correspondence. Subshape IDs depend on the cooked hierarchy; contacts must carry that shape’s generation. A recycled BodyID or changed compound hierarchy is not a durable artist selection identifier. C01C04

Query-world design

A simple initial implementation keeps fixed obstacle bodies in a query world, shares their immutable Shape references with rigid solve worlds, and uses locking narrowphase queries. Another documented route collects TransformedShape snapshots for long-running queries. In either case, pin both shape and transform generations; refcounting only preserves object lifetime, not the meaning of mutable data. Choose one ownership model before adding asynchronous jobs. NoLock interfaces require an independently established locking discipline. C02U01U12

Per-query locking alone does not freeze all obstacles for the whole fit. Use an immutable query-world generation, a private world, or precollected immutable TransformedShapes for every iteration of one job. A new stone edit creates a new generation. Checking revisions only at publication prevents stale output from becoming current; it does not make iterations over mixed obstacle generations coherent.

Register Jolt types, allocators and shared hooks once at the integration lifetime boundary, consistent with existing Physics Lab ownership. Creating a second fitter service must not independently replace the global Factory or unregister types while the rigid service is active. This is an integration requirement inferred from documented global services. U12U13

SDFs: useful query representation, additional implementation

No built-in general SDF collision shape was found in the pinned shape enum or the inspected Jolt/Docs/Samples tree. A standalone SDF adapter can still supply distance and gradients to a custom fitter; a custom Jolt Shape adds collision dispatch, casts, scaling, bounds, serialization and supported-pair obligations. Those are different integration scopes. C08U15

A solid SDF requires a meaningful interior. Mesh repair/signing, grid spacing, narrow-band extent, interpolation, gradient quality and revision invalidation are part of its contract. Thin walls may disappear and gaps may close under voxelization; expanding a margin cannot recover the original topology. At medial axes or sharp corners a unique smooth normal may not exist. Retain multiple relevant constraints or use a qualified local fallback instead of normalizing an unreliable gradient.

There is a useful conservative sampling argument only under explicit assumptions. A true signed distance is 1-Lipschitz. If samples along a segment have maximum spacing d, both endpoints are sampled, and approximation error is bounded by e, then requiring every sampled value to be at least r + clearance + d/2 + e certifies that a constant-radius segment stays clear. Every point is within d/2 of a sample. A sampled grid with an unmeasured error bound does not inherit that certificate merely by being called an SDF. The argument also certifies only the selected radius envelope, not a wider visible blade. This is geometric reasoning; no SDF was built or benchmarked in this study.

Add an SDF backend when the smallest representative experiment shows that it improves a required query or enables a supported collider class at acceptable memory and recooking cost. The available evidence does not justify adding a second cooking stack as the initial default.

Units, transforms, and physical scale

Jolt's architecture uses meters, seconds, kilograms, and radians. Its documented favorable characteristic lengths are approximately 0.1–10 m for dynamic bodies and 0.1–2000 m for statics; these are solver-scale guidelines, not constructor acceptance limits. Grass at millimeter thickness is outside the regime suggested by the default length tolerances. Conversion from Max units alone does not tune those tolerances. A scaled simulation experiment must change all dimensional quantities consistently, including gravity, velocities, mass/inertia, constraint stiffness/compliance as applicable, and collision tolerances; otherwise it changes the model rather than merely its units. C03C10

Use a local solve origin near the patch. JPH_DOUBLE_PRECISION makes world positions double; local shape geometry and much collision math remain float. A close inBaseOffset improves returned query precision. Double world coordinates do not recover detail already lost by first converting huge coordinates to float, and do not resolve tiny-object contact tolerances. C03C11

BodyCreationSettings::mPosition is the body's authored position, while many queries accept a center-of-mass transform. Shapes can recenter around their center of mass. Store the source-to-COM relationship and explicitly select GetWorldTransform versus GetCenterOfMassTransform; a renderer should not accidentally apply the COM shift twice. C01C14C15

Validate scale with IsValidScale. A sphere or capsule requires uniform scale; compounds with rotated children cannot accept scale that introduces shear. MakeScaleValid may discard invalid components, so silently calling it can change the obstacle. Proposed Cyrus policy: bake unsupported affine transforms into a fresh collision proxy, preserve the original render source, and report any approximation. Negative determinant and triangle winding need explicit consistency. C24

07A · Rigid stones on fixed terrain

This follows the official initialization/body/update lifecycle; it extends that example with required Cyrus preflight and publication gates. It is a recipe, not an executed DCC integration. C18

  1. Snapshot and normalize. On the host-safe thread, capture evaluated terrain triangles, each stone's collision-source geometry, instance transforms, stable IDs, scene-unit conversion, and a generation number. Convert once into a patch-local meter coordinate system. Preserve immutable render source geometry separately.
  2. Cook reusable shapes. Use MeshShapeSettings for fixed terrain with overhangs, HeightFieldShapeSettings only for a true height-grid asset. Check ShapeResult and retain ShapeRefC. Use one convex hull per roughly convex stone; author or externally generate compound convex pieces when concavity matters. Select rounding and hull tolerances deliberately. A rigid transform change reuses the same shape; changing vertices or a baked scale recooks it. C04C05C06
  3. Initialize a private solve world. Register allocator/types once at the library lifetime boundary; provide job system and temporary allocator. PhysicsSystem::Init receives body/pair/contact capacities and live filter objects. Use STATIC and MOVING object layers mapped to a small number of broadphase layers. Enable moving-versus-static and, if stones must pile, moving-versus-moving. Disabling debris/debris contact changes the requested result; expose it as a deliberate mode. C02C18C30
  4. Create bodies. Terrain uses EMotionType::Static, added without activation. Stone settings use EMotionType::Dynamic, explicit mass policy, friction, restitution, damping, and initial pose/velocity. Zero restitution is a useful proposed settling preset; friction must be chosen from the intended behavior, not invented as a physical measurement. Check invalid body IDs/out-of-capacity failures. Prefer batch add for many stones. C14C15
  5. Preflight initial overlap. Query the actual collision proxy against obstacles. Distinguish surface overlap, point containment for closed manifold obstacles, and invalid/open solid requests. Reject or visibly repair badly embedded stones before the settle loop. A large timestep, more iterations, or a two-sided ray does not establish a global escape solution. Preserve the artist's initial transforms for Reset.
  6. Step explicitly. A reproducible starting schedule is the official example's fixed 1/60 s with one collision step, then increase collision steps only where fixture evidence requires it. Update(dt, collisionSteps, tempAllocator, jobSystem) runs collision detection and integration for each substep and returns only after its jobs finish. Inspect every EPhysicsUpdateError: full manifold/contact or pair caches can mean ignored contacts; do not accept such a result. C16C17C18
  7. Handle thin/fast motion. EMotionQuality::LinearCast reduces translational tunneling. It does not guarantee rotational swept contact for long thin bodies; the source documentation explicitly calls out this failure. Reduce step motion or use additional conservative validation for those assets. C22
  8. Stop and validate. Use bounded solve budget plus monitored pose change, velocity, and residual penetration. Default sleep criteria include 0.5 s and a three-point speed threshold of 0.03 m/s. Sleeping is an efficiency state, not proof of equilibrium, correct containment, or artist-level clearance. Mark time-budget, cache-capacity, excessive residual, and unresolved initial-overlap failures separately. C10
  9. Publish completed poses. After Update completes and validation passes, copy stable instance IDs → final authored/world transforms, with source and obstacle generation IDs. Atomically swap this immutable result into viewport/render/Bake consumers. Rigid render sources can stay shared instances; collision hulls should not replace render geometry. Keep the last successful result while a new one is computing.
  10. Reset, obstacle edit, and cleanup. Reset recreates from the snapshot or explicitly restores poses, velocities, and all relevant material/constraint settings. Moving fixed terrain through SetPositionAndRotation changes its broadphase placement; editing its geometry creates a new shape then uses SetShape. For a fresh deterministic solve, rebuild from the original initial state. A warm continuation is a separate mode: activate affected sleeping stones and recheck overlaps. At teardown remove bodies before destroying them. C15

Initial-state persistence should remain Cyrus-owned. Jolt's state recorder stores state modified by the engine; application-side property changes and added/removed topology require separate restoration. Its binary shape serialization can deduplicate shape/material references, but the architecture recommends retaining raw application data so shapes can be recooked after a library update. C25

What this recipe delivers

It is dynamic settling, even when the artist sees one Update button and a frozen final pose. It does not require exposing a scene timeline: an isolated job can advance fixed simulation steps internally and publish only the accepted transforms. Conversely, placing each stone at a nearest surface point and aligning its normal is a static placement heuristic; it does not reproduce mutual piles, torque or frictional settling. A height ray alone cannot establish support on irregular terrain or concave edges.

The artist prepares fixed terrain and a solid proxy for each rigid source once, selects participating scatter instances and chooses material/settling settings. Many copies of one pebble can share both render source and collision shape; only their rigid pose/state is unique. Bake can create instances with final transforms where its consumer supports them. No deformation binding is needed for A. Moving a stone that serves as a fixed obstacle for B changes the obstacle snapshot; the same object must not be simultaneously treated as fixed and dynamically moving within one unqualified solve.

08B · Roots, rest shape and material frames

Root position and root orientation: the important hidden coupling in convenience preparation

S: These are distinct pieces of data. A particle has an inverse mass. A rod has a separate inverse mass used for orientation corrections, a rest quaternion, and a live quaternion. However, CalculateRodProperties initializes each rod inverse mass to the minimum of its endpoint particle inverse masses. Consequently a particle root with inverse mass zero also initializes its first rod inverse mass to zero. With zero initial angular velocity that first rod stays at its initial orientation under the rod constraint corrections. The stock sample therefore does not demonstrate a free angular hinge at a pinned root. R02R03R06

The local math can be stated precisely without overstating the implementation. If n is a unit normal pointing out from the obstacle, q is an obstacle witness, u is a qualified centerline parameter and rho is radius plus clearance, use g = n dot ((1-u)x0 + u*x1 - q) - rho >= 0. 11Proposed focused static fitter

P — Focused static fitter v1. This is a proposed implementation and acceptance contract, not an executed solver. Its scope is independently prepared, framed guides against fixed obstacles. It uses the same immutable source data and collision-query adapter as the rod prototype. It deliberately owns all plant-specific constraints and contact response in application code.

Minimal supported scope

Begin with solid spheres, boxes and convex/compound-convex stones, plus explicitly labelled triangle terrain surfaces. Require nonzero ordered spans, known rest material frames, root anchors, positive width/clearance policy and readable source bindings. Permit a narrow conservative capsule envelope first. Treat arbitrary mesh solids as a separate capability requiring qualified containment, and SDFs as a later query backend. Omit arbitrary broad-leaf folds, self collision and plant–plant collision from the first contract unless a fixture requires them.

This limits the first prototype’s unknowns without changing the requested result silently. If a conservative envelope blocks a gap that an oriented ribbon might fit, return envelope too conservative / orientation-aware fit required, not a false proof of physical impossibility. If the actual projected width plus both clearances exceeds the gap and twist is fixed, the geometric conflict is real. X02

State and objective

Use particle positions x[i] and a proper material-frame quaternion q[i] for each segment. Rest data are x0, q0, lengths l0, and relative frames d0[i] = inverse(q0[i]) * q0[i+1]. One proposed discrete model is:

hard root:          x[0] = anchor
stretch / shear:   x[i+1] - x[i] - l0[i] * rotate(q[i], localZ) ≈ 0
rest bend / twist: Log(inverse(d0[i]) * inverse(q[i]) * q[i+1]) ≈ 0
root angle:        clamp q[0], or penalize Log(inverse(qTarget) * q[0])
contact:           every accepted segment / blade envelope clears obstacles

This notation defines a proposed finite-dimensional objective, not a claim of an exact continuum plant material. Use hard or tightly bounded length constraints and weighted rest bend/twist penalties; record the chosen weights and their discretization. An optional small rest-position penalty can break routing ties, but it must yield to mandatory clearance and roots. Authored curvature lives in relative rest frames rather than a universal straight target. Do not conflate the root positional equality with an angular penalty.

Iterative solve order

  1. Start from immutable rest pose in the current placement frame, or a separately labelled validated warm start. Validate root containment, units, scale, nonzero spans and collider semantics before iterations.
  2. Select obstacle candidates with expanded span/envelope bounds. Test complete capsules and relevant containment witnesses. Build an active set with all relevant walls/features; do not reduce a two-stone gap to a single deepest plane.
  3. Linearize the active contacts at qualified witnesses. Apply bounded contact corrections and rest/length/frame constraints using a chosen constrained optimizer or alternating projection method. Record that algorithm and ordering; neither is implied by using Jolt queries.
  4. Refresh normals and witnesses after significant changes. Use a line search or trust region to limit a proposed move; preserve quaternion normalization. Avoid keeping one stale contact plane throughout a large route change.
  5. Recompute full-segment and final evaluated-envelope clearance after the other constraints move the geometry. Check root error, relative length error, frame validity and chosen rest/angle residuals. A small position change alone can mean stagnation in an invalid local minimum.
  6. Accept only if all mandatory residuals meet the configured contract. Otherwise return a bounded-budget, infeasible-input, ambiguous-collider or unresolved-contact status with the failed geometry. Publish no partially accepted plant as a successful fit.

A fixed small number of deterministic, recorded alternative initial directions can be a proposed routing aid for symmetric or blocked cases. Expose when it was used, and evaluate every candidate with the same acceptance function. Local optimization has no general guarantee of finding a path through arbitrary concave obstacles; the first contract should fail clearly when it cannot establish one.

One local contact equation, with its limits

For a qualified segment witness at material fraction u, let p=(1-u)x0+u*x1, outward obstacle unit normal n, obstacle witness c, geometric radius r and desired clearance h. Locally freeze the witness and define g = dot(n, p-c) - r - h. For g<0, a simple hard projection has:

gradient0 = (1-u) * n
gradient1 = u * n
denominator = w0*(1-u)^2 + w1*u^2
deltaLambda = -g / denominator
deltaX0 = w0 * gradient0 * deltaLambda
deltaX1 = w1 * gradient1 * deltaLambda

Here w0,w1 are solver mobilities; a hard root uses zero. A zero denominator with negative gap is a conflict, not a division to regularize until it disappears. Derive u from a validated capsule-side witness or qualified closest-feature calculation. Projecting an arbitrary obstacle-side point onto the axis during deep overlap is not a certified parameter recovery. This is a local constraint illustration, not a complete contact solver: contacts move, constraints compete and the same projection can reintroduce a prior collision.

For an oriented ribbon witness, the point also includes a rotated transverse offset. Its angular correction depends on that offset and the contact normal (a local rotational gradient contains offset × n), with the correct frame interpolation. Endpoint-only corrections cannot generally resolve a blade-edge contact while preserving twist and width. That additional geometry is why an oriented ribbon or cage is a later contact capability, not a radius slider alone.

Initial penetration and route selection

A root inside a required solid collider fails preflight. For a movable blade wholly inside a stone, the artist’s intended exit side is ambiguous; v1 should report it or use an explicitly selected recovery policy, followed by full validation. A closest exit for every particle independently can fold or invert the guide. Dynamic ejection can add outgoing velocity, as H04b demonstrates. Starting from a valid rest pose and moving an obstacle into it still needs the same root/containment checks. X01

Why begin here

The static fitter has new solver work: contact active sets, convergence and frame/length constraints. Its advantage for this product goal is a direct owned interface for those requirements and cooperative cancellation between batches. It avoids depending on a private soft-body update seam solely to add the segment response. This is an integration-cost inference; it is not evidence that a custom fitter will be faster, easier in every case, or automatically correct.

  • Choose the focused static fitter if the product primarily needs a repeatable final pose against fixed obstacles, and the narrow contact/length/frame prototype passes the gates with an owned public-query boundary.
  • Choose CPU rods plus an explicit contact extension if time-dependent flexing or coupled dynamics is a real requirement and the rod material/state model saves enough work to justify maintaining the missing contact integration. Require the same final-envelope gates.
  • Choose a rigid capsule chain if a coarse chain meets the visual and contact contract and its measured body/joint/cooking/delivery cost is acceptable. It uses a different model and cannot inherit a CPU-rod result automatically.
  • Evaluate compute hair later when large animated strand populations and a defined compute/render path justify its separate integration. Its present environment contact still needs the relevant adversarial checks.

The source and probes already rule out “enable CPU rods and increase iterations” as the complete solution. They do not yet select a proven production static algorithm or establish a performance winner.

15Update, cancellation, reset and completed results

P — One result lifecycle for both cases. The visible artist operation is Update; its internal algorithm differs. A rigid job advances time. A static guide job iterates a constrained fit. Both operate on one snapshot and finish through the same validation/publication contract.

Update, cancel and publish

capture generation G on host-safe thread
  → validate inputs and immutable cache keys
  → run owned solve job against pinned obstacle snapshot
  → check cancellation between bounded work units
  → validate complete result against G
  → if current generation still equals G: publish atomically
  → otherwise discard candidate; retain last accepted result

Jolt Update spawns jobs and waits for their completion; its source then frees temporary storage and unlocks the system. It has no general public mid-update abort parameter. A cancellation request should let the current Update drain, then stop scheduling another and discard the candidate. Do not make the job adapter skip required work, delete a world under running tasks or confuse AddBodiesAbort with simulation cancellation. A custom fitter can expose finer batch checkpoints, but its worst-case checkpoint work must still be measured. U01U02U05

The job adapter must respect dynamically added jobs and barrier completion. Jolt’s supplied thread pool is explicitly an example implementation; integration can target a shared scheduler. Avoid a separate hardware-sized pool per patch or nesting blocked host jobs that own the same physics data. A worker captures only owned data; scene evaluation and output object changes occur at approved host boundaries. U05U06

After moving a stone

Mark affected guide results stale using the union of the obstacle’s old and new bounds, expanded by the permitted guide/envelope reach. Use a conservative influence region if fitting can reroute far from a current segment. Pure movement retains the cooked shape and updates its transform revision. Geometry edits recook. Start a fresh fit from immutable rest data by default, so repeated moves do not accumulate bend or change the source. A warm start can be offered explicitly, with full validation and a reset-from-rest comparison.

For a rigid pile, contact dependencies can propagate beyond the moved stone’s immediate neighbors. Rebuild the affected pile/island or the whole selected rigid solve region according to a declared policy; do not assume vegetation’s local invalidation rule is sufficient for debris stacks. A warm dynamic continuation requires activation of affected bodies and fresh overlap checks. C15

The viewport may keep the last accepted geometry visible with a stale status while the new generation runs. Failed placements should be visible as failed, with root/segment/contact witnesses and a short reason. If partial scatter acceptance is allowed, store a per-placement status and mark the overall batch partial; never label stale fallback geometry as newly valid. A root inside a stone, an ambiguous mesh interior, a too-small gap and a solver budget limit need different messages.

Reset and freeze

For rods, recreate runtime state from fresh immutable prepared settings for the baseline Reset. GetSoftBodyCreationSettings references original shared settings; it does not convert current particles/frames into a baked source. SaveState/RestoreState is compatible replay state, assuming the existing configuration. ApplySoftBodyCreationSettings is documented for a body outside the system. For rigid bodies, reset poses, velocities and all application-controlled properties, or recreate the isolated world. R14R15C25

Freeze pins an accepted result generation. If a stone later moves, a frozen result remains visibly marked as tied to the old snapshot; it is not silently recertified. Bake copies the accepted output into independent scene geometry/instances through the canonical delivery path. Export uses that same completed result and explicit units/transforms. Jolt cooked-shape binary data is an acceleration cache that must be recooked after incompatible versions, not the durable plant/result format. U08U16

Geometry sharing and the delivery boundary

A returns stable instance IDs and final transforms; the source pebble mesh remains immutable and shareable. B returns stable guide IDs, positions, frames and validation metadata; the prepared binding evaluates the render mesh. Distinct accepted deformations normally need distinct positions/normals, even though topology, UVs, materials and bindings can be shared. Exact repeated accepted variants may share evaluated geometry. Neither Jolt shape references nor its debug renderer implement Max viewport batching, production renderer submission, picking or Bake. The earlier delivery contract remains a separate acceptance gate. U16R05
