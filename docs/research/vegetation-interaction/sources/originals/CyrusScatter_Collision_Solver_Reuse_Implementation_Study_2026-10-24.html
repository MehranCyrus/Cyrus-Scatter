CyrusScatter Collision and Solver Reuse#

Exact-pin Jolt assessment, rigid-settling path, rooted-guide gaps, and decision experiments#

Date: 24 October 2026
Target host: Autodesk 3ds Max 2027
Jolt source inspected: commit 1b2e77e3c6c09709e5edc79dc208459b8ff32051
Status: Engineering research and architecture evaluation only. No repository was modified and no production feature was implemented.

1. Executive recommendation#

Recommendation: keep two implementation tracks. For rigid stones and debris, continue with the existing Jolt rigid-body path. For rooted vegetation, build a focused static guide fitter first and optionally reuse Jolt’s cooked obstacle shapes and collision-query layer. Do not adopt stock Jolt CPU rods as the first production solution unless the adversarial tests below show that vertex-only collision is acceptable for the supported assets—which is unlikely for long grass segments and thin obstacles.

Case A: reuse broadly#

Jolt is a natural fit for dynamic convex/compound stones settling against fixed terrain. Its body model, broad phase, narrow phase, contact solver, sleeping, shape sharing, and job graph address the actual problem.

Case B: reuse selectively#

The CPU rod constraints preserve length, shear, bend, twist, and rest orientation. The stock collision path, however, produces one deepest collision plane per movable particle. Rod connectivity is not passed into collision.

Do not substitute GPU hair#

The experimental GPU hair system is a separate compute subsystem, not the Physics Lab rigid path. Its own source labels it work in progress, limits environmental shapes, stores CPU and GPU state, and describes CPU readback as slow debugging functionality.

1.2 What this report does not claim#

  • It does not claim that an existing physics engine solves source preparation, guide-to-mesh binding, viewport delivery, renderer delivery, or Bake.
  • It does not claim that “solver completed” means contact quality was achieved.
  • It does not report performance measurements. Every capacity and timing item below is an experiment, formula, or decision gate.
  • It does not independently verify the local CyrusPhysicsLab wrapper. The public Cyrus repository did not expose the listed Physics Lab files during this review; wrapper-specific statements are therefore limited to the supplied project context.

This is a genuine reuse case. Rigid debris needs the exact services a rigid engine provides: broad-phase pairs, shape-to-shape contact generation, friction, mass/inertia, rotational response, sleeping, and stable stepping. A replacement static drop-to-surface routine would have to recreate pile interaction and rotational settling.

3.2 Shape policy for dynamic debris#

  • Analytic primitive: use for genuinely simple geometry or an intentionally simplified collision proxy.
  • Single convex hull: default for approximately convex pebbles and stones. It preserves dynamic support and stable mass properties while discarding concavities.
  • Compound of convex hulls: use when a visible concavity materially affects settling. Keep the child count bounded and cache the compound per source revision.
  • Triangle mesh: use for fixed terrain, curbs, walls, and other static receivers. Do not make it the normal dynamic-stone representation.
  • Heightfield: use for regular terrain without overhangs when the existing terrain data naturally matches a heightfield.

3.3 Initialization and settling#

P The rigid workflow should start from accepted Scatter placements, not regenerate distribution. Each physics body carries the stable placement ID in application metadata. Initial transform, linear/angular velocity, source shape, friction, restitution, damping, gravity factor, and body layer are explicit snapshot inputs.

  • Run at a fixed step. The exact release notes warn that wildly changing delta times can destabilize warm starting, and PhysicsSystem::Update divides the supplied interval into collision steps. J5J22
  • Stop only when all target bodies satisfy a declared sleeping/convergence rule, or when a step/work cap is reached.
  • Record EPhysicsUpdateError; a completed call can still report that contacts were ignored because caches or buffers were full. J23
  • Before simulation, detect severe initial overlap. Do not rely on a finite position-iteration correction budget to rescue arbitrary embedded geometry.
  • After simulation, validate residual penetration against the product tolerance. “Asleep” is not equivalent to “acceptable.”

3.4 Freeze, cache, and publication#

The durable result for Case A is a compact array of final transforms and status records keyed by stable placement ID. It is not the transient Jolt world. This keeps camera navigation, renderer evaluation, save/reopen, and Bake independent from simulation state.

4. Case B — rooted flexible guides fitting around fixed stones#

4.1 What Jolt’s CPU rod model genuinely supplies#

I The exact pin contains a CPU soft-body Cosserat-rod implementation and a public sample with a helix, a branching tree, and a “weed-like structure” of 50 strands × 64 vertices. The sample pins each strand’s first vertex with inverse mass zero, adds one stretch/shear constraint per segment and one bend/twist constraint per adjacent rod pair, calculates rod properties, optimizes constraint order, and creates a soft body. J14

The data model preserves:

  • segment rest length through RodStretchShear::mLength;
  • rod rest orientation through the Bishop frame;
  • rest bend/twist through RodBendTwist::mOmega0;
  • compliance for stretch/shear and bend/twist;
  • render orientation because a rod rotation is an explicit state and the source comments call out attached plant leaves as a use case. J15J16J18

4.2 Root position and root orientation are distinct—but the stock sample couples them#

This distinction is implementation-critical.

I CalculateRodProperties() explicitly sets each rod’s inverse mass to the minimum inverse mass of its endpoints. This subtle rule is why a zero-mass root can lock the adjacent rod’s orientation. J16

4.3 The decisive stock-contact limitation#

Stock CPU soft-body collision is vertex-based. The collision iterator exposes a vertex position and inverse mass, and stores one selected collision plane plus one colliding-shape index. Shape collision functions do not receive rod endpoints, rod indices, or segment thickness. J19

The exact soft-body update:

  1. builds a soft-body AABB from current/predicted vertex positions and expands it by the single body-wide mVertexRadius;
  2. collects overlapping rigid shapes through the broad phase;
  3. asks each shape to collide the vertices;
  4. keeps the largest penetration for each vertex;
  5. projects only vertices whose inverse mass is greater than zero. J18J19

This is not a theoretical edge case; it is the minimum falsification fixture for using stock rods as a vegetation-contact solution.

4.4 Pinned roots are omitted from stock collision response#

I The soft-body collision code and collision-projection loop skip vertices with inverse mass zero. A root embedded in a stone can therefore remain embedded without being depenetrated by the stock vertex path. That is correct for a kinematic particle, but it means Cyrus must preflight and diagnose root conflicts rather than expecting Jolt to repair them. J18J20

4.5 Visible blade width is not represented by a centerline alone#

SoftBodyCreationSettings::mVertexRadius is one scalar radius for all soft-body particles. It can add clearance around vertices, but it does not represent:

  • a varying blade width from root to tip;
  • the two long edges of a ribbon;
  • anisotropic card thickness;
  • crossed cards whose visible envelope is far from the guide;
  • opacity silhouettes extending beyond geometric card edges.

A production contact contract needs a per-segment envelope—at minimum a capsule radius r(s), and for broad leaves possibly two edge guides, an oriented ribbon, or several offset collision samples. This requirement exists regardless of the numerical solver.

4.6 Rest shape versus contact feasibility#

Jolt’s rod constraints preserve rest length and relative rod rotation through compliance-scaled iterative projections. That does not guarantee a feasible shape. A guide can be trapped in a gap narrower than its requested envelope, begin wholly inside a closed solid, or require a bend beyond the artist’s limit. Cyrus must retain independent validation metrics:

  • root position drift;
  • root orientation drift;
  • segment length error;
  • rest-curvature/twist deviation;
  • residual visible-envelope penetration;
  • maximum bend violation;
  • unresolved-contact count and reason.

5. Experimental GPU hair is not the CPU rod answer#

T Jolt 5.6.0 introduced a strand-based GPU hair system and compute backends. I At the exact pin, Hair.h still labels the subsystem “currently still in development” and lists missing LOD, wind, grid advection, non-convex-hull collision support, memory optimization, and multiple neutral poses. It also states that reading GPU state back to CPU is slow and intended for debugging. J5J24

Exact Hair.cpp behavior is narrower than a generic rigid collision world:

  • it gathers leaf shapes from Jolt bodies;
  • it serializes only leaves whose subtype is ConvexHull into GPU collision buffers;
  • compounds work only by expanding to supported convex-hull leaves;
  • ordinary analytic leaves and triangle meshes are not converted by that path. J25
Decision: GPU hair is a future research track for continuous animation, guide/follow-strand generation, and GPU-resident rendering. It is not a low-cost way to add a static Max 2027 vegetation fitting feature to the current CPU/retained-mesh architecture.

7.1 Convex hull limits that matter for source cooking#

I The exact convex-hull settings accept a point cloud, discard interior points, and document a maximum of 256 resulting hull points. The default hull tolerance is 1e-3 in solver units. These values reinforce the need to convert to meters and to avoid treating millimeter-scale source data as if it were already in Jolt units. J9

7.2 Triangle meshes are surfaces, not automatically solids#

For rigid collision, mesh triangle winding, active edges, and internal-edge removal affect contact. For point-inside queries, Jolt’s narrow-phase documentation says mesh results are sensible only for closed manifold meshes. For soft-body vertex collision, triangle contact uses the nearest triangle and a finite backward thickness rather than a global watertight inside/outside classifier. J11J12J20

8.3 Large coordinates#

Jolt’s query API accepts a base offset specifically to improve float precision far from the origin, and the project supports an optional double-precision position build. For a bounded archviz solve, the lower-cost policy is usually:

  1. choose a local solve origin near the affected batch;
  2. subtract it before float geometry/collision work;
  3. use RVec3/base offsets at the Jolt boundary;
  4. restore world coordinates only when publishing final results.

10. Focused static fitter versus Jolt rods#

10.1 Focused static fitter#

The smallest coherent static solver stores only the state needed by the product:

Guide i:
  rest points        x⁰₀ … x⁰ₙ
  fitted points      x₀ … xₙ
  rest lengths       ℓⱼ = |x⁰ⱼ₊₁ - x⁰ⱼ|
  rest frames        q⁰ⱼ
  contact envelope   rⱼ (or oriented ribbon data)
  root position mode and compliance
  root orientation mode and compliance
  maximum bend / shape-preservation weights

A static iteration minimizes or projects constraints such as:

root position:       x₀ = p_root                          (hard or compliant)
root orientation:    dir(x₀,x₁) ≈ d_root                 (independent stiffness)
segment length:      |xⱼ₊₁ - xⱼ| = ℓⱼ
rest curvature:      relative_frame(qⱼ,qⱼ₊₁) ≈ Ω⁰ⱼ
contact:             distance(capsule(segmentⱼ,rⱼ), obstacle) ≥ clearance
bend limit:          angle(dirⱼ,dirⱼ₊₁) ≤ θ_max

It can use Gauss–Seidel/XPBD-style projections without carrying velocities, gravity, contact impulses, sleep state, or a timeline. The result is a fitted static guide state plus explicit validation.

Advantages

  • Directly matches the first product use case.
  • Whole-segment and visible-envelope contact are first-class.
  • Root position and orientation are explicit independent controls.
  • Cooperative cancellation is straightforward.
  • Multi-contact/infeasibility diagnostics can be designed for artists rather than inherited from a game-time solver.
  • No fork of Jolt soft-body internals is required.

Costs

  • Cyrus owns and tests the constraint loop.
  • Collision query choice must be qualified: own triangle BVH, Jolt capsule query, or optional SDF.
  • Future continuous animation would require adding velocities/timestepping rather than simply replaying a static fit.

10.2 Stock Jolt CPU rods#

Advantages

  • Existing tested rod mechanics and explicit rod orientations.
  • Shared settings and optimized constraint grouping.
  • Natural path toward dynamic wind/moving roots later.
  • Existing integration dependency and job system.

Blocking gaps

  • Vertex-only environment contact.
  • One selected collision plane per vertex.
  • One body-wide vertex radius rather than per-segment blade envelope.
  • Pinned roots skipped by collision.
  • Timeline/fixed-step convergence and temporal state for a static product.
  • Still requires Cyrus guide-to-mesh binding, result extraction, renderer delivery, and Bake.

10.3 Jolt rods plus custom segment contact#

This is the most attractive-looking but highest-maintenance hybrid. A custom obstacle shape alone cannot fix the issue because Shape::CollideSoftBodyVertices receives only a vertex iterator. The public SoftBodyContactListener can accept/reject a body pair and alter mass scales, but it does not supply new rod-segment contacts. J19J21

A correctness-complete implementation would likely need to:

  1. expose rod connectivity to collision generation;
  2. generate capsule/segment contacts against each relevant shape;
  3. store more than one contact where corners/gaps require it;
  4. distribute contact corrections to both segment endpoints and potentially rod rotations;
  5. integrate those contacts into each soft-body iteration, friction, callbacks, and diagnostics;
  6. maintain the fork across Jolt updates.

That is no longer “reuse Jolt rods with a small adapter.” It is a soft-body collision extension.

10.4 Jolt collision queries plus a Cyrus fitter#

This is the most credible selective-reuse option. Build a CapsuleShape for a guide segment, align it to the segment, and call NarrowPhaseQuery::CollideShape with a controlled separation distance and collector. The API returns penetration axis/depth and contact points, and supports a local base offset. J12J13

Questions that must be measured:

  • cost of many small capsule queries versus direct BVH segment-triangle queries;
  • collector behavior at corners and compounds;
  • how many contacts are needed per segment;
  • shape/body locking overhead in an offline worker context;
  • whether a query-only PhysicsSystem complicates cancellation more than it saves in collision code.

11. Smallest experiments that decide the architecture#

These experiments should be standalone C++ fixtures against the exact pin before Max UI or renderer work. They are deliberately small and falsifiable.

E1 — exact-pin build and provenance#

Input: build Jolt and the existing Lab wrapper from SHA 1b2e…; log JPH_VERSION_* and binary hash.

Observe: compiler flags, double/single precision, enabled shape/soft-body modules, job adapter.

Decision: stop if the local binary does not correspond to the inspected source or if local patches affect soft-body collision.

E2 — root anchoring modes#

Input: one curved 8-segment rod, no obstacle. Compare root invMass=0, hard skin-position pin with movable root, and static reference-rod construction.

Measure: root position drift, first-segment orientation drift, length and rest-curvature error.

Decision: document which construction maps to hard/soft position and orientation controls.

E3 — segment-crossing falsification#

Input: one rod with both endpoints outside a sphere/box while the segment crosses it. Repeat with 1, 2, 4, and 8 subdivisions and controlled vertex radius.

Measure: reported contacts and residual segment/capsule penetration.

Decision: if stock rods miss the one-segment case, they are not a correctness-complete contact solution. Subdivision is only an approximation, not a fix.

E4 — deep-inside and pinned-root cases#

Input: dynamic guide entirely inside convex hull; same inside closed mesh; pinned root inside each.

Measure: contact generation, exit direction, strain, unresolved status.

Decision: require a Cyrus preflight/inside policy regardless of chosen solver.

E5 — narrow gap and sharp corner#

Input: guide between two planes/convex stones with gap above, equal to, and below requested diameter; then a 90° corner.

Measure: oscillation, simultaneous contact count, residual penetration, bend limit.

Decision: if single-plane vertex contact cannot stabilize without excessive tessellation, prefer multi-contact fitter.

E6 — Jolt capsule query vs own BVH#

Input: identical segment capsules against analytic, convex, compound, and mesh obstacles.

Measure: contact agreement, query count, cold cooking, warm query time, peak scratch, cancellation latency.

Decision: choose Jolt queries only if they materially reduce implementation risk without unacceptable overhead or lifecycle coupling.

E7 — rigid debris baseline#

Input: 100, 1,000, and 10,000 dynamic convex/compound stones over static irregular terrain.

Measure: steps to sleep, update errors, residual overlap, peak memory, repeatability, final transform capture.

Decision: qualify Case A independently from vegetation.

E8 — static-fit parity and publication#

Input: two instances of one prepared source bending differently around two stones.

Measure: stable IDs, source immutability, guide-to-mesh output, viewport/render/Bake vertex parity, cancellation/stale publication.

Decision: no solver is production-ready until this non-physics delivery gate passes.

12.3 Jobs and cancellation#

  • Rigid Jolt solve: an outer Cyrus job owns the world and calls fixed PhysicsSystem::Update steps. Check cancellation between steps. The exact update call internally schedules jobs and waits until they finish; the public job API does not expose cancellation. J22J26
  • Focused fitter: partition affected instances or independent guide groups. Check cancellation between contact-generation batches and solver iterations. Never publish a partial instance set.
  • Shared thread pool: possible through a Jolt JobSystem adapter, but only after proving that barrier waits cannot deadlock and that nested scheduling does not oversubscribe Cyrus workers.
  • Stale results: compare captured revisions before publication. Discard a completed but stale successor without replacing the previous complete result.

12.4 Completed-result publication#

Both cases should publish immutable result generations:

  • Case A publishes transforms, body status, residual-overlap metrics, and source correspondence.
  • Case B publishes sparse fitted guide states, contact diagnostics, and the source-preparation revision used for guide-to-mesh evaluation.
  • Unchanged instances remain on the existing transform-instanced path.
  • Affected vegetation is evaluated into exact geometry or a qualified compact deformation representation; this remains separate from collision/solver selection.

14. Recommended method by total integration and maintenance cost#

14.1 Case A#

Use Jolt rigid bodies. This is where the existing dependency earns its cost. Share immutable source shapes, simulate dynamic convex/compound bodies over static mesh/heightfield terrain, and capture stable-ID transforms as the completed product result.

14.2 Case B#

Build a focused static fitter first. Reuse the front-end snapshot/unit/transform/cache infrastructure. Benchmark two collision back ends: direct segment/capsule-to-triangle BVH and Jolt capsule queries. Keep the solver and artist diagnostics Cyrus-owned.

14.3 When to reconsider Jolt rods#

Reconsider a Jolt rod integration only when at least one of these becomes a near-term requirement:

  • continuous wind and moving obstacles;
  • temporal inertia and damping are visible product requirements;
  • roots move with animated characters/vehicles;
  • the team is willing to maintain a tested segment-contact extension or upstream it;
  • the focused static fitter demonstrably fails quality gates that Jolt rods pass.

14.4 Explicit rejections#

  • Reject “Jolt is already present, therefore plants are solved.” The mechanics/contact/delivery layers are distinct.
  • Reject dynamic triangle meshes for ordinary pebbles. Use convex or compound-convex bodies.
  • Reject vertex subdivision as a proof of segment collision. It is a sampling approximation whose required density depends on unseen obstacle features.
  • Reject GPU hair for the first static feature. It adds a compute/render subsystem while still leaving Max delivery and product lifecycle unresolved.
  • Reject SDF as a default dependency. Add it only if deep-inside recovery or repeated distance queries justify its preprocessing and memory.

15. Direct answers#

What can be shared between rigid settling and rooted fitting?#

Host-thread geometry capture, stable identities, transform/unit conversion, local solve origins, obstacle/source revisions, immutable collision-shape caches, broad affected-region selection, worker lifecycle, diagnostics framework, cancellation tokens at the outer level, and atomic completed-result publication.

What cannot be shared as-is?#

The rigid contact solver, stock soft-body vertex contact, durable result representation, guide-to-mesh deformation, renderer/Bake delivery, artist feasibility diagnostics, and mid-update cancellation.

Does Jolt 5.6.1 at the pin contain CPU rods?#

Yes. The exact source contains CPU soft-body Cosserat rod constraints and a weed-like sample. The pin is a post-5.6.0 snapshot whose header says 5.6.1, not a publicly tagged 5.6.1 release.

Do those rods collide as capsules or full segments?#

No in the stock CPU soft-body path. Collision receives movable vertices and writes one collision plane per vertex. Whole-segment contact requires a separate query/fitter or a nontrivial Jolt extension.

Can root position and orientation be controlled separately?#

They must be separate product controls. In the stock zero-inverse-mass recipe, the first rod’s rotational inverse mass also becomes zero, effectively hard-clamping orientation. A position-only or softly oriented root needs a different construction and qualification.

What is the smallest useful experiment?#

The segment-crossing fixture: two endpoints outside a stone with the rod passing through it. It immediately distinguishes vertex-only contact from a correct segment/capsule contract.

What should be built first?#

Keep Jolt for rigid debris. For vegetation, implement a bounded static guide fitter with independent root position/orientation constraints, rest-length/rest-curvature preservation, and full segment/envelope contact. Benchmark Jolt collision queries against a Cyrus-owned BVH before selecting the collision back end.

17. Final decision#

Use Jolt where the product problem is rigid-body settling. Reuse its collision infrastructure selectively where that lowers risk. Do not force rooted vegetation into a vertex-contact soft-body path merely because rod constraints exist.

The first vegetation implementation should be a static, sparse, root-preserving guide fitter with whole-segment or visible-envelope contact, explicit infeasibility diagnostics, cooperative cancellation, and immutable completed results. Jolt CPU rods remain a valuable control prototype and a future-animation candidate. They become a production candidate only after the segment, deep-inside, narrow-gap, root, scale, and delivery gates pass.
