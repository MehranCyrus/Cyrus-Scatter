Houdini & tyFlow: Practical Vegetation Workflows

A CyrusScatter companion study: rooted grass, two-stone contact, rigid pebbles and rigid versus deforming leaves
24 October 2026 · Evidence baseline: Houdini 22 / tyFlow 2.101

A reproducible workflow study with exact inputs, node and operator order, separate root-position and root-orientation controls, initialization, reset, caching, rendering, export and instance behavior.

The central distinction is between static guide correction, simulation that runs internally at one evaluated frame, and a timeline simulation whose accepted result is frozen. The report keeps those paths separate and ends with a proposed Cyrus artist workflow.

Section 1

Evidence and version boundaries

This is a practical companion to the previous CyrusScatter vegetation study. It examines four repeatable scene situations in Houdini and tyFlow: rooted grass beside one stone, rooted grass between two stones, rigid pebbles on uneven ground, and fallen leaves at a curb. The leaf case has separate rigid and deforming recipes. It does not repeat the earlier numerical-method survey or infer proprietary algorithms from an interface.

Main finding: Houdini offers a documented static guide-collision operation and a Vellum route that can return a settled pose through an internal roll-forward. tyFlow offers documented binding, cloth and rigid-body simulation components, but its history-independent setting is not a documented equilibrium-fitting command. A held simulation frame is a static deliverable obtained through simulation; that distinction remains visible throughout this report. [S01] [S03] [S54]

Decisions that prevent misleading recipes

  • Root position and root orientation are separate. A fixed point can still be a hinge. Two fixed collinear samples establish a base tangent but leave axial roll unconstrained. A noncollinear fixed patch establishes a base frame; the distinction is geometric, not a claim about a hidden solver.
  • Guide clearance and visible-mesh clearance are separate. A collision-free curve can drive a ribbon whose edges still touch a stone. Inspect the decoded mesh before accepting a pose.
  • Guide deformation is separate from collision solving. H22 Guide Deform's shape-preservation controls do not document an obstacle-contact input. Standard Point Deform explicitly warns about wire-like deformation lattices. For the prepared straight blade, use Path Deform; for an arbitrary bound curved blade, the documented Wire Capture/Wire Deform route needs stable correspondence and frames. [S06] [S13] [S10] [S79]
  • Hair Bind in tyFlow means attachment to Ornatrix strands. It requires Position Hair data. The guide simulation recipe instead uses Particle Bind/Angle Bind; the surface alternative uses Cloth Bind. [S41]
  • Collision shape and render shape are separate. Show the actual rigid hull. A whole terrain convex hull can bridge depressions; a convex leaf proxy can bridge a curled underside. These are shape-choice consequences, not friction problems.
  • A shared source asset does not imply shared deformed output. Rigid instances can reuse geometry while their transforms change. Differently bent blades and leaves generally have different visible vertex positions. The report identifies which documented output modes preserve or flatten the instance representation.

Coordinates and units: use metres and Y-up in Houdini; use centimetres and Z-up in Max. Convert a Houdini point (x, y, z) in metres to Max (100x, -100z, 100y) in centimetres. This is a proper rotation plus scale, preserving handedness. Thus both stone centres have the same physical interpretation. Geometry dimensions match; the native stiffness, damping and gravity controls are not assumed to have matching physical calibration across products.

Set 30 fps for the comparison. tyFlow recipes use frame 0 as their initialization frame. Houdini recipes identify their start explicitly; retain that setting in the scene record rather than silently shifting an example's initialization frame. Record the accepted frame and the actual number of evaluated steps. A nominal 90-frame window is a starting test interval, not a guarantee that an object has settled.

Initialization is part of the recipe

The straight-grass fixture intentionally intersects the final stone above the root. Do not start a dynamic collision test embedded and call any resulting escape a reliable fit. Choose and record one of these initialization branches:

  1. Direct static guide collision: evaluate the final obstacle SDF with the static curve operation. This is the cleanest test of that operation's documented purpose; validate lengths, roots and the visible blade afterward.
  2. Clear initial curve, fixed obstacle: author a collision-free starting curve. In a method with a separate straight/rest-shape target, let that target draw the curve toward the obstacle. The tyFlow Flat angle-target variant explicitly chooses a straight target; it does not preserve arbitrary source curvature.
  3. Conditioned simulation: start the collider clear, move it gradually to its final transform, then hold it fixed and allow settling. This is a timeline-dependent loading history. It can produce a static final image, but is not a demonstration of a stone that was fixed throughout or a history-free static fitter.

For two stones, use both obstacles in the same solve. If conditioning is required, move them without initially intersecting the blade or each other. Repeat with the approach order exchanged to reveal history dependence. A gap narrower than the required blade envelope may prevent passage through that gap, but in three dimensions the blade might escape around the stones; gap width alone does not prove global infeasibility.

Attribute and preparation contract

Every grass blade needs an identified root, an ordered guide, enough mesh segments to bend, and a stable blade-to-guide association. A pivot is not enough to describe a disconnected clump. Keep UVs, material assignments and source IDs before capture. Verify that neighbouring blades do not capture each other's guides.

For Houdini, let the Vellum configuration nodes generate solver attributes and constraints. Inspect P, orient, pin state and collision thickness, and preserve point/primitive correspondence or the documented IDs. Rigid pieces need consistent name association between render geometry and proxies. For tyFlow, retain source/particle identity and explicit custom channels only where the recipe requires them; do not invent a Houdini attribute list for an operator that creates its own particle data.

For a rigid leaf, shading alpha is not a collision cutout. Prepare an appropriate geometric outline or accept the card's collision silhouette. For deforming leaves, an unsegmented plane cannot form a smooth fold. A high-resolution render leaf driven by a low-resolution proxy adds a binding task and a separate final-mesh collision check.

Counting manual work honestly

Counts are numbered artist tasks, not measured clicks or setup time. A task may contain several parameter entries. Section 12 reconciles the listed preparation, configuration, inspection and output tasks; shared output tasks are counted once.

The counts assume the small fixture, not an arbitrary imported production plant. Separating hundreds of blades, selecting roots, repairing scans, assigning per-element IDs or hand-authoring guides can dominate the job. Those operations are described as artist preparation and are never treated as automatic merely because a deformation node exists.

Section 3

Houdini: grass and one stone

Static fitting, a fixed-stone relaxation recipe, and a separately labeled conditioning alternative.

Shared guide-to-mesh decoding

Named Path Deform is the primary proposed route. It is supported by the operator help and the inspected official PathDeformPiece example. Connect the rest strip mesh to input 1 and the fitted/simulated guide to input 2. Enable matching geometry to curves using a piece attribute; use primitive name on both. For multiple blades, ensure every blade mesh has exactly its matching curve. One curve per blade avoids assigning a blade to a nearby neighbor in a tight clump. [S84]

For this fixture: set Forward Direction to Y; set the up direction to Z, which is not parallel to Y. Set the curve up control to a constant Z axis. Set position offset to curve U = 0; use the original geometry length (Fraction of Geo Length = 1), not automatic stretching to the whole curve. Confirm the geometry capture origin and centering put the authored root on the curve start. Set Orient Using Point Attributes off: the curve's Vellum pscale is a collision radius, and leaving all transform attributes enabled can wrongly scale the mesh. For the planar single-stone test this is a simple geometric bend frame. For the mild three-dimensional paths in H2C it remains a proposed geometric frame convention supported by Path Deform's up-axis controls, provided the curve tangent does not approach the chosen up axis. It does not transfer Vellum's material twist. Inspect for frame flips and compare the decoded strip against both obstacles. A physically twisting blade requires an explicitly authored and verified moving frame; material-frame collision fidelity is unvalidated here. Until that frame and final-mesh contact are qualified, H2C establishes a proposed guide test, not an accepted full-frame mesh result.

Precurved/wide assets: Wire Capture input 1 = rest mesh, input 2 = rest wire. Restrict each capture primitive entry to the matching blade mesh subgroup, or process one blade per loop; capture radius covers its width, not neighbors. Wire Deform inputs 1/2/3 = captured mesh/rest wire/deformed wire. Keep rest/deformed wire primitive counts and order stable. Align Tangent And Attrib Normal gives an explicit normal-aware frame; the official TwistWireDeform file authors N and a tangent and uses this mode. The appropriate conversion from a simulated material quaternion to a chosen normal basis must be authored and checked. Do not assume arbitrary orient will map to a blade's intended width axis.

Point Deform exception: it is appropriate with a genuine surface or volume cage, or low-resolution simulated leaf surface. Inputs = render mesh / rest cage / deformed cage, stable connectivity or supported ID mapping, and a piece attribute on both mesh and cage to restrict capture. It is not the recommended decoder for a single line per blade. The explicit warning in its help makes a claimed universal wire-to-mesh Point Deform recipe unsound.

Guide Deform distinction: H22 has a documented dense-groom workflow with sparse simulated guides: dense groom input 1, rest skin 2, animated skin 3, rest guides 4, simulated guides 5. The official Capybara shelf workflow is a grooming example. It does not automatically provide mesh skinning for arbitrary scattered grass assets. The H22 Solaris guide procedural similarly addresses groom data; use a separately documented mesh path for blades. Sources: [S06], [S07], [S10], [S11], [S12], [S13], [S78], [S79].

H1A. Conditioned Vellum Hair alternative

Documentation: [S02], [S03], [S04], [S14], [S15]. Mesh decoding: [S10], with inspected PathDeformPiece association. Output: [S23], [S24], [S25], [S26], [S27], [S28], [S29]. The scene assembly and numerical settings below are P.

Network: rest guides → root group → Vellum Constraints (Hair) → Vellum Constraints (Pin to Target) → Vellum Solver → optional cache → Path Deform with rest blade mesh → freeze/cache/export. The geometry and constraints branches run together from each Vellum Constraints node into the next. The collision stone connects to Solver input 3. There is no glue or attraction to the stone.

  1. Import the rest strip and its 17-point guide, verify scale, root order, and matching primitive name.
  2. Create a roots point group at the first vertex of each guide. The inspected HairOrient file uses vertexprimindex(0, @vtxnum)==0; its context is a Group Expression with point output. For hand-selected single-guide fixtures, selecting the first point is sufficient.
  3. Create Vellum Constraints set to Hair on the entire guide. Use Compute Missing Orientation, Rest Orientation Frame = 1. Proposed trial: uniform point mass 1e-5, uniform thickness/radius pscale = 0.002, Stretch Stiffness 1e6, Bend Stiffness 1, stretch/bend Damping Ratio 0.1. Leave Pin Points empty here so root controls are independently authored downstream.
  4. Create a second Vellum Constraints node set to Pin to Target for roots, feeding both geometry and constraints outputs from step 3. Use Pin Type Stopped, Orientation Pin Type Same as Position, Match Animation off for stationary roots. Leave mass/thickness unchanged on this node. This produces an explicit hard position and orientation test. For a flexible base variant, change only Orientation Pin Type to Soft and its Bend Stiffness to an independently chosen value, such as 10; the position remains hard. The body bend setting remains at step 3.
  5. Import a closed polygonal stone into the same coordinate space. Use initial stone centre (0.30, 0.12, 0) m and key a Transform from that pose at frame 1 to its final pose at frame 31, then hold it through frame 91. Verify the sweep itself does not cut through the pinned root. For a stone fixed from frame 1, use H1C below: it keeps original straight-rest constraints while initializing a different, clear curve. Merely rebuilding rest constraints from a pre-bent curve with gravity zero supplies no load that would bend it toward the stone.
  6. Create Vellum Solver. Connect display geometry to input 1, its matching constraint geometry to input 2, the animated stone polygons to input 3. Use the full solver mode and Dynamic simulation. For H22 select Orientation Solve = Dynamic for this baseline.
  7. Configure the trial: Start Frame 1, Substeps 5, Constraint Iterations 100, collision passes 10 and post-collision passes 5, gravity (0,0,0), no wind. Zero gravity isolates the requested geometric deflection; enabling gravity is a different experiment. Leave other forces at their default neutral values. Set Advanced > Default Thickness to 0.0005 m for colliders without pscale; the guide already has pscale=0.002 m. Their combined 2.5 mm envelope is a conservative proxy for a 3 mm-wide blade with clearance, not botanical thickness. Inspect incoming collider pscale, because it overrides Default Thickness.
  8. Reset Simulation, return to frame 1, and run sequentially to 91. The stone is fixed after frame 31. Increase the hold if the guide is still moving; frame 91 is a trial endpoint, not a guarantee of equilibrium.
  9. Inspect root position and outgoing-root direction separately, compare guide arc length, visualize thickness, and inspect failed external/self-collision markers. Measure the render strip against the stone after decoding as well; a nonpenetrating centreline is not alone a mesh collision guarantee. If several blades are simulated, decide whether inter-blade collision is part of the test; do not claim it if self-collision is disabled.
  10. Create Path Deform as specified in the shared mesh-decoding instructions above, using the simulated curves and original mesh with matching name. Check root registration and frame orientation on one blade before expanding the batch.
  11. Freeze the chosen result with Time Shift at the accepted frame. Save a single .bgeo.sc through File Cache with Time Dependent Cache off. Time Shift by itself is not a disk cache. For restartable simulation, save Vellum geometry and constraints with Vellum I/O, plus the collider animation separately.
  12. Assign/render the deformed polygon geometry, and export the frozen mesh through Alembic or USD. Save the rest asset and guide association alongside it if later updates are required.

Action count: 12 after fixture modeling. The flexible-root variant changes one configuration in step 4. The optional per-piece Wire Capture route adds capture/frame preparation actions and should be reported separately, not hidden in this count.

Root semantics: Stopped sets the positional stop bit without destroying mass. Same as Position also stops orientation. Soft orientation adds a bend/twist target constraint and uses that node's bend parameters. A position-only pin (Orientation Pin Type = None) is a hinge; it does not preserve the outgoing tangent. Orientation pinning the tip does not control the incoming segment. These semantics are documented; the numerical behavior of the proposed material values is untested.

After moving the stone: turn off loading the previous cache, regenerate the clear-to-final motion or valid starting guide, reset/replay from frame 1, evaluate contact and roots again, then write a new cache version. Continuing an old simulation state after a teleport is a different history-dependent experiment. Do not silently carry its velocities and collision-disable state into a new static arrangement.

H1B. Documented static alternative: Guide Collide With VDB

Documentation: [S01], [S09]; mesh decoding [S10]. The native static operation is D, while the complete fixture and acceptance procedure are P.

This route has no timeline simulation. It is a reproducible candidate static fit with an explicit acceptance check, not a verified hard-root elastic workflow.

  1. Import the same rest guide and named straight strip.
  2. Import the stone in its final position; ensure a signed inside/outside representation is valid.
  3. Create VDB from Polygons on the stone, with Distance VDB enabled and a proposed 0.001 m voxel size. Use a signed field, not an unsigned distance volume. If guides are deeply embedded, ensure the interior band covers them; Fill Interior is documented but can increase cost.
  4. Create Guide Collide With VDB. Input 1 = guides; input 4 = obstacle distance VDB. Leave inputs 2 and 3 unconnected and Collide With Skin off for this external-obstacle-only test. The page explicitly documents input 4; it does not enumerate input labels 2 and 3. Their exact names are not independently verified here and are deliberately not invented.
  5. Set Blend 1, Surface Offset 0.0025 m, Push Range 0 and Push Amount 0. Enable Curve Mask; set it to 0 at the root and through the first segment (normalized length 0-0.0625), rising to 1 by 0.15. This requests root-area protection; the documentation does not promise exact root invariance, orientation clamping, length preservation, or feasibility.
  6. Evaluate at the current frame and compare root position, first-segment direction, guide arc length, and collisions to the undeformed reference. A mask is not an accepted substitute for these checks. If hard root invariance is required, a separate explicit restoration of the root point or first two points is possible as authored geometry processing, but may reintroduce stone intersections and is not a documented native collision-plus-root solution. It is outside this minimal count.
  7. Decode through named Path Deform with the settings in the shared mesh-decoding instructions above and validate the actual strip surface.
  8. Save the accepted static result using File Cache with Time Dependent Cache off; cache the accepted guide as well if retaining editability.
  9. Render/export the deformed mesh. Record the mask and VDB resolution with the result.

Action count: 9. Moving the stone recooks the distance field and static operator; no simulation reset is required, but a loaded disk cache must be disabled/replaced. Static fitting avoids a conditioning history but may fail the requested root/length/contact criteria. Do not present failed fits as a supported automatic result.

H1C. Fixed-from-start obstacle: separate straight rest constraints and clear initial geometry

Status: P, supported by D and I; not executed in Houdini. The documented two-stream solver architecture, rest attributes, hair orientation initialization, and the HairOrient example support this construction. HairOrient itself demonstrates deformed input geometry with the original constraint stream, but it does not demonstrate the proposed stone collision. The complete branch must therefore be locally qualified. Sources: [S02], [S03], [S14]; inspected HairOrient example; [S10] for decoding. [S77] [S80]

This branch supplies an actual driving load at zero gravity: the original straight-rest bend constraints act on a different, initially clear curve. Rebuilding the rest constraints from the clear curve would erase that load. A pre-bent rest curve with no external force should not be presented as self-bending around a stone.

  1. Import the original straight 17-point guide and named strip mesh; keep the common point order and persistent blade identity.
  2. Create roots as the first point of each guide.
  3. Build Vellum Constraints set to Hair from the straight source, with H1A's body settings (pscale=0.002, point mass 1e-5, Stretch 1e6, Bend 1, damping 0.1, Compute Missing Orientation, Rest Orientation Frame 1). Leave its Pin Points empty.
  4. Append Pin to Target for roots, keeping mass/thickness unchanged: Stopped position, Same as Position orientation, Match Animation on. Name its geometry output REST_GUIDES_PINNED; preserve its constraint output unchanged as REST_CONSTRAINTS. The soft-orientation variant changes this node's orientation mode and independent Bend setting, not the body-rest stream.
  5. Import the one-stone clear initial coordinates in common_grass_initialization.json as a 17-point curve with precisely the same point order/IDs as the original. These points have the same segment lengths and the first two points remain vertical. They are a proposed fixture, not the result of a Houdini solve.
  6. In a branch from REST_GUIDES_PINNED, copy only P from the clear curve by the unchanged point order/IDs. Preserve names, roots, mass, radius and pin state. Do not change point or primitive count.
  7. Delete stale orient from this initial-geometry branch. Remove/zero any imported velocity or angular-velocity history if the source was previously simulated; this fixture starts from fresh source data with zero v/w.
  8. Append a Vellum Constraints Hair node solely to initialize the now-missing orientations for the clear curve: Compute Missing Orientation on, Rest Orientation Frame 1, Mass and Thickness unchanged, no additional pins. Discard this node's constraint output. Its geometry output supplies correctly initialized hair attributes; it must not replace REST_CONSTRAINTS and make the clear curve the new rest shape.
  9. Copy P, orient and the hard-pin state for the roots group from REST_GUIDES_PINNED back onto the initial-geometry branch. This explicitly preserves the planted root frame. Confirm the first edge is still consistent with that frame; inspect orientations along the remaining curve before solving. A missing or inconsistent orientation is a setup failure, not a collision problem.
  10. Import the stone at its final fixed centre (0.05,0.12,0), radius 0.07 m. Check the clear curve against the actual polygon collider and the combined 2.5 mm envelope. The JSON's sphere-distance arithmetic does not replace this check.
  11. Connect Vellum Solver input 1 = initialized clear geometry, input 2 = original REST_CONSTRAINTS, input 3 = static stone. Use full mode. Set Advanced > Target Path to REST_GUIDES_PINNED so the root target is explicitly the original reference, not a changing initialization branch. Point correspondence must agree.
  12. Choose one recorded evaluation mode. Dynamic variant: Simulation Type Dynamic, Start Frame 1, run 1-91. Frame-local variant: Simulation Type Quasistatic, Quasistatic Frames 90, evaluate the current input frame. For both use Substeps 5, Constraint Iterations 100, collision passes 10, post-collision passes 5, Default Thickness 0.0005 m, gravity zero, no wind, and H22 Orientation Solve Dynamic. Leave Clear Dynamics off during inspection so remaining motion can be examined.
  13. Reset/recook and evaluate. Inspect root location/frame, length, collision flags, remaining motion and visible strip clearance. Increase the internal frame budget or dynamic duration only if the remaining issue is incomplete settling. A contact failure or orientation error is not repaired by calling the result quasistatic.
  14. Decode the named strip with Path Deform, following the shared mesh-decoding instructions above, and check its actual surface against the stone.
  15. Save the accepted result through File Cache as a static output; the Dynamic variant can first use Time Shift at the accepted frame, while the frame-local variant caches the accepted current-frame cook. Preserve the separate rest/initial geometry branches and constraints for updates. Clear Dynamics can be enabled on the published static output after motion acceptance if desired.
  16. Render/export the frozen mesh with the ordinary output checks.

Action count: 16 for either evaluation mode. This is more preparation than static Guide Collide because rest shape, initial shape and material orientation must be kept distinct. Quasistatic hides timeline traversal from the artist, but it still internally runs a simulation for the specified number of frames. It does not guarantee a unique or converged solution.

After moving the stone: recook the actual collider, select or author a clear initial curve for the new arrangement, retain the original straight-rest target, recompute initial orientations and reset/recook. If the new obstacle overlaps the pinned root or no valid allowed shape is found, flag failure. Do not use the previous solved geometry as a new rest state silently. No dependence on the previous result is required by the frame-local mode when these inputs are fixed; the choice of clear starting geometry can still affect the final equilibrium.

Section 4

Houdini: grass between two stones

H2A. Conditioned Vellum Hair with simultaneous contact

Documentation: [S02], [S03], [S04], [S14], [S15], [S18]; mesh decoding [S10]. The complete two-stone scene is P.

This is not a pair of sequential single-obstacle pushes. Both obstacles must participate in the same solve, and their final gap must accommodate the modeled collision envelope. A fixed root can make a geometrically narrow or closed gap infeasible regardless of iterations.

  1. Import rest guide and strip; validate scale, root order, and matching names.

Root position, tangent and frame

These must be separate controls in a Cyrus implementation.

  • Position only: deactivate the first guide particle. Its coordinate remains fixed in the bind solve, but the first segment can pivot around it.
  • Hard tangent: deactivate the first two guide samples. Their relative positions fix the base segment's direction. This is a geometric consequence, not a claim about a hidden rotational solver.
  • Twist/full base frame: two collinear samples still permit rotation of a blade cross-section about their common axis. A noncollinear patch of at least three fixed ribbon vertices gives a full geometric base frame. Cloth Bind can deactivate a base patch by face material ID.
  • Orientation stiffness above a clamp: pinning a base patch is a hard constraint. The flexible transition above it comes from bend/shear stiffness and optionally a stiffness map. Do not describe that map as changing the strength of the fixed pins themselves.

For a rooted plant with a local source frame, store/prepare the source root position and at least a tangent plus cross-section direction. A root height threshold is adequate only for the controlled flat-ground fixture below; it is not a general arbitrary-terrain root discovery algorithm.

Important settings and channels

  • Cloth activation is the primary root constraint. No custom root channel is required for the no-Force conditioning baseline. The optional Force branch explicitly creates rootmask using Cloth Bind's deactivated-particle test condition.
  • Preserve/inherit mesh UVWs. Saving vertex indices to a named custom float channel is available for diagnostics or later correspondence; it is not necessary merely to simulate a blade.
  • Use Mass per-cloth = 1.0 for the proposed starting run if changing subdivision should keep total mass comparable. Mass values are asset calibration, not universal grass parameters.
  • High stretch/shear resistance; a starting stiffness of 1 is a proposed inextensible-looking proxy, with lower bend resistance tuned to the fixture. Volume stiffness is unnecessary for an open ribbon. Disable tearing. Constrained stiffness is less dependent on step count, but the docs only say *somewhat* independent, and it does not change stiffness-1 bindings.
  • Enable CUDA collision solver, Object collisions, and generated cloth mesh. Choose small positive cloth thickness and record it; do not assume the documentation's textual thickness label supplies an exact shell/radius convention. Enable self/inter-cloth collisions only when needed, then add their cost. Self-thickness must stay below the relevant separation of adjacent triangles to avoid self-repulsion.
  • Start the main simulation timestep at 1/4 frame (or 1/8 for tighter/faster contacts) and bind-solver steps at a proposed 20-50 for the small strip; refine until changing them does not materially change the accepted pose. The docs warn dense cloth can require hundreds of steps, so the small-fixture starting range is not a guarantee.
  • CCCS repulsion iterations of 3-5 are documented as often useful; dense layers may need 20-50. Do not blindly raise steps when geometry is impossible or starts intersecting.

Expected result and acceptance

The root patch should remain coincident with its original world-space coordinates; the first free region flexes with bend resistance, and the visible strip itself collides with the stone. Inspect both sides and thin edges, not only the camera-facing silhouette. Accept only after visible motion is negligible over a chosen interval, root error is below the declared tolerance, and no surface intersections remain at the chosen clearance. Those are proposed validation criteria, not a claimed built-in tyFlow convergence test.

Shape and failure distinctions

  • Dynamic Mesh hulls become kinematic: a pebble configured that way does not fall as the artist expects. Use Convex Hull, or a deliberate Compound hull if concavity matters. [S65]
  • A sphere is cheap but rounds the silhouette and contact behaviour. A box is similarly coarse. Show hulls before tuning friction.
  • Compound hull voxel modes can discard excessive voxels when Max voxels is exceeded. This can degrade a collision representation even though the source mesh looks intact. Do not automatically choose an extremely detailed compound. [S65]
  • SDF is optional current functionality, not automatically superior. Accurate SDF contact requires both participants to use SDF; resolution and minimum cell size affect memory and detail. [S65] [S66]
  • Excessive separation may come from hull/contact inflation; exploding overlaps may be eased by velocity limits, but clean initialization is preferred for this recipe. Sticky penetrations are a separate approximation and can sink; do not silently use them as clearance correction. [S65]
  • A change to the collision terrain requires recomputation; editing an exported mesh or moving its cached playback object does not rerun the original settle operation.

If a lower-resolution driver is later used with tyParticleSkin, the driver-to-visible-mesh binding becomes a separate preparation and validation step. The visible skinned leaf can contact the curb differently from its driver; collision of the driver is not automatically proof of high-resolution mesh clearance. Section 7 supplies the tyParticleSkin setup and element-matching limits.

Known failures and documented remedies

  • Initial intersections / collision warnings: start from separate meshes and clean colliders; raise insufficient collision-step limits only after removing impossible geometry. CCCS warns via MAXScript Listener when its limits prevent completion. [S34] [S53]
  • Jitter: lower timestep; inspect oversized thickness; increase repulsion work where necessary. More global frames do not fix an overly large per-step move. [S34]
  • Stretchy leaf despite high stiffness: increase Particle Bind steps; use Constrained mode; inspect topology/density. The official cloth FAQ notes that dense cloth may need hundreds of steps. 40 is merely the proposed fixture baseline. [S59]
  • Self-repulsion: reduce self-thickness relative to mesh spacing; remove sliver/coincident geometry. [S46]
  • Pinned/direct-position movement causes unresolvable contact: do not use a post-initialization position overwrite as an ersatz collision solve. CCCS assumes force/velocity-driven movement; the docs explicitly name position-changing operators as failure causes. [S34]
  • Dense layering never settles / slow impact zones: inspect impossible confinement and budget warnings; reduce timestep, limit leaf count and improve clean separation. Shift+Escape can break heavy CCCS computation, after which refresh/reset is required. [S34] [S53]
  • Farm frames differ: CCCS has no deterministic mode; cache locally and render the cache rather than resimulate on each worker. [S34] [S68]
  • Material visible but no geometry: confirm Generate Cloth Mesh; use correct output flags and shader assignment. Shading opacity has no effect on simulated collision shape. [S46]

Geometry sharing and timeline

Each leaf has its own changing vertex positions; initially identical source leaves no longer generally share one identical deformed mesh. This is a geometric consequence, not an inference about tyFlow's private mesh allocation strategy. tyCache records cloth/deforming mesh data separately from rigid particle transforms. Use Include cloth geo on export. Combining data does not restore instancing; the exporter explicitly says Combine meshes per-frame disables particle instancing. [S62] [S56]

History-dependent evaluation is required for this recipe. History-independent mode is a per-frame reset, not a quasistatic equilibrium solve. Once an accepted frame is cached, a tyCache retimer can hold it without rerunning the solver. Editing the source curb requires reset/re-simulation and a replacement cache; the frozen cache has no live connection to the moved collider. [S54] [S55] [S62]

Geometry sharing and instancing

The original source blade can remain one reusable source asset. Once individual blades bend differently, their render vertices are different. A guide or cloth cache can preserve a compact procedural/deformation representation, but it is not ordinary transform-only instancing of one unchanged mesh. The cited modifier/operator documentation does not establish automatic deduplication of independently deformed blade meshes. Do not assert a private implementation or exact memory multiplier.

Per-blade tyParticleSkin normally means separate deformation results and weight state even if source topology/material is shared. A combined exported mesh explicitly removes particle instancing. A Cyrus optimization could cluster similar deformations and create reusable deformed prototypes; that would be a proposed Cyrus feature, not an existing capability inferred from tyFlow's interface.

  • Cloth surface output: Generate Cloth Mesh explicitly creates the actual cloth surface; At rendertime only controls when. Mesh controls the rendering of particle shape meshes.   • Friction units: PhysX Shape/Collision use coefficients (.6/.5 in the proposal); ordinary Collision is labelled Friction% (50 in the proposal).   • Solver naming: Main Settings > Time step; Particle Bind Solver > Steps; CCCS > Repulse steps/Impulse steps/IZ steps; PhysX > Substeps/Pos iterations/Vel iterations are distinct controls. A historical FAQ's generic max-collision-steps wording is not a new current UI field.

User-saved custom defaults can differ. The full reproducibility manifest must include those values; these notes do not invent undocumented factory numbers.

Per-obstacle-edit task count

For either terrain or curb edits, the explicit Manual-mode update path has 6 tasks: (1) return the editable source scene to its configured start frame; (2) edit the obstacle and inspect its collision representation; (3) Clear Cache/reset; (4) replay and inspect to choose a new accepted frame; (5) export a new completed cache version; (6) point the output loader at that version, hold the accepted frame, and check the render. The recipes are small enough to validate locally before adapting a production vegetation library. Keep the same source and obstacle fixtures while changing one setting at a time. The purpose is to expose what the artist must prepare and what state the software carries between edits.

Minimal local run order

  1. Run a single blade/leaf/pebble before the small repeated set. Display its guide or rigid hull beside the visible geometry.
  2. Test the position anchor and orientation control independently. For a curve, intentionally permit base rotation once; then enable the orientation constraint and verify the difference.
  3. Run the two-stone case with both obstacles participating simultaneously. Compare the result with separate sequential edits, without treating either as a unique physical answer.
  4. Move an obstacle away. Recompute from the declared starting state and confirm that any previous deformation or settled transform is handled according to that method's documented lifecycle.
  5. Hold a frame, close/reopen the scene with the cache, and render it. Then export/reimport the same frame and check the geometric and material data.

What would invalidate a recipe locally

An unknown node version, missing licensed solver path, absent CUDA capability, mismatched topology, missing per-piece correspondence or a collider that cannot be represented as selected is a setup failure. Initial penetration, unresolved contacts, unacceptable strain or a root/frame violation is a geometry/solve failure. A correct viewport pose that changes at render or export is an output failure. Preserve these categories in the test record rather than averaging them into a visual-quality score.

A failure can be informative: a straight sparse guide that leaves a twisted or intersecting ribbon identifies a decoder/frame problem. Increasing collision iterations will not fix an incorrect binding. A pebble floating over a valley represented by a convex hull identifies the collider shape. Increasing friction will not restore the missing valley.

Reusable preparation versus repeated work

Root selection, guide creation, frame convention and mesh binding should be reusable for an unchanged vegetation source. Rebuild them after topology or correspondence changes. Moving a stone normally requires collision/solve recomputation, not rebinding a mesh whose rest topology is unchanged. A cache loaded from disk is a deliberate publication; it does not silently inherit edits to the source obstacle.

Rigid settling has the smallest deformation-preparation burden: suitable closed shapes, separated starting transforms and an accurate terrain collider are enough for the proposed baseline. Deforming leaves require surface topology and thickness decisions. Rooted grass adds root/frame identification and, for the guide route, a second geometry representation plus a decoder. This is the practical difference that a Cyrus workflow should reduce without hiding it.

Record versions, units/fps, topology/IDs, collider shapes, root groups, constraint modes, thickness, solve budgets, initialization branch, accepted frame, cache path and renderer. The following checks are proposed, not executed measurements:

  • Compare root coordinates and base frames; distinguish a single position pin from a full clamp.
  • Check guide segments and decoded mesh edges against every obstacle; measure length/shape change.
  • Move a stone into, out of and across contact; reset from the declared initial state and compare with a fresh setup.
  • Freeze, reopen, render and export/reimport; verify UVs, materials, normals, bounds and instance representation.

Section 14 / Product proposal

Proposed Cyrus artist workflow

This final section is a product proposal informed by the workflow study. It is not a description of an implemented Cyrus feature or a claim about Houdini's or tyFlow's private algorithms.

What the artist selects

The artist selects a Cyrus Scatter layer or a subset of its accepted placements, then chooses an interaction mode: Bend rooted vegetation, Settle rigid objects, or Drape deformable leaves. They add the relevant stones, curb and terrain to an obstacle set; a committed Scatter obstacle layer can be selected as a source of obstacle instances.

For rooted vegetation, the source asset must have a confirmed preparation record: root positions, base frames, blade membership, guides and mesh binding. Cyrus may propose roots from an axis/height rule for a simple source, but it must show that proposal for review. The artist can paint or select a root region, reverse a guide, and preview the base frame. A disconnected clump needs separate blade membership; selecting one object does not justify treating it as one rod.

For rigid objects, the artist previews the collision hull. A simple pebble defaults to a convex hull. Terrain and a curb are fixed triangle obstacles or explicit proxies. For deforming leaves, the artist confirms the segmented surface or driver mesh and sees the simulated thickness. Rigid and deforming leaf modes should visibly differ in preparation, cost and expected behavior.

Keep those controls out of the rooted-grass panel unless they affect its selected method. Most artists should start from a source preset and adjust clearance, flexibility and base stiffness.

What Update does

  1. Validate the selected source preparation and capture the current accepted placements and obstacle geometry.
  2. Find affected placements using both current and previous obstacle influence, including previously bent blades that may now relax.
  3. Start from the declared rest/initial state. Rooted fitting uses the authored source and base frame. Rigid settling and draping use their saved initialization poses unless the artist explicitly chooses a future Continue from current result operation.
  4. Fit or internally settle using the selected method and a bounded work budget. The artist does not need to scrub a timeline merely to obtain a static result.
  5. Validate roots/base frames, visible geometry contact, acceptable deformation and output data. A clean guide alone is insufficient.
  6. Publish a complete result, update the dependency state and show counts of affected, unchanged and failed placements. Keep the previous complete publication available if the attempt is cancelled or cannot be accepted.

An internal settling calculation can legitimately sit behind one Update button. The UI should still identify the result as a settled pose when loading history matters. It should not imply that every mode has a unique history-free answer.

How failures appear

Use a persistent result status and selectable affected IDs. Distinguish Preparation needed, Pending obstacle change, Root inside obstacle, Insufficient mesh resolution, Unresolved contact, Excessive deformation, Work limit reached, Cancelled, and Output unavailable. Highlight the relevant blade, contact region or hull; offer the action that matches the cause.

Examples: a root-inside-stone error selects the root and stone; a binding error shows the influenced vertices and guide; a thin rigid leaf with a poor hull shows the hull overlay; an unresolved two-stone contact selects both obstacles. Do not silently move roots, delete placements, convert a rigid leaf into cloth or label a budget-limited attempt successful.

If a new attempt fails, keep the last complete result visible with an explicit pending/failed status. That geometry may no longer match the moved stone, so it must not be labelled current. The artist can lower a clearance requirement, adjust the obstacle, repair preparation, increase a justified work limit or deliberately accept a visible exception; the application should record which choice was made.

After moving a stone

In Manual mode, the stone moves immediately and the affected vegetation is marked Pending. The previous completed vegetation remains visible until Update. On Update, include the union of the old and new affected regions; grass left behind by the stone must be reconsidered as well as grass at its new position. Fit from the source state so repeated moves do not accumulate accidental bending.

In Live mode, show Pending during the drag, then schedule a bounded update after release. Replace the visible result only when a complete successor is ready. Navigation, selection and unrelated animation should not initiate a new fit.

If the stone is removed, surviving rooted blades should return toward their authored rest shape wherever no remaining obstacle requires a bend. For rigid pebbles or draped leaves, moving/removing an obstacle marks the settled result Pending and requires a fresh declared settling operation; a frozen cache remains a frozen result until explicitly updated.

For an already prepared source, the proposed initial artist sequence is: select layer → choose mode → select obstacles → review preparation/hulls → adjust the few relevant controls → Update → inspect and save. The normal later edit is move stone → Update → inspect. These are product-design targets, not measured click counts or a claim that the preparation work has disappeared.
