1. Recommendation and scope

Retain Jolt’s rigid-body route for stones and debris. For rooted vegetation fitting against fixed stones, start with a focused static fitter that reuses qualified Jolt geometry and collision queries. Treat CPU rods as a competing implementation to test, with its contact adapter included in the comparison. This recommendation concerns total integration and maintenance work; it is not a performance claim.

The inspected pin genuinely supplies rigid dynamics, convex/mesh collision infrastructure, broad-phase queries, soft-body rod constraints, job integration and state machinery. It does not combine those pieces into a ready-made plant fitting system. In particular, the CPU rod obstacle path tests particles. A rod segment can cross a stone while both particles are clear. The executed diagnostic reproduced exactly that situation. Plant preparation, root semantics, material frames, visible blade contact, guide-to-mesh evaluation and host delivery remain separate responsibilities. [QUERY] [CPU_RODS] [SOFT_CONTACT]

The work is deliberately divided into two contracts:

Case Product result Recommended starting point Required success test
A · Rigid stones/debris Stable placement transforms for immutable source meshes Dynamic convex or compound-convex objects against fixed terrain mesh/heightfield Completion plus validated proxy/visible clearance and correct body-origin transform
B · Rooted flexible guides Root-preserving guide positions and material frames, followed by mesh evaluation Static root/rest/length fitting with whole-segment and visible-envelope collision queries Root, length, orientation and final surface checks; explicit infeasible/ambiguous states

Evidence boundary. The public source at the exact SHA was downloaded, compared with the tagged release, built, and exercised in a small headless C++ harness. The supplied statement that Cyrus Physics Lab uses this pin is user context. No private Cyrus checkout, Max plug-in, production renderer, real asset library or GPU hair runtime was inspected or executed. “Reusable” below means a capability and interface can be shared; it does not assert that the private application already has a suitable adapter.

This report continues the earlier vegetation/contact and source-preparation studies at implementation level. It does not infer private algorithms from interface behavior or repeat a general literature survey.

Differences that matter

The local comparison found 47 changed or added files under Jolt/, so the pin is not merely a renamed tag. In the inspected rigid code, mDeterministicSimulation was removed and contact/constraint sorting became unconditional; the warm-start impulse timestep ratio is capped at 4; CCD activation/bounds bookkeeping also changed. Copying settings code from tagged documentation can therefore fail to compile or describe different behavior. [PIN_DIFF]

In the compared CPU soft-body files, the rod/contact algorithms are unchanged from v5.6.0. The motion-properties changes concern a radius assertion and unrelated numeric expressions. The Hair subtree was byte-identical in the extracted comparison. These scoped observations do not establish equality of the whole engine or portability of the probe results to another build.

CPU Cosserat rods and experimental GPU hair are distinct systems. The release notes introduce the former in v5.4.0 and the latter in v5.6.0. A CPU implementation of the compute interface for GPU hair is still that separate hair architecture, not the soft-body CPU rod path. [RELEASES]

The probes use deliberately small, inspectable procedural geometry: a unit sphere; capsules; a closed 12-triangle cube and an open variant; two box walls; and an eight-point convex hull dropped onto a 32-triangle sinusoidal terrain. They test particular contracts, not representative production performance. Source and expected interpretation are embedded so that the results can be challenged and repeated.

What the tests establish

Coverage is a representation issue. The crossing fixture has endpoints at (-2,0,0) and (2,0,0), sphere radius 1, and guide collision radius 0.05. Endpoint plane violations were zero; a whole capsule query found a contact. After ten fixed updates, the stock one-rod setup still crossed the sphere, with only about 6.74 × 10⁻⁷ units of endpoint drift. This minimal rod is intentionally hard-rooted in position and orientation, so it is not a feasible flexible-routing benchmark. Its purpose is to expose the absence of segment contacts; the independent capsule query establishes the overlap. The test does not measure how a sufficiently subdivided, freely bending chain would settle.

Inside/outside needs an explicit policy. A capsule wholly inside the cube touched no triangles and returned no surface contact. A deep interior soft vertex got no collision plane, while a shallow interior vertex did. The closed cube’s exact center returned false from CollidePoint, but an off-axis interior point returned true. The inspected fallback shoots a +Y ray and counts raw triangle hits; the center ray crosses the top face’s shared diagonal. This is a concrete degeneracy consistent with the result, not a reason to discard all mesh occupancy queries. A production solid classifier needs degeneracy handling and an ambiguous result state. [POINT_PARITY] [MESH_SOFT]

Small dimensions need qualification beyond one tolerance slider. The same centered capsule/sphere crossing returned one hit at unit scale and zero at scales 10⁻³ and 10⁻⁵. Lowering mCollisionTolerance proportionally did not change those two outcomes. The geometrical overlap remains evident analytically at all three scales. The exact numerical rejection was not instrumented; do not label it a diagnosed engine defect or infer a universal minimum size. The source has additional absolute degeneracy thresholds in EPA construction, so one scaled public tolerance is not a complete remedy. For a static query adapter, normalize into a qualified local metric and validate the mapped result. Physical rescaling of a dynamic simulation needs broader calibration. [EPA_SCALE] [SCALE]

Sleeping is not a clearance certificate. The rigid hull slept after 66 steps of 1/60 s with no update error bits. A final direct shape query still reported maximum penetration of approximately 4.289 mm, with configured penetration slop of 1 mm. Querying active edges only gave the same value. This is the residual reported by that query and build; it is not a rendered-mesh validation or a general engine accuracy bound. Contact solving uses its contact constraints and correction process; sleep does not run a global final clearance audit. Cyrus must apply its own acceptance test. [CONTACT_CORRECT]

Coordinate handling can preserve or destroy the problem before solving. With double world positions and a matching nearby query base offset, the crossing query hit at both origin 0 and origin 1,000,000. A separate arithmetic probe lost a 0.001 delta when adding it to float 1,000,000; subtracting in double before converting to a local coordinate retained it. These are scoped results, not proof that all far-origin or tiny-geometry cases work.

The proposed boundary is a common geometry/query service and job/result protocol, with distinct rigid and guide solve implementations. The engine’s presence does not remove the need to define those interfaces.

A concrete cache and job contract

Use three immutable layers as a proposed application design:

  1. ObstacleSnapshot: source revision/hash, local geometry, shape type/cooking profile, solid-versus-sheet policy, semantic obstacle ID, local-to-job transform and bounds. Local geometry and instance transform revisions are separate.
  2. SolveRequest: prepared source/profile revision, placements, root policy, collision clearance, length/rest controls, obstacle snapshot IDs, unit/origin contract, method/version, work limits and generation ID. Rest initialization and an optional previous-result warm start are distinguishable modes.
  3. CompletedResult: typed transforms or guide/frame arrays, stable placement/guide IDs, validation metrics, per-item status, input signature and solver/build provenance. No mutable engine handles cross this boundary.

Cache keys must include convex rounding, hull tolerance/decomposition revision, collision role, topology/winding, baked nonuniform scale and units. Material or UV edits need not recook a geometric collider, but may invalidate a delivered mesh/profile fingerprint. A rigid stone move can reuse its local cooked shape while rebuilding the affected query instances. A topology or proxy edit requires new cooking. Do not mutate a cached shape while another job is reading it. ShapeSettings caching and shape sharing are engine facilities; this whole application invalidation policy is new integration work. [SHAPE] [HEIGHTFIELD]

PhysicsSystem::Update waits for its scheduled work before returning and has no cancellation-token parameter. Keep calls bounded, cancel between them, and release worlds only after their users finish. Check capacity errors: the documented error bits explicitly mean some body pairs or contacts were ignored. A visually plausible result with those errors is incomplete. Concavity, thin geometry and contact meaning

A closed convex proxy supplies a volume and a natural separating contact. A triangle mesh supplies oriented surfaces; a closed-mesh point query is a separate parity operation. The latter reports occupancy rather than a complete escape path for a blade. The shallow/deep cube test demonstrates why triangle contact and solid membership cannot be interchanged. [MESH] [POINT_PARITY] [MESH_SOFT]

For an open terrain sheet, define “stay on the front side” or a two-sided exclusion shell; do not label the empty half-space below it “inside a stone.” For an open stone scan intended to be solid, require a validated closed collision proxy or field preparation. Automatic hole filling is a geometry alteration and needs a reviewed proxy. In narrow gaps, the proxy’s error budget must be smaller than the gap clearance the artist expects.

Thin rendered cards have area and may have two visible sides, but no physically meaningful thickness until the application supplies one. A blade can clear a stone at its centerline and intersect along its edge. The executed width fixture has a clear center capsule at Y=1.08 and an offset edge at Y=0.92 against a unit sphere; the edge capsule collides. A large circular radius covering the entire ribbon is conservative and may wrongly block a narrow slot that an oriented ribbon could traverse. Start with a documented envelope contract, then refine to swept ribbon samples/triangles where that conservatism is unacceptable.

What adding an SDF actually entails

A proposed field backend needs a watertight-solid or explicit sheet contract; reliable sign classification; voxel/representation resolution; a distance error bound or measured bound; world/local transform treatment; gradient behavior near medial axes and sharp corners; cache keys; out-of-band behavior; and a fallback/ambiguous status. Converting an SDF into a Jolt custom shape additionally needs dispatch/casts against every required partner and the relevant soft-body behavior. Implementing a virtual Shape is not sufficient by itself. [CUSTOM_SHAPE]

For a true signed-distance function with Lipschitz constant 1, a segment sampled with maximum spacing h has a conservative distance lower bound of the minimum sample distance minus h/2; include the field’s worst-case distance error as another subtraction. Thus requiring every sample to exceed radius + requested clearance + h/2 + field error can certify that sampled straight segment under those assumptions. This is a mathematical bound, not an executed SDF implementation. An unqualified trilinear field, unknown sign or unbounded narrow-band extrapolation does not earn that guarantee. Surface samples alone also need a bound between samples for a wide blade.

Use an SDF when repeated qualified distance queries justify the preparation, memory and error-policy cost. Begin with Jolt primitives/hulls and mesh queries for the smallest implementation unless test evidence shows a field substantially simplifies difficult static contacts. No field-build or query benchmark was performed here.

6. Units, margins and large coordinates

The engine uses a right-handed Y-up SI convention in its documentation. A Max integration can convert axes or choose corresponding gravity, but must specify metres/radians/seconds consistently. The documented preferred size ranges are operating guidance, not hard limits. The tiny-scale fixture establishes that a small positive shape dimension alone does not guarantee an accurate query. For queries, subtract a nearby origin in double precision before conversion into local float geometry. Supply the query’s base offset consistently; returned contact positions are relative to it. Double world positions do not make shape geometry, local contacts or every broad-phase calculation double precision. Use islands or bounded regions where appropriate, and include origin/basis/scale in the result metadata. [QUERY] [SCALE] [TRANSFORMS]

Nonuniform scale and shear must be tested against each shape’s documented scaling support. A capsule’s local axis is Y; its cylinder half-height is half the endpoint distance. Its valid scale requires uniform absolute components. Do not stretch a cached capsule in Y to represent arbitrary changing rod lengths. Construct the correct radius/half-height and transform, or implement and qualify a different query adapter. Mirroring additionally affects handedness and triangle winding. [CAPSULE]

A static fitter can normalize geometry and requested distances into a qualified numerical domain, perform geometric queries, then convert results back. A dynamic simulation also contains gravity, time, velocities, density/mass, inertia, compliance and damping; rescaling only vertices changes the physical problem. A unit policy must be tested through the complete rigid/rod setup rather than advertised as a universal precision switch.

7. Case A: a reproducible rigid-settling route

Executed minimal example Production integration recipe

Inputs and preparation

Supply the immutable source render mesh, a convex or approved compound-convex collision proxy for each moving debris type, fixed terrain geometry, source-to-proxy transform, host units, initial placement transforms and a collision profile. A mesh terrain needs consistent winding and meaningful scale; a heightfield is suitable only when the terrain fits that representation. Preserve source materials, UVs and smoothing information independently of the collision mesh. [MESH] [HULL]

The executable uses one convex hull, not a production pebble scan. Its eight input points form a rectangular cuboid and span approximately 0.41 × 0.30 × 0.35 m and use convex radius 0.01 m. The 32 terrain triangles span X/Z ±2 m with heights 0.10 sin(1.3x) cos(0.9z). The hull’s body origin starts at Y=1.5 m (distinct from its COM), with rotation (0.2, 0.35, 0.13) radians in the authored Euler call, friction 0.6 and restitution 0. It steps at 1/60 s with gravity −9.81 along Y and stops at sleep or 600 updates. The embedded C++ source is authoritative for exact construction order and parameters.

API and action order

  1. Snapshot and preflight. Convert geometry into a bounded local metric; validate nondegenerate triangles, proxy role, initial overlaps and host-to-proxy/COM mapping. Keep initial transforms as the reset state.
  2. Cook immutable shapes. Create MeshShapeSettings/compatible terrain representation and ConvexHullShapeSettings or compound children; check every ShapeResult. Reuse shapes for repeated geometry while each placement has its own body state.
  3. Create the world and filters. Initialize PhysicsSystem, layer filters, capacity limits, allocator and job system. Fixed terrain uses EMotionType::Static; moving debris uses Dynamic. Disable unneeded interactions through explicit filters.
  4. Configure bodies and solver profile. Set friction, restitution, mass/inertia policy, activity and initial velocities. Set tested slop, speculative distance and iteration/step settings in physical units. Select LinearCast only where translational CCD is needed and qualified.
  5. Add bodies and settle. Add fixed geometry, add/activate debris, optimize broad phase when appropriate, then perform bounded fixed-duration Update calls. Record update error bits, maximum work, activity and residual motion.
  6. Validate completed geometry. Check surface/solid overlap, initial-containment failures, proxy-to-visible error and supported collision pairs. Sleeping and no error bits are necessary observations, not the acceptance test by themselves.
  7. Publish placement transforms. Convert body-origin transforms back to the host and preserve source scale/pivot bookkeeping. If reading COM transforms, apply the shape COM offset correctly. Commit only if the input generation still matches.
  8. Freeze or reset. Save validated transforms and provenance as the frozen result. Reset by recreating or deliberately restoring the canonical initial world/state; obstacle changes invalidate dependent results and trigger a fresh bounded solve or an explicitly chosen continuation.

The official HelloWorld lifecycle and dynamic-mesh sample are inspectable reference implementations; the harness is the executed minimal variant. The production sequence above remains a proposed Cyrus integration. [LIFECYCLE] [BODY_CREATE] [UPDATE] [DYNAMIC_MESH]

Initialization, collision failure and export

Start from a feasible spawn region where possible. Initial deep overlap is not equivalent to a small contact correction: a shape entirely enclosed by a triangle shell may generate no surface contact, and a convex solver’s depenetration can still be incompatible with surrounding objects. Preflight occupancy and available escape space; report an invalid start rather than silently baking a trapped object.

For fast small debris, translational LinearCast, smaller steps and tested capacity/iteration settings can address the documented classes of missed or unstable contacts. LinearCast is not a promise of complete rotational CCD. For internal triangle-edge artifacts, consistent topology and documented active-edge/enhanced internal-edge handling are relevant; blindly treating every triangle edge as a barrier changes the result. For bad proxy gaps, no solver setting repairs the wrong geometry. [CCD_EDGES] [UPDATE_ERRORS]

Rigid placement changes can retain source mesh sharing and renderer instancing because vertex coordinates relative to the source are unchanged. Bake can write placement transforms or instantiate native objects that reference the same source. This is a product adapter opportunity, not a Jolt render/export service. Test a source whose visible pivot differs from its center of mass; using COM as the host pivot without correction gives incorrect delivery. [TRANSFORMS]

Rest curvature, length, width and twist

CalculateRodProperties() computes lengths and transported frames from rest positions, then stores relative frame orientations. A curved guide therefore has a curved rest state. The constraint residual for stretch/shear is based on x1 − x0 − length × rotated_Z_axis; it couples particle and rod-frame corrections. Finite compliance, finite work and competing contact constraints can leave residual length or frame error. Exact inextensibility is not an unconditional outcome. [CALC_RODS] [ROD_SOLVE]

The first perpendicular frame is a mathematical choice. It does not infer a blade’s width direction, authored twist, UV seam or thickness. Preserve those in the prepared source profile and feed them through the canonical guide-to-mesh evaluator. A proposed authored-frame adapter should first calculate ordinary rod properties, then replace validated rest material frames consistently and recompute every corresponding mOmega0. Do not prefill just mBishop and assume calculation still computes all derived fields: initialized frames can skip parts of that work. Fresh settings are safer after rest-geometry edits. [CALC_RODS]

Calculation can reverse endpoint order; Optimize() can reorder rod constraints and provides remaps. Bindings must refer to semantic guide/segment IDs mapped into current solver indices. Persisting “vertex 8 of rod 12” without a source revision and remap contract is not a reusable plant binding. 9. The missing contact contract

What the stock CPU path does

The soft-body motion-properties implementation gathers candidate shapes and calls their CollideSoftBodyVertices function with a vertex iterator. Each vertex retains one winning collision plane/shape index, selected by penetration. The later collision solver corrects the particle against that plane and applies the associated response. Rod constraints are solved in the same soft body, but the contact pass does not receive rod edges as capsules. Increasing vertex radius thickens those particle tests, not the intervals between them. [SOFT_CONTACT] [VERTEX_PLANE]

Within each world collision step—or one CustomUpdate call—collision planes are determined before integration and reused across the soft body’s mNumIterations substeps. The world’s separate inCollisionSteps setting rebuilds the soft-body update context per collision step. More soft-body iterations do not automatically refresh collision geometry, introduce additional simultaneous planes, detect deep mesh containment, or cover previously untested segments. Smaller world collision steps or a deliberate contact-refresh integration can address applicable dynamic error; use the correct geometry representation for missing coverage. [ROD_SCHEDULE]

Fixed inverse-mass-zero vertices are skipped in the inspected sphere and mesh contact passes. The executed root-inside-sphere test found occupancy but no fixed-root collision plane. This is a feasibility problem: if the product promises both an unchanged root and clearance from a stone enclosing it, the constraints conflict. Offer an explicit artist action such as relocating the placement, choosing a different source, allowing root movement, or excluding the obstructed placement. Do not silently unpin it. [SPHERE_SOFT] [MESH_SOFT]

Whole-segment queries are available; a rod contact solver is not supplied by them

For endpoints a,b, construct a capsule with cylinder half-height |b−a|/2, midpoint (a+b)/2, Y-axis rotated toward b−a, and tested radius. Query fixed obstacles through NarrowPhaseQuery::CollideShape or direct dispatch. Include the artist clearance through a declared envelope/separation policy, accounting for query tolerance. Zero-length segments require explicit rejection or a sphere fallback. [CAPSULE] [QUERY]

CollideShapeResult defines its penetration axis in the direction that moves shape 2 out. When the query capsule is shape 1 and the obstacle shape 2, the corresponding capsule translation points along the negative normalized axis. With positive maximum separation distance, nearby results can have negative penetration depth. Test signs and coordinate offsets with a known primitive; do not silently treat a nearby-contact query as an exact global signed-distance oracle. [CONTACT_RESULT]

A capsule represents an entire straight segment at its current pose. That is spatial coverage, not continuous coverage throughout a moving/deforming timestep. A final-pose static operation may allow intermediate iterates to cross a solid, provided its completed geometry passes the full contact/occupancy contract. Continuous clearance during deformation is an additional requirement when the artist expects motion continuity or preservation of a route around obstacles. A rigid translation shape cast does not represent arbitrary endpoint deformation or rotation of a ribbon. For that additional contract, use bounded steps, conservative subdivision and/or a qualified swept-deformation test; both modes require a final validator. [SHAPE_CAST]

For a deformable segment, one query result must become constraints on endpoint and possibly material-frame degrees of freedom. The application must choose a contact location along the segment, distribute corrections consistently, preserve hard roots, re-enforce length/rest constraints and handle multiple obstacles at once. A sphere/capsule penetration vector cannot simply be copied onto both vertices and assumed to preserve the rod model. Narrow gaps need simultaneous constraints or a convergent active-set/projection policy, plus a stalled/infeasible outcome.

10. A focused static fitter: proposed minimum architecture

This section is a design proposal, not an executed solver. Its advantage is alignment with a single artist operation: find a valid nearby shape against fixed obstacles and keep the source’s intended appearance. It does not remove nonlinear optimization, difficult geometry or feasibility work.

State and objective

Store guide nodes x, material frames q, immutable rest nodes/frames, rest segment lengths and root transforms. Use hard root-position constraints. Make root orientation a separate hard/free/finite-restoring policy. Fit all constraints to one explicit clearance envelope and source profile.

A minimal objective can combine deviation from rest shape, changes in neighboring material-frame rotation, and a root-orientation penalty. Enforce segment lengths exactly within a declared tolerance, or use a controlled length compliance whose error is reported. An artistic “bend resistance” can map to these relative weights; do not label it a physical elastic modulus unless geometry, units and a calibrated constitutive mapping support that meaning. A dynamic interpretation additionally needs mass and time calibration.

For each segment or final surface element, impose a clearance inequality against obstacles. The practical formulation is nonconvex, especially around two stones: there may be several routes, a locally stuck state or no feasible shape at the permitted length/root stiffness. “No progress” is a solver status, not proof of global infeasibility. Distinguish confirmed local contradictions, such as a pinned root inside the required solid exclusion zone, from an iteration limit.

Proposed fitting loop

  1. Validate prepared guides, finite nonzero segment lengths, root frames, units, source revision and obstacle solid/sheet policy. Detect rooted points inside exclusion volumes before iteration.
  2. Build/query nearby obstacles using cached Jolt shapes. Start from canonical rest or an explicitly selected valid warm start. Classify entire-inside cases separately from surface contact.
  3. Generate whole-segment contacts and any wider-ribbon envelope contacts. Keep multiple relevant obstacles/features; store semantic guide/segment/contact IDs.
  4. Apply constrained corrections with length, root-position, root-orientation and rest-shape terms. Bound the step; refresh candidate geometry after changes. Use deterministic ordering within a defined build/profile if repeatability is required.
  5. Adaptively subdivide a guide or refine surface checks where curvature, obstacle detail or width makes the current representation inadequate. Keep binding interpolation and new-node identity explicit.
  6. Run an independent final validator on the delivered surface/envelope, roots, length and frames. Stop at accepted tolerance, a diagnosed contradiction, stall, cancellation or work limit.
  7. Publish a completed result and diagnostics atomically. Preserve the previous completed output on cancellation or failed replacement; display its stale state clearly.

Prefer a limited first supported contract: fixed closed convex/compound stones, prepared nonbranching guide chains, a qualified scale range, a declared circular or ribbon envelope, explicit root policies and no claim of two-way dynamics. Triangle obstacles can enter once occupancy/sheet semantics and inside cases pass. This narrows the engineering surface without pretending it solves every scanned asset.

The fitter still owns difficult choices: contact-step control, alternative routes around obstacles, infeasibility, sharp normals, refinement and final validation. Its maintenance advantage is conditional: it can use public queries without editing Jolt’s soft-body solver, and it avoids dynamic state, friction history and partial rod resets when those are not product requirements. If the required static model becomes a full anisotropic rod mechanics system with robust dynamics, reassess the choice against the actual CPU-rod adapter rather than continuing by inertia.

13. Why experimental GPU hair does not close the gap

The exact Hair API is a work-in-progress compute subsystem with HairSettings, shaders, compute buffers and queues. It supports simulation and render/follow hairs and scalp-related preparation. Its header lists limitations including general collision-shape support and several simulation/rendering features. None of these APIs should be inferred from the availability of CPU rigid bodies or soft-body rods. [HAIR] [RELEASES]

Although hair updates consult a PhysicsSystem for obstacle discovery, the inspected packing code flattens compounds and accepts only convex-hull leaves for collision data. Support for spheres, capsules, boxes, triangle terrain or heightfields elsewhere in Jolt does not establish support in this path. A supported compound must consist of accepted hull leaves. [HAIR_PACK]

The collision shader is also per non-root vertex and keeps one deepest winning plane. It does not demonstrate whole-segment capsule coverage or collision of a wide rendered blade. Thus switching to this subsystem would retain the central coverage question while adding compute/output integration. The header’s readback function is described as a debugging facility; it is not evidence of a qualified Max viewport/renderer/Bake bridge. 14. Proposed artist operation and completion contract

The artist selects a prepared source/profile, placements and obstacle objects. The UI distinguishes Rigid settle from Rooted fit. For rooted fitting, expose root-position lock separately from root-orientation policy; rest/bend resistance; allowed stretch or length tolerance; visible-envelope clearance; obstacle solid/sheet policy; and quality/work limit. Show the chosen profile’s supported scale and unresolved preparation requirements. Keep numeric engine tolerances in an advanced diagnostic profile rather than presenting a single misleading “margin” control.

Update captures a new immutable generation, resolves units and shapes, runs preflight, fits or settles in the background, evaluates the canonical output geometry, validates it and atomically publishes the completed result. A hidden bounded simulation is allowed for a rod mode; it should not require the artist to scrub a timeline just to update a fixed-obstacle fit. The method and initialization mode remain in result metadata.

Failures appear on the affected placement/guide and in a concise list: root inside obstacle; solid sign ambiguous; unsupported scale/transform; whole segment or visible edge still intersecting; blocked gap; length/rest error; work limit/stall; contact-capacity error; stale source binding. Show the problematic geometry and measured residual in scene units. Preserve the last completed output with a visible stale marker until a replacement succeeds; never silently replace it with a partial or collision-invalid result.

After a stone moves, invalidate placements influenced by both its old and new regions, expanded by guide reach/clearance and any solver dependency region. Recompute from canonical rest by default so grass can relax back when the obstruction is removed. Reuse unchanged local shape cooking; rebuild/update transformed query instances safely. If cross-guide contacts or rigid stacks couple placements, invalidate their connected dependency region as well. Pure local independent fitting can be narrower than a coupled simulation.

Freeze records a completed, validated geometry/transform result and its source/obstacle signatures. Define whether a frozen result intentionally ignores subsequent obstacle edits; if so, mark the dependency change rather than implying continued physical validity. Bake emits the same evaluated output used for viewport and rendering, with source materials, normals/tangents, bounds and stable picking/placement identity handled by the geometry-delivery adapter. Neither operation mutates the original vegetation source.

Rigid instances can keep sharing geometry. Flexible outputs share immutable source/binding data but generally have distinct evaluated vertices; batching reduces submission overhead, not the uniqueness of those vertices. Explicit variants can share identical fitted geometry, with an approximation/clearance policy if reuse spans different obstacle contexts. These are application decisions; the collision engine does not implement them.

 747  
 748  Note that the physics simulation works best if you use SI units (meters, radians, seconds, kg).  750  # Big Worlds {#big-worlds}
 751  
 752  By default the library compiles using floats. This means that the simulation gets less accurate the further you go from the origin. If all simulation takes place within roughly 5 km from the origin, floating point precision is accurate enough.
 753  
 754  If you have a bigger world, you may want to compile the library using the JPH_DOUBLE_PRECISION define. When you do this, all positions will be stored as doubles, which will make the simulation accurate even at thousands of kilometers away from the origin.
 755  
 756  Calculations with doubles are much slower than calculations with floats. A naive implementation that changes all calculations to doubles has been measured to run more than 2x slower than the same calculations using floats. Because of this, Jolt Physics will only use doubles where necessary and drop down to floats as soon as possible. In order to do this, many of the collision query functions will need a 'base offset'. All collision results will be returned as floats relative to this base offset. By choosing the base offset wisely (i.e. close to where collision results are expected) the results will be accurate. Make sure your base offset is not kilometers away from the collision result.
 757  
 758  Keep in mind that:
 759  
 760  * There are a lot of 'epsilons' in the code that have been tuned for objects of sizes/speeds as described in the @ref conventions-and-limits section. Try to keep the individual objects to the specified scale even if they're really far from the origin.
 761  * When the collision results of a single query are kilometers apart, precision will suffer as they will be far away from the 'base offset'.
 762  * The effectiveness of the broad phase (which works in floats) will become less at large distances from the origin, e.g. at 10000 km from the origin, the resolution of the broad phase is reduced to 1 m which means that everything that's closer than 1 m will be considered colliding. This will not impact the quality of the simulation but it will result in extra collision tests in the narrow phase so will hurt performance.

 367

 369  
 370    JPH::Shape::ShapeResult my_scaled_shape = my_non_scaled_shape->ScaleShape(JPH::Vec3(x_scale, y_scale, z_scale));

 375  Updating scaling after a body is created is also possible, but should be done with care. Imagine a sphere in a pipe, scaling the sphere so that it becomes bigger than the pipe creates an impossible situation as there is no way to resolve the collision anymore.
 376  Please take a look at the [DynamicScaledShape](https://github.com/jrouwe/JoltPhysics/blob/master/Samples/Tests/ScaledShapes/DynamicScaledShape.cpp) demo. The reason that no ScaledShape::SetScale function exists is to ensure thread safety when collision queries are being executed while shapes are modified.
 377  
 378  Note that there are many functions that take a scale in Jolt (e.g. CollisionDispatch::sCollideShapeVsShape), usually the shape is scaled relative to its center of mass. The Shape::ScaleShape function scales the shape relative to the origin of the shape.

 381  
 382  If the defined Shape classes are not sufficient, or if your application can make a more efficient implementation because it has specific domain knowledge, it is possible to create a custom collision shape:
 383  
 384  * Derive a new class from Shape (e.g. MyShape). If your shape is convex you can consider deriving from ConvexShape, if it contains multiple sub shapes you can derive from CompoundShape or if it wraps a single other shape it can be derived from DecoratedShape.
 385  * Create a settings class that configures your shape (e.g. MyShapeSettings) and inherit it from the corresponding settings class (e.g. ShapeSettings, CompoundShapeSettings or DecoratedShapeSettings).
 386  * Override the ```MyShapeSettings::Create``` function to construct an instance of MyShape.
 387  * If you want to serialize the settings class, register it with the factory: ```Factory::sInstance->Register(RTTI_OF(MyShapeSettings))```

 391  * Implement the virtual functions that your selected base class exposes. Some functions could be implemented as a dummy if you don't care about the functionality, e.g. if you don't care about buoyancy then GetSubmergedVolume does not need to be implemented.
 392  * Create a ```MyShape::sRegister()``` function to register all collision functions, make sure you call this function after calling ```RegisterTypes()```, see [MeshShape::sRegister](@ref MeshShape::sRegister) for an example.
 393  * Now write collision detection functions to test collision with all other shape types that this shape could collide with and register them with [CollisionDispatch::sRegisterCollideShape](@ref CollisionDispatch::sRegisterCollideShape) and [CollisionDispatch::sRegisterCastShape](@ref CollisionDispatch::sRegisterCastShape).  669  ## Continuous Collision Detection {#continuous-collision-detection}
 670  
 671  Each body has a motion quality setting ([EMotionQuality](@ref EMotionQuality)). By default the motion quality is [Discrete](@ref EMotionQuality::Discrete). This means that at the beginning of each simulation step we will perform collision detection and if no collision is found, the body is free to move according to its velocity. This usually works fine for big or slow moving objects. Fast and small objects can easily 'tunnel' through thin objects because they can completely move through them in a single time step. For these objects there is the motion quality [LinearCast](@ref EMotionQuality::LinearCast). Objects that have this motion quality setting will do the same collision detection at the beginning of the simulation step, but once their new position is known, they will do an additional CastShape to check for any collisions that may have been missed. If this is the case, the object is placed back to where the collision occurred and will remain there until the next time step. This is called 'time stealing' and has the disadvantage that an object may appear to move much slower for a single time step and then speed up again. The alternative, back stepping the entire simulation, is computationally heavy so was not implemented.
 672  
 673  ![With the Discrete motion quality the blue object tunnels through the green object in a single time step. With motion quality LinearCast it doesn't.](Images/MotionQuality.jpg)

 679  ## Ghost Collisions {#ghost-collisions}
 680  
 681  A ghost collision can occur when a body slides over another body and hits an internal edge of that body. The most common case is where a body hits an edge of a triangle in a mesh shape but it can also happen on 2 box shapes as shown below.
 682  
 683  ![A blue box sliding over 2 green boxes. Because the blue box can sink into the green box a little bit, it can hit the edge between the two boxes. This will cause the box to stop or jump up.](Images/GhostCollision.jpg)
 684  
 685  There are a couple of ways to avoid ghost collisions in Jolt. MeshShape and HeightFieldShape keep track of active edges during construction.
 686  
 687  ![An inactive edge (concave) and an active edge (convex, angle > threshold angle).](Images/ActiveEdge.jpg)
 688  
 689  Whenever a body hits an inactive edge, the contact normal is the face normal. When it hits an active edge, it can be somewhere in between the connecting face normals so the movement of the body is impeded in the scenario below.
 690  
 691  ![Contact normal (red) of hitting an active vs an inactive edge.](Images/ActiveVsInactiveContactNormal.jpg)
 692  
 693  By tweaking MeshShapeSettings::mActiveEdgeCosThresholdAngle or HeightFieldShapeSettings::mActiveEdgeCosThresholdAngle you can determine the angle at which an edge is considered an active edge. By default this is 5 degrees, making this bigger reduces the amount of ghost collisions but can create simulation artifacts if you hit the edge straight on.
 694  
 695  To further reduce ghost collisions, you can turn on BodyCreationSettings::mEnhancedInternalEdgeRemoval. When enabling this setting, additional checks will be made at run-time to detect if an edge is active or inactive, this only works if:
 696  * Edges between shapes are shared. For example, if the 2 green boxes above have different sizes in the direction of the edge, ghost collisions can still occur. In the same way, triangles connected so that they form a T-edge can also cause ghost collisions.
 697  * Shared edges need to be part of the same shape. So if the two green boxes above belong to two different bodies, the ghost collision can still occur. Use a StaticCompoundShape to combine the green boxes in a single body to allow the system to eliminate ghost collisions between the blue box and the two green boxes.
 698  
 699  You can also use this functionality for your custom collision tests by making use of InternalEdgeRemovingCollector.

 838  # Rolling Back a Simulation {#rolling-back-a-simulation}
 839  
 840  When synchronizing two simulations via a network, it is possible that a change that needed to be applied at frame N is received at frame N + M. This will require rolling back the simulation to the state of frame N and repeating the simulation with the new inputs. This can be implemented by saving the physics state using [SaveState](@ref PhysicsSystem::SaveState) at every frame. To roll back, call [RestoreState](@ref PhysicsSystem::RestoreState) with the state at frame N. SaveState only records the state that the physics engine modifies during its update step (positions, velocities etc.), so if you change anything else you need to restore this yourself. E.g. if you did a [SetFriction](@ref Body::SetFriction) on frame N + 2 then, when rewinding, you need to restore the friction to what is was on frame N and update it again on frame N + 2 when you replay. If you start adding/removing objects (e.g. bodies or constraints) during these frames, the RestoreState function will not work. If you added a body on frame N + 1, you'll need to remove it when rewinding and then add it back on frame N + 1 again (with the proper initial position/velocity etc. because it won't be contained in the snapshot at frame N). The [SaveState](@ref PhysicsSystem::SaveState) function comes with a StateRecorderFilter interface that you can use to selectively save state. E.g. [ShouldSaveBody](@ref StateRecorderFilter::ShouldSaveBody) could simply return false for all static or inactive bodies which can be used to limit the size of the snapshot.
 841  
 842  If you wish to share saved state between server and client, you need to ensure that all APIs that modify the state of the world are called in the exact same order. So if the client creates physics objects for player 1 then 2 and the server creates the objects for 2 then 1 you already have a problem (the body IDs will be different, which will render the save state snapshots incompatible). When rolling back a simulation, you'll also need to ensure that the BodyIDs are kept the same, so you need to remove/add the body from/to the physics system instead of destroy/re-create them or you need to create bodies with the same ID on both sides using [BodyInterface::CreateBodyWithID](@ref BodyInterface::CreateBodyWithID).

 154  
 155  If you're only accessing the physics system from a single thread, you can use Body pointers instead of BodyID's. In this case you can also use the non-locking variant of the body interface.
 156  
 157  Note that there are still some restrictions:
 158  
 159  * You cannot read from / write to bodies or constraints while PhysicsSystem::Update is running. As soon as the Update starts, all body / constraint mutexes are locked.
 160  * Collision callbacks (see ContactListener, SoftBodyContactListener) are called from within the PhysicsSystem::Update call from multiple threads. You can only read the body data during a callback.
 161  * Activation callbacks (see BodyActivationListener) are called in the same way. Again you should only read the body during the callback and not make any modifications.
 162  * Step callbacks (see PhysicsStepListener) are also called from PhysicsSystem::Update from multiple threads. You're responsible for making sure that there are no race conditions. In a step listener you can read/write bodies or constraints but you cannot add/remove them.
 163

E.g. if there is a clear owner of a Body and you ensure that this owner does not read/write state during PhysicsSystem::Update or while other threads are reading the Body there will not be any race conditions.
