1 CyrusScatter Vegetation–Obstacle Interaction

1.1 Engineering research, architecture evaluation, and bounded prototype plan

Date: 24 October 2026
Target qualification host: Autodesk 3ds Max 2027
Status: Research and architecture evaluation only. No repository modifications or production implementation were performed.
Decision target: Whether CyrusScatter should add static vegetation contact fitting; what minimum asset contract, solver, collision representation, publication path, and proof gates are required before implementation.

1.2 Evidence boundary and version note

This report uses four evidence classes and keeps them deliberately separate:

  1. Supplied product context. The governing brief describes a local Scatter test delivery 0.86.9.2, scene schema 59, a retained transform-instanced viewport, stable placement identities, and a separate Jolt-based Cyrus Physics Lab. Those details are accepted as supplied context, not independently verified here.

Public-code observations in this report therefore do not silently replace the supplied local-version facts.
  3. Primary external sources. Original papers, authors’ implementations, official SideFX documentation, official Autodesk SDK documentation, and official library source/release material are used for solver, collision, host, dependency, and licensing claims.
  4. Engineering proposals. Architecture, tolerances, data structures, UI, benchmarks, and go/no-go thresholds are recommendations to test. They are not measured product results.

2 1. Executive recommendation

2.1 1.1 Decision

Proceed to a bounded prototype. Do not proceed directly to a production feature.

The feature is practical for CyrusScatter when defined as the bounded behavior below. Public Cyrus code already demonstrates stable candidate identity, owned native snapshots, bounded worker computation, and retained instanced presentation, but not plant deformation itself. [R2–R7]

Static, one-way, root-preserving vegetation contact fitting for selected, prepared plant sources against fixed scene meshes or an explicitly ordered Scatter obstacle layer.

The first useful implementation should use low-dimensional plant guides, a focused static constrained solver, and triangle-BVH segment/capsule contact. Sparse-guide deformation and rooted curve constraints are established production/research patterns, while the precise Cyrus architecture remains a proposal. [P1–P3, S1–S3] It should attach a sparse deformation result to existing stable placement identities, leave unaffected instances on the current transform-only instanced path, and publish a complete immutable successor atomically.

The recommended first solver is not a general rigid/soft-body engine and not a continuous simulation. It is an iterative static fit with:

  • hard root position and, where authored, root orientation;
  • near-inextensible guide segments;
  • rest-curvature or rest-shape preservation;
  • maximum bend limits;
  • capsule/segment clearance against all relevant obstacle surfaces;
  • explicit completion and quality statuses.

A simple root-weighted procedural projection should be implemented as the control baseline. XPBD-style compliant constraints should be admitted only if the baseline fails the defined corner, multiple-obstacle, length, and rest-shape gates. XPBD specifically addresses compliance and timestep/iteration sensitivity, but that does not make it the automatic product choice. [P1] Full discrete elastic rods or position/orientation Cosserat rods should be deferred until twist, broad-leaf anisotropy, or continuous animation is a demonstrated requirement. Those models explicitly represent material orientation, bending, and twist and therefore solve a broader problem than the initial grass fit. [P2, P3]

2.3 1.3 Recommended product claim

The feature may honestly claim:

  • static obstacle-aware vegetation fitting;
  • rooted, length-aware bending of supported prepared assets;
  • reduced visible intersection within a declared tolerance and work budget;
  • stable placement identity and unchanged distribution for fitted instances;
  • matching viewport, render, and Bake within a measured tolerance for qualified paths.

It should not claim, without separate evidence:

  • biological growth toward light or around obstacles;
  • true material or botanical simulation;
  • guaranteed collision-free output in infeasible geometry;
  • physically correct force, stress, or plastic deformation;
  • real-time response at arbitrary instance counts;
  • plant-to-plant physical interaction;
  • universal support for opaque renderer proxies or arbitrary imported meshes;
  • deterministic equality across different processors, compiler modes, solver versions, or GPU backends.

2.4 1.4 Biggest unresolved risks

  1. Presentation and renderer translation. Different per-instance shapes break the existing “one source mesh plus instance transforms” assumption. A correctness prototype can materialize affected meshes, but production memory and translation cost are unknown.
  2. Asset contract adoption. The best solver cannot make an unsegmented, disconnected, pivot-inconsistent asset behave like rooted blades without metadata or authored guides.
  3. Contact quality in concave and infeasible configurations. Thin/open meshes, roots inside obstacles, narrow gaps, and mutually opposing contacts require explicit diagnostic policy rather than silent approximation.
  4. Scale target. The intended benchmark includes 10,000 affected clumps, but this is a test scenario, not a credible capacity promise before measurement.
  5. Local code divergence. Public repository evidence and the supplied local delivery differ; exact insertion points, serialization version, and Physics Lab reuse cannot be decided until the local checkout is inspected.

3 2. Precise feature definition and initial limits

3.1 2.1 Proposed feature name

For engineering purposes, call the feature Vegetation Contact Fit. Avoid “physics,” “growth,” or “soft body” in the first product name because those terms imply behavior outside the proposed scope.

3.2 2.2 Authoritative behavior

Given:

  • accepted Scatter placements with stable identities;
  • a supported source asset with a valid deformation contract;
  • one or more fixed obstacle bindings;
  • artist settings and a finite work budget;

Vegetation Contact Fit computes an optional per-instance shape in which:

  1. the placement transform and source identity remain unchanged;
  2. the root remains fixed within tolerance;
  3. supported blades/stems remain approximately inextensible;
  4. deformation remains close to the source rest shape unless contact requires otherwise;
  5. guide segments attempt to maintain the requested obstacle clearance;
  6. maximum bend and quality/work constraints are enforced;
  7. unresolved contact is reported rather than hidden by deleting the instance or moving its root.

3.3 2.3 First-release inclusion

  • Static architectural-visualization scenes.
  • Ordinary mesh-convertible Max objects as fixed obstacles.
  • A Scatter layer as an obstacle source when it can be snapshotted with stable instance/source correspondence and an acyclic dependency direction.
  • Segmented grass blades and prepared disconnected clumps represented by one or more guide polylines.
  • Manual mode as the required baseline.
  • A bounded Live mode only after relevant-dependency invalidation is proven.
  • One-way vegetation-to-fixed-obstacle interaction.
  • CPU reference deformation and standard mesh materialization for render/Bake correctness.

3.4 2.4 Explicit first-release exclusions

  • Animated or deforming obstacles.
  • Wind, inertia, velocities, damping, temporal settling, or motion blur.
  • Plant-to-plant or two-way contact.
  • Root translation, uprooting, breaking, crushing, cutting, or plastic deformation.
  • Biological growth.
  • Dense photogrammetry plants without an authored cage/guide contract.
  • Branching trees and complex woody plants unless represented by an explicitly supported guide graph.
  • Arbitrary renderer proxies whose underlying geometry cannot be evaluated through an agreed API.
  • Nonuniform scale, mirroring, and shear in the initial qualified contract unless separately tested and normalized.
  • GPU computation or a generic node/graph system.

3.5 2.5 Placement in the Scatter pipeline

The feature should operate after placements have been accepted and finalized, but before viewport/render/Bake geometry publication:

Distribution / projection / source selection / spacing / cleanup
                            ↓
               accepted stable placements
                            ↓
                Vegetation Contact Fit
                            ↓
          viewport / render translation / Bake

This choice preserves the distribution and root transforms. Existing spacing, Relax, projection, cleanup, or source policy must not run after contact fitting unless they explicitly invalidate and recompute the deformation result. Acceptance/rejection is not deformation and must not be reused as such.

4.2 3.2 A. Proximity-driven procedural deformation

A minimal algorithm can sample obstacle distance and normal at guide nodes, push penetrated nodes outward with a root-height weight, then reproject edge lengths and smooth toward the rest shape.

For node j with normalized root distance u_j, signed or unsigned distance d_j, requested clearance h, contact normal n_j, and root falloff w(u_j):

penetration p_j = max(0, h - d_j)
provisional displacement Δx_j = w(u_j) p_j n_j

A forward/backward projection restores segment lengths, followed by a rest-shape or curvature smoothing pass.

4.2.1 What it can achieve

  • convincing single-obstacle deflection for simple convex rocks;
  • inexpensive “grass makes room for stone” results;
  • no time integration or external physics dependency;
  • compact per-instance parameters if the field can be represented by a bend axis/profile.

4.2.2 Failure modes

  • At a sharp edge, the nearest normal can switch discontinuously.
  • In a concave corner or narrow gap, alternating projections can oscillate between surfaces.
  • A single displacement direction cannot represent multiple simultaneous contacts.
  • Overhangs and cavities can produce an outward normal that pushes a blade deeper into another region.
  • Repeated point projection without length constraints shrinks or stretches the guide.
  • Heavy smoothing can remove intentional local shape and cause volume loss.
  • Endpoint-only sampling misses a segment that crosses an obstacle while both endpoints remain outside.

4.2.3 Decision

Implement this as the control algorithm because it is cheap and may be sufficient for a valuable subset. Reject it as the sole architecture if it fails the defined multi-contact, corner, length, or rest-shape gates. The guide representation, collision queries, validation, publication, and diagnostics should be shared with the more constrained solver so the baseline is not throwaway work.

4.3 3.3 B. Low-dimensional guide deformation

A guide is a polyline or oriented chain embedded in a blade, card, stem, or clump. Sparse guide-to-dense-render binding is an established workflow, but Cyrus must define its own asset contract and validation. [S2, S3] Visible vertices bind to the guide by normalized arc coordinate and a local rest-frame offset. The solver moves guide nodes; a deterministic deformer reconstructs visible geometry.

This is the best architectural compromise because it separates behavioral guides from dense render geometry, a pattern also used in official guide-deformation workflows. [S2, S3] It separates:

  • behavioral resolution (G × S guide segments);
  • render resolution (V mesh vertices);
  • instance count (A affected placements).

A single clump guide is usually too coarse. It bends all blades as a rubber bundle, removes internal variation, and can make blades on the far side of an obstacle follow the same bend as contacting blades. The smallest useful clump representation is normally:

  • one guide per visible blade for hero/simple clumps; or
  • several representative guides plus authored blade-to-guide groups; or
  • a small cage only when the desired result is intentionally bundle-like.

The representation can preserve instancing better than unique meshes because per-instance state scales with guide nodes, not render vertices. It does not by itself solve contact; it is the representation on which procedural, XPBD, rod, or variant approaches can operate.

4.4 3.4 C. Rooted flexible curves or rods

4.4.1 Static PBD/XPBD chain

A guide can be modeled by node positions x_i and constraints for root, segment length, bend/rest curvature, and contact. XPBD adds compliance to reduce constraint stiffness dependence on iteration count and pseudo-timestep. [P1, L1] A scalar XPBD constraint update is commonly written:

Δλ = [ -C(x) - α̃ λ ] / [ Σ_j w_j ||∇C_j||² + α̃ ]
α̃ = α / Δt²
Δx_j = w_j ∇C_j Δλ

For this static feature, Δt is a fixed numerical scale, not a physical timeline and should not be exposed as an artist control.

Benefits:

  • explicit root and length preservation;
  • multiple constraints can be iterated together;
  • compliance offers a meaningful flexibility model;
  • static equilibrium can be approximated without carrying velocities;
  • a future dynamic path remains possible.

Limitations:

  • quality remains iteration/order/contact-generation sensitive;
  • extreme stiffness can converge slowly;
  • conflicting constraints remain infeasible rather than magically solvable;
  • contact and binding quality still dominate visible results;
  • deterministic equality is not automatic across parallel schedules or floating-point environments.

4.4.2 Discrete elastic or Cosserat rods

Twist-aware rods carry a material frame/orientation in addition to the centerline. [P2, P3] They are valuable for:

  • anisotropic stems;
  • broad leaves whose face orientation matters;
  • twisting ribbons/cards;
  • branching or future dynamic plants;
  • render geometry that must follow guide orientation, not merely a transported tangent.

They are not required for a narrow grass-contact prototype if a parallel-transport frame plus bend constraints is visually adequate. Full rod mechanics increase unknowns, constraint count, authoring requirements, and debugging burden.

4.4.3 Static equilibrium versus dynamic settling

The first release should solve a static objective or constraint system from the rest pose. It should not run hidden dynamic frames until “settled,” because that introduces timestep, damping, frame count, initial velocity, and reproducibility questions without user value for static archviz.

4.5 3.5 D. Shell, cloth, and soft-body methods

A thin-shell or cloth model can be appropriate for broad leaves, fabric-like foliage cards, or large flexible sheets where two-dimensional bending and in-plane strain matter. Position-based frameworks and production Vellum workflows expose such specialized constraint families separately from hair/string constraints. [L1, S1] It requires a well-formed sheet mesh, adequate triangulation, attachment constraints, self/contact policy, and a render-binding strategy.

Volumetric soft bodies are inappropriate for ordinary grass because they require volumetric discretization, add many degrees of freedom, and solve material behavior that the requested result does not need. PhysX soft bodies, for example, are documented as tetrahedral FEM simulation/collision meshes with render-mesh binding and GPU-oriented requirements rather than a direct rooted-blade solution. [L3]

4.6 3.6 E. Reusable variants and hybrid approaches

A variant system stores K bent prototypes and assigns affected instances to a nearest variant. It can retain ordinary instancing and reduce draw/translation cost from per-instance geometry to K shared meshes plus instance transforms.

Tradeoffs:

  • quantization introduces contact error;
  • a small K produces visible repetition;
  • a large K approaches unique-mesh memory;
  • cache keys must include source, solver, obstacle-relative feature, clearance, bend profile, and quality revisions;
  • moving an obstacle can cause variant switching or popping;
  • variants cannot guarantee exact local clearance unless the obstacle-relative configuration is represented.

The strongest production hybrid is likely:

  • exact guide solve for the affected subset near obstacles;
  • compact guide parameters in the viewport;
  • CPU materialization on render/Bake;
  • optional variants for distant, low-salience, or highly repeated configurations after approximation error is measured.

5 4. Geometry and asset contract

5.1 4.1 Recommended source representation

struct PlantSourcePrep {
    SourceStableId sourceId;
    Revision sourceGeometryRevision;
    Revision contractRevision;
    AlgorithmVersion prepVersion;

    MeshTopology topology;                 // indices, material IDs, smoothing groups
    std::vector<RestGuide> guides;         // local-space rooted chains
    std::vector<VertexBinding> bindings;   // render vertex -> guide/frame coordinates
    Bounds restBounds;
    Bounds conservativeReachBounds;
    Hash contentHash;
};

struct RestGuide {
    GuideStableId id;
    std::vector<Vec3> restNodes;
    std::vector<double> restLengths;
    std::vector<Quat> restFrames;          // optional in minimum contract
    std::vector<double> radii;
    RootConstraint root;
};

struct VertexBinding {
    GuideStableId guide;
    uint32_t segment;
    float segmentT;
    Vec3 restFrameOffset;
    // Future: 2–4 guide weights for cages/branch junctions.
};

For one guide, a vertex at rest can be represented by an arc coordinate u and offset o in a parallel-transport frame R(u):

v_rest = g_rest(u) + R_rest(u) o
v_fit  = g_fit(u)  + R_fit(u)  o

This preserves UV coordinates, material IDs, topology, and index order. Positions, normals, tangents, bounds, and acceleration data must be updated.

5.2 4.2 Identifying roots and growth direction

5.2.1 Reliable methods

  1. Authored guide root and orientation.
  2. Named root vertex group or selection set.
  3. Vertex color channel encoding root weight/growth coordinate.
  4. Skeleton/bones with a declared root bone.
  5. Explicit per-component root points and local up axis.

5.2.2 Heuristics acceptable only for a limited auto mode

  • pivot-local height relative to a declared up axis;
  • minimum local height band as root candidates;
  • connected-component analysis plus geodesic distance from the lowest boundary;
  • longest principal axis for a simple isolated blade.

These become unreliable when:

  • the pivot is not at the soil plane;
  • the asset is rotated or pre-bent;
  • leaves extend below the stem root;
  • a clump contains disconnected components;
  • cards cross or overlap;
  • geometry has hidden support meshes;
  • the asset uses nonuniform scale, mirror, or shear;
  • the visible leaf edge comes from opacity rather than geometry.

An auto-inferred contract must show a preview and require artist acceptance before it becomes authoritative.

5.3 4.3 Minimum supported asset contract for the first prototype

A source is supported only when all of the following are true:

  1. The evaluated underlying triangle mesh is available; an opaque proxy is not sufficient.
  2. Topology is static during the fit.
  3. The source has a declared local growth axis.
  4. Roots are explicit or verified from a simple pivot/height rule.
  5. One or more guide polylines are explicit or reliably generated for simple components.
  6. Every deforming render vertex has a valid guide binding.
  7. Guide and render segmentation can represent the requested bend.
  8. The qualified transform is rigid plus uniform scale; shear and nonuniform scale are rejected or baked.
  9. The source contract reports validation metrics and unsupported components before fitting.

A practical first prototype should ship with controlled test assets rather than claim broad auto-preparation.

5.4 4.4 Broader future contract

A later contract may add:

  • multiple weighted guides per vertex;
  • oriented Cosserat guide segments;
  • skeletal and branching guide graphs;
  • sheet/cage bindings for broad leaves;
  • per-guide stiffness, thickness, and maximum curvature;
  • proxy adapters that expose canonical render geometry;
  • nonuniform-transform-aware metrics;
  • LOD-specific guides and bindings;
  • source-authored collision and display meshes.

5.6 4.6 Segmentation requirement

There is no universal segment count. Two criteria matter:

  1. Curvature approximation. For a circular arc of radius R and permitted sagitta error ε, a useful upper bound on guide segment length is approximately:
h_guide ≤ sqrt(8 R ε)
  1. Obstacle feature resolution. Guide segments must be shorter than the smallest obstacle feature whose contact shape must be followed. A blade cannot conform to a 5 mm ridge using a 100 mm straight segment.

Prototype fixtures should test S = 4, 8, 16 segments per guide and report quality/cost, rather than hard-code one count.

5.7 4.7 Normals, tangents, UVs, and materials

  • UV coordinates and material IDs remain copied from the source.
  • Smoothing groups remain associated with topology but do not by themselves produce correct deformed normals.
  • CPU reference output should recompute geometric normals and, when required, tangents from deformed positions and unchanged UVs.
  • A guide-frame deformer may transform source normals/tangents, but it must be compared against recomputed geometry at high curvature and blended bindings.
  • Alpha-card normals need an explicit two-sided/shading policy.
  • Viewport, renderer, and Bake must use the same canonical position deformation and an equivalent normal/tangent policy.

5.8 4.8 Transform policy

5.8.1 Uniform scale

Supported. Scale guide lengths, thickness, clearance, and rest offsets consistently.

5.8.2 Nonuniform scale

It converts spherical/capsule thickness into an anisotropic metric. A naive local-space solve can produce wrong world-space clearance. The initial contract should reject it or bake it into source geometry and rebuild bindings.

5.8.3 Mirror

A negative determinant reverses frame handedness and triangle winding. It can invert tangent frames and contact normals. Defer or normalize with explicit handedness handling.

5.8.4 Shear

Shear invalidates simple orthonormal guide frames and capsule radii. Reject in the first prototype.

5.9 4.9 Preprocessing invalidation

Rebuild source preprocessing when any of these change:

  • vertex positions or topology;
  • source pivot/object transform if baked into local geometry;
  • root group or root orientation;
  • guide count, node positions, connectivity, radii, or stiffness metadata;
  • vertex-to-guide binding data;
  • algorithm/preprocessing version;
  • segmentation or LOD selection.

UV-only or material-only changes need not invalidate the guide solve, but they must invalidate the publication/render cache that contains those channels. A source-reference replacement must not be treated as the same source merely because its display name matches.

6 5. Collision detection and local interaction

6.1 5.1 “Closest object” is not the query

Object-center distance is insufficient. A long blade can contact a large rock whose pivot is far away, and several objects can constrain one blade simultaneously. The correct question is:

Which obstacle primitives can contact the plant’s conservative world-space reach volume during fitting?

6.2 5.2 Two-level broad phase

For ordinary objects:

  1. Snapshot each obstacle’s evaluated triangle geometry and transform on the host thread.
  2. Build a per-object bottom-level BVH over triangles.
  3. Insert obstacle world bounds into a top-level BVH, AABB tree, or spatial hash.

For a Scatter obstacle layer:

  1. Reuse one bottom-level structure per source mesh.
  2. Build a top-level structure over stable obstacle instance bounds and transforms.
  3. Preserve source and instance IDs in query results.

Affected vegetation instances are selected by querying the full transformed source reach bounds, expanded by influence distance and clearance. Root position alone is not enough.

6.3 5.3 Narrow phase

The first robust narrow phase should use guide segment or capsule versus triangle contact. The use of explicit centerlines/segments is consistent with rod representations; the exact collision implementation is a Cyrus proposal. [P2, P3] Point-only contact is insufficient because a segment may cross a triangle while both endpoints remain outside.

For each guide segment:

  • query overlapping BVH leaves using its swept/capsule AABB;
  • compute segment–triangle closest points and distance;
  • emit a contact when distance is below segmentRadius + clearance;
  • retain feature IDs, closest points, normal, depth, and obstacle identity;
  • cluster redundant coplanar contacts while preserving distinct opposing features.

Contact generation must be refreshed or conservatively expanded when deformation can move a guide outside the initial candidate region.

6.4 5.4 Normals and inside/outside policy

6.4.1 Closed manifold obstacle

A signed inside/outside classification may be useful for initial penetration recovery, but it must be validated for winding consistency and degeneracy.

6.4.2 Open or thin obstacle

Treat as a two-sided surface with unsigned distance and a normal selected from the closest feature plus the previous/rest displacement direction. Do not pretend an open mesh has an unambiguous interior.

6.4.3 Sharp edge or vertex

Triangle normals are discontinuous. Use the closest feature geometry or a contact manifold rather than blindly averaging unrelated face normals. A persistent feature ID can reduce iteration-to-iteration normal flipping.

6.6 5.6 Initial interpenetration

Initial penetration is not an exceptional edge case; imported vegetation and rocks may already intersect deeply. Recovery should:

  1. detect contact for full segments/capsules;
  2. classify root-zone contact separately;
  3. create multiple surface constraints when necessary;
  4. solve from root outward while enforcing length/rest shape;
  5. cap per-iteration correction to avoid tunneling and instability;
  6. report residual depth after the work budget.

A pinned root inside an obstacle is usually infeasible. The solver must not move the root or silently remove the plant.

6.7 5.7 Units, tolerances, and large coordinates

  • Convert settings to a canonical world unit before snapshotting.
  • Derive epsilon from source/obstacle scale, not a fixed raw float constant.
  • Solve each instance in a local frame near the plant root to reduce large-world cancellation.
  • Transform obstacle candidates into that local frame using double-precision CPU math where practical.
  • Record clearance, guide radius, and tolerance separately; do not hide numerical epsilon inside the artist clearance.

6.8 5.8 Independence and coupling

With fixed obstacles and no vegetation-to-vegetation contact, each plant instance can be solved independently after obstacle snapshots are immutable. This is ideal for bounded parallel work.

Plant-to-plant contact creates a graph of coupled instances. A correction to one plant changes another plant’s contacts, so the selected region can expand and a global or island solve is required. That is a separate feature with different complexity, memory, determinism, and scheduling. It should not be implied by the first release.

7 6. Static solver formulation

7.1 6.1 Recommended objective and constraints

For each guide with rest nodes r_i and fitted nodes x_i, define:

7.1.1 Hard constraints

  • root position: x_0 = r_0 in instance-local fit space;
  • optional root direction: first segment direction remains within an authored cone;
  • maximum bend/curvature limits;
  • explicit artist-frozen nodes, if added later.

7.1.2 Near-hard length constraints

C_len,i(x) = ||x_{i+1} - x_i|| - l_i^0 = 0

7.1.3 Rest-shape energy

A simple positional/curvature form is:

E_shape = w_pos Σ_i a_i ||x_i - r_i||²
        + w_bend Σ_i ||(x_{i+1} - 2x_i + x_{i-1}) - κ_i^0||²

where root-proximity weights a_i may be stronger near the base.

7.1.4 Contact inequalities

For each candidate segment/obstacle feature pair:

C_contact(x) = d_capsule(segment_i, obstacle) - clearance ≥ 0

The contact thickness includes guide radius plus artist clearance.

7.1.5 Optional directional preference

An artist-directed bend direction or “spread away from obstacle” term may bias underdetermined solutions, but it must not override hard root, length, and maximum-bend constraints.

7.2 6.2 Focused static iteration

A practical order per iteration is:

  1. root position/orientation projection;
  2. contact projection with capped corrections;
  3. forward/backward segment-length projection;
  4. bend/rest-shape projection;
  5. maximum-curvature projection;
  6. root projection again;
  7. refresh contacts when movement exceeds a threshold;
  8. compute residual metrics and early-out.

Order dependence should be measured. Alternating contact order or graph coloring may improve bias but can affect repeatability. The first prototype should preserve a deterministic stable ordering by placement ID, guide ID, segment index, obstacle binding, and primitive ID.

7.3 6.3 Completion versus achieved quality

A solve can finish because it reached its iteration or time budget while contact remains unresolved. Store both:

enum class SolveCompletion {
    Converged,
    BudgetReached,
    Cancelled,
    Failed,
    Stale
};

enum class ContactQuality {
    Satisfied,
    Approximate,
    Infeasible,
    Unsupported
};

“Completed” must never be presented as “contact quality achieved.”

9 8. Recommended Scatter integration

9.1 8.1 Public-code observations relevant to the design

The public code already demonstrates several useful contracts. [R2–R7]

  • placement records carry source, transform basis, candidate identity, and receiver anchor metadata;
  • the Max bridge copies evaluated mesh triangles into owned native structures;
  • bounded workers consume owned numerical data and are joined synchronously;
  • the retained mesh display shares source triangles and supplies one matrix stream per instance;
  • Manual publication, stable candidate identity, immutable retained results, and avoidance of camera-driven regeneration have already been used in adjacent product work.

The new feature should extend these principles rather than replace the scatter engine.

9.5 8.5 Threading rule

All Max scene evaluation, INode/Object access, reference traversal, undo interaction, and scene publication occur on the host thread. Workers receive only Cyrus-owned numeric snapshots. This matches both the supplied constraint and the public code’s existing worker policy. [R5, R6]

9.6 8.6 Manual and Live semantics

9.6.1 Manual

  • Relevant edit increments a pending revision.
  • The last complete result remains visible and renderable with an “Out of date” state.
  • Only Update Fit starts snapshot/solve/publication.
  • Camera movement, selection, viewport navigation, and unrelated animation do nothing.

9.6.2 Live

  • Available only after Manual is qualified.
  • Relevant dependencies are source geometry/contract, accepted placements, bound obstacle geometry/transforms, and fit settings.
  • Changes are debounced/coalesced.
  • A generation token cancels or stales superseded work.
  • Camera, selection, display-only changes, and unrelated nodes do not invalidate.

9.7 8.7 Interacting Scatter layers and dependency cycles

A layer-to-layer binding creates a directed edge:

Vegetation layer A  ──depends on──>  Obstacle layer B

First-release policy should be one of:

  1. only allow dependencies on an explicitly frozen snapshot of B; or
  2. require an acyclic graph and evaluate in topological order; or
  3. only allow dependencies on earlier layers in a declared order.

Reject a cycle such as A → B → A. Do not alternate silently until “stable.” If a future deformed B is used as an obstacle for A, B’s deformation generation ID becomes part of A’s obstacle key.

9.8 8.8 Undo/Redo

Recommended policy:

  • Authored settings, references, source contracts, and per-instance overrides are ordinary undoable scene state.
  • DeformationGeneration objects are immutable and reference-counted.
  • An undo record stores generation identity/pointers where memory permits, not deep duplicated meshes.
  • A bounded generation history has an explicit memory cap. Evicted generations are recomputed on demand.
  • Undo/Redo must restore the exact authored state and either the matching complete generation or a declared pending state; it must never expose a half-built result.

9.9 8.9 Save/load

Save:

  • authored settings and stable references;
  • source-contract metadata/version;
  • last complete sparse guide state and diagnostics, optionally compressed;
  • all revision/fingerprint keys needed to validate it;
  • schema and algorithm versions.

Load:

  • restore the last complete generation immediately only when identity/fingerprint checks pass;
  • if dependencies differ, preserve the saved generation as an explicitly stale Manual result or hide it according to a declared policy, then request Update;
  • do not retarget by name;
  • missing dependencies remain visible in diagnostics.

Saving only materialized unique meshes is not recommended as the authoritative state because it loses source/guide semantics and makes future algorithm migration difficult.

10.3 9.3 Prototype publication recommendation

For the first correctness prototype:

  • unaffected placements remain on the existing transform-instanced path;
  • affected placements are CPU-deformed and materialized into standard Max-compatible mesh output;
  • affected meshes are batched by source/material where practical;
  • the same CPU deformation is used for viewport reference, render translation, and Bake;
  • a diagnostic guide display is separate from final shading.

This is deliberately not the final scale architecture. It minimizes ambiguity during quality and renderer qualification.

10.4 9.4 Production candidate

After the correctness gates pass, measure a split path:

  1. Viewport: shared source plus per-instance guide node/frame streams in a custom render item.
  2. Render/Bake: CPU materialization on demand from the immutable guide state.
  3. Optional variants: only for low-salience/distant cases where measured error is acceptable.
  4. Renderer-specific procedures: only if a vendor path proves substantial translation/memory benefit and preserves parity.

Do not build the custom shader before CPU reference output and renderer tests exist.

10.5 9.5 Max SDK contract

A custom retained viewport item must realize/cache streams, draw from retained data, update bounds, and implement hit testing against deformed data. Autodesk’s custom render-item contract separates realization, display, and hit testing. [A1] A renderable Max geometry object must provide a valid render mesh or another documented render path. [A2] These SDK contracts establish how Cyrus can publish geometry; they do not prove that Corona, Arnold, and V-Ray share a compact custom-guide interface.

10.6 9.6 Renderer qualification experiment

For each of Default Scanline, Arnold, Corona, and V-Ray available in the target environment:

  1. Create one source with two stable instances and visibly different bends.
  2. Verify viewport shape and bounds.
  3. Render stills from two cameras.
  4. Inspect material IDs, UVs, alpha cards, smoothing, displacement/modifiers where applicable.
  5. Change only deformation and confirm renderer translation updates the correct instance.
  6. Render after save/reopen and Undo/Redo.
  7. Bake/export and compare vertex positions.
  8. Measure translation time, peak memory, retained memory, and whether geometry is duplicated internally.

Decision rule: a renderer can be claimed only if image/geometry parity and lifecycle tests pass in Max 2027. Any compact procedural path is a renderer-specific enhancement, not a prerequisite for the core feature.

10.7 9.7 Bounds, culling, and picking

  • Compute one deformed local/world bound per affected instance.
  • Use conservative guide radius and bound inflation during in-progress preview, but replace with exact fitted bounds after publication.
  • Update retained culling data atomically with geometry.
  • Hit testing must evaluate deformed geometry or an explicitly documented guide/capsule approximation.
  • Source-rest bounds are not sufficient once a blade bends sideways.

10.8 9.8 Bake/export

Bake must materialize affected instances as ordinary geometry or a documented supported deformation stack while preserving:

  • world transform and stable instance metadata;
  • topology, UVs, material IDs, smoothing groups;
  • recomputed normals/tangents;
  • source and placement identity in custom properties where appropriate;
  • exact fitted positions within the declared tolerance.

Unchanged instances may remain instances when the export target supports them. A Bake that silently returns undeformed source instances is a feature failure.

10.9 9.9 Provisional parity tolerance

A starting comparison tolerance is:

max vertex position difference
≤ max(1e-5 × source diagonal, 0.01 × requested clearance)

This is a proposed test threshold, not a product promise. Tighten or revise it from Max/renderer measurements and float-path behavior. Image comparison should accompany geometry comparison because normal/tangent or alpha differences may be visually significant even when positions match.

Dependencies: Eigen and several included/associated demo/runtime dependencies; exact minimal subset needs a build spike.
Windows: README records Windows/Visual Studio support, but the currently relevant Max 2027 toolchain must be tested.
License: MIT.
Assessment: valuable reference and experimental comparator; likely broader and older-release-heavy than needed for a focused production core. Do not import the entire framework before a minimal subset demonstrates a quality or engineering advantage.

12.3 11.3 Jolt Physics 5.6.0

Relevant capability: rigid collision, soft-body edge/dihedral/Cosserat constraints, and a new GPU strand-hair system with guide/follow hairs. [L2]
Current public release reviewed: 5.6.0, July 2026.
Toolchain: C++17, Visual Studio 2022+, standard-library core.
License: MIT.
Important limitation: the 5.6 GPU hair path is identified as work in progress and its environment collision is limited to convex hull and compound shapes in the release notes.
Assessment: the presence of a Jolt-based local lab does not establish fit. Extending the lab may be useful for a future animation experiment, but a GPU/WIP strand system and general physics world are not justified for the first static mesh-obstacle feature. If local Jolt code contains reusable collision snapshots or build infrastructure, evaluate those separately from adopting Jolt as the deformation solver.

12.4 11.4 PhysX / ovphysx

Relevant capability: rigid/deformable simulation; official soft-body documentation describes tetrahedral FEM simulation/collision meshes and render-mesh binding. [L3]
Current repository line reviewed: ovphysx 0.7.0 over PhysX SDK 5.12, October 2026; the release labels ovphysx pre-1.0 and subject to API change.
Soft-body qualification caveat: publicly inspected detailed soft-body documentation was from PhysX 5.4.1 and describes CUDA/GPU-oriented volumetric soft bodies; exact 5.12 behavior must be reverified.
Distribution: large package and broader USD/tensor/simulation surface than Cyrus needs.
License: repository uses a BSD-style 3-clause notice with additional license files in subfolders.
Assessment: reject volumetric soft body for rooted grass. It does not remove root/guide/binding/render integration and introduces a mismatched representation and GPU dependency.

12.5 11.5 Intel Embree 4.4.1

Relevant capability: production-grade triangle acceleration, multilevel instancing, and point-query BVH traversal with user callbacks. [L4]
Current release reviewed: 4.4.1, April 2026.
Platform: Windows x64/MSVC package available; TBB is part of/common to packaged configurations.
License: Apache 2.0.
Assessment: a credible collision-acceleration candidate, not a deformation solver. Embree point queries provide traversal but Cyrus still implements closest-feature/contact logic. Compare a small internal BVH against Embree on T = 1k/100k/1M, repeated segment/capsule queries, build/refit cost, binary size, memory, cancellation, and installer complexity. Adopt only if it wins materially.

12.6 11.6 OpenVDB 13.1.0 / NanoVDB

Relevant capability: sparse hierarchical volumetric storage suitable for narrow-band distance fields. [L5]
Current release reviewed: 13.1.0, September 2026.
Windows dependencies: OpenVDB documentation lists Boost, TBB, Blosc, zlib, and MSVC/CMake tooling for core builds.
License: Apache 2.0.
Assessment: useful for an SDF experiment, but too much dependency/preprocessing surface for the baseline. Consider only if BVH closest-contact queries are the measured dominant cost and sparse-field accuracy/robustness gates pass.

12.7 11.7 Dependency decision

  1. Build the reference prototype with a focused solver and focused triangle BVH/contact layer.
  2. Use PositionBasedDynamics as a numerical/reference comparator, not an automatic product dependency.
  3. Benchmark Embree only if collision maintenance/performance justifies it.
  4. Do not extend Jolt, PhysX, or OpenVDB into the product path merely because they contain adjacent features.
  5. Maintain a third-party notice and exact-version manifest for every serious spike.

14 13. Static results and future animation

14.1 13.1 Smallest coherent static feature

The smallest coherent feature is:

  • Manual update;
  • one prepared source family;
  • ordinary fixed mesh obstacles;
  • one-way contact;
  • authored/verified guides;
  • static root/length/rest/contact constraints;
  • sparse stable-ID results;
  • CPU materialized affected geometry;
  • viewport/render/Bake parity tests;
  • diagnostics and atomic failure behavior.

Anything smaller that bends only the viewport, deletes intersecting plants, moves roots, or cannot render/Bake consistently is not the requested feature. Autodesk’s viewport and render-mesh contracts are distinct, so a viewport-only deformation is not sufficient evidence of render output. [A1, A2]

14.2 13.2 What continuous animation adds

A future dynamic mode requires new authoritative state beyond the static constraints described in XPBD/rod work: [P1–P3]

  • positions, orientations, velocities, angular velocities, and constraint multipliers;
  • fixed step and substep policy;
  • initial/rest/start state and explicit reset;
  • checkpointing and replay for forward/backward seeking;
  • animated/deforming collider snapshots at subframes;
  • wind and moving-root inputs;
  • temporal contact/friction stability;
  • subframe render evaluation and motion blur;
  • deterministic/repeatable cache versioning;
  • timeline invalidation and partial-cache policy.

It also changes user expectations from “fit when updated” to “simulate through time.” This should be a separate product phase.

14.3 13.3 First-version choices that preserve a future path

Preserve:

  • guide-based representation;
  • oriented frames as an optional extension;
  • immutable source preprocessing;
  • a solver interface separated from Max publication;
  • collision queries independent of solver backend;
  • algorithm/schema versioning;
  • stable placement/source/obstacle identities;
  • explicit static state that can later seed dynamic state.

Premature abstractions:

  • generic simulation graph;
  • general GPU compute subsystem;
  • timeline checkpoint manager;
  • two-way scene physics world;
  • universal plant material model;
  • renderer-agnostic procedural API that no renderer has been shown to support.

  • failures for roots inside, narrow gaps, segment crossing, and insufficient segmentation.

15.1.3 Gate

Choose the simplest solver that passes. XPBD does not win by default; it must improve failed quality cases enough to justify its complexity.

15.2 Phase 1 — Max 2027 correctness integration

15.2.1 Scope

  • Manual mode only;
  • one ordinary mesh obstacle set;
  • uniform transforms;
  • authored test sources;
  • sparse stable-ID state;
  • CPU materialized affected meshes;
  • source/obstacle snapshots on host, solve on workers;
  • atomic publication, cancel/stale/failure handling;
  • Undo/Redo and save/reopen;
  • Scanline/Arnold/Corona/V-Ray qualification where installed.

15.2.2 Go/no-go gates

  1. Root drift ≤ 1e-5 × source diagonal; root orientation drift ≤ 0.1° where pinned.
  2. Proposed max segment-length error ≤ 0.5%, RMS ≤ 0.1% for feasible fixtures.
  3. For feasible contact tests, proposed 95th-percentile residual penetration ≤ 0.1 × clearance and maximum ≤ 0.5 × clearance.
  4. Every infeasible case is flagged; no instance is silently deleted and no root transform moves.
  5. Unaffected placement IDs, transforms, and source assignments are byte/epsilon-equivalent to the no-fit path according to existing product conventions.
  6. Camera, selection, and unrelated changes produce zero solve/publication/upload counter changes.
  7. Cancelled, stale, failed, and out-of-memory successors preserve the previous complete generation.
  8. No NaNs, inverted output beyond the declared binding policy, UV/material corruption, or invalid bounds.
  9. Viewport, each claimed renderer, and Bake agree within the qualified geometry/image tolerance.
  10. A representative 1,000-affected-clump scene fits a product-defined update and peak-memory budget on the reference machine. The budget must be set before interpreting results.

Thresholds above are proposed starting values and must be reviewed against scene units, close-up visual acceptance, and renderer precision.

Adopt compact viewport or variants only if they reduce measured peak/upload/draw/translation cost materially without violating parity, contact quality, picking, or stability.

18 17. Direct answers

18.1 Is this practical for CyrusScatter?

Yes, with a strict static and prepared-asset scope. Cyrus already has the essential architectural ingredients: stable placement identity, native numeric computation, host-thread scene extraction, retained results, and a transform-instanced unaffected path. The new work is substantial but bounded if it is treated as sparse per-instance deformation rather than a replacement scatter engine. The public code’s stable identity, native snapshot, and retained-display boundaries make this integration direction plausible. [R2–R7]

18.2 What is the simplest useful first version?

Manual, static, one-way fitting of prepared segmented grass against ordinary fixed mesh obstacles, using guide chains, root/length/rest/contact constraints, triangle-BVH capsule contact, sparse placement-ID results, CPU materialization for affected instances, and explicit unresolved-contact diagnostics.

18.3 Does that version require actual physics?

No. It requires a constrained numerical fit that preserves selected physical-looking invariants. It does not require velocities, forces, mass, damping, time integration, or a general physics world. XPBD/rod literature provides useful constraint formulations, but a static fit can use only the relevant subset. [P1–P3] XPBD is a possible constraint method, not a product requirement.

18.4 Can ordinary imported grass models work, and what preparation is unavoidable?

Some can work when they are segmented, have reliable roots/pivots and growth direction, and can be bound to one or more guides. Arbitrary disconnected clumps, alpha cards, photogrammetry meshes, broad leaves, branching plants, and opaque proxies require additional metadata or authored guides/cages. The unavoidable minimum is: root definition, growth direction, adequate segmentation, guide representation, and vertex binding validation.

18.5 How do we retain efficiency when each affected instance bends differently?

  • store deformation only for affected stable placement IDs;
  • leave unaffected instances on the existing shared-source transform path;
  • retain per-instance guide nodes/frames rather than full meshes as the authoritative state;
  • share source preprocessing and obstacle BLAS data;
  • use a compact custom viewport path only after CPU reference correctness;
  • materialize unique geometry on demand for render/Bake;
  • evaluate variants/hybrid LOD only where measured approximation is acceptable.

18.6 What should we measure before committing to an architecture?

Contact quality, root/length/rest-shape error, infeasible-case diagnostics, source-preparation effort, cold/warm stage time, old+new peak memory, compact versus unique publication, GPU upload/draw, renderer translation, Bake parity, Undo/save cost, cancellation/stale behavior, and 100/1,000/10,000 affected scenarios within predeclared budgets.

18.7 Which requested effects should be deferred, and why?

  • continuous animation/wind/moving obstacles: requires temporal state, stepping, seeking, caches, motion blur, and temporal contact;
  • vegetation-to-vegetation interaction: couples plant solves and expands contact regions;
  • biological growth: a different model and product claim;
  • full cloth/volumetric soft body: mismatched cost/asset model for grass;
  • broad branching/proxy/arbitrary-mesh support: lacks a reliable automatic plant contract;
  • GPU/general physics integration: premature before CPU quality and renderer bottlenecks are measured;
  • renderer-specific procedurals: separate maintenance burden without verified necessity.

20 19. Final decision statement

The attractive mistake would be to label the problem “soft-body grass,” connect the existing physics lab, and begin with a general simulation or GPU strand system. Current public engine options demonstrate adjacent capabilities but also broader representations, dependencies, or WIP constraints that do not solve Cyrus’s asset and publication contracts. [L1–L5] That would leave the hardest product questions unsolved: what a plant asset means, how contact is detected, how stable Scatter identities retain distinct shapes, how results survive failure and save/reopen, and how viewport/render/Bake agree.
