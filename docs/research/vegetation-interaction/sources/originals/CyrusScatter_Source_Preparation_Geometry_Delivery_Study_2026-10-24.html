CyrusScatter Vegetation Source Preparation and Geometry Delivery#

Supported-asset contract, source audit, canonical evaluator, and Max 2027 publication study#

Date: 24 October 2026
Purpose: Focused extension to the earlier CyrusScatter vegetation-interaction research.
Target qualification host: Autodesk 3ds Max 2027.
Status: Research and architecture proposal only. No Max, renderer, or Cyrus production implementation was executed for this report.

1. Executive answer#

Product answer: an artist can prepare a vegetation source once and reuse that preparation across thousands of Scatter placements. The preparation must be stored at the source level as immutable guides, root metadata, and mesh bindings. Individual placements then need only a small fitted guide state or a reference to a reusable deformation variant. The artist must not rig every placement.

That answer is conditional. Cyrus can eliminate per-placement rigging, but it cannot promise zero preparation for arbitrary imported assets:

  • Clean segmented ribbon blades can usually be recognized and bound automatically.
  • Disconnected clumps can usually be separated by geometric connected components, provided each component really represents one blade or card.
  • Welded/shared-base clumps can often be separated by removing a confirmed root region and finding the components above it.
  • Crossed opacity cards can be prepared at card or whole-clump level, but geometry alone cannot recover the individual blades painted into the alpha texture.
  • Dense scanned vegetation normally needs an authored cage, guide graph, or deliberately simplified deformation proxy.
  • Opaque renderer proxies are not deformable unless Cyrus can obtain canonical geometry or a renderer-specific adapter; a viewport bounding box or point-cloud preview is not enough.

The recommended product is therefore a hybrid source-preparation pipeline:

Evaluate accessible source mesh
        ↓
Audit topology, channels, transforms, and proxy access
        ↓
Choose preparation level
        ↓
Auto-segment where evidence is strong
        ↓
Generate/import guides and vertex bindings
        ↓
Show ambiguity overlays and require confirmation
        ↓
Store immutable source preparation by stable ID + content hashes
        ↓
Reuse it for every placement of that source

1.1 Recommended first implementation boundary#

The first supported contract should accept:

  1. a static, accessible triangle mesh;
  2. baked or rigid-plus-uniform source transforms;
  3. an explicit or confirmed root region and local growth axis;
  4. either:
    • recognized ribbon strips,
    • separated components with one guide each, or
    • authored guide curves / existing Skin data;
  5. complete vertex-to-guide bindings with no unresolved vertices;
  6. unchanged topology while fitted results are in use.

The first delivery path should use the same CPU guide-to-mesh evaluator for Max viewport reference geometry, production render geometry, and Bake. Compact GPU guide evaluation should be treated as a later optimization, not as the first correctness path.

1.2 Biggest unresolved risks#

  1. Automatic semantics: topology can reveal connected pieces, but it cannot always reveal botanical meaning.
  2. Welded clumps: removing the shared root region works only when blades become topologically separate above that region.
  3. Opacity cards: the visible blade silhouette may exist only in the texture.
  4. Renderer proxies: vendor objects may expose only a display proxy or renderer-owned file, not an evaluable mesh.
  5. Production rendering scale: standard Max render meshes are the safest interoperability path, but exact per-instance deformation expands affected geometry and must be measured in the intended renderer.

2.1 Decision-critical documented facts#

  • Houdini 22.0 treats the first curve vertex as the root and can create a root group; its guide utilities preserve explicit root/skin correspondence. S1
  • Houdini Guide Deform supports sparse-guide deformation, precomputed guide weights, Point Deform capture, and guide orientation attributes; this demonstrates a mature source-level capture/deform split. S2S3
  • CGAL connected components are defined by face adjacency across unconstrained edges; this is a suitable basis for strict component discovery. C1
  • CGAL mean-curvature-flow skeletonization requires a triangulated, borderless, single connected component; that requirement excludes many open grass cards and noisy plant scans from reliable automatic use. C2
  • CGAL’s shape-diameter segmentation is designed around a surface bounding a 3D solid; it is not a safe default for open ribbon foliage. C3
  • Max stores geometric vertices, texture vertices/faces, vertex colors, face material IDs, smoothing groups, and explicit normals as distinct channels. UV seams and shading splits therefore must not automatically define botanical pieces. A3A4A5A6
  • Max Skin exposes bone initial transforms and per-vertex bone assignments/weights; existing rigs can be imported rather than rebuilt manually. A7A8A9
  • A Max GeomObject can provide instance-dependent render meshes, while ICustomRenderItem supplies retained viewport realization, display, and hit-testing hooks. A1A2

3. Source-level preparation model#

3.1 One preparation, many placements#

Cyrus should not create a Max rig, bones, or helper objects for every Scatter instance. It should capture one immutable source representation and let each placement reference it:

struct PreparedVegetationSource {
    SourceStableId sourceId;
    Revision sourceNodeRevision;
    Hash geometryHash;          // positions + topology + vertex order
    Hash channelHash;           // UVs, materials, normals, colors
    Hash authoringHash;         // roots, guides, bones, cages, piece labels
    uint32_t evaluatorVersion;

    RestMesh mesh;              // immutable source channels
    std::vector<PreparedPiece> pieces;
    std::vector<RestGuide> guides;
    std::vector<VertexBinding> bindings;
    SourceAudit audit;
};

struct RestGuide {
    GuideStableId id;
    PieceStableId piece;
    std::vector<Vec3> restNodes;
    std::vector<Quat> restFrames;
    std::vector<float> halfWidth;
    std::vector<float> thickness;
    RootAnchor root;
};

struct VertexBinding {
    uint32_t vertex;
    float deformWeight;       // 0 at a fixed root, 1 for full deformation
    uint8_t influenceCount;
    GuideInfluence influence[4];
};

struct GuideInfluence {
    GuideStableId guide;
    uint16_t segment;
    float segmentT;
    Vec3 localOffset;         // rest guide frame coordinates
    float weight;
};

Every affected placement stores only its fitted guide state, diagnostics, and the prepared-source revision it was solved against. Unaffected placements remain on the existing transform-only path.

3.2 What preparation is authoritative#

The authoritative preparation is the accepted combination of:

  • source geometry snapshot identity;
  • piece IDs;
  • root region and root anchor for each piece;
  • guide topology and node order;
  • rest frames, width/thickness, and optional twist data;
  • vertex bindings;
  • preparation level and evaluator version;
  • an audit record listing auto-inferred, artist-confirmed, and unsupported regions.

Display names, node names, or approximate bounding boxes are not sufficient identity.

4.1 Root masks#

Required information and assumptions

A root mask is a scalar on geometric vertices or corners, normally 0 for fully fixed and 1 for fully deformable, with a transition zone between them. It can come from:

  • a named vertex selection or root group;
  • a vertex-color channel;
  • an explicit root face set;
  • an imported root-bone weight;
  • a confirmed pivot/local-height heuristic.

A root mask requires a declared source-local growth axis. It does not by itself identify individual blades.

What can be inferred reliably

  • the planted region;
  • a deformation falloff from root to free geometry;
  • the shared-base region that may be temporarily removed for welded-clump partitioning;
  • a root centroid or root boundary for each already known piece.

Ambiguity detection

Flag the mask when it produces:

  • no root vertices or nearly the whole mesh as root;
  • multiple disjoint root islands inside one purported blade;
  • roots at both ends of a strip;
  • roots far above the declared support plane;
  • a root transition that cuts across the middle of visible leaves.

No fixed numeric thresholds are proposed here; thresholds must scale with source dimensions and be qualified on the asset library.

What the artist confirms or corrects

The artist confirms the root overlay and local up axis, or paints/adds/removes root vertices. Root position and root orientation are separate: the root mask fixes translation, while orientation stiffness acts on the first guide segment or root frame.

Preservation

  • Root position is preserved by an identity/placement influence where mask weight is zero.
  • Rest curvature is preserved by the guide, not by the mask.
  • Width and twist require guide frames or strip cross-sections.

UV seams and duplicated vertices

Root data must be reconciled across coincident geometric duplicates. A UV seam alone is not a root boundary because Max stores texture topology separately from geometry. A3A6

Invalidation

Changing the mask, root group, color channel used as the mask, local up axis, or pivot policy invalidates preparation and all fitted guide states for that source.

4.2 Connected-component analysis#

D Strict connected components should be computed on face adjacency using geometric topology. CGAL documents the same fundamental definition: faces are connected when an adjacency path exists across non-constrained edges. C1

Required information and assumptions

  • an accessible triangle/poly mesh;
  • valid face indices;
  • a policy for non-manifold edges and hidden/support geometry;
  • optional artist-authored piece IDs that override automatic components.

Reliable inference

  • truly disconnected blades;
  • separate crossed cards;
  • separate leaves or stems that do not share geometry;
  • tiny debris/support components that can be reported separately.

UV seams and render-vertex splits

Segmentation must use geometric adjacency, not UV vertices, material IDs, smoothing groups, or explicit normals. Max’s mesh model keeps those channels separate. A3A4A5 Imported files may nevertheless duplicate geometric vertices at UV or normal seams. Therefore Cyrus may offer an optional virtual weld pass:

  1. find boundary edges whose endpoints are coincident within a source-scaled tolerance;
  2. require a one-to-one reversed edge match;
  3. reject matches with competing candidates or incompatible face orientation;
  4. create virtual adjacency without modifying the source mesh;
  5. show every virtual weld in the preview.

Virtual welding must never be silently accepted when two real blades merely touch or intersect.

Ambiguity detection

  • many tiny components that collapse into a few pieces after virtual welding;
  • coincident boundaries with multiple possible mates;
  • non-manifold edges;
  • components with multiple root islands;
  • a component whose shape is broad or branched rather than blade-like.

Artist correction

The artist accepts/rejects virtual weld groups, merges or splits piece IDs, or supplies an explicit piece channel.

Preservation and invalidation

Connected components do not preserve curvature, width, or twist by themselves; they only define pieces. Any topology or vertex-order change invalidates component IDs unless a stable author-provided piece channel can be remapped exactly.

4.3 Strip recognition#

P Strip recognition is the preferred automatic method for segmented grass blades and rectangular cards. It is deliberately narrower than generic skeletonization.

Supported assumptions

A candidate component should be:

  • an open, non-branching ribbon or thin shell;
  • topologically disk-like;
  • longer than it is wide;
  • segmented along its length;
  • attached to one confirmed root end;
  • free of major self-overlap in the rest pose.

Proposed recognition order

component
  → validate manifold/boundary structure
  → identify root end from root mask
  → find geodesically farthest tip region
  → split the boundary into two longitudinal rails and two end regions
  → pair rail samples or recover quad/triangle cross-sections
  → centerline = cross-section midpoint
  → half-width vector = rail difference / 2
  → build rest frame and twist sequence
  → bind component vertices by arc coordinate + frame offset

For a regular quad strip, edge-ring traversal is the highest-confidence case. For triangulated strips, Cyrus can reconstruct cross-sections from the face graph, but confidence should fall when multiple valid traversals exist.

What can be inferred reliably

  • one center guide;
  • root-to-tip order;
  • rest arc length and curvature;
  • width at each cross-section;
  • a width direction that seeds the guide frame;
  • rest twist as the width direction rotates around the centerline.

Ambiguity detection

Reject or request confirmation when:

  • the component branches;
  • there is no unique root or tip end;
  • boundary traversal produces more than two plausible rails;
  • width changes sign or paired rails cross;
  • the component has internal holes;
  • duplicated front/back surfaces form two coincident shells;
  • segmentation is too sparse to approximate the requested bend;
  • the component is volumetric rather than ribbon-like.

UV V direction may be used as supporting evidence, but never as the sole authority. UVs can be mirrored, tiled, rotated, or shared across multiple blades.

Artist correction

The artist can reverse root/tip, select two boundary rails, choose a guide curve, or mark the component as whole-piece/cage deformation instead.

Invalidation

Any change to geometry positions, topology, vertex order, root assignment, or the accepted rail pairing invalidates the generated guide and binding. UV edits invalidate only those preparations whose audit says UV direction was used as evidence.

4.4 Automatic centerline extraction#

Generic skeletonization is useful only under much stronger assumptions than most vegetation libraries satisfy.

D CGAL’s mean-curvature-flow skeletonizer requires a triangulated mesh with no boundary and one connected component. It produces a curve graph and associates source vertices with skeleton vertices. C2 This is useful for closed stems or deliberately watertight deformation proxies, but not for ordinary open grass ribbons or crossed cards.

D CGAL’s shape-diameter segmentation assumes a mesh bounding a 3D solid and derives local diameter by inward ray sampling. C3 Open foliage and thin cards violate that model or make the result unstable.

Potentially reliable cases

  • a closed tubular stem;
  • a watertight simplified proxy around a dense scanned clump;
  • a single closed leaf/stem object with a known root and no ambiguous branches.

Ambiguous or unsupported cases

  • open ribbons and cards;
  • fused scanned leaves with holes;
  • multi-component scans;
  • one mesh containing multiple touching plants;
  • branching skeletons without authored botanical piece labels.

Artist responsibility

An automatically extracted graph must be shown as a preview. The artist must choose the root, prune/merge branches, and confirm which graph edges drive which render regions. Automatic skeletonization should never silently become authoritative.

4.5 Authored curves#

Authored curves are the clearest contract for hero assets and complex clumps.

Required information

  • one or more ordered curves;
  • first point/root convention or explicit root index;
  • piece ID;
  • optional width/thickness samples;
  • a root normal, width vector, or orientation frame when twist matters.

Houdini’s guide utilities use the first curve vertex as the root, illustrating a simple and inspectable convention. S1

Reliable inference

  • root-to-tip direction;
  • rest curvature and length;
  • guide topology;
  • local frames when an orientation attribute or cross-section direction is supplied.

Artist responsibility

The artist supplies or approves curves and resolves any region captured by multiple guides. Cyrus may auto-generate curves from recognized strips and store them internally; the artist does not need visible spline helpers in the scene unless editing is requested.

Binding

Vertices are captured by piece ID first, then nearest guide arc coordinate and frame offset. Houdini Guide Deform and Point Deform document the practical value of separating capture from repeated deformation and of limiting capture by piece attributes. S2S3

Invalidation

Curve point count/order, curve shape, root order, piece assignment, width/thickness, or source rest geometry changes require recapture.

4.6 Existing bones and Skin#

Existing Skin rigs are a valuable import path, especially for broad leaves, stems, and purchased assets that are already animated.

D Max ISkin exposes bone initial transforms and the reference frame. ISkinContextData exposes each vertex’s assigned bones and weights. ISkinImportData can add bones and weights. A7A8A9

Cyrus policy

  • Import the rig into the immutable source-preparation representation.
  • Do not instantiate a full Max bone hierarchy per Scatter placement.
  • Treat each bone chain as a guide chain with full rigid frames.
  • Map the designated root bone to root-position and root-orientation controls.
  • Preserve original weights and DQ blend preference as metadata.

Width, curvature, and twist

Bones preserve rest curvature through their bind transforms and twist through full rotations. Linear blend skinning can collapse near large opposing rotations; dual-quaternion blending is a documented alternative and Max exposes a DQ-blending state. L2A7

Ambiguity

  • helper bones unrelated to vegetation deformation;
  • multiple skeletons affecting one mesh;
  • missing root designation;
  • scale/shear in bone transforms;
  • weights spanning unrelated leaves.

The artist maps or disables ambiguous bones once at source-preparation time.

4.7 Cages and low-resolution lattices#

Cages are appropriate when individual blade semantics are unavailable or unnecessary.

Best uses

  • Level 1 whole-clump deformation;
  • broad leaves or compound foliage requiring area preservation;
  • dense scans driven by a simplified authored proxy;
  • art-directed deformation where exact per-blade contact is not required.

Binding choices

  • direct point-capture weights;
  • surface/volume barycentric coordinates;
  • bounded biharmonic weights or biharmonic coordinates;
  • piece-restricted capture to prevent cross-clump bleeding.

Libigl documents bounded biharmonic weights as smooth, nonnegative, partition-of-unity weights for bones, points, regions, or cages, and documents GPU-friendly linear blend evaluation. L1 Those methods still require meaningful handles/cages and do not infer plant semantics.

Ambiguity and correction

Flag vertices outside the cage, negative/invalid coordinates, cross-piece influences, and excessive influence spread. The artist adjusts the cage or piece restriction.

Invalidation

Cage topology/rest shape, capture weights, or source rest positions invalidate the binding.

4.8 Recommended hybrid preparation#

The product should choose the strongest available evidence in this order:

Existing accepted Cyrus prep
  → existing Skin/bones or authored guide curves
  → explicit piece/root channels
  → strict connected components
  → virtual seam weld (previewed)
  → strip recognition
  → root-cut partition for welded bases
  → authored cage / manual correction
  → unsupported

This avoids forcing every asset into one algorithm and avoids pretending that interface behavior reveals a vendor’s private implementation.

5. Asset-class evaluation#

5.1 Segmented individual blades#

Recommended level: Level 2, independent blade fitting.
Automatic confidence: High for clean ribbon topology.

Preparation recipe

  1. identify the blade component;
  2. confirm root end from root mask or pivot/local-height rule;
  3. recognize longitudinal strip topology;
  4. generate one center guide and rest frames;
  5. bind every blade vertex to guide arc coordinate and local offset;
  6. audit segmentation density and unbound vertices;
  7. artist accepts the overlay.

Preservation

  • root position: mask/guide root;
  • root orientation: first guide frame, controlled separately;
  • rest curvature: rest guide nodes;
  • blade width: local frame offset and half-width samples;
  • twist: width-vector rotation along the guide.

Failure cases

  • only one or two segments along the blade;
  • irregular branch-like geometry;
  • double-layered coincident surfaces;
  • root and tip equally plausible;
  • nonuniform source transform not baked.

A clean library can therefore be prepared once without manually drawing one guide per blade.

5.2 Disconnected multi-blade clumps#

Recommended level: Level 2 when each component is a blade; Level 1 when components are entire cards or clusters.
Automatic confidence: Medium to high after seam audit.

Preparation recipe

  1. strict component discovery;
  2. optional previewed virtual weld for imported seam splits;
  3. classify each component as ribbon, card, stem, debris, or ambiguous;
  4. run strip recognition per ribbon/card;
  5. assign one stable piece ID and guide per accepted blade;
  6. report rejected components.

Ambiguity

A disconnected component is not necessarily a biological blade. It may be:

  • a crossed card containing many texture blades;
  • a hidden support mesh;
  • one side of a duplicated two-sided card;
  • a leaf cluster;
  • an importer-created fragment.

The audit must show component colors and classification, not merely a count.

5.3 Welded/shared-base clumps#

Recommended level: Level 2 only when the shared base can be isolated cleanly; otherwise Level 1 or authored Level 3.
Automatic confidence: Medium and explicitly conditional.

Proposed root-cut partition

confirmed root mask
      ↓
mark shared root/base faces
      ↓
remove those faces only in the analysis graph
      ↓
connected components of remaining upper geometry
      ↓
for each upper component, find its interface to the root region
      ↓
create one blade piece + root anchor at that interface
      ↓
reattach root-region render vertices using root/cage influences

This method is reliable when blades are connected only through the base. It fails when blades share faces above the root, merge into a continuous tuft, or the root mask cuts through blade bodies.

Artist correction

The artist adjusts the root mask, manually splits piece labels, supplies curves, or accepts whole-clump deformation. Cyrus must not physically detach the source mesh; the cut exists only in the analysis graph.

5.4 Crossed opacity cards#

Recommended level: Level 1 whole-clump bend, or card-level Level 2.
Automatic confidence: High for recognizing the cards; low for inferring visible individual blades.

The geometry exposes card planes and segmentation, not the opacity silhouette. Therefore Cyrus can preserve:

  • card root edge;
  • card centerline;
  • card width and twist;
  • UVs and material IDs;

but cannot claim individual blade fitting for blades painted inside the texture. Contact uses the geometric card envelope plus a declared thickness/clearance, not alpha pixels.

Artist options

  • whole-clump guide/cage;
  • one guide per card;
  • authored simplified blade guides for hero cards;
  • replace with geometric grass for Level 2 contact.

Opacity texture edits do not necessarily invalidate geometric bindings, but they invalidate the visual audit and may change whether the preparation level remains acceptable.

5.5 Dense scanned vegetation#

Recommended level: Level 1 cage or authored Level 3.
Automatic confidence: Low.

Dense scans commonly contain fused leaves, holes, duplicated surfaces, disconnected debris, and topology unrelated to botanical structure. Generic skeletonization is not a dependable solution because common documented methods require closed, single-component input or produce graphs without semantic root/leaf assignment. C2C3

Supported preparation

  • author a low-resolution deformation cage or guide graph;
  • decimate only for deformation control, not as the render source;
  • capture the high-resolution scan to that proxy by piece-restricted weights;
  • validate folds, inversions, and unbound regions.

Unsupported claim

Cyrus should not promise automatic independent leaf extraction from arbitrary scans.

5.6 Renderer proxies with limited geometry access#

Recommended level: Unsupported as deformable sources unless canonical geometry is accessible.
Automatic confidence: Determined by a Max 2027 access test.

The source audit should attempt, on the host thread:

  1. evaluate the object at the preparation time;
  2. query whether it can convert to a triangle/poly representation;
  3. verify that the returned geometry is the canonical render geometry rather than only a bounding box, point cloud, or low-detail preview;
  4. verify stable topology and channels;
  5. compare a test render to the evaluated mesh.

If any step fails, the artist must provide one of:

  • the original source mesh;
  • a renderer-vendor export/materialization path;
  • a matching deformation sidecar mesh plus a renderer-specific adapter;
  • prebuilt bent proxy variants.

An opaque proxy may still be used as an obstacle through an explicit collision mesh, but not as an exactly deformable vegetation source.

6. Three source-preparation levels#

6.1 Level 1 — Simple whole-clump artistic bending#

Representation

  • one principal guide, two-to-four guide handles, or one coarse cage per clump;
  • one root region;
  • one root orientation frame;
  • all render vertices captured to the clump guide/cage.

Visually sufficient when

  • vegetation is mid-ground or background;
  • the clump is small relative to the obstacle;
  • the contact is a broad push-away rather than a narrow gap;
  • individual blade silhouettes are not scrutinized;
  • the asset is crossed cards, a dense scan, or a compact tuft;
  • art direction matters more than per-blade physical plausibility.

Not sufficient when

  • two stones trap individual blades;
  • hero close-ups reveal rubber-bundle motion;
  • blades should split around opposite sides of an obstacle;
  • a wide clump contacts several unrelated surfaces.

Artist preparation

Select source → choose Level 1 → confirm root region/up axis → accept generated guide/cage or edit a few handles → save preparation. There is no per-placement rigging.

6.2 Level 2 — Independent blade fitting#

Representation

  • one guide per recognized blade/card/stem piece;
  • per-blade root anchor and root frame;
  • one-influence bindings for most vertices, with limited blending near a shared root;
  • per-guide width/thickness and rest twist.

Visually sufficient when

  • grass or narrow stems are the dominant source;
  • stones and curbs are visible near camera;
  • blades must separate around obstacles;
  • narrow gaps and multiple obstacles matter;
  • broad leaf area deformation and branching are not required.

Preparation boundary

Automatic preparation is practical for separated or root-cut ribbon blades. Ambiguous components require one-time source correction, not per-instance rigging.

6.3 Level 3 — Advanced leaf/stem deformation#

Representation

  • authored guide graph, bone hierarchy, oriented rods, multi-guide bindings, or a leaf/stem cage;
  • full local frames and twist;
  • branch/junction semantics;
  • optional broad-leaf surface coordinates or multiple guide influences.

Visually necessary when

  • broad leaves fold or twist against a surface;
  • stems branch or share load;
  • leaf orientation is a major shading cue;
  • scanned/complex plants require a cage;
  • hero assets must preserve leaf area and branch structure.

Preparation cost characteristic

Level 3 is still source-level and reusable, but it cannot be honestly advertised as automatic for arbitrary assets. Existing Skin rigs or authored curves can substantially reduce authoring.

7. Canonical guide-to-mesh evaluator#

7.1 One evaluator for all delivery paths#

Cyrus should define one mathematical evaluator for source preparation, CPU reference output, GPU viewport output, render materialization, and Bake. The evaluator is piecewise-rigid guide-frame skinning with up to four guide influences, blended by normalized dual quaternions.

For simple Level 2 blades, each vertex normally has one guide influence. Multiple influences are reserved for shared roots, cages, branch junctions, and advanced leaves.

7.2 Rest guide frames#

For each guide:

  1. sample or use authored rest nodes c⁰_i;
  2. compute tangents from neighboring nodes;
  3. seed the root frame from an authored root orientation, strip width vector, or confirmed source axis;
  4. propagate a rotation-minimizing frame along the guide;
  5. record authored/rest twist as rotation around the tangent relative to that frame;
  6. store width and thickness separately from the frame.

A round stem with no meaningful width direction may omit rest twist. A ribbon blade must have a stable width direction.

7.3 Vertex capture#

For each render vertex and each selected guide influence, store:

  • guide and segment ID;
  • segment parameter u;
  • local rest offset in the rest guide frame;
  • influence weight;
  • root/deformation weight.

For one influence:

p⁰ = c⁰(u) + F⁰(u) · o
p¹ = c¹(u) + F¹(u) · o

where F⁰ and F¹ are rest and fitted orthonormal frames and o is the stored local offset. This preserves the source’s cross-section, width, and local twist while the guide supplies the new centerline.

7.4 Fitted frames and twist#

The fitted guide provides new nodes c¹_i. Cyrus recomputes a rotation-minimizing frame from the fitted tangents, seeded by the fitted root orientation. It then applies:

  • preserved rest twist for Level 1/2 sources;
  • an authored/solved twist delta for Level 3 sources.

Root-position anchoring changes the root node position. Root-orientation stiffness changes only the root frame / first segment target. These controls remain independent.

7.5 Multi-influence blending#

Each influence yields a rigid transform from its rest frame to fitted frame. Blend the transforms with normalized dual quaternions and apply the blended transform to the vertex. Libigl documents dual-quaternion skinning as a remedy for matrix-blend collapse around large rotations. L2

The root mask is represented as an additional identity/placement influence with weight 1 - deformWeight, rather than as an unrelated post-deformation displacement. This makes the transition an explicit part of the evaluator.

7.6 Normals, tangents, UVs, and materials#

  • Topology, UV arrays/faces, material IDs, and smoothing groups remain unchanged. Max stores them in distinct channels. A3A5A6
  • If explicit per-corner normals exist, transform them by the evaluator’s blended rotation and preserve explicit-normal indexing. Max exposes explicit normal storage and recomputation APIs. A4
  • If normals are not explicit, recompute them from the deformed triangles using the original smoothing groups.
  • Recompute tangents from deformed positions and unchanged UVs for the final materialized mesh.
  • Audit transformed explicit normals against geometric normals in high-curvature regions; warn rather than silently discarding authored shading.

7.7 Why this evaluator is canonical#

  • It is simple for one-guide blades.
  • It preserves width and rest twist better than centerline-only displacement.
  • It can import Skin/bone weights.
  • It can represent cage/branch blending without a second deformation system.
  • It has a CPU implementation and a plausible shader implementation.
  • It does not require changing source topology or modifying the shared source object.

The evaluator does not solve collision or physics. It consumes the fitted guide state produced by whatever static fitting method Cyrus adopts.

8. Geometry delivery to Max 2027 viewport, renderer, and Bake#

8.1 Source immutability and output classes#

Cyrus keeps the source mesh immutable and divides placements into:

  1. Unaffected: shared source geometry + transform, using the existing fast path.
  2. Affected exact: unique fitted guide state, evaluated to unique vertex positions when required.
  3. Affected variant: optional reference to one of K accepted reusable deformed meshes.

The fitted guide state is authoritative. Expanded meshes and GPU buffers are derived caches.

8.2 Max 2027 viewport — correctness path#

The first viewport implementation should materialize affected geometry on the CPU using the canonical evaluator, then upload retained batches grouped by:

  • prepared source ID and revision;
  • material layout;
  • evaluator version;
  • display mode;
  • optional variant ID.

ICustomRenderItem is the documented retained hook: Realize() prepares/caches geometry, Display() draws it, and HitTest() handles selection. Autodesk recommends caching to avoid rebuilding every frame. A1

Batching policy

  • One scene node per Scatter controller, not per plant.
  • Combine affected vertices into source/material chunks.
  • Store per-instance ranges and stable IDs for picking.
  • Keep unaffected transform instances in their existing shared draw path.
  • Atomically replace complete affected buffers and bounds after Update.

No fixed batch size is proposed without measurement.

8.3 Max 2027 viewport — later compact path#

After CPU parity is qualified, Cyrus may evaluate the same guide-frame formula in a custom shader using:

  • shared rest vertex/index buffers;
  • source-level binding streams;
  • per-instance fitted guide transforms/frames;
  • instance-to-guide-buffer indices.

This can preserve geometry sharing, but exact buffer/stream layout and device support must be prototyped against the Max 2027 SDK. The public ICustomRenderItem contract establishes custom retained rendering and instanced draws; it does not by itself prove a particular structured-buffer design. A1

8.4 Bounds, culling, and picking#

  • Calculate an exact deformed bound for every affected placement after evaluation.
  • Use source reach bounds only for affected-instance selection and temporary conservative display.
  • Update geometry and bounds in the same publication revision.
  • Hit test against the deformed triangles in the CPU path; a guide/capsule approximation may be offered only as a documented fast selection mode.
  • Preserve stable placement IDs in hit records.

Max’s object contract includes local/world bounds and hit testing; source-rest bounds are insufficient after sideways bending. A2

8.5 Production renderer — supported baseline#

The renderer-neutral baseline is a standard Max render-mesh path:

  • a renderable GeomObject provides GetRenderMesh() or multiple render meshes;
  • affected placements are materialized by the canonical CPU evaluator;
  • unchanged placements continue through the existing renderer instancing path where supported;
  • output chunks preserve face material IDs, UV channels, smoothing, and normal policy.

Autodesk documents GetRenderMesh() for renderable geometry and IsInstanceDependent() for objects whose mesh differs by instance. A2

Because the prompt does not name one renderer and public documentation does not establish a universal compact guide-deformation interface across Arnold, Corona, and V-Ray, the product claim should be:

Exact vegetation fitting is supported through standard Max-compatible geometry after the intended production renderer passes the Max 2027 parity matrix.

Renderer-specific procedural deformation is an optional optimization, not the baseline contract.

8.6 Renderer qualification matrix#

T Run the following in the actual production renderer:

  1. one source, two placements, visibly different fitted shapes;
  2. opaque mesh and opacity-card variants;
  3. multiple material IDs and UV channels;
  4. explicit-normal and smoothing-group variants;
  5. save/reopen and Undo/Redo;
  6. deformation-only update without distribution regeneration;
  7. motionless still render from two cameras;
  8. render after changing the source material only;
  9. render after moving the obstacle and pressing Update;
  10. compare viewport, rendered mesh, and Bake positions/normals.

Record translation time, peak memory, retained memory, and whether the renderer duplicates unchanged source geometry internally. No capacity or performance claim should precede this test.

8.7 Bake and export#

Bake should materialize affected placements as ordinary mesh/poly geometry or a documented supported deformation stack. It must preserve:

  • fitted world-space shape;
  • stable source and placement IDs in custom metadata;
  • topology, UVs, material IDs, and smoothing groups;
  • explicit-normal policy and recomputed tangents;
  • exact local/world bounds;
  • prepared-source revision and evaluator version.

Unchanged placements may remain instances if the chosen Bake/export target supports them. A Bake that returns the undeformed source for affected placements is a failure.

8.9 Renderer proxies#

Opaque renderer proxies are a separate contract:

  • if the proxy exposes the full canonical mesh through supported Max evaluation, it can enter the normal preparation path;
  • if it exposes only preview geometry, preparation is invalid;
  • a sidecar mesh is sufficient only when the renderer path can consume the same deformation or a matching set of proxy variants;
  • vendor file internals must not be reverse-engineered from interface behavior.

9.1 Safe lifecycle after a source edit#

  1. detect the source revision/hash change on the host thread;
  2. keep the previous complete fitted result visible but mark it Source changed — preparation stale;
  3. do not publish partially remapped bindings;
  4. in Manual mode, wait for Analyze/Update;
  5. rebuild preparation in a new owned snapshot;
  6. require confirmation if auto classification changed;
  7. refit against the current obstacle snapshot;
  8. atomically publish only after preparation, fit, validation, and delivery all succeed.

If the source is missing or becomes an opaque proxy, preserve the old result as stale and report the dependency failure; do not silently delete plants or roots.

11. Practical supported-asset contract#

11.1 First supported contract#

A source is Supported only when all conditions below pass:

  1. Geometry access: full evaluated triangle/poly geometry is available in Max 2027.
  2. Static rest topology: vertex order and topology are stable during the static fit.
  3. Transform policy: shear is absent; nonuniform source scale is baked or explicitly rejected.
  4. Root authority: every deforming piece has one accepted root region and a declared growth axis.
  5. Piece authority: pieces come from accepted components, root-cut components, or authored IDs.
  6. Guide authority: every deforming piece has a valid ordered guide or cage/bone representation.
  7. Binding coverage: all deforming vertices have valid influences; no silent nearest-guide fallback across unrelated pieces.
  8. Segmentation adequacy: guide/render segmentation can represent the requested curvature.
  9. Channel preservation: UVs, material IDs, smoothing, and explicit normals can be copied and validated.
  10. Revision identity: source geometry, authoring metadata, and evaluator version are hashed and saved.

11.2 Supported with limitations#

  • Crossed cards: whole-clump or card-level only; no alpha-silhouette blade semantics.
  • Welded clumps: independent blades only when root-cut partition succeeds.
  • Broad leaves: advanced guide/cage/Skin preparation required.
  • Dense scans: authored deformation proxy required.
  • Multiple LODs: separate preparation per LOD or a verified shared guide mapping.

11.3 Unsupported in the first contract#

  • opaque renderer proxies with no canonical geometry;
  • arbitrary scanned foliage with automatic leaf semantics;
  • animated source topology;
  • shear or unbaked nonuniform source transforms;
  • a component with unresolved branch/piece ambiguity;
  • unbound vertices accepted by silent global nearest-neighbor capture;
  • exact collision against alpha pixels;
  • one source preparation automatically transferred to topologically unrelated replacement geometry.

14. Proposed Cyrus product workflow#

14.1 Library preparation#

  1. Artist selects one vegetation source in the Cyrus source list.
  2. Cyrus runs Audit Source on the host thread and copies an owned geometry snapshot.
  3. The artist selects a preparation level or accepts the recommended level.
  4. Cyrus analyzes components, roots, strips, guides, or existing Skin/cage data.
  5. Cyrus displays piece colors, roots, guides, virtual welds, and ambiguity markers.
  6. The artist corrects only flagged issues and accepts preparation.
  7. Cyrus stores the immutable preparation under the source stable ID and hashes.
  8. Every current and future placement of that source reuses it.

14.2 Scatter fitting#

When interaction Update runs:

  • placements keep their stable IDs and source correspondence;
  • Cyrus selects affected placements using their prepared reach bounds;
  • the fitting stage modifies guide states only;
  • the canonical evaluator produces validation and delivery geometry;
  • a complete successor is published atomically;
  • unaffected placements remain transform instances.

14.3 What happens after moving a stone#

  • Source preparation remains valid because the vegetation source did not change.
  • Only obstacle and affected-placement fit revisions become stale.
  • Manual mode keeps the previous complete deformation visible and shows Pending interaction update.
  • Pressing Update recomputes fitted guide states and derived geometry.
  • Live mode coalesces the relevant obstacle change and cancels stale work.
  • Camera movement, browsing, selection, and unrelated animation do not recapture the source or rebuild completed geometry.

14.4 How source-preparation failures appear#

Examples:

  • 3 pieces could not be classified as blades.
  • Shared base remains connected above the accepted root region.
  • Opacity card contains no geometric representation of individual blades.
  • 24 vertices are unbound after piece-restricted capture.
  • Renderer proxy exposes preview geometry only; supply the original mesh or a supported adapter.
  • Source topology changed; existing preparation is stale and was not applied.

A failure never silently switches to global nearest-guide binding, moves roots, deletes vegetation, or modifies the shared source.

15. Direct answers#

Can the artist prepare a source once and reuse it across thousands of placements?#

Yes. The preparation is source-level and immutable; placements reference it and store only fitted guide state or a variant ID. This eliminates per-placement rigging.

Can Cyrus avoid manually rigging every blade?#

For clean segmented ribbon blades and well-separated clumps, yes. Connected-component analysis plus strip recognition can generate guides and bindings automatically. Welded-base clumps are often automatable with a confirmed root-cut partition. Arbitrary cards, scans, and proxies are not.

What is the minimum useful preparation level?#

Whole-clump deformation is enough for mid/far assets, crossed cards, compact tufts, and broad push-away contact. Independent blades are needed for close grass, narrow gaps, and multiple obstacles. Advanced guides/bones/cages are needed for broad leaves, branching stems, and scans.

Which preparation should be the default?#

A hybrid audit: import explicit rig data first, then strict components, previewed seam welds, ribbon recognition, and root-cut partition. Anything still ambiguous is shown for correction rather than guessed.

What is the canonical deformation representation?#

Ordered guides with rest/fitted rotation-minimizing frames, local vertex offsets, up to four influences, a root identity influence, and normalized dual-quaternion blending. The same evaluator supplies CPU reference, viewport, render materialization, and Bake.

How should exact results reach the production renderer?#

Through standard Max-compatible materialized render geometry first. Compact renderer-specific guide procedures can be added only after the actual intended renderer passes a Max 2027 parity and memory test.

What should be rejected from the first version?#

Automatic semantic decomposition of arbitrary scans, individual-blade recovery from alpha textures, exact deformation of opaque proxies, animated topology, and silent application of stale bindings after source edits.

17. Final recommendation#

Build the source-preparation system before committing to a large-scale vegetation solver or renderer-specific procedural. The source contract is the dependency that every later approach needs.

The recommended sequence is:

  1. implement the audit and immutable preparation data model;
  2. support Level 1 whole-clump guides/cages;
  3. add strict components, root-cut partitioning, and ribbon-strip recognition for Level 2;
  4. import authored curves and Skin data;
  5. implement the canonical CPU evaluator and Max 2027 materialized delivery;
  6. qualify the actual production renderer and Bake;
  7. only then measure compact viewport guide evaluation and reusable variants;
  8. defer generic scan skeletonization and opaque-proxy deformation until asset evidence justifies them.

The most valuable product promise is not “any plant bends automatically.” It is:

Prepare supported vegetation once, review any ambiguity once, and reuse the accepted source rig across every stable Scatter placement without modifying the original asset.
