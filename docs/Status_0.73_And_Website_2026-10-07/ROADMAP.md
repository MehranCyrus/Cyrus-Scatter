# Next engineering loops

7 October 2026. Start from the exact corrected compact 0.73 identity in [README](README.md). This is an ordered acceptance plan, not a schedule or a declaration of completed fixes. Keep every loop small: identify one failure, retain its witness, make the smallest justified source change, check deterministic behavior and failure retention, then qualify the matching host/package identity.

## Entry gate — use the intended build

The normal-profile script inspected on disk is the earlier compact build. Prepare an owned disposable Max 2027 profile with the latest corrected script and matching native modules. Record actual loaded paths/hashes. Do not mix a new script with an old DLL or overwrite the artist's current scene/profile. A changed version caption alone does not satisfy this gate.

## Stage 2 — measured performance and bounded resources

- **Brush admission:** budget aggregate derived dabs, patch links and bytes before expansion; preserve authored history and the preceding complete field/publication on failure. Verify ordinary replay equality and persistence plus a pathological wide-stroke/dense-surface case.
- **Proxy drawing:** measure a retained-display experiment against the same shown subset, geometry, shading and scene. Preserve placements and compare frame-time distributions, CPU draw work, GPU upload identities and memory. Do not claim a gain by reducing output unnoticed.
- **Projection and spacing extremes:** establish worst-case work and cancellation/failure behavior for large motion, dense receivers and outlier radii. Reuse prepared geometry where dependencies allow. Keep host reads and publication on the host thread.
- **Acceptance:** useful measured gains on representative scenes, deterministic/equivalent ordinary results, bounded stress failure, and no Point Cloud/Mesh retention regression. Synchronous redraw time is not presented FPS; stable buffers still incur drawing cost.

## Stage 3 — assistant actions and useful diagnostics

- Retain passive cached reads, explicit enrollment, units, ownership, local exact-proposal approval, freshness, limits and rollback.
- Add a requested authoring slice at a time: a feature catalog entry is not an implemented write operation. Explicitly keep unsupported Brush/container/Edit/renderer actions unavailable until qualified.
- Reconcile conservative stale capability status/CLI labels with their precise receipts, regenerate pinned catalog inputs and test public contracts.
- Build a bounded user-controlled troubleshooting archive with build identity, scene/result references, reason chains and retention/deletion. Recording, sharing and permission to train remain separate decisions.
- **Acceptance:** each new action passes validation, approval, main-thread execution, failure/timeout reconciliation, Undo/recovery and actual Max tests; reports explain causes without silently recalculating scenes or collecting unapproved assets.

## Stage 4 — learning value and independent commercial readiness

The offline ten-feature preference ranker is an experiment with `deployable=False`. Create consented, attributable comparisons with matching assets/camera/render settings before expanding it. Compare proposed improvements against simple deterministic baselines on held-out projects and artist review. Reference-image interpretation and an automated render/adjust loop are future capabilities, not current claims.

Licensing has separate gates: complete operation coverage, expiry/renewal and recovery behavior, customer activation, seat/account service, protected state, signing operations, installers and supported render/workstation workflows. A learning experiment does not complete licensing, and licensing does not establish artistic quality.

**1.0 gate:** named supported platforms/versions, completed release acceptance, reproducible matching packages, recovery documentation and supportable licensing. Remain at development versions until those gates are met; no release date is promised.
