# Cyrus Scatter: codebase, performance and reliability decisions

**Investigation date: 1 October 2026.** Baseline: the dirty working tree at `f3f30ce98c4c1a8105e47805870ba73aef47794d`, Scatter 0.62 / Analyzer 0.14. This is an independent first codebase investigation; the separate web researcher's report was not read. This report's final audit is a self-audit, not independent review.

## 1. Decision brief for the artist-owner

1. **Keep the improvements already shipped.** The current code has prepared boundary calculations, native row filtering/transforms, bounded parallel cluster work, cached proxy triangles, and deferred layer synchronization during mouse input. Reimplementing these from an older roadmap would waste work. Fresh tests passed for both SDK builds and isolated Max 2027 fixtures. These passes support the tested behavior, not a broad production compatibility claim. **[A, B; C01–C05]**
2. **The best next display experiment is a small retained Nitrous proxy path.** Today's proxy cache saves CPU calculations but still sends triangles through GraphicsWindow every redraw. Historical same-population measurements make display submission and surrounding script work credible targets. The exact Autodesk instancing interface compiles and links with both local SDKs, but a correctly shaded, selectable, persistent Max implementation has not been demonstrated. Start with the existing pyramid population and keep the current path as fallback. **[A–D, F; C06, C07, C12; X01]**
3. **Faster placement math will not automatically make dragging faster.** There are host mesh conversions, MAXScript values, preview preparation, notification batches, Analyzer work and deliberate timer waits around it. Measure one edit from input to its first correct displayed result before adding background threads. Some event coalescing already exists. **[A, F, G; C08, C09; X02]**
4. **Reuse the existing nearest-surface tree only after preserving triangle identity.** A new isolated probe found a large advantage on larger synthetic surfaces, but a loss on a two-triangle surface. It also disproved a tempting shortcut: equal-distance queries can return the same position but a different face. At a pavement corner that can turn a plant or change which UVs it uses. A replacement must preserve the original face winner, not merely place the plant nearby. **[A, B; C10; X03]**
5. **Keep GPU computation and broader threading deferred.** Current automatic clustering took roughly half the serial time in eligible 32k/100k native cases with identical output bytes. This is useful evidence for the existing narrow policy, not a reason to use every core. No evidence here shows that CUDA/OpenCL readback, packaging and maintenance would improve a complete artist operation. GPU viewport instancing is a different, better-grounded display experiment. **[A, B, D, F; C11, C15–C18; D04–D06]**

The largest uncertainties are completed-frame and input-to-visible latency, detailed full-Mesh previews, renderer contention/startup, memory on a real 32 GB machine, and Max 2026 application behavior. No production feature, installer, artist scene or normal Max profile was changed. Experiments below are deliberately capable of rejecting the attractive ideas.

### Cost model and the measurement that decides each workflow

All times below use milliseconds. Define disjoint exclusive spans; a parent includes its children and must not be added to them.

`T_refresh = host evaluation/copy + script/native packing + pure-native work + downstream policies + preview preparation/publication`.

`T_first_correct = event wait/coalescing + queued work + T_refresh + next display/presentation opportunity`.

`T_render_start = Cyrus render evaluation + PFlow transport + renderer translation/initialization`.

These are instrumentation models [F], not fitted equations. During unchanged navigation, rebuilding ideally contributes zero. CPU submission and GPU execution can overlap; a steady pipelined interval is sometimes approximated by their maximum plus synchronization, not their sum. A scripted camera/redraw/message-pump step can call the scatter callback multiple times and is not one presented frame. Only frame/presentation measurements justify FPS; reciprocal historical step time is explicitly excluded.

| Artist operation | Competing explanations [F/G] | Discriminating measurement |
|---|---|---|
| Navigate unchanged scene | Per-triangle CPU submission, controller discovery, overlays, GPU rasterization or presentation wait | Callback exclusive spans, zero rebuild counters, ETW GPU/CPU trace and actual viewport swap-chain presents; fixed resolution/style/count |
| Drag boundary/source | Repeated generations, expensive valid rebuild, Analyzer revision, timer delay | Event ID → generation → extraction count → cache commit → first visible generation; group spans by cause |
| Explicit rebuild | Host conversion, packing/GC, native loop or proxy preparation | Inclusive root and exclusive children; nodes/triangles/rows/bytes allocated; cold vs warm |
| Animate | Time invalidates many controllers/sources; renderer/viewport contention | Fixed time sequence, per-frame generations and source validity intervals, outputs and first-visible latency |
| Load/clone/merge | Deserialization, reference remap, lazy cache rebuild, stale ownership | Time to ready and first correct view separately; reference identity, memory before/after release |
| Production / IR | PFlow rebuild, debounce, translation or renderer resource pressure | Separate transport and renderer spans; time to first render update, emitted count, renderer sampling and UI response |

The release timer is 200 ms in `performance.cjs`; Analyzer has separate 250 ms timer/150 ms node-event settings, and IR's settled-key patch waits at least 1,000 ms before its stop/rebuild phases. These are source settings [A], not measured input latency or guarantees of maximum wait. Shortening them blindly could increase redundant rebuilding. Their contribution must be separated from computation.

**Amdahl example [F].** If profiling finds only 10% of an edit in a kernel, making that kernel ten times faster gives `1 / (0.90 + 0.10/10) = 1.099`, about 9% less total time, before new overhead. Do not compare a 10 ms synthetic native case with a 1 s historical controller refresh and subtract them: their inputs and boundaries differ.

**Memory [A/B/F].** The native probe measured 144 bytes/Triangle and 112 bytes/Instance. One million triangles alone is 144 MB decimal before indices, Max mesh, UV storage, script values and temporary copies. One million instances alone is 112 MB. Old and new GC-owned previews can coexist. Historical proxy payload 1,509,568 bytes is consistent with 37,704 × 40 triangle/shade bytes plus 44 × 32 batch bytes; it is not total plugin memory. The 16/64 MiB caps only cover the added prepared payload. Measure private commit, working set, allocations, retained capacity, GPU dedicated/shared allocation and peak old+new generations. A 96 GiB pass cannot establish a 32 GB workload envelope.

### Algorithm comparison [A; complexities and choices F]

| Operation | Current cost / existing reuse | Narrow option, costs and reasons to stop |
|---|---|---|
| Nearest surface | Movement/anchors O(QT); relaxation already BVH. | Reuse tree for movement after tie-safe query and conservative bounds. Typical build O(T log T), memory O(T), queries often sublinear but worst-case O(T). Rebuild per evaluation/topology; no cross-generation cache initially. k-d tree over centroids alone is not a correct nearest-triangle replacement. Stop if measured refresh contribution is small. |
| Boundaries / falloff | Prepared bases exist; membership still O(E). Segment tree already handles falloff distance. | Reuse prepared predicate in remaining `final.inc::bandAt` paths only if profiled. Distance tree does not answer parity. Any edge index must retain boundary/holes/first-band/error-order semantics; tiny loops often favor scans. No second universal geometry engine. |
| Repeated host evaluation | Density area and placement can repeat conversion/copy; simple proxies still extract bounds. | Transaction-owned mesh snapshot may share extraction/area/preparation. First count repeated work. Persistent cache needs validity across topology, modifiers, time, UV and transforms; a node pointer/time alone is insufficient. Avoid unreliable fingerprinting and stale results. |
| Weighted sampling | O(T) CDF build, O(log T) lookup; group/source scans. | Alias tables offer O(1) lookup after O(T) build but can change RNG consumption/mapping and ordered output. Keep CDF; inspect source-group cardinality before another table. A mathematically identical distribution is not identical seeded placements. |
| Density / rejection | Fixed thinning vs refill up to bounded attempts; UV map sampled in script. | Measure rejection ratio and attempts, report exhausted count. Importance sampling or blue-noise changes the distribution/acceptance contract; expose as a new mode if ever wanted, not a transparent speed patch. |
| Spacing / overlap | Native hashed grid, bridge ordered map grid; neighbor buckets depend on radius. | Dense clusters/heterogeneous radii can make buckets quadratic. Measure occupancy/candidates first; multilevel grid or radius-aware BVH would add memory and tie/order complexity. Keep ordered acceptance and global Analyzer spacing. Parallel insertion would alter winners. |
| Relax / final smoothing | Rebuilt point grid, bounded neighbor visits, surface tree; constrained sequential final moves. | Independent “next position” calculations are plausible only where reading an immutable iteration snapshot. Do not parallelize sequential proposals or change the visited-neighbor cap as an optimization. Thin triangles, pins and holes are essential oracles. |
| Analyzer | Raster inside/distance roughly O(R²E), then skeleton/placement/spacing. | Prepared edges or tiled owned raster may help. Approximate distance transforms/skeleton changes can alter branches, clearance, count and minimum overrides. Defer until isolated Analyzer vs scatter timing identifies the problem. |
| Layout / allocation | Double AoS triangles and instances; Max floats converted to doubles and boxed outputs; multiple vectors/maps. | Reserve/group within a measured hot stage first. SoA/AoSoA adds conversion/storage cost; use only when vectorization or locality demonstrably benefits the full operation. Transient arena ownership ends with evaluation; never allocate GC/host objects in it. |

**Numerical contract [A, D, F].** Keep ordered source/placement IDs and exact bits for equivalent CPU optimizations on the tested build/FP environment. Do not silently replace them with tolerances. The bridge intentionally does not skip identity transforms, because arithmetic and signed zero can be observable. SIMD work must establish pointer non-aliasing, alignment, scalar fallback and runtime instruction dispatch; casting packed Vec3 data to aligned vectors is not a proof. `/fp:fast`, reassociation and FMA contraction can change results; VS 2022's default precise behavior does not enable contraction, while runtime FP-environment dependence needs additional care. [Microsoft `/fp`, Arguments and floating-point environment](https://learn.microsoft.com/en-us/cpp/build/reference/fp-specify-floating-point-behavior?view=msvc-170). Copying fenv/MXCSR into workers supports matching their environment; it does not prove every compiler optimization honors arbitrary rounding modes. Qualify alternate rounding/FTZ states separately before broad reproducibility claims.

GPU preview tolerances, if ever accepted, must be a written visual-only contract with absolute and scale-relative errors, mirrored/nonuniform/shear cases and exclusion from authoritative placement, picking and CS Edit fingerprints. Current proxy shading is derived from transformed face edges; applying an uncorrected source normal after nonuniform/mirrored scaling is not equivalent.

## 5. Concurrency: retain the safe boundary

**Documented boundary [D/G].** Autodesk describes Max as generally not thread-safe: scene/reference evaluation and arbitrary SDK calls must not be moved to workers. Selected rendering callbacks have explicit reentrancy requirements; that exception is not general permission. The accessible authority was the 2026 [Thread Safety guide](https://help.autodesk.com/cloudhelp/2026/ENU/MAXDEV-Developer/files/best_practices/thread_safety.html). The corresponding 2027 developer-guide URL could not be fetched. Local 2027 headers and successful builds verify available types, not a blanket threading guarantee. Before introducing a new concurrent SDK call, require its version-specific documented contract.

For this code [A/F], keep node evaluation/conversion, references, MAXScript Value construction/GC interaction, notifications, modifier/UI work and render-transport scene edits in their supported host callbacks. Copy numeric triangles/settings first, operate only on owned data, join, then pack results. Do not retain an `INode*`, Mesh conversion, Value pointer or graphics window in a numeric worker. A private mutex does not make host calls legal. Nitrous custom render-item callbacks have a different documented context: they may run on another thread and must be self-contained, without reaching back into the plugin/scene. [Autodesk, CustomRenderItem cautions](https://help.autodesk.com/cloudhelp/2026/ENU/MAXDEV-Developer/files/3ds_max_sdk_features/viewports_and_graphics_windows/nitrous/about_renderitem.html).

**Existing executor [A/B].** `execution.h::forRanges` creates bounded contiguous ranges, includes the caller, captures floating-point state, joins workers, records exceptions by range and rethrows after joining. Thread-launch failure joins started workers and falls back to serial execution. Automatic policy is capped at four participants and available hardware. Eligible cluster work writes separate output ranges and local statistics; RNG/order-sensitive completion is serial. There is no persistent pool, no asynchronous host publication and no reason to count this as all-core utilization. Fresh native differential tests and R03 support keeping it; render contention and hybrid CPU behavior remain unmeasured.

| Choice [F] | When it could help | Costs / counterargument | Decision |
|---|---|---|---|
| Keep synchronous ranges | Large eligible independent numeric work; simple lifetime | Repeated thread startup may cost on many short rebuilds | Keep; compare launch/join time before replacement |
| One bounded persistent executor | Frequent measured launch overhead after coalescing | Shutdown, plugin unload, cancellation, exceptions, per-job FP state, queue and memory ownership | Defer; never one pool per layer |
| oneTBB arena | Multiple proven parallel stages needing a shared scheduler | Version/ABI/deployment burden and renderer oversubscription still exist | Defer; no dependency adopted |
| More participants | Larger compute-dominated work with spare resources | Host/renderers compete; bandwidth, hybrid scheduling and small grains can lose | Explicit 1/2/4 experiments under contention before changing automatic policy |

The public oneTBB `task_arena` contract limits concurrent execution **in that arena**, not Max and all renderers. Its `latest` specification identifies itself as provisional; selecting a tested library release is separate work. [oneAPI, task_arena description](https://oneapi-spec.uxlfoundation.org/specifications/oneapi/latest/elements/onetbb/source/task_scheduler/task_arena/task_arena_cls). Avoid shared global controls as a supposed host-wide resource governor. Measure per-thread work, scheduling/wait, cache misses and memory bandwidth; low aggregate CPU use cannot distinguish serial host work from an efficient short kernel. Per-range statistics reduce contentious writes; cache-line padding is only justified after evidence of false sharing.

**Smallest asynchronous design, if later justified [F; unimplemented].** A host callback creates an immutable snapshot of numeric inputs, settings/seed, source IDs and a monotonic scene epoch/controller generation. Keep one active job and one latest pending request per owner; replace the pending snapshot rather than growing a queue. Workers own no SDK/GC objects, check cancellation at bounded chunk boundaries and produce an immutable numeric result. Completion merely schedules supported host-thread work. Publication verifies scene epoch, owner existence, generation, time/input signature and Manual/held policy before creating Values/cache; mismatch discards the result. Node deletion, Undo/Redo, reset/open/merge and clone advance/reassign generations. Shutdown cancels and joins before releasing plugin code/resources. Errors publish once to the matching generation; partial output never replaces a valid preview. Old display remains until a complete accepted result exists, with explicit stale status if the UI needs it.

Proposed bounds: one active plus one pending snapshot, one displayed plus one publication result, globally accounted memory with admission rejection to the synchronous path. Exact byte limits must derive from measured scene envelopes; the old roadmap's 2 GiB scratch/512 MiB GPU limits are experiment ceilings, not product requirements. Do not pump arbitrary messages from the middle of native computation. First test whether synchronous work with current batching plus deduplication is sufficient: it is much easier to reason about and preserves Manual semantics. An async system that computes every obsolete generation is likely worse under IR.

## 7. GPU computation: no backend selected

For a CPU-owned input whose result returns to Max [F], the complete operation is:

`T_gpu_total = host extraction + packing + allocation/setup + upload + launch + kernel + synchronization + download + unpack/host publication`.

Residency can remove repeated terms only when ownership/invalidation proves they are reusable. A model for crossover is `N* = fixed GPU overhead / (CPU per-item cost − GPU per-item cost − transfer/packing per-item cost)`, only if the denominator is positive, under linear-scaling assumptions. Measure all terms; if the denominator is nonpositive there is no crossover in that regime. At 100k items, just three input and three output doubles already imply 4.8 MB transferred without IDs, fields, triangles or extra copies. This is an illustrative lower-bound payload, not measured bandwidth or a prediction.

NVIDIA recommends minimizing host/device movement and keeping intermediates resident where possible. Pinned memory is scarce and expensive to establish; async copy/compute overlap requires supported hardware, pinned buffers, suitable streams and independent work. [CUDA C++ Best Practices Guide 13.4, §10.1–10.1.2](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html). This does not establish overlap through the Max bridge; current results become host Matrix3/Value arrays and PFlow scene state. No CUDA toolkit/runtime benchmark or Nitrous compute interop was run.

|---|---|---|
| Cluster fields on fixed sampled candidates | Independent arithmetic; plausible larger-N kernel. Existing four-participant CPU is already useful; small batches, branches/noise and host packing reduce benefit. | Same streams, group/source identities and exact authoritative rows; compare full refresh. Defer. |
| Point-preview transforms | Regular numeric work; could stay resident only with a compatible new display path. Existing marker path needs CPU points. | Fixed selected samples, visual-only error contract, picking unaffected; compare complete cache build/draw. Prefer viewport instancing experiment first. |
| Analyzer raster distance/containment | Many cells over shared edges; potential reuse/tile parallelism. Irregular holes, skeleton/spacing and host extraction remain. | Same region classification, skeleton decisions/clearance/count; CPU prepared/tiled baseline first. Defer. |
| Ordered spacing, refill, final smoothing | Serial acceptance, divergent paths, dependent mutable state | Parallel reordering changes winners. Reject as first GPU project. |

| CUDA | NVIDIA compute platform; documented transfer/residency model above. | Possible optional single-vendor spike only if a measured full operation earns it. Check supported device/driver/toolkit combination, FP64 throughput, compiler/runtime redistribution and actual free VRAM. RTX 3090 presence is not a deployment matrix. |

[Khronos clGetDeviceInfo, DOUBLE_FP_CONFIG and memory](https://registry.khronos.org/OpenCL/specs/unified/refpages/man/html/clGetDeviceInfo.html). | Broader API intent does not guarantee every AMD/Intel/NVIDIA driver or device. ### D01 / X01 — retain proxy display between redraws

**Artist problem / subsystem.** Unchanged navigation repeatedly resubmits cached proxies. Patch boundary: a new isolated native display test module plus `preview.cpp` numeric snapshot export; later a narrow generator-owned bridge around `AminScatterObjectDraw`/`viewportLayerEntries`. Do not alter `scatter`, CS Edit data, PFlow or scene class IDs. Current path is the baseline and immediate rollback.

**Evidence / unknowns.** A: triangle submission every draw. C: same-count historical improvement and residual callback cost. B/D: SDK interfaces compile/link. G: actual retained visual equivalence, graphics lifecycle, companion ownership and completed-frame advantage. Historical brighter retained meshes and invisible legacy paths are the strongest contrary evidence: lower timings can reflect wrong display.

**Simplest implementation / simpler alternative.** First retain the existing prepared world-space pyramid triangles using a native display owner; test shared-geometry instance data as a second variant only after parity. Simpler alternative: keep 0.62 and reduce only proven script bookkeeping in X02. Keeping current batches may be entirely sufficient for current scenes; that is the strongest argument against adopting new graphics code.

**Helps / loses / semantics.** Could help stable navigation with many repeated proxies; may lose on tiny populations or changing topology/count every frame due to upload/recreation. Authoritative placement/render behavior must remain unchanged. Selection, style and shading differences reject equivalence. Full Mesh/Point Cloud are excluded from the first claim.

**Benefit / resources / burden.** End-to-end benefit is unknown until experiment; exploratory historical timings are not a forecast. RAM/VRAM and cache keys/ownership/bounds are specified in §6. Costs include native object/reference integration, yearly SDK builds, device/style testing and maintaining fallback. No CUDA/OpenCL dependency.

**Smallest falsifiable experiment.** Phase A, completed R05: compile/link exact interfaces for both SDKs, preserve command and DLL identity. Phase B, unexecuted: in a separate visible test host using copied scenes, show one pyramid then 6,284 with exact current face colors/shading; validate geometry before timing. Compare 0.62, retained world triangles, then optional instancing on the original artist-scene copy and separately the synthetic demo. Include 200/6,284/50k displayed proxies, many controllers, count/transform/color changes, selected/hidden states, two viewports and cache overflow. Use identical seeds, cameras, viewport size/styles and quality settings. Measure construction/upload, unchanged callback, synchronous step, actual presents/GPU busy, peak memory and input-to-visible changes. Preserve screenshot pairs and numeric triangle/ID oracles; any accepted pixel tolerance must be agreed and justified by rasterization, not changed lighting.

**Proposed acceptance / rejection / rollback / stop.** Require zero placement/source/count/lifecycle differences, correct visuals and explicit fallback at every resource failure. Target ≥20% median improvement in the nominated unchanged-navigation operation with no repeatable P95 regression >5%, and no required small-case regression exceeding `max(5%, 2 ms)`. Measure at least three warmups and 30 edits or three paired ≥60-step navigation blocks, reverse order and inspect per-block medians. If host/GPU trace shows submission is not limiting, stop. If parity requires large controller/scene migration, stop this spike and re-estimate separately. A single switch returns to the old path, releasing all new resources; no saved-scene dependency may be necessary to roll back. Confidence: medium that investigation is worthwhile, low in any speed forecast. Correct same-count frame results with lower total latency reverse the “experiment only” recommendation; unfixable lifecycle/visual differences close it.

### D02 / X02 — measure an edit, then deduplicate a transaction

**Artist problem / subsystem.** Slow drag/release/explicit refresh can arise outside the math. Patch only opt-in tracing in `tools/performance/CyrusPerformanceMonitor.ms`, `AminScatter/tools/ui/performance.cjs`, `compute-performance.cjs`, generated `placements`/`refreshPreview`, bridge extraction/packing boundaries and Analyzer `runAnalysis`. **Evidence / unknowns.** A: duplicate area/extraction opportunities, multiple revisions/timers, explicit Manual/held rules and whole-scene controller discovery. B: existing callback/held/Undo/Manual fixtures pass. C: a full-refresh improvement exists but lacks this whole interaction breakdown. G: how much remaining delay is duplication vs necessary evaluation vs intentional waiting. The strongest objection is that current coalescing already solves the dominant case; adding another cache can only introduce stale results.

**Simplest implementation / simpler alternative.** Record a causal generation and nested inclusive/exclusive spans first, with counters for evaluations, rows, bytes, dirtiness reason and Analyzer revision. Simpler alternative: keep synchronous operation and current event coalescing; tune no timers and add no persistent cache. Ownership ends with the transaction; proposed admission cap 64 MiB across concurrent evaluation snapshots, fall back to current independent calls if it cannot fit. Record old/new snapshot coexistence. This cap is a test limit, not a new shipped memory contract.

**Helps / loses / semantics.** Helps only repeated evaluation/packing of unchanged inputs. May lose when validation/key work exceeds reuse, or topology changes every request. Point Cloud's all-valid-source sampling is a candidate only if trace proves unused-source work significant; source filtering/error behavior cannot change incidentally.

**Benefit / resources / burden.** Unknown until causal trace. If duplicate work has exclusive fraction `f`, its perfect elimination is bounded by `1/(1−f)` before cache costs. Tracing consumes bounded buffered records; disable by default, flush outside timed spans, and compare trace-on/off overhead. Transaction reuse adds RAM and API plumbing, no new runtime/worker. A cross-frame cache or async job system is explicitly outside this patch.

**Smallest falsifiable experiment.** Completed: source path audit plus original host fixtures R02; this establishes current semantics but does not time real input. Proposed/unexecuted: instrument one controller/layer and one Analyzer dependency in a copied artist scene; replay surface-transform, topology/boundary, density, source-scale, disabled-source and Manual refresh changes. Log input timestamp, event batch/generation, time spent waiting, extraction count/triangles, native exclusive work, boxing/GC/preview construction, commit and first displayed generation. Compare current traced/untraced code, then one deduplication patch; three warmups +30 ordered paired recomputations and five process-cold loads. No camera navigation benchmark substitutes for editing.

Only promote deduplication if a repeated stage accounts for ≥10% of the nominated operation and a candidate improves full edit median ≥15%, with no P95 regression >5% or required-case regression >`max(5%, 2 ms)`. Require exact outputs, zero stale/lost generations, unchanged explicit Manual behavior, visibility and Undo/Redo correctness. Stop at a read-only trace if duplication is negligible; select the measured necessary stage instead. Roll back by disabling trace/reuse and restoring existing independent calls; snapshots die at transaction end. Confidence: high in value of attribution, low in a particular optimization. A trace showing native computation dominates reverses the reuse priority; timer wait dominance suggests a separate UX decision.

### D03 / X03 — exact movement projection using existing geometry code

**Artist problem / subsystem.** Movement over detailed surfaces can do O(QT) closest-face tests. If reopened, one backend/one workload, pinned binary/device identity, full-operation cold/warm sweep and exact or preapproved visual-only oracle. Proposed adoption ≥25% complete-operation median gain on a stated workload with no interaction-tail/contention regression, and bounded memory/failure fallback. Reject missing residency/interop assumptions; stop if no crossover in supported scene sizes. Confidence high in “no backend yet”; measured complete-operation gains and a supportable hardware envelope could reverse it.

**D07 reject**: whole-engine rewrites and all-core defaults have no demonstrated artist bottleneck here; reduced counts/invisible geometry/private-internals assertions fail the comparison contract. Existing focused code is the simpler alternative. These proposals add large migration/dependency/maintenance cost or change output, with benefit unknown. Reopen a rewrite only after narrower measured experiments fail an explicit user workflow requirement and a reproducible prototype passes full output/lifecycle/resource gates. Reject any performance comparison with unequal workload or wrong visibility before timing; rollback to current code. Confidence high in present rejection, not a claim that these technologies can never be useful.

For a performance comparison record viewport pixel size, driver mode, visual style, display/triangle/generated/render counts, all seeds, adaptive degradation/culling/budgets and exact scene state. Disable variable degradation for like-for-like trials or record actual work and treat it as a quality experiment. Use paired order reversal/randomization within one machine, no competing trials, stable power state, warmups, raw samples and per-repeat summaries. Default proposed edit protocol: three warmups and 30 measured recomputations, separate 30 cache hits and five process-cold loads. Navigation needs enough actual frames per repeat to see stalls. Report P95 with adequate samples and uncertainty; do not imply five cold starts give a trustworthy P99. Measure trace-on/off overhead and exclude setup/validation only when explicitly labeled; also retain the inclusive whole-operation time.

**Correctness properties [F].** Preserve deterministic ordered placement/source identity and CS Edit fingerprints for equivalent optimizations; valid finite transforms and source ranges; current area/boundary/clearance/spacing policies including explicit minimum overrides; no cache rebuild on unchanged redraw; Manual updates only through its allowed paths; latest released edit becomes visible; zero stale publication. Distribution tests supplement exact differential tests for new modes but cannot replace identity checks. Use mirrored/nonuniform/shear and signed-zero cases rather than only axis-aligned boxes. Scene comparisons must cover render outputs separately from preview rows.

**Tools and blind spots [D/F].** Native `steady_clock` measures a CPU operation and allocations inside its span; it cannot measure Max or the GPU. Batch tests validate host data/lifecycle but lack an interactive viewport oracle. Existing QPC/redraw logs measure callback and synchronous step boundaries, not completion. For CPU attribution use symbolized sampling/ETW and explicit nested spans; tracing can perturb scheduling and script allocation. GPUView exposes CPU scheduling, GPU command submissions/resource activity and synchronization; capture short ETW windows and budget disk space, as its logs can be large. [Microsoft GPUView](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/using-gpuview), updated 14 November 2025. It does not automatically name a Cyrus triangle or explain artist input delay.

PresentMon distinguishes time between presents, display changes and completion-related metrics. [Official capture metric definitions](https://github.com/GameTechDev/PresentMon/blob/main/README-CaptureApplication.md). Select the actual Max viewport swap chain; UI windows and multiple viewports can confuse attribution. Verify which metrics are available and compare observer overhead. A present is still not proof of a correct new generation; correlate with a visible generation marker or controlled external capture. GPU timestamp queries need correct device/context ownership and validity checks; disjoint timestamps are invalid. [Microsoft D3D11 timestamp-disjoint structure](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/ns-d3d11-d3d11_query_data_timestamp_disjoint). Do not insert arbitrary queries into Nitrous's private context. No GPUView/PresentMon/timestamp capture was run in this investigation.

MSVC AddressSanitizer is documented for Windows x86/x64 and can test the standalone core with `/fsanitize=address /Zi` when the runtime is available. It is not a race detector; MSVC's documented future sanitizer list must not be mistaken for supported `/fsanitize=thread`. [Microsoft AddressSanitizer, platform support and use](https://learn.microsoft.com/en-us/cpp/sanitizers/asan?view=msvc-170). Start with isolated native fault/property tests, not instrumenting an artist's live Max. Any separate race-sanitizer platform needs its own verified toolchain; it would not validate Max callbacks. Sanitizer/driver-failure runs are proposed, not completed here.

**Limited beta vs production [F].** Current evidence supports targeted Max 2027.1 candidate testing, not unrestricted production support. A new experiment reaches limited beta only after native differential tests, target-host visual/lifecycle checks, same-count full-operation benefit and fallback/memory gates pass; name supported scenes, host/renderer versions, limitations and recovery. Production claims require the intended runtime/renderer matrix, installation and saved-scene compatibility, long sessions, 32 GB workload envelopes, failures and artist acceptance. An SDK build, saved-down file reopened in 2027, or successful native unit test cannot substitute for that matrix.
