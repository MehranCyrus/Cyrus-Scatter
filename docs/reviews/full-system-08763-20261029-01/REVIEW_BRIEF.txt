CYRUS SCATTER 0.87.6.3 — INDEPENDENT FULL-SYSTEM REVIEW

Act as a skeptical senior C++/3ds Max plug-in engineer, performance investigator,
graphics engineer, and software reliability reviewer. Independently review the
current Cyrus Scatter implementation. Find defects, unnecessary work, unsafe
assumptions, missing coverage, and practical opportunities to improve speed and
reliability. Be rigorous and direct. Do not manufacture findings or praise the
architecture without evidence.

This assignment is REVIEW AND VALIDATION, not implementation. We will validate
your findings and choose fixes afterward. You may create isolated test drivers,
fixtures, benchmark harnesses, reports, and experimental patches in a disposable
copy. Do not modify the product working tree, change versions, install into the
artist's profile, rebuild knowledge indexes, commit, push, publish, or create a
release installer. Preserve unrelated work and all artist data.

PRODUCT PRIORITIES

This is an interactive architectural landscaping tool. The priorities are:
1. Responsive viewport movement and immediate useful visual feedback.
2. Predictable artist controls, stable scenes, and reliable save/load/Undo.
3. Efficient use of CPU, GPU, and memory at realistic scene sizes.
4. Simple workflows and trustworthy Library, recipes, presets, and licensing.

The artist values the existing broad Bend/Trim appearance over realistic physics.
Do not recommend restoring expensive detailed contact refinement to normal
dragging merely to improve physical accuracy. Faster execution is useful only
when the intended appearance, responsiveness, and authored data are preserved.
Simplification is welcome; silently reducing density, quality, functionality,
authorization, or error detection is not an equivalent optimization.

5. PERFORMANCE, CPU PARALLELISM, GPU AND NAVIGATION

Measure before proposing an architecture change. Identify the dominant costs for
each workflow and determine whether they are necessary. Explicitly investigate:
- Repeated scans, sorting, hashing, geometry capture, preparation, allocation,
  copies, map construction, packet creation, and full-container bookkeeping.
- Broad-phase locality, per-branch pruning, source reuse, shared instance data,
  bounds inflation, hidden/offscreen work, and old/new collider dirty regions.
- Fully fixed/zero-Bend behavior while preserving enabled Trim/hiding and children
  that must follow a moving parent.
- Camera-only activity causing solver work, placement rebuilding, texture reloads,
  buffer uploads, unnecessary picking setup, or preview repacking.
- Rapid dragging: obsolete work, coalescing, cancellation, backpressure, stale
  publication, and a final result that fails to catch up after release.
- All current draw paths, including fallback paths and CPU-baked posed geometry;
  do not assume compact-GPU optimizations automatically apply everywhere.
- Memory through simultaneous old/new generations, caches, Undo/history, scratch,
  CPU meshes, compact poses, renderer output and GPU resources.

For multithreading, identify genuinely independent numeric work, copied input
ownership, host-thread restrictions, lifetime/join/shutdown, races, publication,
determinism, false sharing, locks, allocation contention and oversubscription with
Max/renderers. Compare serial and suitable bounded worker counts on identical
inputs. Include scheduling overhead and small-workload thresholds. Do not replace
host-thread work with unsafe worker calls merely to improve a timer.

For GPU handling, inspect the actual Max 2027 graphics path and SDK constraints:
instancing, shared sources, pose packing, draw submission, culling/LOD, resource
reuse, uploads, fences/synchronization, CPU stalls/readbacks, device lifetime,
recovery, memory pressure, display/picking agreement and render equivalence.
GPU drawing/deformation is not proof of GPU contact solving.

Assess CUDA/OpenCL/compute shaders only as evidence-backed opportunities. For each
candidate state its parallel structure, resident input/output, transfer volume,
synchronization, interop availability, CPU/GPU break-even size, fallback, vendor
coverage and failure costs. Use Amdahl-style end-to-end reasoning. A fast isolated
kernel does not prove faster Max interaction. Verify uncertain SDK/API claims
against versioned primary sources; label inference and unavailable measurements.

Do not promise unlimited/million-instance realtime. Explain the measured limits
and tradeoffs. Distinguish avoidable global work from necessary global metadata.

9. EVIDENCE STANDARD FOR EVERY FINDING

Each finding must contain:
- Stable ID, concise title, subsystem and affected build/source hashes.
- Type: correctness / performance / concurrency / graphics / usability / security /
  persistence / test gap / maintainability.
- Severity P0-P3, separately from confidence and evidence status.
- Evidence status: reproduced, statically demonstrated, measured opportunity,
  hypothesis requiring measurement, not reproduced, or already fixed/not applicable.
- Artist-visible trigger, expected behavior, actual behavior and impact.
- Exact repository-relative file/symbol/line references and causal explanation.
- Reproduction steps or runnable driver, command, fixture and raw evidence links.
- For performance: measured cost, avoidable work, scaling and equivalent baseline.
- Minimal repair direction, affected ownership/invalidation, risks and tradeoffs.
- Regression test and measurable acceptance criteria, including an unaffected case.

For a static finding, show a reachable path and violated invariant; do not label it
runtime reproduced. Passing tests do not disprove an untested path. A potential
issue is not confirmed just because similar code caused a past problem. Check the
backlog and previous review, merge duplicates, and identify newly introduced issues
versus preexisting behavior. Keep architectural preferences and readability cleanup
separate from defects. Avoid arbitrary finding quotas.
