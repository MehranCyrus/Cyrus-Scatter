Current CPU architecture
- Native source policy filtering preserves ordered rows and existing density/falloff semantics.
- Source scale and Z-offset application moved to native code but still operates on Max/Matrix3 values on the calling thread.
- Prepared closed-boundary calculations remove repeated preparation; boundary orientation avoids copying a full band for each point.
- Parallel cluster evaluation is deliberately narrow: at least 4,096 candidates, eligible clustering configuration, no movement, area masks, UV-density rejection or anchors in that path. Verify exact predicates in scatter.cpp.
- Automatic policy uses up to four total participants including the caller. Serial mode remains available. Sampling/random draws and ordered result handling remain on the caller; workers process owned numeric ranges.
- Workers do not evaluate Max nodes, access MAXScript/GC objects or draw viewports. Work is joined before return; there is no persistent pool or asynchronous result publication.
- Event callbacks retain invalidation while coalescing redraw requests within a callback batch. Other callbacks/timers can still cause additional work.

Current viewport architecture
- Preview placements/source data already had a cache. The viewport optimization adds prepared world-space proxy triangles and face shading to that cache.
- Applies to box, sphere and pyramid previews. Full Mesh retains the prior source geometry/instance-transform path. Point Cloud and other overlays have their own paths.
- Triangles are submitted through GraphicsWindow on each redraw; source-preserving batches contain at most 4,096 triangles.
- Additional prepared batch payload is capped at 16 MiB per cache and 64 MiB process-wide. These are not limits on all plugin/process memory. Oversized caches or allocation/cap failures preserve the old drawing path and displayed population; fallback may therefore become slower.
- Cache lifetime follows MAXScript GC. Old generations can coexist before collection.
- Script 0.62 bypasses full layer synchronization during held input, uses last completed previews, and returns to the full path afterward. This must remain correct for edits, live flags and Manual mode.
- No retained Nitrous render-item renderer, GPU viewport instancing, OpenCL/CUDA compute or asynchronous editing implementation has been shipped. Exploratory retained-mesh experiments in the reports were not packaged.

Evidence, with boundaries
1. Controlled CPU records (project report, not rerun for this prompt): full controller refresh around 3.98-4.05 seconds before vs 1.01-1.17 seconds after, across five defined geometry states; all 60 ordered preview/render outputs matched. These measurements exclude several scheduling/render/appearance concerns described in the report.
2. Original artist scene: 52,143 generated placements; 6,284 displayed pyramid proxies; 37,704 displayed proxy triangles. Do not confuse generated count, display count, point-cloud samples, scene statistics and render count.
3. Original viewport comparison: GraphicsWindow batch boundaries reduced from 6,284 to 44, with unchanged prepared triangle positions/shading/colors. Median scripted navigation-step wall time fell 88.10 to 30.16 ms in that specific comparison. A measured step can trigger multiple callbacks. These are not completed-frame FPS measurements.
4. Script 0.62 held-input comparison: 33.1% less scatter callback time and 9.1% less full step wall time in its controlled matrix. Small real-gesture samples support that the intended path is exercised, but do not establish a general FPS multiplier.
5. User observation in original scene: roughly 20 FPS before and 80 FPS after; removing scatter gave roughly 150-160 FPS. Uncontrolled, not interchangeable with the synthetic demo.
6. User observation in synthetic demo: roughly 23 FPS when opened with the normal profile's older 0.60 DLL/script; roughly 150 FPS after updating to 0.62. Loaded-module paths and hashes exposed the version mismatch. The 150 FPS report is the user's observation; there is no controlled capture attached for it.
7. Demo: six layers, 6,284 simple pyramid proxies / 37,704 triangles, built-in sources/materials, no external assets; automatic render preparation disabled. Counts match the original displayed population but source grouping, scene complexity and workload differ. Do not assign the original scene's 44-batch count to the demo without measuring it.
8. Max 2026 build passed eight Scatter native suites and one Analyzer suite. The demo was saved to Max 2026 format using Max 2027 and reopened in Max 2027. None of this is a Max 2026 application test.
9. Existing fixtures exercise geometry/color/shading parity, mirrored/nonuniform transforms, batch boundaries, memory limits/fallback/GC, Manual refresh, held/released changes and some Undo/Redo/save/reopen cases. This is scoped evidence, not exhaustive product qualification. Visual captures were close but not pixel-identical even where geometric data matched.
