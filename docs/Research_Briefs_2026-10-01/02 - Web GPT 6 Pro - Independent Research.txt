3. RESEARCH TRACKS

A. Measurement and performance models

Explain how to distinguish CPU computation, host evaluation, script/native marshalling, geometry preparation, draw submission, GPU frame execution, scheduling and artist-visible latency. Separate navigation without edits, edit-to-visible-result time, rebuild time, animation throughput and render preparation.

Use Amdahl's law to bound complete-operation benefit from a faster kernel. Explain data locality, bandwidth limits, allocations and arithmetic intensity where they change a decision. Account for parallel/overlapping CPU and GPU work instead of naively summing all timers. Provide a practical interpretation of frame time, medians, tail latency, variability, cold/warm caches and instrument overhead.

Assess suitable profiling tools and supported attachment methods for Windows/3ds Max, including CPU sampling/timelines and GPU timing where applicable. Explain what each measurement proves and what it cannot prove. The viewport's FPS overlay, synchronous redraw duration and a GPU-completed frame measurement are different evidence.

B. Mathematics and CPU algorithms for scattering

Research sampling, source selection, geometric queries and placement constraints relevant to surface scatter: area/weighted sampling, density rejection, deterministic pseudorandom streams, spacing/Poisson-disk or blue-noise methods, proximity/collision checks, relaxation, boundary containment and distance, closest-point/ray queries, normals and transforms.

Compare simple loops, prepared predicates, uniform grids/spatial hashes, BVHs and k-d trees where appropriate. Include construction, update and query costs; memory; density/skew; degeneracy; boundary holes; extreme coordinates; topology edits; and small-workload crossover. Explain what changes an algorithm's distribution, point count, order, source identity or tolerance, rather than presenting a different result as an equivalent optimization.

Evaluate data layout, temporary allocation, reuse, compiler vectorization and explicit SIMD after algorithmic waste is considered. Discuss floating-point reproducibility, fused operations, reassociation, robust predicates, near-boundary decisions and transformed normals under nonuniform/mirrored scaling. Separate strict equivalence from explicitly accepted approximation. Identify where exact cross-device bitwise parity is unrealistic and what narrower contract would be appropriate, without presuming permission to change the plugin's current contract.

For every promising technique, give a concrete scatter use case, the conditions in which it loses, and the measurement needed to select it. Do not offer a catalog of algorithms without a decision rule.

C. Safe CPU concurrency in a host application

Research actual Autodesk restrictions around node/reference evaluation, scene access, MAXScript, memory managed by the host, notifications, graphics, modifiers and render interfaces. Distinguish documented guarantees from examples or anecdotal success. Verify guidance against the target SDK versions.

Compare serial optimized code, bounded synchronous parallel ranges and persistent executors. Evaluate standard C++ facilities and oneTBB/other runtimes only where appropriate. Cover workload size, grain size, deterministic order/reductions, thread startup, oversubscription, renderer contention, hybrid cores, cache/NUMA effects where relevant, exception propagation and teardown. Explain why higher CPU utilization can accompany worse latency.

Separately examine asynchronous interaction: snapshot host data on the permitted thread, compute on owned data, then publish safely with generation checks and cancellation. Include stale results, Undo/Redo, node deletion, scene load/reset and shutdown. Compare it against the simpler option of event coalescing and synchronous work. Do not assume a generic game-engine job system fits Max's lifetime and threading rules.

D. Professional viewport display architecture

Research the supported Nitrous plugin interfaces, retained geometry/buffers, GPU instancing, CPU batching and relevant compatibility paths. Explain shared source geometry plus instance transforms versus expanded per-instance triangles. Distinguish viewport GPU instances from native Max instance nodes and renderer instances.

Verify the applicable SDK API names, lifecycle and dependencies. Examine integration with scripted/native hybrid plugins, object bounds, selection/hit testing, visibility, multiple viewports, Standard/High Quality styles, colors/materials/UV overrides, changed instance counts, deforming sources, geometry topology, device changes and resource release.

Compare proxy, point-cloud, full-mesh and sprite approaches. Assess culling, LOD and display budgets with explicit quality tradeoffs. Preserve like-for-like workload for performance claims. Explain why viewport culling rules cannot automatically be used for rendered reflections or shadows. Include circumstances where CPU caching/batching remains an appropriate long-term choice.

Use Autodesk, tyFlow and Chaos documentation to identify documented mechanisms and limitations, while marking unknown proprietary internals. Do not promise that copying a mechanism reproduces a product's performance.

E. GPU computation: is it worth adding?

Separate graphics acceleration from calculation acceleration. Compare an optimized CPU implementation with optional CUDA, OpenCL and a short list of truly plausible alternatives, such as DirectCompute or SYCL. Do not give every API equal attention or propose a multi-backend abstraction before identifying a worthwhile workload.

For each plausible kernel, model host extraction/marshalling, allocation, upload, dispatch, compute, synchronization, readback and publication. Consider persistent device data and valid overlap, but verify interoperability with Max/Nitrous/renderer APIs. Expose assumptions and quantify crossover only when the inputs are supported. Unknown measured inputs must remain unknown.

Investigate irregular geometry queries, branch divergence, iterative dependencies, precision/determinism, GPU memory capacity, transfer bandwidth, renderer/viewport contention, driver/runtime support, cross-vendor deployment, debugging and CPU fallback. CUDA/OpenCL popularity or theoretical FLOPS does not establish a user-visible benefit.

Make an explicit case for or against adding GPU compute at this product stage, conditional on the local measurements that would settle it. Include the smallest experiment that could reject the GPU proposal quickly.

F. Production engineering and qualification

Define what a supported plugin must demonstrate beyond high FPS: correct invalidation, stable scene persistence, meaningful deterministic behavior, memory bounds, resource ownership, correct errors/fallback, cancellation, responsive shutdown, reproducible packaging and compatibility with supported hosts/renderers.

Research host-specific ABI/toolchain constraints, dependency coexistence and redistribution requirements relevant to any proposed library. Avoid adding a runtime that conflicts with Max or another renderer. Distinguish compiler/native-test success from real target-host validation.

Design a staged test matrix for small/large workloads, repeated detailed meshes, many unique sources/controllers, pathological geometry, long editing sessions, animation, cold/warm caches, low-memory conditions and renderer contention. Include serial/parallel parity, numerical boundaries, visual checks, Manual/Real-time behavior, scene load/save/reset/merge/clone, Undo/Redo, device/resource failures and render start/stop. Choose tests that expose real failure modes rather than mechanically mirroring the implementation.

Define reproducible comparisons: verify actual loaded DLL/script identities, fixed seeds, scene/build hashes, viewport size/style, displayed counts, adaptive degradation and measurement boundaries. Use paired repeated trials, warmups, order reversal or randomization, raw samples, robust summaries and uncertainty. Do not hide small-scene regressions behind large-scene averages or demand arbitrary test quantities without justification.
